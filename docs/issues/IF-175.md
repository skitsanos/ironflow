# IF-175 — Flow source can abort the process during load and validation

## Evidence and boundary

Review of `develop` at 1.21.1-dev.1 on 2026-11-12, reproduced with a local
optimized build through `ironflow validate`.

1. Script-controlled sizes reach `Vec::with_capacity`.
   - `return { _name = "x", _steps = {}, _step_count = 1000000000000000 }`
     (70 bytes) ends with `memory allocation of 184000000000000000 bytes
     failed`, exit status 134.
   - Setting `__len` on a step's `dependencies` table to return the same
     number aborts the same way (`24000000000000000 bytes`).
   - `src/lua/runtime/extractor.rs:17-21` reads `_step_count` from the
     returned table and `:47-49` uses `Table::len()`, which honours `__len`.
     Builder state lives in ordinary, script-writable table fields
     (`src/lua/runtime/api.rs:23-26`).
2. Validation walks the syntax tree recursively.
   - A flow whose top-level chunk contains `local v = 1` followed by `+1`
     200,000 times (400 KB, under the 1 MiB source cap) ends with `thread
     'main' has overflowed its stack`. 20,000 terms pass on the CLI's main
     thread.
   - `collect_functions` (`src/lua/analysis.rs:143-157`) and the scope
     analyzer (`src/lua/analysis/scope.rs:63-78, 207-224`) recurse once per
     tree level. Left-associative operator chains parse into a tree as deep as
     the chain, and Lua's own compiler accepts them.

Both are aborts, not panics. The same loader serves `POST /flows/validate`
and `POST /flows/run` with inline source (`IRONFLOW_ALLOW_ADHOC_FLOWS`
defaults to `true`), webhooks, schedules and subworkflows, where server
threads have 2 MiB stacks.

Boundary: the HTTP paths were not executed; they share the code shown above.
An API key is required unless the server is unauthenticated on loopback.

## Required outcome and acceptance

- Never size an allocation from a script-supplied count: iterate with
  `raw_len`, enforce an explicit step and dependency cap, and use fallible
  reservation. Prefer keeping builder state out of script-writable fields.
- Replace the recursive tree walks with an explicit stack and a depth cap that
  returns a validation error.
- Regressions: both `_step_count` and `__len` inputs return a load error; a
  200,000-term expression returns a validation result on a 2 MiB thread; the
  API returns 4xx for each rather than losing the connection.
- Evidence: focused Lua runtime and validation tests, API validate test.

## Outcome and validation

Resolved on 2026-11-12 at 1.21.1-dev.1.

Outcome:

- `src/lua/runtime/extractor.rs` measures `_steps` and each `dependencies`
  list by raw length, rejects either list when it carries a metatable, caps
  both at 10,000 entries and reserves fallibly. `_step_count` sizes nothing:
  it must be an integer equal to the measured step count.
- The builder in `src/lua/runtime/api.rs` appends by raw length, so
  `flow:step` and `depends_on` no longer read `_step_count` or `__len`.
- `src/lua/analysis/tree.rs` walks the syntax tree with a cursor and fails
  above 1,000 levels. `scope.rs` keeps an explicit stack of steps, and
  `names.rs` holds scope state. Both function collection and scope analysis
  are free of recursion.
- Docs: the `validate` section and `IRONFLOW_MAX_FLOW_SOURCE_BYTES` row of
  `docs/CLI_REFERENCE.md`, and "Flow size limits" in
  `docs/LUA_FLOW_GUIDE.md`.

Contract boundary:

- The step and dependency caps are fixed and apply on every load path. A
  hand-written flow table must keep `_step_count` equal to its steps; a lower
  value used to truncate the flow silently.
- Builder state still lives in script-visible fields. The preferred move out
  of them was not made; no allocation or index depends on them now.
- The syntax cap applies to validation only, which alone walks the tree. Lua
  accepts about 200 nested constructs, at most 500 tree levels in the cases
  measured, so only operator, index or call chains reach the cap. Such a flow
  fails validation and still loads for execution.
- The API was exercised through the in-process router, not a live server.
- A 10,000-step dependency chain took 10 s to validate in an unoptimized
  build: the phase computation in `src/engine/recovery.rs` is quadratic.
  Tracked in [IF-207](IF-207.md).

Validation on 2026-11-12:

- Failing first, unoptimized test build: `_step_count` aborted with `memory
  allocation of 184000000000000000 bytes failed`, `__len` with
  `24000000000000000 bytes`, and both 200,000-term cases overflowed a 2 MiB
  thread. The same inputs aborted the API test binary and ended `ironflow
  validate` with a signal. The cap, mismatch and `depends_on` tests failed on
  assertions.
- After: `test_flow_load_limits` 10 passed; the six new API and CLI cases in
  `test_validation_diagnostics` passed (`valid: false`, exit status 1);
  `lua::analysis` 12 unit tests passed.
- The old and new analyzers gave identical `validate` and `--strict` output
  for all 156 example flows and for six flows covering each scoping rule (34
  warnings, two rejections).
- Focused targets: library 577, `engine` 284, `cli` 92, `examples` 11,
  `flow_load_admission` 1.
- `cargo fmt --all -- --check`, the module-size gate and `cargo clippy
  --all-targets -- -D warnings` pass.
