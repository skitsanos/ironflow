# IF-111 — Initial PDF loading leaves object-stream decompression uncapped

## Required outcome and acceptance

- Use bounded PDF load options for extraction and shared metadata/split/merge loading so object streams cannot decompress without admission.
- Define coherent input, decompressed-stream, and object-count boundaries without silently weakening existing limits.
- Test early rejection with a small compressed fixture whose object stream exceeds the selected cap, plus a valid object-stream PDF under budget.

## Evidence and cause

Fresh review on 2026-09-12, finding R06. See
[AUDIT_2026-09-12.md](./AUDIT_2026-09-12.md) for the reviewed candidate,
evidence boundaries, and complete finding-to-issue mapping.

[Source: extract/pdf.rs:76](../../src/nodes/extract/pdf.rs), [image/pdf_input.rs:45](../../src/nodes/image/pdf_input.rs).

Both loaders use lopdf defaults. In 0.45, object streams are decompressed during loading with `max_decompressed_size=None`, before IronFlow's page/text/retained-object budgets. A small encoded fixture with a 4 MiB object stream was accepted under a 32 KiB PDF input cap and 1 KiB extraction-output cap; its object-stream metadata was successfully read. This establishes the missing admission boundary, not a measured out-of-memory event. It affects extraction and the shared metadata/split/merge loader.

Fix and coverage: use bounded LoadOptions, distinguish input/decompressed/object-count limits, and test early refusal of oversized object streams. Evidence: extraction probe `object-stream`; upstream `reader.rs:1013` calls `ObjectStream::new_with_limit` with the configured optional bound.

## Progress

Open. Implementation and regression validation are pending.
