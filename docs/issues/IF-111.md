# IF-111 — Initial PDF loading leaves object-stream decompression uncapped

## Required outcome and acceptance

- Use bounded PDF load options for extraction and shared metadata/split/merge loading so object streams cannot decompress without admission.
- Define coherent input, decompressed-stream, and object-count boundaries without silently weakening existing limits.
- Test early rejection with a small compressed fixture whose object stream exceeds the selected cap, plus a valid object-stream PDF under budget.

## Evidence and cause

Fresh review on 2026-09-12, finding R06. See
[AUDIT_2026-09-12.md](./AUDIT_2026-09-12.md) for the reviewed candidate,
evidence boundaries, and complete finding-to-issue mapping.

[Source: extract/pdf.rs:76](../../src/nodes/extract/pdf.rs), [image/pdf_input.rs:45](../../src/nodes/image/pdf_input.rs).

Both loaders use lopdf defaults. In 0.45, object streams are decompressed during loading with `max_decompressed_size=None`, before IronFlow's page/text/retained-object budgets. A small encoded fixture with a 4 MiB object stream was accepted under a 32 KiB PDF input cap and 1 KiB extraction-output cap; its object-stream metadata was successfully read. This establishes the missing admission boundary, not a measured out-of-memory event. It affects extraction and the shared metadata/split/merge loader.

Fix and coverage: use bounded LoadOptions, distinguish input/decompressed/object-count limits, and test early refusal of oversized object streams. Evidence: extraction probe `object-stream`; upstream `reader.rs:1013` calls `ObjectStream::new_with_limit` with the configured optional bound.

## Outcome and validation

Resolved locally on 2026-09-13 alongside the uncommitted IF-110 changes, after
commit `a813d26`. Extraction and metadata/split/merge now use the shared policy
in [pdf_load.rs](../../src/util/pdf_load.rs). Both byte-slice and capped-reader
entry points pass strict `LoadOptions` with an explicit decompression ceiling.
Existing regular-file, verified-handle, input-growth, cancellation, page, text,
and retained-output limits remain in place.

The new `IRONFLOW_MAX_PDF_DECOMPRESSED_STREAM_BYTES` ceiling defaults to 64 MiB
per object/cross-reference stream, including filter intermediates. Strict mode
propagates unencrypted object-stream load errors. Retained cross-reference
streams and decrypted object streams receive an additional bounded check before
the document is accepted, covering streams skipped by upstream loading paths.
Inputs readable with an empty password still work; password-protected documents
fail instead of returning a successful partial document.

`IRONFLOW_MAX_PDF_OBJECTS` defaults to 250000 loaded objects per source. It is
checked after parsing and before downstream processing, so it is not an
object-preallocation guard. It includes retained containers and expanded members
and does not replace `IRONFLOW_MAX_PDF_MERGE_OBJECTS`, which still bounds the
retained output graph across all merge sources. Zero/invalid limit overrides
retain safe defaults.

The original review evidence remains above. A new bounded regression reproduced
the defect before this fix: a PDF smaller than 32 KiB, with a 64 KiB object
stream and small text/metadata output, was accepted by `extract_pdf` despite a
1 KiB stream ceiling. Post-fix CLI tests reject it across all four nodes, for
paths and verified artifacts, without writing split pages or replacing existing
merge output. Exact stream/object boundaries remain inclusive; ordinary and
larger admitted fixtures preserve text, metadata, page count, and page output.

Fixtures also cover an active compressed xref, an unused retained xref behind a
valid xref table, and an empty-password encrypted retained object stream. The
last two are accepted by upstream bounded strict options alone but rejected by
IronFlow's retained-stream check under the small ceiling. Raising the ceiling
admits them. This does not disable every upstream xref repair path or validate
all historical revisions. No large-allocation or out-of-memory probe was run.

Post-fix validation on Rust 1.98.1:

- `cargo test --lib util::pdf_load`: three policy/count/deadline tests passed.
- `cargo test --lib nodes::image::pdf_`: eight capped-input, merge-budget,
  sharing, inheritance, and output-durability tests passed.
- `cargo test --test test_pdf_load_safety --test test_pdf_limits_defaults`:
  eight tests passed, including seven CLI scenarios and default/override checks.
  All four updated Lua examples validate and run in isolated temporary
  directories/stores with cleared environments.
- `cargo test --test test_extract_pdf_limits --test test_pdf_merge_safety
  --test test_pdf_merge_split_nodes --test test_pdf_page_graph --test
  test_artifact_nodes`: 16 tests passed.
- `cargo test --test test_extract_nodes extract_pdf`: three tests passed,
  including fragmented CID Unicode text and existing metadata behavior.
- `cargo test --test test_pdf_page_rendering -- --ignored`: one explicit
  native Poppler test passed; the selected split page and four merged pages
  still match source rendering pixel-for-pixel.
- `cargo clippy --all-targets -- -D warnings`, formatting, module-size policy,
  `cargo audit --deny warnings`, issue-registry checks, and `git diff --check`:
  passed.

That is 38 focused tests plus one native rendering test, not a full integration
gate, feature-backend suite, serve-mode run, or deployment result. The
[shared loading contract](../PDF_LOADING.md), CLI reference, four node documents,
and four Lua examples describe the new limits. Per-stream decoding, encoded
input, and post-parse object count are independent limits, not a cumulative
decompressed-byte or process-memory ceiling. Parser/decoder calls remain opaque
and observe cancellation between calls, not midway through one.
