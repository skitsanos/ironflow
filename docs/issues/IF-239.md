# IF-239 — Integration gate receipt can identify a different tree from the one tested

## Evidence and boundary

At `ae1f686`, the integration gate first read the Git tree when writing its receipt, after validation. A content commit made during the gate could leave a clean checkout and receive a receipt for code the earlier checks had not tested.

## Required outcome and acceptance

Bind validation to a clean, known input tree. Prefer validating an isolated snapshot; at minimum capture the starting tree and refuse a receipt if the end tree differs or is dirty. Cover a commit during validation, an unchanged tree, and the intended message-only amend behavior.

## Outcome and validation

The gate captures the clean starting tree before validation and requires the same clean tree before writing a receipt. A content commit during a check fails the gate without issuing a receipt. Dirty starts and finishes are refused; an unchanged tree or a message-only amend remains eligible. The pre-push check rejects receipts from before the start-tree check.

The gate runs in the caller's worktree, not an isolated snapshot. Use a dedicated worktree for concurrent development: changes reverted between the two observations are not detected.
