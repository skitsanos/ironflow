# IF-136 — Step handlers convert the entire run context under the JSON-to-Lua budget

## Required outcome and acceptance

- A function handler can run after a step that produced a large value it does
  not read (embedding vectors, a big result set) without the conversion budget
  failing the step: convert lazily per key, let a handler declare the keys it
  reads, or exclude keys a flow marks as opaque.
- Existing behaviour for handlers that do read large values is unchanged
  (`IRONFLOW_MAX_CONVERSION_NODES` still bounds what is materialised).
- Test with a context holding a 200 000-number array under one key and a
  handler that returns a constant: the handler succeeds; a handler that indexes
  into the array still hits the budget.

## Evidence and cause

Found on 2026-09-14 while building the document-ingestion flows of the HARMOny
`ironflow-hooks` service (IronFlow 1.18.1-dev.4).

[Source: lua/conversion/json_to_lua.rs:59](../../src/lua/conversion/json_to_lua.rs).

`ai_embed` over 48 chunks stores `embed_embeddings` — 48 × 3072 = 147 456
numbers. The next handler, which only checked `embed_dimension` and
`embed_count`, failed with:

```
JSON-to-Lua maximum node count 100000 exceeded at $.embed_embeddings[32][1606].
This counts the whole value being converted, which for a step handler is the
accumulated run context, not just the keys this step reads
```

Raising the variable only moves the cliff (a 64-chunk batch is 196 608
numbers). The flows now avoid Lua entirely between the embedding node and the
database write: the vectors are bound to AQL as a JSON string through context
interpolation, merged server-side, and blanked with `template_render` before
the next handler. That works, but it makes the natural "check then write"
handler pattern unusable for any vector-producing pipeline.
