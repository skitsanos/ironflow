# IF-136 — Step handlers convert the entire run context under the JSON-to-Lua budget

## Required outcome and acceptance

- A function handler can run after a step that produced a large value it does
  not read (embedding vectors, a big result set) without the conversion budget
  failing the step: convert lazily per key, let a handler declare the keys it
  reads, or exclude keys a flow marks as opaque.
- Existing behaviour for handlers that do read large values is unchanged
  (`IRONFLOW_MAX_CONVERSION_NODES` still bounds what is materialised).
- Test with a context holding a 200 000-number array under one key and a
  handler that returns a constant: the handler succeeds; a handler that indexes
  into the array still hits the budget.

## Evidence and cause

Found on 2026-09-14 while building the document-ingestion flows of the HARMOny
`ironflow-hooks` service (IronFlow 1.18.1-dev.4).

[Source: lua/conversion/json_to_lua.rs:59](../../src/lua/conversion/json_to_lua.rs).

`ai_embed` over 48 chunks stores `embed_embeddings` — 48 × 3072 = 147 456
numbers. The next handler, which only checked `embed_dimension` and
`embed_count`, failed with:

```
JSON-to-Lua maximum node count 100000 exceeded at $.embed_embeddings[32][1606].
This counts the whole value being converted, which for a step handler is the
accumulated run context, not just the keys this step reads
```

Raising the variable only moves the cliff (a 64-chunk batch is 196 608
numbers). The flows now avoid Lua entirely between the embedding node and the
database write: the vectors are bound to AQL as a JSON string through context
interpolation, merged server-side, and blanked with `template_render` before
the next handler. That works, but it makes the natural "check then write"
handler pattern unusable for any vector-producing pipeline.

## Outcome and validation

The implementation adds explicit opt-in `context_keys` projection
to code nodes (string source, inline functions, and authenticated bytecode) and
the `:context_keys({...})` builder for `flow:step` / `flow:step_if` code handlers.
Omission remains backward-compatible: it still converts the complete context.
An empty Lua list `{}` (JSON `[]`) exposes no context values. Keys are literal
top-level names; duplicates select once, missing keys are absent, and invalid
selectors fail instead of falling back to the full context.

Code nodes select before cloning the snapshot for the blocking task. Shared
sandbox setup converts borrowed context entries without constructing another
cloned JSON object. One converter counts the root and every selected subtree
cumulatively at their original depths. Selecting a 200,000-number array still
fails, including when the handler would not read it. Excluded values remain in
the run context for later native nodes, and output conversion is unchanged.

Foreach continues to use the same shared full-context setup and cumulative
limits; it does not gain a projection option in this scoped change. Composition
modules retain their own input-projection contracts.
Any future foreach opt-in must separately preserve the required source array
and bound its materialization; filtering its whole input snapshot would remove
`source_key`, while resetting the converter per selected key would bypass the
cumulative limit. A `step_if` projection affects its handler, not its guard.

Focused coverage:

- `src/lua/conversion/context_tests.rs`: deterministic small-budget tests for
  root counting, cumulative selection, duplicate keys, unchanged depth/path
  accounting, 200,000-number exclusion/rejection, and parity with whole-object
  conversion.
- `tests/test_lua_context_projection.rs`: source and bytecode handlers, both
  builders, empty list normalization, literal keys, missing/null values, isolated
  mutations, reused descriptors, unchanged guards, invalid selectors, late config
  mutation, and unchanged cumulative foreach setup.
- `tests/test_context_projection_workflow.rs`: the checked-in example completes
  after a native JSON node produces 200,000 numbers; selecting that array makes
  the following handler fail with a JSON-to-Lua budget error.
- `examples/07-advanced/context_projection.lua`: runnable without credentials,
  network access, fixtures, or conversion-limit overrides.

## Validation

Post-fix checks on 2026-09-14 with Rust 1.98.1:

- All 11 `test_lua_context_projection` and both
  `test_context_projection_workflow` tests passed in default and combined
  PostgreSQL/Redis feature builds. The 200,000-number example succeeds when the
  array is excluded and fails when selected, without raising limits.
- Library conversion tests passed in both builds. Default `test_lua_runtime`,
  `test_foreach_node`, `test_conversion_limits_env`, `test_lua_limits`,
  `test_lua_preemption`, and interpolation regressions passed.
- The catalog validates every checked-in Lua example; the fixture-backed CLI
  matrix and the new projection example execution passed from isolated working
  directories. Guide, architecture, CLI limit table and node docs were updated.
- Default and full-feature Clippy, formatting, module-size policy and dependency
  audit passed for the batch.

## Follow-up (2026-09-15)

Code review of commit `874b28f` found two gaps in this projection, tracked and
resolved as [IF-144](./IF-144.md):

1. `project_context` was an exact allowlist, so an `on_error` handler that
   declared `context_keys` lost the engine-injected `_error_message`,
   `_error_step`, `_error_node_type` and `_error_output` values (and
   `_flow_dir`) without any warning. Engine-reserved `_` keys now always pass
   through; the list governs user data keys only. The example's empty-list
   step now asserts that its user keys are hidden instead of asserting an
   empty table, so it also holds under `ironflow run`, which injects
   `_flow_dir`.
2. Only the builder form rejected non-code steps. The descriptor form
   (`nodes.log({ context_keys = {...} })`, `nodes.foreach({ context_keys = ... })`)
   passed `ironflow validate --strict` and ran with the full context. Flow
   extraction now rejects `context_keys` on any non-code step with the shared
   `context_keys is only supported for code nodes and function handlers`
   message, for well-formed and malformed values alike.

The "empty list exposes an empty table" wording above describes the original
contract; the current contract is documented in
[`docs/nodes/code.md`](../nodes/code.md).
