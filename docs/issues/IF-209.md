# IF-209 — Follow-ups recorded while fixing IF-182, IF-183 and IF-184

## Evidence and boundary

Recorded on 2026-11-12 from the three fixes. Each item says how it was
established. None was re-verified for this page, except (c), which the
verification probe for IF-182 also showed.

Scheduler (IF-182):

- (a) By reading: the run-permit acquire inside `FlowExecutor::run` is still
  fail-fast. If the run cap fills between the capacity probe and that
  acquire, the instant is reported as `Failed` instead of `AtCapacity`. It is
  consumed either way; only the outcome label is wrong.
- (b) By reading: the run permit is held while a start waits for a load
  permit, so with a small `IRONFLOW_MAX_CONCURRENT_RUNS` waiting schedules
  occupy run capacity for up to 5 seconds.
- (c) Measured: at startup an every-minute schedule lost 19 of 40 catch-up
  instants to the overlap rule, because one schedule's catch-up instants are
  evaluated back to back while its first run is active. Documented overlap
  behaviour, but operators may not expect it from catch-up.
- (d) By reading: a 5-second permit wait followed by a parse near the
  10-second Lua limit can reach the 15-second evaluation budget, which still
  consumes the schedule's due instants as `TimedOut`.

Shutdown (IF-183):

- (e) Measured: `test_artifact_restore_cli::replica_consumer_cli_restores_or_cancels_without_partial_publication`
  failed once in five full `cli` runs and passed alone three times. The new
  stuck-worker test spins one core for about six seconds in the same binary.
- (f) Observed: `POST /flows/validate` is still served during a drain; only
  run and webhook admission answer `503`.
- (g) Decision needed: the five-second runtime shutdown bound is a constant
  with no configuration.
- (h) Not run: the extended `scripts/replica_acceptance.ts` under Docker.

Event fence (IF-184):

- (i) By reading: state and events are deleted in two steps, so a `DELETE`
  that overlaps a new submission of the same ID can remove and fence the new
  run's first events. Closing it needs the state delete to name the
  incarnation it removed. Documented as a caller obligation.
- (j) Measured: tests in `tests/redis_atomicity/event_legacy_expiry.rs` and
  `event_legacy_recovery.rs` failed in three of five `storage_redis` runs on
  a heavily loaded machine and passed 19 of 19 on re-run, on the unfixed and
  the fixed tree. They use a one-second expiry.
- (k) By reading: a failed or timed-out `begin_incarnation` (2-second bound)
  is only logged and leaves that run without events; there is no retry and
  no metric.

Boundary: none of these is a regression from the three fixes. Earlier
follow-ups are in [IF-207](IF-207.md).

## Required outcome and acceptance

- Triage each item: fix it under this page, promote it to its own finding
  when it needs a design decision (likely (c), (g), (i) and (k)), or close it
  with the reason.
- (e) and (j) need a deterministic wait or a longer bound, shown stable over
  repeated runs under load. (h) needs one live run of the acceptance script.
- A fixed item gets a regression. Resolve the page when none is left.
