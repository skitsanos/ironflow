# IF-146 — `ai_chunk_semantic` and `ai_embed` send all inputs in one embeddings request

## Required outcome and acceptance

- Both nodes batch their inputs to the provider (a configurable `batch_size`, default
  well under the common 2048-input cap, with the concatenated results in input order),
  so a long document or a large `input_key` array no longer depends on the provider's
  per-request limit.
- Provider errors for an oversized batch remain visible; retries apply per batch.
- Test `ai_chunk_semantic` on a text with 3 000 sentences and `ai_embed` with a
  3 000-string array against a stub that rejects requests over 2048 inputs: both
  succeed and return one vector per input in order.

## Evidence and cause

Found on 2026-09-15 while ingesting a 243-page clinical trial protocol with the
HARMOny `ironflow-hooks` service (IronFlow 1.18.1-dev.8).

[Source: ai/chunking_semantic/provider.rs](../../src/nodes/ai/chunking_semantic/provider.rs)
and [ai/embeddings/provider.rs](../../src/nodes/ai/embeddings/provider.rs).

`ai_chunk_semantic` embeds every sentence of its input in a single `/embeddings` call.
The 243-page document (503 KB of Markdown) failed with:

```
OpenAI API error (400 Bad Request): Invalid 'input': array length must be 2048 or less.
```

Azure OpenAI and OpenAI both cap one embeddings request at 2048 inputs, so any
document beyond roughly 100–150 pages cannot be chunked semantically. `ai_embed` has the
same single-request shape for its `input_key` array. The service works around both by
cutting documents into ~80 KB segments at page boundaries and running the chunker per
segment with `parallel_subworkflows`, and by embedding chunks in batches of 64 — logic
that belongs in the nodes.
