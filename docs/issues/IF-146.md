# IF-146 — `ai_chunk_semantic` and `ai_embed` send all inputs in one embeddings request

## Required outcome and acceptance

- Both nodes use shared sequential batches for OpenAI, OAuth, and Ollama, with
  configurable `batch_size` (default 512) and concatenated results in input order.
  Batching controls request input counts and bytes, not every provider token limit.
- Validate response cardinality, indices, dimensions, and cumulative vector size;
  bound body reads and preserve cancellation and step deadlines.
- Transient retries apply per failed batch within one node execution. Permanent
  errors remain failures with batch position and HTTP status; workflow retries
  can still restart the entire node.
- Test `ai_chunk_semantic` on 3000 sentences and `ai_embed` with 3000 strings
  against a stub rejecting requests over 2048 inputs. `ai_embed` returns one
  ordered vector per input; `ai_chunk_semantic` runs one global boundary pass
  and returns chunk strings preserving sentence content and order.

## Evidence and cause

Found on 2026-09-15 while ingesting a 243-page clinical trial protocol with the
HARMOny `ironflow-hooks` service (IronFlow 1.18.1-dev.8).

[Source: ai/chunking_semantic/provider.rs](../../src/nodes/ai/chunking_semantic/provider.rs)
and [ai/embeddings/provider.rs](../../src/nodes/ai/embeddings/provider.rs).

`ai_chunk_semantic` embeds every sentence of its input in a single `/embeddings` call.
The 243-page document (503 KB of Markdown) failed with:

```
OpenAI API error (400 Bad Request): Invalid 'input': array length must be 2048 or less.
```

The reported failure was an input-count limit of 2048, not a document-page
limit. Page count does not reliably predict sentence count or token budgets.
`ai_embed` has the
same single-request shape for its `input_key` array. The service works around both by
cutting documents into ~80 KB segments at page boundaries and running the chunker per
segment with `parallel_subworkflows`, and by embedding chunks in batches of 64 — logic
that belongs in the nodes.

## Outcome and validation

Implemented on 2026-09-15 in the shared embedding helpers:

- Sequential requests obey `batch_size` (default 512, maximum 2048) and
  `batch_max_bytes` (default 262144 UTF-8 input bytes, maximum 50 MiB). One
  oversized input fails before embedding requests rather than being truncated.
  Byte admission is not an exact tokenizer or a guarantee of provider limits.
- OpenAI/OAuth indexed responses are reordered, validated, and concatenated;
  completely unindexed compatible responses retain response order. Every provider
  must return the expected count and consistent, nonzero, finite dimensions.
- `batch_retries` defaults to two additional attempts, at most five. Connection
  failures, request timeouts, and HTTP 408/429/500/502/503/504 retry only the failed
  batch. Backoff, `Retry-After`, status reporting, no-partial-output behavior, and
  the distinction from whole-node workflow retries are documented in `ai_embed`.
- Success bodies use the existing bounded provider reader, now named
  `bounded_response_text`; its notification callers retain the same behavior.
  Non-success bodies are discarded without reflection. The full vector matrix
  obeys `IRONFLOW_MAX_EMBEDDING_VALUES` (16777216 by default). This does not bound
  total RSS, downstream JSON conversion, or persisted output size.
- The semantic chunker uses the complete ordered vector matrix for one global
  boundary pass. Provider batches do not become independent semantic segments.
- No detached request/retry tasks: dropping the future stops further batches,
  and the inherited step deadline bounds HTTP attempts and retry delays together.

Pre-fix evidence at `4014c8d`: the new 3000-input and 3000-sentence regressions
both failed with the stub's HTTP 400 input-count error. The batch-boundary test
also demonstrated that configured batching was ignored.

Post-fix default-feature validation:

- `cargo test --locked --test test_embedding_batches`: 14 tests. Both nodes process
  3000 inputs through each of OpenAI, OAuth, and Ollama using local deterministic
  stubs capped at 2048; calls are six bounded batches and OAuth is acquired once.
  Tests cover indexed ordering, global topic boundaries, failed-middle-batch
  retries, permanent errors, exhaustion, malformed/count/dimension responses,
  byte budgets, empty/small inputs, interpolation, cancellation, and deadlines.
  CLI probes exercise the actual executor with 3000 embeddings and reject both
  declared and streamed response overruns plus a cumulative matrix overrun.
- `cargo test --locked --lib nodes::ai::`: 68 tests, including batch option
  validation, index validation, cumulative budget arithmetic, and HTTP dates.
- `cargo test --locked --test test_ai_nodes --test test_semantic_chunk_boundaries
  --test test_provider_redirect_security --test test_notification_response_limits`:
  29 tests. The redirect fixture was corrected to supply two embedding inputs
  for its two-vector response, preserving the redirect assertions.
- Strict validation passed for the changed `embed_openai.lua` and
  `semantic_chunks_embed.lua` examples using the freshly built binary.
- Formatting, module-size policy, `cargo clippy --all-targets -- -D warnings`,
  `cargo audit --deny warnings`, and issue-registry validation passed.

No live OpenAI/Azure/Ollama deployment or clinical document was used. These tests
prove request orchestration and deterministic chunk preservation, not real-model
retrieval quality. The full integration gate remains for a merge/push/release
boundary. Native multipage PDF slices remain a separate IF-147 feature.
