# IF-140 — `copy_file` writes through destination symlinks; `move_file` bypasses the destination policy

## Required outcome and acceptance

- `copy_file` refuses a destination symlink, dangling link or special file and
  never opens or truncates the link target; an existing regular destination is
  replaced atomically after a complete, synced copy.
- `move_file` applies the same destination policy as `write_file` (alias-root
  resolution, pinned directory on Unix, no-follow leaf, special-file refusal)
  before renaming, and cross-device moves still fail with an error.
- The `copy_file` source follows the `read_file` policy and the copy is bounded
  by `IRONFLOW_MAX_FILE_BYTES`.
- Both nodes keep their output keys; plain copies and moves keep working,
  including through directory aliases.
- Regressions prove the symlink target is unchanged for both nodes, that a
  FIFO destination is refused without blocking, that a source symlink and an
  oversized source are refused before staging, and that ordinary copy/move
  flows succeed through the CLI.

## Evidence and cause

Found on 2026-09-15 during code review of commit 874b28f (the IF-133 through
IF-139 batch) and reproduced on macOS with a disposable directory: with
`dest.txt -> target.txt`, `copy_file` reported success and `target.txt` held
the source bytes.

[Source: file/io.rs](../../src/nodes/file/io.rs) implemented `copy_file` as
`tokio::fs::copy(source, destination)`. `std::fs::copy` opens the destination
with `O_WRONLY | O_CREAT | O_TRUNC` and follows a final symlink, so the node
truncated and overwrote the link target. This is the class IF-139 closed for
`base64_decode`; that review did not audit the sibling file nodes.

`move_file` used `tokio::fs::rename`. The kernel does not follow the
destination leaf, but the node had no root, alias or special-file policy: it
silently replaced a symlink or any destination the shared writer refuses, did
not resolve configured directory aliases through the pinned root, and ran
outside the tracked blocking bridge.

An attacker must control the destination namespace; no unauthenticated remote
path or production data loss was established.

## Outcome and validation

The shared atomic writer's request now carries its operation label, so every
error names the node that raised it. `copy_file` opens its source with the
`read_file` policy (`O_NOFOLLOW`, non-blocking open, opened-handle
regular-file check), admits the size against `IRONFLOW_MAX_FILE_BYTES`, and
streams it into a sibling staged file that is flushed, synced and committed
with the `write_file` leaf rules. `move_file` prepares the destination
directory with `RootedDir::prepare` and renames through the new
`RootedDir::rename_into`: Unix validates the leaf against the pinned
directory handle (missing or regular only) and calls
`renameat(AT_FDCWD, source, parent_fd, leaf)`; portable platforms validate
the observed path and call `fs::rename`. The same review also fixed the
rooted writer's error text: a non-`ELOOP` open failure of an append
destination now reports the real error and file name instead of symlink
wording, and an unreadable destination ancestor names the operation and path.

Contract boundary: a `copy_file` source that is a final symlink, FIFO, device
or directory is refused (previously followed), the copy is bounded by
`IRONFLOW_MAX_FILE_BYTES` (previously unbounded), and `move_file` creates
missing parent directories (previously an error). A `move_file` source
symlink is moved as a link, matching `mv`. Both nodes replace an existing
regular destination; neither imposes a sandbox on a trusted flow's configured
destination. Portable platforms revalidate the observed leaf immediately
before replacement but cannot close a hostile parent-directory swap race;
their destination trees still require protection from same-identity mutation.

## Validation

Post-fix checks on 2026-09-15 with Rust 1.98.1 on macOS:

- `test_copy_move_file_safety` (5 tests) passed through the CLI binary:
  symlink destinations refused for both nodes with the sentinel target and the
  link itself intact, FIFO destinations refused without blocking, a plain copy
  onto a stale regular file followed by a move into a new nested parent, the
  byte limit refusing a copy before staging, and a source symlink refused
  before staging. Staged temporary files were never left behind.
- `test_file_alias_roots` (3 tests) passed, including the new copy, move and
  `pdf_merge` case through a symlinked root and a created nested parent.
- `test_base64_write_safety` (6 tests) passed with the streaming decode.
- The rooted-writer unit tests passed, including the new unreadable-append
  (mode `0o200`, skipped as root) and symlinked-append wording regressions.
- `cargo fmt --all`, `python3 -B scripts/check_module_size.py`, `cargo check`,
  `cargo test --lib nodes::file` and `cargo test --lib nodes::utility` passed.
  This is focused local validation on macOS; the portable (`cfg(not(unix))`)
  rename path was reviewed but not compiled here, and the issue registry index
  was not regenerated in this pass.
