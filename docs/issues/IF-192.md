# IF-192 — s3vector_query_vectors runs unfiltered when filter_key does not resolve

## Evidence and boundary

Review of `develop` at 1.21.1-dev.1 on 2026-11-12, by reading
`src/nodes/s3vector/vectors_query.rs:52-60`. Not executed against S3
Vectors.

```rust
let source_key = resolve_optional(config, &["filter_key"], &[], ctx);
source_key
    .and_then(|value| ctx.get(&value).cloned())
    .map(|value| parse_metadata(&value, "s3vector_query_vectors"))
    .transpose()?
```

- When `filter_key` names a context key that is absent (an upstream step was
  skipped, the key is misspelled, or a guard routed around it),
  `ctx.get` returns `None` and the request is built with no filter.
- The node then succeeds and returns the nearest vectors from the whole
  index.
- A flow that relies on the filter for tenant or access scoping (for example
  `filter_key = "tenant_filter"`) therefore returns other tenants' vectors
  instead of failing.
- The sibling inputs fail closed on a missing key: `query_vector_key`,
  `vectors_source_key`, `keys_source_key`, and ArangoDB's `bindVars_key`.

Boundary: an inline `filter` is parsed and validated; only the context-key
form is affected. A present key holding an invalid value already errors
through `parse_metadata`.

## Required outcome and acceptance

- When `filter_key` is configured, require the key to exist and hold a valid
  metadata filter; otherwise fail the step with a message naming the key.
- Regressions: missing key, non-string `filter_key`, null value and a valid
  filter, asserting the request carries the filter in the last case and that
  no request is sent in the first three.
- State the behaviour in `docs/nodes/s3vector_query_vectors.md`.
- Evidence: focused s3vector unit tests; live S3 Vectors only if the request
  shape changes.

## Outcome and validation

Resolved on 2026-11-13.

**Outcome.** A configured `filter_key` is a requirement. The step fails while
the request is prepared, before the AWS client is built, unless the key
resolves to a filter:

| Case | Result |
|------|--------|
| Key absent from context | `requires filter_key '<key>' to exist in context` |
| Value is `null`, `{}`, an array, a string, a number or a boolean | `requires filter_key '<key>' to hold a non-empty filter object` |
| `filter_key` is not a string, or is empty after interpolation | `requires 'filter_key' to be a non-empty string` |
| Value is a non-empty object | Sent as the request filter, as before |

An empty object is refused because it restricts nothing. Messages name the
key and never its value.

**Contract boundary.** The inline `filter` form is unchanged: it is sent as
written, accepts any JSON value, is not interpolated, and wins when both
parameters are set. A step without `filter` and `filter_key` still queries
the whole index. The request shape for a valid filter is unchanged. A flow
that relied on the fallback now fails; `docs/releases/next.md` says how to
keep an intentionally unfiltered query.

**Audit of optional context-key parameters.** Every `*_key` parameter in
`src/` and every `ctx.get` in `src/nodes` was read; none was executed apart
from `filter_key`.

- Fail closed already: `query_vector_key`, `vectors_source_key`,
  `keys_source_key`, `bindVars_key`, `messages_key`, `input_key` (llm,
  ai_embed), `schema_key`, `body_key`, `status_key`, the `repeat_subworkflow`
  state keys, and `source_key` on the file, image, PDF, cache and transform
  nodes.
- Output names, not lookups: `output_key`, `metadata_key`, `comments_key`,
  `cues_key`, `child_output_key`.
- Same defect: `filter_key` only. No other optional key in this area selects
  or scopes.
- Related fallbacks, not fixed here and not yet tracked:
  - `subworkflow` `input` mapping drops an entry whose parent key is absent,
    so the child runs without that key instead of failing.
  - `tool_dispatch` input mapping resolves a missing `ctx.` path to `null`
    and treats a bare name that is not a context key as a literal string.
  - `s3vector_query_vectors` reads `strict`, `return_metadata` and
    `return_distance` with a default of `false` when the value is not a
    boolean, so a malformed `strict` disables the cosine requirement for
    `min_similarity`.
  - The inline `filter` is not interpolated, so `"${ctx.tenant}"` inside it
    is sent as literal text.

**Evidence.**

- Before the fix: 7 new unit tests added to
  `src/nodes/s3vector/vectors_query/tests.rs` and run on the unfixed tree
  (the `execute` test excluded so nothing could reach a client). 4 failed:
  the missing key and the non-string key built a request with no filter, a
  `null` value built a `null` filter and a string value was sent as the
  filter.
- After the fix: `cargo test --lib s3vector` 57 passed; `cargo test --lib`
  740 passed, 1 ignored; `--test nodes` 265, `--test nodes_network` 144,
  `--test examples` 11, `--test serial -- --test-threads=1` 191, all passed.
  The valid-filter test asserts the built request carries the object; the
  `execute` test asserts the missing-key error with an unroutable endpoint.
- `ironflow run` of a one-step flow with a missing key ended `failed` with
  the missing-key message; the documented Lua snippet and the seven
  `examples/16-s3vector` flows pass `ironflow validate`. No example uses
  `filter_key`.
- `cargo fmt --all -- --check`, `python3 -B scripts/check_module_size.py`
  and `cargo clippy --all-targets -- -D warnings` passed.
- Not run: live S3 Vectors (the request shape is unchanged), the PostgreSQL
  and Redis feature builds, and the full integration gate.
