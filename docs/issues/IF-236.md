# IF-236 — rmcp 3.11.0 reads a JSON error body up to the full response limit

## Evidence and boundary

Found on 2026-11-18 while integrating a Renovate update of `rmcp` from 3.10.0
to 3.11.0. Reproduced: with 3.11.0,
`test_mcp_response_limits::initialize_does_not_materialize_an_oversized_json_error_body`
fails. An HTTP 500 response with a JSON content type and a 32 MiB body of
undeclared length is read to about 19.7 MiB before the client stops, where
3.10.0 stopped near 64 KiB.

By reading the 3.11.0 source: the fixed limits became a public
`StreamableHttpResponseLimits` (`max_json_response_size`, default 16 MiB, and
`max_error_response_size`, default 64 KiB) with setters on the transport
configuration. A JSON error body is now read within the JSON limit so its
JSON-RPC error can be parsed, and only its text is cut to the error limit.
The read is still bounded, by the same limit as a successful response, and
the failure message stays short; what changed is how much a failing server
can make `mcp_client` buffer before the step fails.

`docs/SECURITY.md` stated the 64 KiB error cap (IF-173). Until the decision
below, `rmcp` stayed at 3.10.0 and `renovate.json` excluded exactly 3.11.0.

## Required outcome and acceptance

Decide one of:

- accept the upstream behaviour: update the test to the new bound and the
  error-cap statements in `docs/SECURITY.md` and `docs/nodes/mcp_client.md`;
- or set the transport's limits explicitly so the documented bound holds,
  if the new configuration allows it without lowering the cap for successful
  responses.

Then update `rmcp`, remove the Renovate exclusion and rerun
`tests/test_mcp_response_limits.rs`.

## Outcome and validation

Decided by the maintainer on 2026-11-18: accept the upstream behaviour.
`rmcp` is updated to 3.11.0 and required as the minimum, and the Renovate
exclusion and its policy test are removed.

Contract boundary: a JSON response, including the JSON body of an error
response, is read up to 16 MiB; at most 64 KiB of an error body's text is
kept and the failure message stays short. A failing server can therefore
make `mcp_client` buffer up to 16 MiB per request, the same as a successful
response. Non-JSON error bodies and rate-limit responses are still not read.

`initialize_does_not_materialize_an_oversized_json_error_body` now sends a
48 MiB error body and asserts that the client stops within the response cap
plus socket buffering, never reads the whole body, keeps the HTTP status and
produces a failure under 2 KiB. `docs/SECURITY.md`, `docs/nodes/mcp_client.md`
and the release notes state the new bound. Validation: the `nodes_network`
binary, default Clippy, the policy tests, audit and the registry check; the
integration gate was not run for this change alone.
