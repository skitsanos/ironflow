# IF-184 — A deleted run's event fence mutes a re-created run with the same ID

## Evidence and boundary

Review of `develop` at 1.21.1-dev.1 on 2026-11-12, reproduced against a local
`ironflow serve` with the default in-memory event store.

1. `POST /flows/run` with `Idempotency-Key: K` created run `idem-...`; its
   event stream held 7 events.
2. `DELETE /runs/idem-...` returned 200.
3. The same `POST` with `K` created the run again; it finished `success`
   with both tasks.
4. `GET /runs/idem-.../events` returned 0 events. The server logged `Failed
   to publish workflow event ... Event stream for run ... deleted` for each
   event.

- `lifecycle::delete_run` (`src/storage/lifecycle.rs:15-27`) always calls
  `events.delete_run`, which installs a deletion fence that publish enforces
  (`src/storage/event_store/sql/store.rs:106-115, 200-216`,
  `event_store/memory.rs`, `scripts/delete.lua`, `scripts/publish.lua`).
  Nothing clears the fence when the state store accepts the same ID again.
- By reading: the fence is installed on the NotFound path too, so `DELETE`
  of an ID that never existed returns 404 yet pre-fences it. Idempotent and
  scheduled run IDs are deterministic. On SQL the fence is permanent; on
  Redis it lasts until `REDIS_TTL`, or forever without one; each memory-store
  fence consumes a slot of the bounded queue.

Boundary: `docs/CLI_REFERENCE.md` and `docs/REPLICA_DEPLOYMENT.md` say
"Deleting the run releases the retained identity". Run state is unaffected;
only events and SSE are lost. SQL and Redis event stores were not executed.
Related: IF-020, IF-078.

## Required outcome and acceptance

- Scope the fence to a run incarnation, or clear it when `init_run_owned`
  succeeds for that ID, on every event backend.
- Do not install a fence when neither state nor events existed.
- Regressions per backend: delete then re-submit with the same key yields a
  complete event stream; a late publish from the deleted incarnation is
  still rejected; a 404 delete leaves no fence.
- Align the two documents with the implemented behaviour.

## Outcome and validation

Resolved on 2026-11-12. The fence is now scoped to a run incarnation on the
memory, SQL and Redis event backends.

- `EventStore` gained three methods with defaults, so other implementations
  compile unchanged: `publish_as(event, incarnation)`,
  `begin_incarnation(run_id, incarnation)` and `delete_orphaned_run(run_id)`.
  The engine uses the run's lease owner, which is unique per accepted run, as
  the incarnation: after `init_run_owned` succeeds it calls
  `begin_incarnation` and publishes every event through `publish_as`.
- Past a retained fence only the admitted incarnation may publish. The
  deleted incarnation, any other one, and a publisher that names none are
  rejected with `Conflict`. `begin_incarnation` records nothing for a run
  that has no fence. Deleting the re-created run closes the fence again.
- `lifecycle::delete_run` calls `delete_orphaned_run` when state is absent.
  It fences only if it removed events, so a `404` leaves no fence.
- Storage: SQL keeps the admitted incarnation in a nullable `incarnation`
  column of the event-deletion table, added to existing tables at startup;
  Redis in an `event_incarnations:v1:` key that shares the fence's remaining
  lifetime; memory in the fence entry.

Contract boundary:

- State and event deletion remain two steps. A `DELETE` that overlaps a new
  submission of the same ID can remove that run's first events and fence it.
  The documents tell callers to wait for the `DELETE` response.
- During a rolling upgrade an older replica still rejects every event for a
  deleted ID. Fence lifetime per backend is unchanged (IF-020), except that
  Redis and memory give the deletion of a re-created run a fresh lifetime.
- A failed `begin_incarnation` is logged and leaves the run muted, because
  events are best-effort and state is already durable.

Evidence:

- Before, unfixed tree: the HTTP reproduction above returned 7 events, then
  0 after delete and re-submit, with 7 publish failures logged. The new
  re-submit and `404` regressions failed on memory and SQLite (4 of 4) and on
  live Redis (2 of 2).
- After, default features: the same HTTP probe returns 7 and 7 with no
  publish failure. Library tests 671 passed, `storage` 96, `api` 59,
  `engine` 291, `scheduler` 109, `serial` 187 with one test thread. The
  regressions cover, per backend, re-submit after delete, a late publish
  from the deleted incarnation, a `404` delete, and for SQLite the upgrade
  of a fence table without the column.
- After, live services: `storage_redis` passed 95 of 95 against a disposable
  Redis 8.10 with `IRONFLOW_REDIS_TEST_REQUIRED=1`. Against a disposable
  PostgreSQL 18, the same contract including the table upgrade passed, with
  the 14 existing event-store tests, under `--features postgres`.
- `cargo clippy --all-targets -- -D warnings`, the same with
  `--features postgres,redis`, formatting and the module-size gate pass.
  `sql/store.rs` shrank from 359 to 310 lines and its ceiling was lowered.
- Not run: the integration gate, the `storage_postgres` binary, a deployed
  or multi-replica environment, and a live rolling upgrade. The overlapping
  `DELETE` race was reasoned about, not reproduced.
- Observed while validating: four Redis legacy-migration expiry tests failed
  intermittently when the machine was heavily loaded, and passed on re-run
  on both the unfixed and fixed tree. They use a one-second expiry and are
  not touched by this change.
