# IF-184 — A deleted run's event fence mutes a re-created run with the same ID

## Evidence and boundary

Review of `develop` at 1.21.1-dev.1 on 2026-11-12, reproduced against a local
`ironflow serve` with the default in-memory event store.

1. `POST /flows/run` with `Idempotency-Key: K` created run `idem-...`; its
   event stream held 7 events.
2. `DELETE /runs/idem-...` returned 200.
3. The same `POST` with `K` created the run again; it finished `success`
   with both tasks.
4. `GET /runs/idem-.../events` returned 0 events. The server logged `Failed
   to publish workflow event ... Event stream for run ... deleted` for each
   event.

- `lifecycle::delete_run` (`src/storage/lifecycle.rs:15-27`) always calls
  `events.delete_run`, which installs a deletion fence that publish enforces
  (`src/storage/event_store/sql/store.rs:106-115, 200-216`,
  `event_store/memory.rs`, `scripts/delete.lua`, `scripts/publish.lua`).
  Nothing clears the fence when the state store accepts the same ID again.
- By reading: the fence is installed on the NotFound path too, so `DELETE`
  of an ID that never existed returns 404 yet pre-fences it. Idempotent and
  scheduled run IDs are deterministic. On SQL the fence is permanent; on
  Redis it lasts until `REDIS_TTL`, or forever without one; each memory-store
  fence consumes a slot of the bounded queue.

Boundary: `docs/CLI_REFERENCE.md` and `docs/REPLICA_DEPLOYMENT.md` say
"Deleting the run releases the retained identity". Run state is unaffected;
only events and SSE are lost. SQL and Redis event stores were not executed.
Related: IF-020, IF-078.

## Required outcome and acceptance

- Scope the fence to a run incarnation, or clear it when `init_run_owned`
  succeeds for that ID, on every event backend.
- Do not install a fence when neither state nor events existed.
- Regressions per backend: delete then re-submit with the same key yields a
  complete event stream; a late publish from the deleted incarnation is
  still rejected; a 404 delete leaves no fence.
- Align the two documents with the implemented behaviour.
