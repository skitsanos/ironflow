# IF-142 — `subworkflow_error` persists after a later successful subworkflow

## Required outcome and acceptance

- A waiting `subworkflow` call always writes `subworkflow_error` and, when
  `output_key` is set, `{output_key}_error`: a string when the child did not
  succeed and JSON `null` when it did, so a later call overwrites an earlier
  tolerated failure's text.
- Without `output_key`, the child's own `subworkflow_name`,
  `subworkflow_success`, `subworkflow_error`, and `subworkflow_async` keys are
  not merged into the parent; the parent's keys describe its direct child only.
- Test with a parent that runs a failing child with `on_error = "ignore"` and
  then a successful child: the run context ends with `subworkflow_success =
  true` and `subworkflow_error = null`, and a Lua handler sees `json_null`, not
  the stale string. Test with a child that itself ignored a failing grandchild
  and detached another: the parent reports `subworkflow_success = true`,
  `subworkflow_error = null`, and no `subworkflow_async`.

## Evidence and cause

Found on 2026-09-15 during code review of commit `874b28f` (the IF-135 batch).

[Source: composition/subworkflow.rs](../../src/nodes/composition/subworkflow.rs)
and [engine/executor/phase_output.rs](../../src/engine/executor/phase_output.rs).

The node always wrote `subworkflow_success` but wrote `subworkflow_error` and
`{output_key}_error` only when the child failed. Node outputs are published by
extending the run context (`PhaseOutputAccumulator::commit`), which can add or
replace keys but never remove them. Two consequences followed:

- A flow that tolerated one failing child and then ran a successful one kept
  the first call's error text beside `subworkflow_success = true`; a later step
  that logged or forwarded `subworkflow_error` reported a failure that had been
  superseded.
- A child flow that had itself ignored a failing grandchild carried its own
  `subworkflow_error` in its context, and the un-namespaced merge loop copied
  it into the parent output; the parent then set `subworkflow_success = true`
  without clearing the inherited error. The same loop could forward a detached
  grandchild's `subworkflow_async = true`.

`parallel_subworkflows` already skips its own result metadata keys during the
un-namespaced merge (`RESULT_METADATA_KEYS` in `parallel_runner.rs`); the single
`subworkflow` node did not.

## Outcome and validation

- `subworkflow.rs` computes one error value per waiting call — a string on
  failure, `serde_json::Value::Null` on success — and writes it to
  `subworkflow_error` and, when namespaced, `{output_key}_error` on every call.
- A `RESULT_METADATA_KEYS` constant lists the node's own result keys; the
  un-namespaced merge skips them alongside `_`-prefixed keys. Namespaced output
  keeps the child's full public context, including its own metadata, under
  `output_key`.
- `docs/nodes/subworkflow.md` documents the always-present error slot, that
  flows should branch on `subworkflow_success`, that a JSON `null` reaches Lua
  as the truthy, non-`nil` `json_null` sentinel (so `type(...) == "string"` or
  `~= json_null` is the correct check), that interpolation renders it as an
  empty string, and the un-namespaced metadata rule. [IF-135](./IF-135.md)
  records the follow-up.

## Added Regression Targets

- `tests/test_child_failure_details.rs`:
  `later_success_resets_error_and_nested_metadata_does_not_leak` runs a
  sequential ignored-failure-then-success parent through the engine (namespaced
  under `run`) whose Lua check step asserts `subworkflow_error == json_null`,
  and a nested child that ignored a failing grandchild and detached another,
  asserting `subworkflow_success = true`, `subworkflow_error = null`, and no
  `subworkflow_async` in the parent output.
- `multiple_unresolved_errors_are_sorted_and_recovered_children_have_no_error`
  now asserts that a successful child leaves `subworkflow_error` (and
  `child_error` when namespaced) present as `null`.

## Validation

Post-fix checks on 2026-09-15 (focused, default features):

- `cargo test --test test_child_failure_details`: all 6 tests passed, including
  the new regression and the strict CLI run of the IF-135 example pair.
- `cargo test --lib composition::subworkflow` passed.
- `cargo fmt --all`, `python3 -B scripts/check_module_size.py`, and
  `cargo check` passed.

This is a contract fix to node output keys; parallel, repeat, and tool-dispatch
consumers keep their existing result shapes. No live-service or deployed
validation is claimed.
