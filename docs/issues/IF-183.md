# IF-183 — New connections hang for the whole drain and readiness never reports draining

## Evidence and boundary

Review of `develop` at 1.21.1-dev.1 on 2026-11-12, reproduced against a local
`ironflow serve` with one 25-second run in flight.

- After SIGTERM, new connections to `/health/ready` completed the TCP
  handshake in under a millisecond and then received no response. Three
  probes at 2, 8 and 14 seconds each hit a 4-second client timeout. The
  documented `503` draining response was never observed.
- The in-flight request finished with `status: success` and the process
  exited after 23 seconds, so draining of existing work is correct.
- `serve_until` (`src/api/server.rs:106-134`) selects on the server future
  and the signal, then awaits `lifecycle.drain(grace)` without polling the
  server future. The accept loop lives inside that future, so the listener
  is neither accepted from nor closed until the final settle timeout.
  Connections that existed before the signal keep working because they run
  on spawned tasks.
- Observed in a separate probe: after the CLI printed a final run status,
  the process stayed alive while an uninterruptible blocking worker was
  still running. On the success path `main` drops the runtime, which waits
  for blocking closures (`src/main.rs:41-51`); only the error path calls
  `process::exit`. For `serve`, "forced shutdown" therefore still depends on
  blocking work returning.

Boundary: `docs/REPLICA_DEPLOYMENT.md` and `docs/ARCHITECTURE.md` promise a
`503` readiness answer while draining and a bounded termination (IF-077).
`scripts/replica_acceptance.ts` checks that in-flight runs drain, not what
new connections see. With the default 30-second grace (up to 3,600) the hang
lasts that long plus the settle window.

## Required outcome and acceptance

- Keep the server future polled during the drain so new connections are
  either refused or answered with `503`, and `/health/ready` reports
  draining.
- Bound process exit after the settle timeout (`shutdown_timeout` on the
  runtime, or an explicit exit) so stuck blocking work cannot hold the
  process.
- Regressions: during a drain a fresh connection gets a prompt `503` or a
  refusal; a stuck blocking task does not prevent exit after the documented
  bound.
- Extend the replica acceptance script with a new-connection probe.

## Outcome and validation

Resolved 2026-11-12. Both defects were reproduced on the unfixed tree at
1.21.1-dev.5 before any change.

Outcome:

- `serve_until` no longer ties Axum's graceful shutdown to the start of
  draining. It polls the server future for the whole run drain and closes
  the listener only after `lifecycle.drain` returns. During the drain a new
  connection is accepted and answered: `/health/ready` returns `503`
  `draining`, run and webhook admission return `503`, and run reads still
  work. Afterwards the listener closes (new connections are refused) and
  open connections keep their existing five-second bound.
- `main` ends with `Runtime::shutdown_timeout` of five seconds instead of
  dropping the runtime, for every command. A blocking worker inside an
  uninterruptible call ends with the process.

Contract boundary: accepted runs still drain for the grace, are then
cancelled and get 20 seconds to settle, and keep their admission permits
until they settle; IF-077's ordering (readiness false before listener
shutdown and before cancellation) now holds for new connections too. The
longest termination is grace + 30 seconds (20 settle, 5 connections, 5
runtime), previously documented as + 25 but in fact unbounded. Requests that
are not run admission, such as `POST /flows/validate`, are still served
during the drain. The failure path of `main` already exited immediately and
is unchanged.

Evidence, local debug build, loopback, JSON store:

- Before: with a 25-second run in flight, fresh `/health/ready` probes at 2,
  8 and 14 seconds after SIGTERM connected in under a millisecond and each
  hit the 4-second client timeout; exit after 23 seconds with the run
  `success`. A `run` whose step timed out inside an uninterruptible Lua
  pattern match and was recovered printed `Status: success` and was still
  alive 15 seconds later.
- After: the same three probes returned `503` `draining` in 1 to 3 ms, a new
  `POST /flows/run` returned `503`, the run finished `success`, exit after 23
  seconds, then connection refused. `serve` with the stuck worker exited 5
  seconds after SIGTERM. With a 2-second grace the held run was `cancelled`
  and the process exited after 2 seconds.
- Regressions, both failing before the fix and passing after:
  `tests/test_serve_drain.rs` (`api` binary; child `serve`, SIGTERM, fresh
  connections) and `tests/test_cli_exit_bound.rs` (`cli` binary; child `run`
  with a stuck blocking worker, exit within the bound).
- `scripts/replica_acceptance.ts` now probes readiness on new connections
  after SIGTERM and fails on a hang. Its probe functions were exercised
  against the local debug server; the Docker acceptance itself was not run.
- Not run: the full integration gate, feature-enabled and live-storage
  suites, and any deployed platform. The stuck-worker `serve` case has no
  pre-fix timing.
