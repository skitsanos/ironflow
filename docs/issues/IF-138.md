# IF-138 — `arangodb_aql` bind variables from context are always strings

## Required outcome and acceptance

- A bind variable can take a typed context value — array, object, number,
  boolean — for example through a `bindVars_key` (whole object from a context
  key) or per-variable `{ key = "ctx_key" }` references, in addition to today's
  interpolated strings.
- Documented alongside the existing rule that the query text itself must not
  interpolate context.
- Test with an array of documents bound to `@docs` and used in
  `FOR d IN @docs UPSERT …`, a numeric `@limit`, and a boolean flag: no
  `JSON_PARSE`/`TO_NUMBER` needed on the AQL side.

## Evidence and cause

Found on 2026-09-14 while building the document-ingestion flows of the HARMOny
`ironflow-hooks` service (IronFlow 1.18.1-dev.4).

[Source: database/arangodb.rs:12](../../src/nodes/database/arangodb.rs).

`bindVars` values pass through the generic string interpolation, and a
`"${ctx.docs}"` placeholder renders an array as its JSON text, so the server
receives a string. Every write in the ingestion service therefore ships
documents as `docs = "${ctx.docs_json}"` and opens with `FOR d IN
JSON_PARSE(@docs)`, numbers arrive as `"48"` and are wrapped in `TO_NUMBER()`,
and booleans travel as `"true"`/`"false"` compared as strings. It works, but
it pushes type handling into every query and doubles the size of large
payloads (JSON inside JSON). The database node is where string-only
interpolation costs the most, because AQL has its own typing and the server
would otherwise validate the bound values.

## Outcome and validation

- Added explicit `bindVars_key`: a non-empty string naming one literal top-level
  context key containing the whole bind object. The request receives a clone of
  that JSON object without interpolation or string conversion. Nested arrays,
  objects, numbers, booleans, null values, and template-looking strings retain
  their types and values; the context is not mutated.
- Missing context values, non-object values, and malformed key parameters fail
  before query I/O without including context contents in errors. Empty bind
  objects remain valid. Both bind sources present is an error, including null
  fields, for every action. A single bind source is query-only: next/close never
  resolve or replay it.
- Literal `bindVars` and its recursive string interpolation remain unchanged.
  No implicit per-variable `{ key = ... }` reference or generic interpolation
  change is introduced. AQL query interpolation remains prohibited; static
  queries use `@var`/`@@collection` placeholders with either bind source.
- Request-capture regressions in `tests/arango_cursor/bind_vars.rs` cover the
  typed document-array UPSERT shape, numeric limit, boolean flag, nested objects,
  collection binds, errors, legacy literals/templates, and cursor isolation.
  The read-only `examples/12-arangodb/aql_typed_bind_vars.lua` has a focused CLI
  regression; `docs/nodes/arangodb_aql.md` also shows the ingestion UPSERT variant.

## Validation

- `test_arangodb_cursor`: 21 tests passed; `test_arangodb_node`: 4 passed in the
  combined-feature build. Request capture confirms typed JSON, unchanged query

  authenticated, loopback-only ArangoDB 3.12.11 Docker container (Linux/ARM64),
  using the locally compiled 1.18.1-dev.4 CLI and Bun 1.4.2.
- The first real UPSERT inserted two documents; the second updated both without
  duplicates. A numeric limit excluded a third document, and a false boolean
