# IF-188 — Child workflows have no nesting limit and outlive a timed-out parent step

## Evidence and boundary

Review of `develop` at 1.21.1-dev.1 on 2026-11-12, reproduced with a local
optimized build.

1. No nesting limit. A flow `self.lua` whose only step is
   `nodes.subworkflow({ flow = "self.lua" })` started about 67,000 nested
   child executions in 12 seconds and was still descending when stopped. No
   depth error is raised, `ironflow validate` does not load child flows, and
   `IRONFLOW_MAX_RUN_SECONDS` is unset by default. Every composition node
   re-registers the others in its child registry
   (`src/nodes/composition/registry.rs:20-24`), and none carries a depth
   (`subworkflow.rs:146-154`, `parallel_runner.rs:73-90`,
   `repeat_subworkflow.rs:115-124`, `tool_dispatch/runner.rs:57-63`).
2. Parent does not wait for child work. A parent step
   `subworkflow(...):timeout(2):on_error("handler")` whose child was inside
   an uninterruptible tracked blocking node timed out at 2 s; the handler
   started at once and the parent run was finalized `success` while the
   child's worker was still running. The same node placed directly in the
   parent keeps the run open until the worker stops (still open at 25 s).
   Tracked workers register with the task that spawns them, which is the
   child coordinator's own task, so the parent's wait sees an empty set
   (`src/engine/executor/handle.rs:53-99`, `src/util/execution.rs:75-84,
   217-236`).
3. Eager child contexts, by reading. `parallel_subworkflows` builds every
   child context before `max_concurrent` applies
   (`parallel_subworkflows.rs:89-146`) and has no item ceiling, unlike
   `tool_dispatch` and `repeat_subworkflow`. It also calls
   `Path::canonicalize` on the async thread once per entry.

Boundary: `docs/ARCHITECTURE.md` states that run and task admission is held
until physical work stops (IF-064, IF-065). Item 2 means a handler or
dependent step can run, and admission can be released, while the child is
still writing. Memory growth in item 3 was not measured.

## Required outcome and acceptance

- Carry a nesting depth through child execution and fail above a small
  documented ceiling.
- Make the parent step's completion, timeout and cancellation wait for the
  child's tracked workers before releasing permits or starting handlers.
- Build each child context after its concurrency permit is acquired, add an
  item ceiling to `parallel_subworkflows`, and resolve paths off the async
  thread.
- Regressions: self- and mutually-recursive flows fail fast; a timed-out
  parent does not finalize before a child worker stops; fan-out memory stays
  proportional to `max_concurrent`.
- Document the limits in the four composition node pages.

## Outcome and validation

Resolved on 2026-11-12 for all three items.

1. Nesting depth. A composition node captures a `ChildLink` on its own task
   and passes it to the engine with every child. The link carries the child's
   level, which the child coordinator scopes around its steps. A child more
   than `IRONFLOW_MAX_SUBWORKFLOW_DEPTH` levels (default 16, validated at
   startup) below its top-level run is refused before its flow is resolved or
   loaded, for all four nodes and for detached children, which keep their
   level. Sixteen was chosen because each level holds a loaded flow, a
   context and a coordinator, while a bounded agent loop (`repeat_subworkflow`
   around `tool_dispatch`) needs two levels.
   Each level reports the refusal alone, because sixteen wrapped child
   failures exceed the failure-summary cap and would cut it off.
2. Waiting. The child coordinator registers with the starting step's attempt
   and run worker sets before it is spawned and releases that only after it
   has drained its own workers and finalized. Timeout, cancellation and the
   run deadline still cancel the child at once, but the step result, its
   `on_error` handler, run finalization and admission wait for the child.
3. Fan-out. `parallel_subworkflows` refuses more than
   `IRONFLOW_MAX_PARALLEL_SUBWORKFLOWS` entries (default 1024, the existing
   `max_concurrent` cap), resolves flow paths with `tokio::fs` once per
   distinct path before any child starts, and creates each child, with its
   context, only inside the `max_concurrent` window. Dynamic entries refer to
   their item instead of copying it. `subworkflow` and `tool_dispatch` also
   resolve their path off the async thread.

Contract boundary:

- The depth limit does not bound the total children of a nested fan-out;
  sixteen levels of wide `parallel_subworkflows` still multiply.
- An uninterruptible child worker now delays the parent's timeout result, as
  the same node in the parent already did.
- Both refusals are step errors that `on_error = "ignore"` on the same step
  does not suppress. Collected results still grow with the number of children.
- `ironflow validate` still does not load child flows.

Evidence (debug build, default features):

- Item 1 before: self- and mutually-recursive flows under `ironflow run`
  reached 1,185 and 1,887 nested runs in 6 s with no error and were killed.
  After: both fail at level 17 in under a second with the refusal; 7 new
  tests in `test_subworkflow_depth` cover the four nodes, mutual recursion,
  16 levels passing and 17 failing, a detached chain stopping at 17 runs, and
  both environment overrides.
- Item 2 before: with a `markdown_to_html` child that ignores cancellation,
  the handler started at the 2 s deadline and the parent was finalized
  `success` 3.3 s before the child worker stopped; the same node in the
  parent delayed the handler until the worker returned. After: the handler
  starts after the child run has stopped. Three new unit tests gate a tracked
  worker for all four nodes; the timeout and cancellation tests failed (2 of
  3) with the registration disabled and pass with it.
- Item 3: the eager build was read, not measured, before the fix. After: a
  unit test runs seven children with `max_concurrent = 2` and observes at
  most two started at once; others cover the ceiling in both modes, a missing
  flow failing before any child starts, and unstarted children never starting
  after a drop. Memory use was not measured.
- Suites: library 683 passed (1 ignored), `engine` 298, `nodes` 258,
  `nodes_network` 134, `scheduler` 113, `api` 60, `cli` 95, `examples` 11,
  `serial` 187 single-threaded, `extract_execution` 2, `schema_execution` 2.
  All 160 Lua examples validate. `cargo fmt --check`, the module-size gate
  and `cargo clippy --all-targets -- -D warnings` pass.
- Not run: `postgres` and `redis` feature builds, live stores, the full
  integration gate, and other platforms.
