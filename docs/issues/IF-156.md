# IF-156 — PDF extraction ignores logical ActualText for shaped RTL content

## Evidence and boundary

On 2026-10-26, the unreleased Markdown document-generation work produced a
visually checked PDF from `examples/fixtures/markdown-multilingual.md`. Its
tagged, line-level `/ActualText` spans retain the original logical Unicode,
verified independently in `tests/test_markdown_multilingual.rs` using structured
content-stream parsing and PDF text-string decoding.

At the initial report, `extract_pdf` used lopdf 0.46.0's glyph-oriented
`extract_text_with_limit`. A real CLI round-trip probe successfully extracted
the generated two-page PDF, but neither the original Hebrew heading nor the
original Arabic heading could be found in the returned text. Hebrew letters
were reversed and Arabic shaped/combining glyphs produced replacement or
duplicated characters. Success status and readable rendering do not establish
lossless extraction. Source inspection found no ActualText handling in this
extraction path.

This is a confirmed extraction limitation, not proof that every PDF or RTL
document fails. Poppler's text output also applies bidi and reading-order
heuristics, so its default text output is not an exact ground-truth oracle.
PDF display and logical ActualText preservation are validated separately.

## Required outcome and acceptance

- Honor logical ActualText spans where present, replacing the corresponding
  glyph text once without duplicate nested-span output.
- Preserve the existing path/artifact, single-parse, page-selection, output-byte,
  stream/object admission and cooperative cancellation guarantees.
- Decode supported PDF text-string encodings through structured APIs. Bound
  marked-content nesting and indirect property resolution; reject malformed or
  cyclic properties safely. Do not reverse strings heuristically.
- Add regressions for Hebrew, joined Arabic, combining marks, mixed RTL/LTR and
  numbers, nested spans, ordinary untagged PDFs, limits and cancellation.
- Reproduce the failure through `extract_pdf`, not merely a direct dependency
  call, and qualify the fixed round trip against the preserved source text.

## Initial mitigation

Retain the original Markdown for text/RAG ingestion instead of regenerating it
through a glyph-only PDF extraction pass. Generated PDFs preserve logical
ActualText for readers that support it, but renderer/extractor heuristics still
vary. The new generation nodes do not claim a lossless `extract_pdf` RTL round
trip. That generation-only batch did not include an extraction fix.

## Outcome and validation

The local follow-up now uses a bounded page-content walker. Outermost ActualText
strings replace the covered glyph operations once; nested replacements do not
duplicate text and an empty replacement suppresses its glyphs. Plain text still
uses lopdf font decoding, not heuristic reversal. Named Properties resources,
inherited resource dictionaries, indirect references, PDFDocEncoding, UTF-16BE
and UTF-8 BOMs are supported through structured APIs.

Marked-content/text-operand nesting is capped at 64 levels, property references
at 32 hops, and named-resource inheritance at 64 ancestors. Cycles, broken or
malformed properties, invalid Unicode strings and unbalanced markers fail.
Decoded replacement size is admitted before materialization. Operations, font
bindings, reference/ancestor hops, text operands and 4 KiB source-string chunks
share the existing work-item budget, with cooperative cancellation checkpoints.
Page/font stream decoding uses the smaller of remaining output bytes and the
shared decompressed-stream limit. The source document is still parsed once.

Nine integration regressions cover the real generated multilingual PDF through
`extract_pdf` in text and Markdown modes, nested/empty replacements, legacy
spacing, inherited/indirect properties, all three text-string encodings,
malformed input, reference/depth limits and page selection via `pdf_split`.
One sequential resource test covers replacement growth, cumulative multipage
output, work-item/stream limits and expired deadlines. The seven original
behavior/safety regressions were observed failing before the fix; all expanded
tests passed after it. The existing PDF output/regular-file and shared-load
regressions passed too. A real `serve` HTTP workflow now generates the sample
and asserts logical Hebrew/Arabic after extraction; the runnable multilingual
example exposes the same round trip as `pdf_text`.

The full native integration gate passed with ZIP 9.1.2 and Comrak 0.59.0: all
178 Cargo targets in both default and PostgreSQL/Redis modes, exact Clippy in
both modes, doc tests, audit, release build, all 155 Lua examples and live TLS
storage acceptance/rejection against disposable services. A real CLI sample
round trip returned coherent full multilingual text. The final 67 Bun policy
tests and updated workflow actionlint checks passed separately. The gate's
initial disk-exhaustion failure and bounded-runner fix are preserved in IF-158;
that failure was not treated as a passing run.

This resolves implementation and local qualification. Stable publication and
hosted acceptance are separate validation boundaries. This is not OCR,
general semantic layout reconstruction, or new traversal of Form XObjects or
structure-tree-only ActualText. Untagged documents retain font/stream-order
limitations. External extractors can still apply their own bidi heuristics.
