# IF-211 — Lua run by a step is not tracked work and outlives a timed-out step

## Evidence and boundary

Found on 2026-11-12 while verifying IF-188 (item (e) of
[IF-210](IF-210.md)); reproduced on a debug build of `develop` at
1.21.1-dev.7.

A function step whose body spends about five seconds inside one
`string.find` call, with `:timeout(2):on_error("handler")`: under
`ironflow run` the handler ran and the run was finalized `success` at 2 s
while the call was still running. The process exited when the call returned
or at the runtime shutdown bound from IF-183, whichever came first.
Reproduced the same way for:

- a `foreach` transform;
- a function step in a child flow called through `subworkflow`, where the
  child run was also finalized before its function returned;
- the top-level code of a child flow while `subworkflow` loads it.

Cause, by reading: a function handler is serialized to bytecode and runs as a
`code` node. `code`, `foreach` and flow loading already run on the blocking
pool with an instruction hook that checks the step deadline and
cancellation, but through `run_blocking_step`, which does not register the
worker with the step's attempt and run worker sets
(`src/util/execution.rs`). The hook cannot run inside a single C library
call, so the executor stopped waiting while the worker continued.

Not affected, by reading: a `step_if` condition is an `if_node` expression,
not Lua, and a function passed to `step_if` is an ordinary function step. A
plain Lua loop was already stopped at the next hook check (reproduced).

Boundary: `docs/ARCHITECTURE.md` states that run and task admission is held
until physical work stops (IF-064, IF-065). Here a handler or dependent step
could run, and admission be released, while the Lua call was still
executing. The sandboxed VM has no file or network access, so the exposure
is ordering and capacity, not data.

## Outcome and validation

Resolved on 2026-11-12. `code` (function steps and `nodes.code`), `foreach`
and `LuaRuntime::load_flow_async` now use `run_tracked_blocking_step`. The
engine is unchanged: the step's existing wait on its worker sets covers
them, and IF-188's link carries that to a parent step. Flow loads by the
API, webhooks and scheduler run outside a step, have no worker sets and keep
their own flow-load admission.

Contract boundary:

- Interruptible: Lua between instructions. A timeout, cancellation or run
  deadline stops it at the next hook check (every
  `IRONFLOW_LUA_HOOK_INTERVAL` instructions) and between `foreach` items.
- Not interruptible: time inside one C library call (`string.find`,
  `string.match`, `string.gsub`, `string.rep`, `table.concat`). The step
  result, `on_error` handler, dependent steps, run finalization and
  admission now wait for it, so a stuck call delays the timeout result, as a
  stuck built-in blocking node already did. The Lua time and instruction
  budgets are also checked only by the hook and do not bound such a call.
- Steps that finish in time are unchanged.

Evidence (debug build, default features):

- Before, all four cases: handler at 2.1 to 2.4 s, process exit at 5.6 to
  7.1 s. After: handler at 5.3 to 5.7 s, when the call returned, and exit
  0.3 s later. A `while true do end` function step ends in 0.2 s before and
  after, on the instruction budget.
- `function_workers` (4 unit tests) covers the four cases for timeout and for
  run cancellation, a Lua loop stopped at the deadline and on cancellation,
  and an in-time function step. The timeout and cancellation tests failed on
  the unfixed tree and pass with the fix; the other two are guards. The
  stuck call is calibrated to at least 1.2 s.
- `tests/test_cli_exit_bound.rs` (IF-183) used a stuck `code` step as its
  untracked worker and would now wait for it. Its stuck call moved into a
  detached child, which nothing waits for; it still exits at the bound.
- `serve`, probed after the fix: a function step that never returns, grace
  2 s: the run was cancelled at the grace, did not settle, and the process
  exited 32 s after SIGTERM (grace + 30) with the run left `running` for
  recovery. A call that returned inside a 30 s grace ended its run `success`
  and the process exited at once. `/health/ready` answered `503` throughout.
- Suites: library 709 passed (1 ignored), `engine` 304, `nodes` 258,
  `nodes_network` 134, `scheduler` 113, `api` 60, `cli` 95, `examples` 11,
  `serial` 190 single-threaded, `extract_execution` 2, `schema_execution` 2,
  `flow_load_admission` 1, `scheduler_admission` 1. All 162 Lua examples
  validate. `cargo fmt --check`, the module-size gate and
  `cargo clippy --all-targets -- -D warnings` pass.
- Not run: `postgres` and `redis` feature builds, live stores, the full
  integration gate, other platforms. The loop guard test was not run on the
  unfixed tree in its final form.
