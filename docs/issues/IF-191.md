# IF-191 — block_private_network passes CGNAT, NAT64 and other internal address ranges

## Evidence and boundary

Review of `develop` at 1.21.1-dev.1 on 2026-11-12, by reading
`src/nodes/http/helpers.rs:17-37`. Not executed against a network.

`ip_is_internal` is the classifier behind `block_private_network` for
literal hosts, redirects and every pinned DNS answer
(`src/nodes/http/request/dns.rs:30`, `transport.rs:190-198`).

- IPv4 covers RFC 1918, loopback, link-local and the single address
  `0.0.0.0`.
- IPv6 covers IPv4-mapped addresses, loopback, unspecified, unique local and
  link-local.

Not covered:

- `100.64.0.0/10` (shared address space): used by carrier-grade NAT, overlay
  networks and some cloud secondary ranges, and it contains one provider's
  metadata endpoint at `100.100.100.200`.
- NAT64 (`64:ff9b::/96`, `64:ff9b:1::/48`): on an IPv6-only network with a
  NAT64 gateway, `http://[64:ff9b::a00:5]/` reaches `10.0.0.5`.
- 6to4 (`2002::/16`) and IPv4-compatible forms that embed an IPv4 address.
- The rest of `0.0.0.0/8`, `192.0.0.0/24`, `198.18.0.0/15` and
  `240.0.0.0/4`.

Boundary: the guard is opt-in and off by default. Decimal, octal and hex
host forms are normalized by the `url` crate before the check, and DNS
answers are validated and pinned, so those bypasses are closed. Whether a
given range is reachable depends on the deployment network.
`docs/nodes/http_request.md` says the option refuses "private, loopback,
link-local, metadata" targets, which overstates current coverage. Related:
IF-041, IF-061, IF-104.

## Required outcome and acceptance

- Add the missing IPv4 ranges and unwrap NAT64, 6to4 and IPv4-compatible
  addresses to their embedded IPv4 address before classifying.
- Table-driven unit tests for each range, both as URL literals and as DNS
  answers, plus public addresses adjacent to each range that must still
  pass.
- List the exact refused ranges in `docs/nodes/http_request.md` and
  `docs/SECURITY.md`.
- Check whether `mcp_client` Streamable HTTP should honour the same guard
  and record the decision.

## Outcome and validation

**Historical status:** Resolved on 2026-11-12.

The classifier moved to `src/nodes/http/address.rs` and now answers one
question: is this address a public unicast destination? It stays a pure
function on the standard library, shared by URL literals, redirect targets
and DNS answers.

Reproduced before the fix: a table of 77 addresses across the ranges below
was run against the unchanged classifier and 56 passed as public, failing
five new tests (classifier, URL literal, DNS answer, redirect, numeric host
forms). `ironflow run` of `http_request` with `block_private_network = true`
refused `127.0.0.1` but attempted `0.0.0.1` (transport error) and
`[::127.0.0.1]` (timeout). After the fix the same runs, and `100.64.0.1` and
`[64:ff9b::a00:5]`, end with `blocked: target is a private network address`.

Decision table:

| Range | Decision |
|-------|----------|
| `0.0.0.0/8`, `10/8`, `172.16/12`, `192.168/16`, `127/8`, `169.254/16` | Refused (whole `0/8` is new) |
| `100.64.0.0/10` | Refused: CGNAT, overlays, a metadata endpoint |
| `192.0.0.0/24`, `198.18.0.0/15`, `240.0.0.0/4` and broadcast | Refused; the anycast addresses in `192.0.0.0/24` are not HTTP destinations |
| `192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24`, `192.88.99.0/24`, `224.0.0.0/4` | Refused: documentation, deprecated relay anycast, multicast; never a public unicast server |
| IPv4-mapped, NAT64 `64:ff9b::/96`, 6to4 `2002::/16` | Unwrapped; the embedded IPv4 address decides, so public targets behind NAT64 still pass |
| IPv4-compatible `::/96`, IPv4-translated, `64:ff9b:1::/48` | Refused outright: deprecated or local-use by definition, stricter than unwrapping |
| All IPv6 outside `2000::/3` (`::`, `::1`, `100::/64`, `5f00::/16`, `fc00::/7`, `fe80::/10`, `fec0::/10`, `ff00::/8`, unassigned) | Refused: an allow-list of global unicast replaces the list of bad prefixes |
| `2001::/23` (Teredo, benchmarking, ORCHID, AMT, AS112), `2001:db8::/32`, `3fff::/20` | Refused; Teredo is not unwrapped because the whole block is refused |
| ISATAP interface identifiers under a public prefix | Not interpreted: the prefix, not the identifier, routes the packet |

Other consumers of network destinations, by reading: none honours
`block_private_network` or exposes an equivalent address restriction, so the
guard was not extended. `mcp_client` Streamable HTTP takes `url` unchecked
and follows only same-origin `307`/`308` redirects; `llm`, `ai_embed`,
`ai_chunk_semantic`, `transcribe`, `slack_notification`, Resend `send_email`
and `arangodb_aql` share a client that follows same-origin redirects only
and uses the system proxy; SMTP `send_email`, `db_query`/`db_execute`, the
S3 and S3 Vectors `endpoint_url`, `shell_command` and stdio `mcp_client`
have no restriction. Decision for `mcp_client`: it should gain the same
opt-in guard, but that needs a custom client injected into the MCP
transport and is a separate change. The gap is documented in
`docs/SECURITY.md` under "Outbound destinations".

Contract boundary: the option remains opt-in and `http_*` only. Flows that
set it and call a newly refused range (for example a `100.64.0.0/10`
overlay) now fail; `docs/releases/next.md` says so. Addresses that are
public by registry but routed internally by a deployment are outside what a
classifier can know.

Validation (debug build, no network host contacted):

- Library tests: 713 passed, 1 ignored, including the five table tests over
  77 refused and 43 adjacent public addresses.
- `tests/test_http_nodes.rs` gained a 15-literal regression through the
  node. Area binaries: `nodes_network` 134, `nodes` 258,
  `examples` 11, `http_proxy_modes` 1, `serial` 191 passed with
  `--test-threads=1`.
- `cargo fmt --all -- --check`, `python3 -B scripts/check_module_size.py`
  and `cargo clippy --all-targets -- -D warnings` passed.
- Not run: the integration gate, feature-enabled builds, any request to a
  real NAT64 or CGNAT network, and the consumer audit was reading only.
