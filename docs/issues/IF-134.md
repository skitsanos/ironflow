# IF-134 — File-writing nodes disagree about symlinked destination roots

## Required outcome and acceptance

- One destination policy for every node that writes a file (`write_file`,
  `base64_decode` with `output_file`, `read_file`/`extract_*` inputs,
  `shell_command` is out of scope): either all of them accept a path whose root
  component is a symlink to a directory, or all of them refuse it.
- When a path is refused, the error names the resolved directory to use.
- Test on a platform where the temp directory is a symlink (macOS `/tmp` →
  `/private/tmp`): the same scratch path either works or fails identically
  across the nodes.

## Evidence and cause

Found on 2026-09-14 while building the document-ingestion flows of the HARMOny
`ironflow-hooks` service (IronFlow 1.18.1-dev.4).

[Source: file/archive/rooted/unix.rs](../../src/nodes/file/archive/rooted/unix.rs)
and [portable.rs:168](../../src/nodes/file/archive/rooted/portable.rs).

A flow decodes an upload to `/tmp/extract-<id>.docx` with `base64_decode`
(`output_file`), reads it with `extract_word`, and removes it with
`shell_command rm` — all of which accept the path on macOS. The same flow's
URL branch materialises an artifact with `write_file { path = "/tmp/…",
source_key = "fetch_artifact" }` and fails:

```
write_file: destination root '/tmp' is a symlink
```

The rooted-destination check that `write_file` shares with the archive nodes
rejects the symlinked root, while the sibling nodes have no such check. The
flow had to be pointed at `/private/tmp` on macOS only. In containers `/tmp`
is a real mount, so the difference is invisible there, which is how it stayed
unnoticed.
