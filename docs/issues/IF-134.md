# IF-134 — File-writing nodes disagree about symlinked destination roots

## Required outcome and acceptance

- One destination policy for every node that writes a file (`write_file`,
  `base64_decode` with `output_file`, `read_file`/`extract_*` inputs,
  `shell_command` is out of scope): either all of them accept a path whose root
  component is a symlink to a directory, or all of them refuse it.
- When a path is refused, the error names the resolved directory to use.
- Test on a platform where the temp directory is a symlink (macOS `/tmp` →
  `/private/tmp`): the same scratch path either works or fails identically
  across the nodes.

## Evidence and cause

Found on 2026-09-14 while building the document-ingestion flows of the HARMOny
`ironflow-hooks` service (IronFlow 1.18.1-dev.4).

[Source: file/archive/rooted/unix.rs](../../src/nodes/file/archive/rooted/unix.rs)
and [portable.rs:168](../../src/nodes/file/archive/rooted/portable.rs).

A flow decodes an upload to `/tmp/extract-<id>.docx` with `base64_decode`
(`output_file`), reads it with `extract_word`, and removes it with
`shell_command rm` — all of which accept the path on macOS. The same flow's
URL branch materialises an artifact with `write_file { path = "/tmp/…",
source_key = "fetch_artifact" }` and fails:

```
write_file: destination root '/tmp' is a symlink
```

The rooted-destination check that `write_file` shares with the archive nodes
rejects the symlinked root, while the sibling nodes have no such check. The
flow had to be pointed at `/private/tmp` on macOS only. In containers `/tmp`
is a real mount, so the difference is invisible there, which is how it stayed
unnoticed.

## Outcome and validation

Configured destination directory aliases are accepted, including macOS `/tmp`
and missing directories below an existing alias. The shared rooted writer
resolves the nearest existing directory once before creating missing parents.
Unix then pins that directory with an open handle. `write_file` append reads
the existing file relative to the same pinned handle, so retargeting the alias
cannot change which existing file is copied into the staged output.

This applies to every `RootedDir::prepare` caller: `write_file`, file-output
`base64_decode`, `pdf_merge`, the `zip_create` and `zip_extract` output roots
and, since IF-140, `copy_file` and `move_file`. `read_file` and extraction
input paths already accept directory aliases.
Destination-file links and special files remain prohibited; archive entry paths
still cannot traverse symlinked descendants. The configured alias is a trusted
root selection, not an archive-controlled path. Dangling/cyclic aliases cannot
be resolved and return a contextual error instead of being followed.

Portable platforms use the resolved directory and observed-path checks but
cannot close hostile concurrent directory-replacement races. Their destination
trees still require protection from same-identity mutation.

## Validation

Post-fix checks on 2026-09-14 with Rust 1.98.1:

- `test_file_alias_roots` passed for writes, base64 file decoding, read-back,
  DOCX extraction, archive extraction, append, and newly created nested parents.
  The direct macOS `/tmp/<unique-file>` regression passed.
- The rooted-writer unit regression retargets an alias after preparation and
  verifies both existing-file reads and staged publication stay in the original
  directory. Existing root-replacement and cancellation/cleanup tests passed.
- `test_write_file_safety` (4), `test_zip_security` (8), and
  `test_zip_cancellation` (3) passed. Symlinked archive source roots remain
  intentionally prohibited by the source-recursion contract.
- The binary-file example now exercises both write and decode paths and passes
  strict CLI validation/execution with isolated outputs and cleanup.
- Default and full-feature Clippy, formatting, module-size policy, dependency
  audit and all-example catalog validation passed for the batch. Runtime path
  tests ran on macOS; no Windows filesystem race guarantee is claimed.

### Scope follow-up, 2026-09-15

The IF-140 review found that the original scope sentence listed only three of
the rooted writer's callers. `pdf_merge` already used `RootedDir::prepare`
and therefore inherited alias acceptance without documentation or a
regression; `copy_file` and `move_file` did not use the rooted writer at all.
`copy_file` and `move_file` now go through it, `docs/nodes/pdf_merge.md`
states the alias contract, and `test_file_alias_roots` gained a case that
copies, moves and merges the sample PDF through a symlinked root and a newly
created nested parent below it.
