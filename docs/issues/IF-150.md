# IF-150 — Published container cannot secure its default JSON store directory

## Evidence and boundary

On 2026-09-28, onboarding smoke tests pulled the published linux/amd64 image
`ghcr.io/skitsanos/ironflow:sha-d9ecb38cba33bddbb747ad72676bdd15ca16a8be`
(OCI index digest
`sha256:a0748da0e19b9bd3b8992335d1b4685fbd79f5d5f1d8da0248cc1e8111a2d561`).
A read-only bind mount supplied the README's one-step `hello.lua`; a fresh,
test-owned named volume was mounted at `/data`. Running `validate` succeeded,
but `run /data/flows/hello.lua` exited 1 before executing the step:

```text
Using JSON state store at /data/runs
Error: Failed to initialize workflow run ...: Failed to secure JSON store directory: Operation not permitted (os error 1)
```

The Dockerfile creates `/data/runs` as root, makes it root-group writable, and
runs as `1001:0`. `src/storage/json_store/platform.rs::harden_directory`
requires mode `0700`; group write permission does not allow UID 1001 to chmod
that root-owned directory. A fresh named volume inherits the image directory's
ownership. The current Dockerfile at develop `953afac` retains this setup.
The reproduction used Docker Desktop locally, not an OpenShift or Railway
deployment; it does not establish a failure with PostgreSQL or Redis stores.

## Required outcome and acceptance

- Make the image's default JSON store usable by its default non-root user
  without disabling private-directory permission enforcement.
- Preserve the documented arbitrary-UID deployment boundary and distinguish
  fresh volumes from existing root-owned volumes that may need migration.
- Add a container smoke regression using a fresh named volume, the default
  store path, workflow execution, and run inspection after container removal.
- Update the Docker onboarding guidance if its explicit store path is no
  longer needed. Validate the actual runtime image, not only Dockerfile text.

## Current workaround and validation

The Quick Start explicitly sets `IRONFLOW_STORE_DIR=/data/state/runs`, allowing
the runtime user to create and own the store inside the persistent volume.
With that setting, the same published image passed workflow validation and
execution, `/health/ready`, the README's `POST /flows/run` request (status
`success`), and inspection of that run from a new container after server
removal. Test-owned containers and volumes were removed afterward.

This is fresh local workaround evidence. The image's default remains broken;
the finding stays open. The previous full integration gate did not exercise
this container/default-JSON-store combination and does not close it.
