# IF-167 — Pre-push gate repeats CI on every develop push and pulls floating service images

## Evidence and boundary

Audit of `develop` at 1.20.1-dev.6 on 2026-10-28.

- `.githooks/pre-push` runs `scripts/check_incoming_prs.ts` (needs `gh` and
  network access, fails closed), a clean-worktree check, the development
  version check, then `scripts/integration_gate.sh`.
- The gate requires `cargo`, `cargo-audit`, `python3`, `bun`, `actionlint`,
  `docker` and `openssl`, exports `CARGO_INCREMENTAL=0`, runs
  `cargo clean --package ironflow` three times, then: fmt, policy scripts,
  hook tests, actionlint, check/clippy/full suite/doc tests/audit with default
  features, check/clippy with features, `cargo build --release` plus 156 Lua
  example validations, a pull of `redis:latest` and `postgres:latest`, the
  full suite again with features serially, and the TLS tests.
- CI runs the equivalent on every push (51.7 runner-minutes, see
  [IF-166](IF-166.md)), so the local gate duplicates it. `AGENTS.md` mandates
  the gate before every `develop` push.
- Floating `redis:latest` and `postgres:latest` are used in both
  `scripts/integration_gate.sh` and the `services` of
  `.github/workflows/ci.yml`, while the Rust builder image is digest-pinned and
  `AGENTS.md` requires reproducible exact pins. A service image release can
  break the gate or CI without any repository change.

Boundary: the gate's cleanup correctness ([IF-160](IF-160.md)) is not in
question. The finding is cost per push and reproducibility.

## Required outcome and acceptance

- Reduce the mandatory pre-push to fast checks (fmt, policy, default clippy
  and a focused or consolidated test subset) and make the full gate explicit
  for release and merge, with `scripts/integration_gate.sh` remaining the
  release-skill entry point; or make the full gate opt-out through a
  documented environment variable. Update `AGENTS.md`,
  `.agents/skills/release-ironflow`, `.claude/skills/release-workflow` and
  `repository_policy.test.ts`.
- Pin the `redis` and `postgres` images to exact tags with digests in both
  files and group them under Renovate.
- Remove the triple clean once IF-162 lands, or keep a single final clean.
- Resolution evidence: a timed local pre-push before and after, and CI services
  pinned with Renovate updating them.

## Outcome and validation

Resolved on 2026-10-28 on branch `fix/if-167-prepush-gate` at 1.20.1-dev.8.

Outcome:

- `.githooks/pre-push` keeps the full `scripts/integration_gate.sh` as the
  default for every `develop` push and adds a documented opt-out:
  `IRONFLOW_PREPUSH_GATE=fast` runs `cargo fmt --all -- --check`, the issue
  registry check, `bun test scripts/tests/*.test.ts`,
  `cargo clippy --all-targets -- -D warnings` and the `examples` and `cli`
  test binaries through `scripts/test_rust_targets.ts --test`. The
  incoming-PR, clean-worktree, remote-ancestry and development-version checks
  run in both modes and precede the choice; any other value blocks the push.
  `repository_policy.test.ts` asserts the structure and ordering.
- `AGENTS.md`, `.claude/skills/check/SKILL.md` and
  `.claude/skills/release-workflow/SKILL.md` state when the fast mode is
  acceptable (an intermediate push) and that the full gate remains mandatory
  before merging a release branch or tagging; the release skill forbids the
  fast mode for a release candidate.
- The three mid-gate `cargo clean --package ironflow` phases were already
  reduced to the pre-run prune and the exit-trap clean by [IF-162](IF-162.md),
  which made the linked executables small enough not to need them.
- The disposable `redis:latest` and `postgres:latest` service images in
  `scripts/integration_gate.sh` and `.github/workflows/ci.yml` stay unpinned by
  maintainer decision on 2026-10-28: the storage suites are meant to run
  against the current server releases, the containers are disposable, and a
  digest pin with a Renovate group would trade that freshness for
  reproducibility. The decision is revisited if a `latest` update ever breaks
  the gate; the acceptance item is closed as decided, not implemented.

Contract boundary: the default behaviour of a `develop` push is unchanged.
The fast mode is explicit, bounded and documented; it never replaces the gate
for merges or releases. CI runs the full validation on every push regardless
of the local mode.

Validation on 2026-10-28: `bash -n .githooks/pre-push`,
`bun test scripts/tests/*.test.ts` with the extended pre-push policy test, and
the issue registry check pass. A timed local pre-push before and after was not
measured; the fast path replaces the roughly thirty-minute gate with a few
minutes of lint and two test binaries, and the full gate's timing is recorded
by the release skill when it runs.
