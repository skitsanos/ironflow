# IF-212 — The outbound destination guard covers only the HTTP nodes

## Evidence and boundary

Recorded on 2026-11-13 from the consumer audit done while fixing IF-191. The
audit was by reading, by a search pass; two call sites were spot-checked.
Nothing here was executed against a network.

`block_private_network` exists on `http_request` and its method variants
only. No other node that opens a connection to a flow-controlled destination
honours it or has an equivalent:

- (a) `mcp_client` Streamable HTTP: `url` is unchecked. The `rmcp` transport
  uses its own `reqwest` client.
- (b) The shared provider client (`src/util/provider_http.rs`) behind `llm`,
  `ai_embed`, `ai_chunk_semantic`, `transcribe`, `slack_notification`,
  `send_email` through Resend and `arangodb_aql`: base URLs and OAuth token
  URLs can name internal hosts, and credentials are attached.
- (c) An `llm` custom provider with an absolute `chat_path`,
  `responses_path` or `path` replaces `base_url` entirely.
- (d) SMTP, `db_query` and `db_execute` connections, and S3 and s3vector
  `endpoint_url` have no restriction.
- (e) There is no process-wide setting that forces the guard on. Ad-hoc
  flows are allowed by default, so protection depends on each flow author.

Boundary: the guard is opt-in and these nodes never claimed it.
`docs/SECURITY.md` now lists exactly what is covered (IF-191). Operator-only
endpoints (artifact store, state and event stores) are out of scope.

## Outcome and validation

**Historical status:** Resolved on 2026-11-15.

Decided model (maintainer, 2026-11-15): a process policy, the existing
per-node option, and an operator allowlist.

- `IRONFLOW_BLOCK_PRIVATE_NETWORK` (`block_private_network` in
  `ironflow.yaml`), default `false`, forces the guard on for every covered
  node. It is one-way: the `http_*` option can only add the guard.
- `IRONFLOW_PRIVATE_NETWORK_ALLOWLIST` (`private_network_allowlist`), named
  after `IRONFLOW_ENV_ALLOWLIST`: host names, `host:port`, addresses, CIDR
  ranges. A name entry matches the requested host exactly and permits its
  answer for that connection only; another name with the same answer is
  still refused. A malformed value of either setting stops startup.
- Full coverage through `src/util/outbound` (literal, pinned DNS answer,
  redirect hop): `http_*`; the provider client behind `llm`, `ai_embed`,
  `ai_chunk_semantic`, `transcribe`, `slack_notification`, Resend
  `send_email` and `arangodb_aql`, with OAuth token URLs and absolute custom
  `llm` paths; `mcp_client` Streamable HTTP; S3 and S3 Vectors. Guarded
  clients bypass a system proxy.
- SMTP connects to the validated address while TLS names the configured
  server, so it is pinned. `db_query` and `db_exec` (the trigger said
  `db_execute`) get a host check only: the driver resolves again.
- Out of scope: artifact store, state and event stores, metrics,
  `shell_command`, stdio `mcp_client`.

Reproduced before the fix on unchanged `develop` (1.21.1-dev.12):
`tests/test_outbound_policy.rs` ran `ironflow run` with the policy variable
set against a loopback listener for 19 client configurations. Eighteen
connected and none was refused; six of seven tests failed, and the one
asserting unchanged behaviour with the policy off passed.

After the fix the file passes: every client is refused with no accepted
connection, connects with an allowlist entry or with the policy off, and a
per-node `false`, the config keys and malformed values behave as
documented. In-crate tests with a scoped DNS table (no real lookup) cover
refused and mixed DNS answers through nine client configurations, an
allowlisted name reaching its validated answer, SMTP pinning, database URL
hosts, the AWS resolver, a refused redirect on `http_get`, and the provider
client refusing with no call-site check.

Boundaries: provider and MCP clients follow same-origin redirects only, so
their redirect regression also passed before the fix. The AWS path ran end
to end with a literal endpoint only; its DNS path is tested at the
resolver. A virtual-hosted bucket is judged as its endpoint host.
`aws-smithy-http-client` and `aws-smithy-runtime-api`, already locked, are
now named in `Cargo.toml`.

Validation (debug build, no external host contacted):

- Default build: library 855 passed, 1 ignored; `nodes_network` 176,
  `nodes` 304, `cli` 108, `examples` 11, `api` 68, `engine` 319, `serial`
  199 single-threaded. The policy tests also pass with `postgres,redis`.
- `cargo fmt --all -- --check`, the module-size check, and
  `cargo clippy --all-targets -- -D warnings` with and without
  `--features postgres,redis` passed, as did `cargo audit --deny warnings`
  and the license check.
- Not run: the integration gate and live PostgreSQL, SMTP or S3 services.
