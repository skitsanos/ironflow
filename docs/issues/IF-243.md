# IF-243 — CSV header escaping can collapse distinct object keys

## Evidence and boundary

Reviewed 2026-11-19 on local `develop` at `ae1f686`.

`src/nodes/transform/csv/stringify.rs:123` and `:171` collect distinct object keys but escape them only when writing the header. With default settings `@region` and `'@region` produce the same emitted header. Both values appear in the CSV but parsing it back to an object (`src/nodes/transform/csv/parse.rs`) loses one. IF-223 addresses formula escaping, not collisions introduced by escaping. Source inspection.

CLI confirmation: a single object with `@region=first` and `'@region=second` emitted two identical headers. Parsing the CSV back produced just `'@region=first`. Both nodes reported success.

## Required outcome and acceptance

With both keys and distinct values, test single-object and object-array exports. Emit distinct safe headers that retain the columns or report an explicit collision before returning CSV. Do not disable formula protection.

## Outcome and validation

Both object export paths now check the actual escaped header labels before
writing the header record. A collision fails the node and identifies both
one-based column positions in export order, without logging the field names.
The author can rename a source field; IronFlow does not invent a new schema
or turn off escaping. For object arrays the check covers the union of keys
across all rows. Repeated use of the same key is not a collision.

Regression coverage includes single objects, nonadjacent collisions across
rows, and headerless and raw exports that preserve both columns. The change
does not alter how `csv_parse` handles duplicate headers in an external CSV.
