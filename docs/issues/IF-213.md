# IF-213 — Several built-in blocking nodes are not tracked work, and Lua C calls have no time bound

## Evidence and boundary

Recorded on 2026-11-13 from the IF-211 and IF-188 fixes.

- (a) By reading: many built-in nodes still start their worker through the
  untracked `run_blocking_step` (extract nodes, HTML conversion, `xml_parse`,
  `validate`, `cache`, several image and PDF helpers). If such a worker
  stalls between cancellation checkpoints, a timed-out step lets its handler
  start and the run finish while the worker is still running. This is the
  defect IF-211 fixed for Lua and IF-188 fixed for child workflows.
- (b) Measured while verifying IF-211: time inside one Lua C library call
  (`string.find`, `string.match`, `string.gsub`, `string.rep`,
  `table.concat`) is not interruptible, and neither `IRONFLOW_LUA_MAX_SECONDS`
  nor `IRONFLOW_MAX_RUN_SECONDS` ends it. A pattern with nested quantifiers
  ran for more than 40 seconds. Since IF-211 such a call holds the step, the
  run and its admission until it returns.
- (c) By reading: a child's steps do not inherit the parent step's deadline;
  they are stopped by cancellation when the parent times out (IF-188).

Boundary: `docs/ARCHITECTURE.md` states that admission is held until
physical work stops. (a) breaks that for the listed nodes; (b) honours it but
turns one bad pattern into an unbounded hold.

## Required outcome and acceptance

- (a) List every `run_blocking_step` caller, move each to the tracked form,
  or record why it cannot stall. Regression: one stalled worker per node
  family does not let a handler start early.
- (b) Bound Lua string-library work: a subject and pattern length ceiling, a
  step budget for pattern matching, or a documented statement that such calls
  are unbounded, with the string functions that are affected.
- (c) Decide whether child steps should carry the parent deadline, and
  document the answer in the composition node pages.
