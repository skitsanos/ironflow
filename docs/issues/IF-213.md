# IF-213 — Several built-in blocking nodes are not tracked work, and Lua C calls have no time bound

## Evidence and boundary

Recorded on 2026-11-13 from the IF-211 and IF-188 fixes.

- (a) By reading: many built-in nodes still start their worker through the
  untracked `run_blocking_step` (extract nodes, HTML conversion, `xml_parse`,
  `validate`, `cache`, several image and PDF helpers). If such a worker
  stalls between cancellation checkpoints, a timed-out step lets its handler
  start and the run finish while the worker is still running. This is the
  defect IF-211 fixed for Lua and IF-188 fixed for child workflows.
- (b) Measured while verifying IF-211: time inside one Lua C library call
  (`string.find`, `string.match`, `string.gsub`, `string.rep`,
  `table.concat`) is not interruptible, and neither `IRONFLOW_LUA_MAX_SECONDS`
  nor `IRONFLOW_MAX_RUN_SECONDS` ends it. A pattern with nested quantifiers
  ran for more than 40 seconds. Since IF-211 such a call holds the step, the
  run and its admission until it returns.
- (c) By reading: a child's steps do not inherit the parent step's deadline;
  they are stopped by cancellation when the parent times out (IF-188).

Boundary: `docs/ARCHITECTURE.md` states that admission is held until
physical work stops. (a) breaks that for the listed nodes; (b) honours it but
turns one bad pattern into an unbounded hold.

## Outcome and validation

Resolved on 2026-11-15 for all three items.

(a) The reading was out of date. At 1.21.1-dev.11 every node named above
already used `run_tracked_blocking_step`, so the early handler start could
not be reproduced for them. The untracked `run_blocking_step` had three
production callers, all outside a step (API flow validation and inline
loads, `artifacts prune`), and about twenty tests. It is removed; the
tracked bridge is the only one. One related defect was fixed:
`markdown_to_html` converted on the async runtime thread, with no worker.

(b) `string.find`, `string.match`, `string.gmatch` and `string.gsub` run on
a Rust port of the Lua 5.4 matcher. It counts steps against
`IRONFLOW_LUA_MAX_PATTERN_STEPS` (default 50,000,000 per Lua state, `0`
disables, in `limits::ALL`) and checks the step deadline, cancellation and
`IRONFLOW_LUA_MAX_SECONDS` every 4,096 steps. Three more unbounded C loops
were found and closed: `string.rep("", n)`, `table.move` over any index
range, and `table.insert`/`table.remove` when `__len` claims any length.
`table.concat` and the other calls are linear in data the Lua memory cap
bounds (`docs/nodes/code.md`). Conditions are `if_node` expressions, not Lua.

(c) Implemented: the deadline a child step's work observes is the earlier of
its own and that of the parent step that waits, at every level. `wait =
false` children inherit none. Timeout results are unchanged.

Contract boundary:

- A worker without checkpoints still delays its step's timeout result.
- A spent pattern budget stays spent for its Lua state, also after `pcall`.
- With the Lua memory cap disabled, linear library calls are bounded only by
  host memory.
- Nodes that compute on the step's own task (`csv_parse`, `yaml_parse`,
  `html_sanitize`, `template` and similar) cannot start a handler early.
  Moving them to the blocking pool is not decided here.

Evidence (debug build, default features; no feature build or live store):

- (a) `builtin_workers` (3 unit tests) holds the worker of 17 node types
  after its operation, under `:timeout(0.2)` with `on_error` and under
  cancellation. With registration disabled in the bridge both tests fail at
  the first node; on the unfixed tree they failed only at `markdown_to_html`.
- (b) Before, base binary under `ironflow run` with `:timeout(2)`, `on_error`
  and `IRONFLOW_MAX_RUN_SECONDS=5`: `^.-.-.-.-b` on 1,500 characters in a
  function step and in a child flow, `string.rep("", maxinteger)` and
  `table.move({}, 1, maxinteger - 1, 2)` were each still running, handler
  unstarted, when killed at 45 s. After: timeout and handler at 2.0 s; the
  budget error after 2.1 s without a timeout; the time budget at 10.0 s with
  the step budget disabled; `rep` at once; `move` fails in 0.1 s.
- (b) 13 unit tests compare about 200 authored and 20,000 generated calls
  with an unmodified Lua state, error text included. `lua_library_bounds`
  (3 tests) covers a function step, a `foreach` transform, and a child flow's
  function and top-level code for the budget, a timeout and cancellation.
- (c) `child_deadline` (3 tests) fails without the inheritance.
- The IF-211 and IF-183 tests used a slow `string.find` as their stuck
  worker; they now use the bridge's test gate and a FIFO-backed cache read.
