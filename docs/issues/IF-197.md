# IF-197 — llm sends unknown providers to OpenAI and ignores documented parameters

## Evidence and boundary

Review of `develop` at 1.21.1-dev.1 on 2026-11-12, by reading. Not executed:
no provider calls were made.

1. Provider fallback. `Provider::resolve`
   (`src/nodes/ai/llm_providers/config.rs:32-45`) maps `openai_compatible`,
   `compatible`, `azure` and `custom`, and sends every other string to
   `Self::OpenAI`. A typo or an unsupported name such as
   `"openai-compatible"`, `"ollama"` or `"gemini"` therefore resolves to the
   OpenAI configuration, so the prompt and `OPENAI_API_KEY` go to the OpenAI
   endpoint rather than the gateway the operator configured through the
   compatible-provider settings. `transcribe` and `ai_embed` reject unknown
   providers.
2. `response_format`. `docs/nodes/llm.md` lists it as a parameter, but no
   code under `src/nodes/ai` reads it for `llm` (the only uses are in
   `transcribe`). It reaches the request only through `extra`, which is what
   the shipped examples use.
3. `input_key`. The document gives a default of `"prompt"`, but
   `src/nodes/ai/llm_providers/request.rs:41-52` has no default: with none
   of `prompt`, `input_key`, `messages` or `messages_key` set, the node
   errors.
4. Empty replies. A 200 response without usable choices sets the text to
   the placeholder `"<no reply>"` (`src/nodes/ai/llm.rs:245`) and reports
   success, so a downstream step cannot tell a provider failure from a
   model reply.
5. Lead, not confirmed: in `mode = "responses"` the request body may carry
   only `model` and `input`, dropping `tools`, `tool_choice` and
   `system_prompt` without an error. Check `request.rs` while fixing.
6. OAuth token path for embeddings (`src/nodes/ai/embeddings/oauth.rs`). A
   non-2xx token response body is copied into the node error (`:86-88`),
   although `docs/nodes/ai_embed.md` says provider error bodies are omitted.
   Expiry is computed as `Instant::now() + Duration::from_secs(expires_in)`
   (`:96-98`), which panics on a huge value. The body is read without the
   bounded reader the other provider paths use, and nothing evicts a cached
   token after a 401.

Boundary: item 1 is the reason for P2: data and a credential go to an
unintended third party after a configuration typo. Item 5 needs
confirmation before it is fixed.

## Required outcome and acceptance

- Reject unknown `provider` values with the accepted list in the message.
- Honour top-level `response_format` or remove it from the document; make
  the `input_key` default real or remove it.
- Fail the step on a successful response with no usable reply.
- Error on chat-only parameters in responses mode, or map them.
- Use the bounded reader for token responses, omit provider bodies from
  errors, use checked expiry arithmetic and evict a token after a 401.
- Unit tests with a local mock provider for each item; update
  `docs/nodes/llm.md` and `docs/nodes/ai_embed.md`.

## Outcome and validation

Resolved 2026-11-14. Every item was executed against a mock provider on
loopback before it was changed; no real provider was called.

Before (regressions run on the unfixed tree: 11 of 16 then written failed):

1. Confirmed. With the OpenAI base URL pointed at one mock and the
   compatible base URL at another, `provider = "openai-compatible"` posted
   `/chat/completions` to the OpenAI mock with the prompt and the bearer key;
   the gateway mock received nothing and the step succeeded.
2. Confirmed: a top-level `response_format` was absent from the request body.
3. Confirmed: no default, a context key named `prompt` was not read.
4. Confirmed: `{"choices": []}` succeeded with the text `<no reply>`.
5. Confirmed, the lead is real: in responses mode `system_prompt`, `tools`
   and `tool_choice` were absent from the body. Also found: a Responses
   result holding only typed non-message items produced "text" scraped from
   their identifiers, and `function_call` items were not reported.
6. Confirmed: a 401 token body appeared in the step error; a 4 KiB token
   response passed under `IRONFLOW_MAX_HTTP_BODY_BYTES=256`; a revoked cached
   token was reused on every run. Parser detail could also echo body values.

Outcome:

1. `Provider::resolve` returns an error for any value outside `openai`,
   `openai_compatible` (alias `compatible`), `azure` and `custom`, matched
   without regard to case, and for a non-string. It runs first in the node,
   before credentials are resolved; the message lists the accepted names.
   `ai_embed`, `ai_chunk_semantic` and `transcribe` already rejected unknown
   names; a non-string `provider` there fell back to `openai` and is now
   rejected too.
2. Top-level `response_format` (an object) is sent in chat mode, since the
   documented parameter was silently ignored. `extra` is still merged last
   and wins when both are given.
3. The default was removed from the document. An implicit read of a context
   key named `prompt` would send data to a provider that the flow never
   named; the existing "is required" error stays.
4. A usable reply is non-empty text or at least one tool call. Chat: first
   choice content, or its `tool_calls`. Responses: `output_text` or text of
   non-reasoning `output` items, or `function_call` items, which are now
   reported as tool calls. Anything else fails with `returned HTTP 200 with
   no usable reply` plus a short `finish_reason` or `status`; the body is not
   copied. Untyped gateway items are still searched for text.
5. `system_prompt` maps to `instructions`. `tools`, `tool_choice` and
   `response_format` are chat-shaped, so they fail before a request in
   responses mode and the Responses-shaped fields keep going through
   `extra`.
6. Token responses use the bounded provider reader; a non-2xx reply is not
   read; send, status and parse errors name only the kind of failure. A 401
   from the embedding endpoint evicts the token that was sent (only if it is
   still the cached one) and repeats once with a new token; a second 401
   fails and evicts again. Expiry arithmetic was already checked (IF-195).

Found while fixing item 6 and fixed here: the token cache was keyed by token
URL, client ID and scope only, so a step with the same client ID and a
different secret received the cached token without authenticating (mock:
one token request for two secrets). The key now includes a SHA-256 digest of
the client secret (two requests, each identity cached separately).

Contract boundary: the provider client still has no private-network guard
(IF-191, IF-212). The retry after a 401 restarts at the first batch. Tool
loops with `tool_dispatch` remain chat-mode. Non-2xx `llm` errors still carry
the redacted provider body as documented (IF-176).

Validation (debug build, default features, mock providers only):

- New regressions `test_llm_provider_contract` (12) and
  `test_embedding_batches::oauth` (6), plus unit tests for the output
  builder and the `transcribe` provider: all pass after the change.
- `cargo test --lib` 749 passed, 1 ignored; `nodes_network` 162 passed;
  `nodes` 280 passed; `engine` 304 passed; `examples`
  11 passed; `serial` with one thread 191 passed.
- The Lua examples under `examples/13-ai` validate; `cargo fmt --all --
  --check`, `scripts/check_module_size.py` and `cargo clippy --all-targets --
  -D warnings` pass.
- Not run: live providers, feature-enabled builds, the integration gate.
