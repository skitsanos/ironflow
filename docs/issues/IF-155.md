# IF-155 — SQLite index verification mixes stale pooled schema metadata

## Evidence and boundary

The Linux default-test job for PR #226 failed
`standalone_sqlite_defaults_and_explicit_urls_serve_and_persist` before the
listening message, at `tests/support/sql_backend_cli.rs:82`
([original job](https://github.com/skitsanos/ironflow/actions/runs/40170651757/job/121100616979)).
The five-test target finished in 0.14 seconds. The helper reported only
`server exited before listening`: it discarded earlier stderr and did not
report the child's exit status. This was an early EOF, not its ten-second
startup watchdog. The log does not identify a SQLite error, resource limit,
signal, or ZIP regression.

The unchanged-head Linux retry and the first post-merge run passed. Those
passes do not establish or fix the original cause. The test already requests
port zero and parses the OS-assigned address, so it does not use a
reserve-and-release port selection scheme.

## Required outcome and acceptance

- Retain bounded, credential-redacted startup stderr and the exit code or
  signal for early exits, read failures, malformed addresses and timeouts.
- Kill and reap failed startup children; retain the existing ten-second
  startup deadline and genuine startup failures, without automatic retries.
- Prove failure diagnostics and cleanup with deterministic negative tests.
- Identify and reproduce the original startup failure before declaring its
  cause resolved; qualify the resulting fix under the hosted Linux test
  profile. Improved diagnostics or repeated passes alone do not close this
  finding.

## Investigation and implemented diagnostic fix

On 2026-10-25, two new tests failed against the unchanged helper: a SQLite
database path beneath a regular file lost its connection error and exit
code, and a rejected backend URL lost its safe configuration diagnostic.
With the diagnostic fix both pass. The helper retains the last 16 stderr
lines, at most 1,024 Unicode scalar values per line, after redacting sensitive
URL content. It includes the child status and kills/reaps on failure instead
of relying only on kill-on-drop. Successful startup still uses the actual
listening address, and persistence assertions remain unchanged.

A controlled exclusive SQLite lock exercises a shortened test-only deadline
and verifies the child is reaped. Unit regressions cover tail bounds, UTF-8
and URL credential redaction. This lock is a deliberate failure fixture,
not evidence that locking caused the original CI exit. That initial diagnostic
patch did not change production storage or runtime configuration.

The original exit initially did not reproduce in 100 macOS repetitions of the
SQLite persistence test or 200 complete native CLI suites run by four
concurrent workers. Linux startup probes used the default-feature release
binary from commit `334a22a5dac13df253d5d20731619ec77b97e03b` in disposable,
network-isolated Ubuntu 24.04 amd64 containers: 200 sequential starts and
800 starts across four workers passed, alternating omitted and explicit
SQLite URLs. Linux execution was emulated on the local arm64 host and used
the release profile, not the failing hosted debug profile. An earlier probe
using graceful shutdown was interrupted and is excluded from these counts;
the completed probes use kill-and-wait like the test fixture.

All ten default `test_sql_backend_cli` tests pass after the diagnostic fix,
including 50 further complete repetitions. The feature-enabled target passes
its 13 applicable tests; the genuine PostgreSQL replica test is explicitly
filtered out because no disposable PostgreSQL service is required for this
harness-only change. Default and feature-enabled all-target Clippy pass with
warnings denied, as do formatting, module-size policy, the issue registry
and its five Bun tests. No full repository integration or hosted test run is
claimed for these uncommitted changes.

## Native Linux reproduction and cause

The user's development host reproduced the failing test in a native
Ubuntu 22.04 x86_64 debug build with Rust 1.99.1. Build inputs matched local
SHA-256 hashes; the toolchain, sources, artifacts and temporary SQLite files
were isolated in a private scratch directory. The build used two low-priority
jobs and did not change system packages, profiles or running services.

Four stress workers completed 39 full CLI suites before worker 1, iteration
10 failed with exit code 1 and `Managed SQLite event sequence index has an
incompatible definition`. A temporary diagnostic-only probe reproduced it
again after 31 completed suites, worker 3, iteration 8: the managed index was
unique, non-partial and explicitly created, but `PRAGMA index_xinfo` returned
an empty column list. Both omitted and explicit SQLite URL cases failed.
These native runs establish a production index-verification defect behind the
same test's early exit. The original hosted log remains too sparse to prove
that its individual exit had the identical cause.

The verifier used separate pool acquisitions for the catalog query,
`PRAGMA index_list` and `PRAGMA index_xinfo`. SQLite caches schema metadata per
physical connection; a PRAGMA on an older connection could see an index-free
or empty schema after DDL on another connection. A controlled regression
primes four pooled connections against an empty database, creates the table
and index, then invokes verification. It failed twice before the production
fix, without load or timing assertions, and passes afterward.

## Outcome and validation

SQLite index verification now acquires one connection, refreshes its metadata
with the existing catalog query and runs both PRAGMAs on that same connection.
The index's table, uniqueness, origin, partial predicate and exact ordered
key-column checks remain intact. Regressions additionally reject nonunique,
partial, reversed-column and expression indexes. PostgreSQL verification,
pool size, timeouts, retry policy, configuration and database schema are
unchanged. The temporary diagnostic probe was removed.

After the production fix, the deterministic schema regression and incompatible
index tests pass on macOS and native Linux. The 31 focused default integration
tests (`test_sql_backend_cli`, `test_event_store`, `test_sql_event_migration`)
pass locally. Native Linux additionally passes all 21 event-store/migration
tests. The feature-enabled CLI target passes 13 applicable tests locally;
the genuine PostgreSQL replica test remains explicitly filtered out. No live
PostgreSQL or Redis service is required for this SQLite-only production fix.

The native debug-profile CLI target completed 1,000 full ten-test suites with
four stress workers across six CPUs (363.82 seconds), followed by 500 suites
with two workers restricted to four CPUs (294.21 seconds). All 1,500 suites
passed without retries; the stress harness stops scheduling work on its first
failure. Final remote production/test hashes match the local working tree.
Both default and feature-enabled all-target Clippy pass with warnings denied;
formatting, module-size policy, issue-registry validation and the dependency
audit with warnings denied pass as well.

The private remote scratch directory retains sources, the isolated Rust
toolchain/build cache and the before/after logs for further verification.
All test children were reaped and the temporary SQLite directory is empty.
No system package, shell profile, existing service or service configuration
was changed.

Integration qualification completed on implementation commit
`8c99bb3ff523e2d7559eabd49eeba9b7426dc6de` (`1.19.2-dev.3`). The complete local
`scripts/integration_gate.sh` passed with `IRONFLOW_TEST_PUBLIC_TLS=1`, including
the exact default Clippy command, feature-enabled Clippy, default and required
live-service tests, audit, repository policies, Lua example validation and
public TLS acceptance. Disposable PostgreSQL 18.6 and Redis 8.10.2 also passed
TLS-only CLI/serve persistence, restart and certificate/plaintext rejection.
The gate removed its containers and linked workspace artifacts; optimized
IronFlow outputs were package-cleaned afterward.

[Fresh hosted CI](https://github.com/skitsanos/ironflow/actions/runs/40191399311)
passed every check on that implementation, including macOS tests and Linux
default/full-feature Clippy, tests and live storage/TLS. Hosted Linux logs
record 1,780 passing default tests and 1,905 passing full-feature tests, with
four preexisting manual tests ignored per suite. No CI retry was needed.

Resolved after implementation, regressions, documentation and local/hosted
qualification completed. The closure follow-up changes only this record and
the generated indexes; its final PR head is separately CI-gated before merge.
These are integration and native CLI/serve results, not a deployment or a
stable release claim.
