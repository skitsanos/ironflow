# IF-120 — Validation rejects a valid callback reused on two steps

## Required outcome and acceptance

- Allow one Lua source function to be registered as the handler for multiple steps without losing source association.
- Retain undefined-global, captured-local, and genuine ambiguity diagnostics.
- Add validate/run parity coverage for reused callbacks, distinct callbacks, and invalid handlers.

## Evidence and cause

Fresh review on 2026-09-12, finding R15. See
[AUDIT_2026-09-12.md](./AUDIT_2026-09-12.md) for the reviewed candidate,
evidence boundaries, and complete finding-to-issue mapping.

[Source: lua/analysis.rs:72](../../src/lua/analysis.rs).

Source-handler association is claimed only once. The same Lua function used for two steps runs successfully, but `validate` fails to map the second registration. Support repeated references to the same source function and test validate/run parity. Evidence: engine reusable-handler probe.

## Outcome and validation

Resolved on 2026-09-14. Source analysis now matches a unique function by its
start/end line range without consuming that association. Repeated registrations
reuse the match and record its diagnostics only once. This supports shared
callbacks and separate closures created from the same source function across
`flow:step`, `flow:step_if`, `nodes.code`, and `nodes.foreach`.

Lua's line metadata cannot distinguish multiple source functions with the
same range. The old matcher guessed by source/registration order; validation
now rejects that ambiguity explicitly and advises placing definitions on
distinct lines. Missing source matches still fail. Warning positions, strict
mode, captured-local rejection, serialization, sandboxing, admission, and
execution limits are otherwise unchanged. This is source-analysis behavior,
not a new restriction in normal workflow execution.

Validation:

- The corrected eight-test pre-fix regression had six failures and two passes.
  Reused callbacks and factory-created closures executed successfully before
  failing validation on a repeated registration; the ambiguity test exposed
  the old positional guess. Distinct callbacks and captured-local rejection
  already behaved correctly.
- All 71 focused tests passed after the fix: nine `lua::analysis` unit tests
  and 62 integration tests across `test_reused_handlers`,
  `test_reused_handlers_cli`, `test_validation_diagnostics`, `test_lua_runtime`,
  `test_foreach_node`, `test_lua_preemption`, `test_flow_source_limits`, and
  `test_example_catalog`.
- Coverage includes all four function entry points, sync/async inline/file
  validation, out-of-order registration, reused warning locations and
  deduplication, unused functions, captured locals, missing/nested/ambiguous
  ranges, strict validation, runtime failures, cancellation, and source limits.
- Added `reused_callbacks.lua`, registered it in the example catalog, and
  exercised it through ordinary/strict CLI validation and actual execution.
  All 146 Lua examples passed CLI validation from an isolated working directory
  and environment without loading repository credentials.
- API route tests verified ordinary/strict responses and rejection diagnostics.
  Their helper serializes requests to avoid competing for the existing
  process-wide flow-loading limit; production admission was not changed.
- `cargo fmt --all -- --check`, `python3 -B scripts/check_module_size.py`,
  `cargo clippy --all-targets -- -D warnings`, and
  `cargo audit --deny warnings` passed on current stable Rust 1.98.1. No module
  size exceptions were added or widened.

The gate used local CLI processes and in-process API routes, not a deployed
server or external services. No full release gate, commit of this issue, or
push was performed.
