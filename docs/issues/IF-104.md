# IF-104 — HTTP transport cannot safely carry artifact-native binary workflows

## Required outcome and acceptance

IronFlow's generic HTTP nodes collect every response into memory and convert it
through lossy UTF-8 before producing context output. They cannot upload an
artifact without first materializing its bytes as text or Base64, and every node
execution constructs a separate HTTP client. The opt-in private-network guard
also checks only literal hosts: a public-looking hostname can resolve to a
loopback, link-local, or private address after the URL check.

Required outcome:

- add an explicit artifact response mode that streams the final response body
  into the configured content-addressed artifact store without retaining the
  binary payload in workflow context;
- add replayable raw-artifact and multipart request bodies whose binary parts
  accept only artifact descriptors or canonical artifact URIs, preserve verified
  handles until transport ownership is established, and remain bounded by the
  HTTP body-byte ceiling;
- retain the existing text/JSON response contract by default, including status,
  headers, success, attempts, status retries, and error redaction;
- make proxy selection explicit while preserving compatibility: ordinary calls
  may keep the system proxy, direct mode must bypass it, and
  `block_private_network = true` must use direct transport;
- when private-network blocking is enabled, validate every address returned by
  DNS for the initial host and every redirect host, reject the complete
  resolution if any address is internal, and return only the validated address
  set to the connector so validation and connection cannot be rebound;
- centralize clients with redirects disabled at the transport layer, then apply
  bounded same-origin/cross-origin redirect policy while rebuilding replayable
  requests for every hop and status retry;
- cover private DNS results, mixed public/private results, direct/system proxy
  configuration, redirect method/body behavior, raw and multipart artifact
  uploads, binary artifact downloads, response/request limits, failed streams,
  and compatibility with existing HTTP-node output; and
- update node documentation, environment-limit documentation, and one runnable
  Lua example without requiring a network service during example validation.

This initiative does not add arbitrary local-path uploads, cookie persistence,
custom certificate authorities, client certificates, OAuth token acquisition,
or a general HTTP cache. Native TLS termination and response compression for
the inbound REST API remain deployment-ingress concerns. HTTP request IDs and
bounded inbound route metrics are a separate follow-up rather than part of this
release contract.

## Outcome and validation

**Historical status:** Resolved on 2026-08-27.

The HTTP nodes now support replayable raw-artifact and multipart uploads plus an
artifact response mode that streams binary responses into the configured
content-addressed store without publishing inline response bytes. Existing
inline text/JSON behavior remains the default. Shared clients expose explicit
`auto`, `system`, and `direct` proxy modes, while private-network blocking uses
a direct DNS-aware connector that rejects an entire resolution when any address
is internal and pins the validated addresses through connection establishment.
Redirects are handled explicitly so every hop re-applies origin, credential,
method, body replay, network, timeout, retry, and size policies.

Focused validation covers 9 HTTP unit tests and 45 HTTP integration tests,
including exact binary round trips, multipart framing, request replay, failed
and oversized streams, proxy bypass, DNS classification, and redirect body
semantics. `scripts/integration_gate.sh` also passed in full, including format,
policy and issue checks, exact Clippy warnings-as-errors, dependency audit,
default and Redis/PostgreSQL feature-enabled test matrices, the release build,
and validation of all 137 Lua examples.

A subsequent real-binary smoke run streamed the 108,505-byte
`data/samples/sample.pdf` through `read_file` artifact mode and `http_post`, then
downloaded it with `http_get` artifact mode and restored it through `write_file`.
The server observed `application/pdf`, a fixed `Content-Length`, and no
`Transfer-Encoding`; both uploaded and restored files matched the source
byte-for-byte at SHA-256
`85e68c368d78c273a4244a25ea0691eedae3a08ca6b0ecb0eb1831a5eb3a1434`.
