# IF-144 — `context_keys` dropped recovery diagnostics and was silently ignored on non-code nodes

## Required outcome and acceptance

- An `on_error` handler that opts into `context_keys` projection still receives
  the scalar recovery diagnostics (`_error_message`, `_error_step`,
  `_error_node_type`) and `_flow_dir`. Bulky engine payloads such as
  `_error_output` and invocation overlays remain selectable only by listing
  them, so a projection can always exclude a large value; an empty list still
  hides every user key.
- Declaring `context_keys` on a node that cannot honor it fails loading and
  `ironflow validate` with one clear message, whether it is written through the
  builder (`:context_keys(...)`) or a descriptor
  (`nodes.log({ context_keys = ... })`, `nodes.foreach({ context_keys = ... })`),
  and whether the value is a list or malformed.
- Behaviour for code nodes and function handlers that select only user keys is
  otherwise unchanged: missing keys stay absent, duplicates select once, invalid
  selectors still fail, and the cumulative conversion budget still applies.

## Evidence and cause

Found on 2026-09-15 during code review of commit `874b28f`
(IF-133 through IF-139), which introduced the IF-136 projection.

[Source: lua/context_keys.rs](../../src/lua/context_keys.rs),
[lua/runtime/extractor.rs](../../src/lua/runtime/extractor.rs).

1. `project_context` was an exact allowlist. The executor merges the recovery
   overlay into the invocation context *before* the code node filters it
   ([task_runner.rs](../../src/engine/executor/task_runner.rs),
   [error_handler.rs](../../src/engine/executor/error_handler.rs)), so
   `flow:step("recover", fn):context_keys({"order_id"})` used as an `on_error`
   target observed `ctx._error_message == nil` with no warning. The same
   filter hid `_flow_dir`, so the checked-in example's empty-projection step
   (`assert(next(ctx) == nil)`) only held when no engine key was injected.
2. The builder rejected `nodes.log(...):context_keys({...})`, but the
   descriptor form bypassed that check: `nodes.log({ context_keys = {"x"} })`
   and `nodes.foreach({ context_keys = ... })` passed `ironflow validate
   --strict` and ran with the full context, because the extractor only parsed
   `context_keys` for `node_type == "code"`.

## Outcome and validation

- `project_context` retains a key when it is in `ALWAYS_PROJECTED_KEYS`
  (`_error_message`, `_error_step`, `_error_node_type`, `_flow_dir`) or in the
  list. The first fix passed every `_`-prefixed key through, which review
  showed defeats projection: an excluded large `_error_output` or invocation
  overlay still hit the conversion limit. Bulky engine payloads are now
  selectable only explicitly. The shared `CONTEXT_KEYS_UNSUPPORTED` wording
  lives in `src/lua/context_keys.rs`. Projection remains a conversion-budget
  control, not a secrecy boundary.
- `extract_flow` fails any non-code step whose config contains `context_keys`
  with `Step '<name>': context_keys is only supported for code nodes and
  function handlers`; the builder uses the same constant. The builder's
  duplicate non-table pre-check was removed; `parse_context_keys` still reports
  `context_keys must be an array of strings` for `'x'`, `false`, and
  `json_null`.
- `examples/07-advanced/context_projection.lua` asserts that its user keys are
  hidden instead of asserting an empty table, so it holds under `ironflow run`
  (which injects `_flow_dir`) and under the engine-level test.
- Docs: `docs/nodes/code.md` lists the pass-through keys and the load-time
  rejection; `docs/LUA_FLOW_GUIDE.md` adds `context_keys()` to the `step_if`
  builder list and the recovery section; `README.md` and
  `docs/ARCHITECTURE.md` context-projection sentences updated; IF-136 carries a
  dated follow-up.

Focused coverage:

- `src/lua/conversion/context_tests.rs::context_projection_always_keeps_engine_reserved_keys`:
  a `{"order_id"}` list keeps `_error_message`, `_error_step`, `_flow_dir`
  and drops `unused`; `[]` keeps only `_` keys; listing `_flow_dir` explicitly
  selects it once; omission still clones everything.
- `tests/test_lua_context_projection.rs::cli_recovery_handler_projection_keeps_engine_reserved_keys`:
  `ironflow run` with `--context '{"order_id": 42}'`; the failing step's
  handler with `context_keys({"unrelated"})` asserts `_error_step`,
  `_error_node_type`, `_error_message` and `order_id == nil`; a
  `context_keys({})` step asserts `_flow_dir` is a string; the run succeeds
  and `_error_*` never reach the published context.
- `tests/test_lua_context_projection.rs::descriptor_projection_on_non_code_nodes_fails_load_and_validation`:
  `nodes.log` with a list, a string, and `json_null`, plus `nodes.foreach` with
  a list, all fail `load_flow_from_string` with the shared message and fail
  `validate_flow_from_string`.
- `tests/test_context_projection_workflow.rs::context_projection_example_keeps_engine_keys_injected_by_the_cli`:
  the example succeeds with `_flow_dir` in the initial context.
