# IF-201 — A Redis TTL shorter than a schedule's grace window re-runs a completed occurrence

## Evidence and boundary

Review of `develop` at 1.21.1-dev.1 on 2026-11-12, by reading. Not executed:
no Redis instance was used.

- Since IF-078 the scheduler's execution fence is the deterministic run ID,
  not the claim. In `decide` (`src/scheduler/evaluation.rs:133-147`), a claim
  result of `Ok(false)` ("claimed by a peer") is only logged
  (`:152-179`) and evaluation proceeds to `start`, which converges on the
  existing run through `init_run_owned`.
- On Redis, a finished run's hash expires after `REDIS_TTL`. The
  initialization script treats a missing hash as a new run
  (`src/storage/redis_store/scripts/init.lua:16-28, 109-118`). The claim key
  lives for at least seven days (`redis_store/claims.rs:26-46`), so it still
  reports `false`, but nothing consults it as a fence.
- A scheduler that starts later seeds its watermark at `now - grace` and
  enumerates the already-completed instant again.

Trigger: `grace_seconds: 86400` with `REDIS_TTL=3600`. The 02:00 run
finishes and its record expires about an hour later. Any replica that starts
or restarts before 02:00 the next day runs the flow a second time for the
same instant.

Boundary: nothing validates the TTL against configured grace windows
(`src/cli`, `src/scheduler`). `docs/ARCHITECTURE.md` and
`docs/REPLICA_DEPLOYMENT.md` promise one run record per instant and no
replay, and the trait documentation for `claim_schedule`
(`src/storage/mod.rs:178-185`) still describes the claim as the fence. An
explicit `DELETE /runs/{id}` inside the grace window has the same effect on
any backend; only Redis does it implicitly. SQL stores keep records until
deleted and are not affected.

## Required outcome and acceptance

- Fail startup, or warn loudly, when `REDIS_TTL` is not greater than the
  largest configured `grace_seconds` plus a margin.
- Make a lost claim with a missing run distinguishable from an orphaned
  claim, for example by recording "run created" in the claim, so the instant
  is not started again.
- Regression with the `redis` feature against a disposable instance: finish
  a scheduled run, expire its record, restart the scheduler inside the grace
  window, and assert no second run.
- Correct the two documents and the `claim_schedule` trait documentation.

## Outcome and validation

Resolved 2026-11-14.

**Reproduced first.** Through the real `Scheduler` and `FlowExecutor` on a
disposable Redis with a one-second record TTL and a one-day grace window: the
02:00 occurrence ran, its record expired, and a scheduler started at 03:00
returned `Fired` for the same instant and executed the flow a second time.
The same happened after `delete_run` on JSON, SQLite and Redis.

**Fence.** The claim now records that its occurrence produced a run.
`StateStore` gains `record_schedule_run` and `schedule_run_recorded`: JSON
writes a marker file beside the claim file, SQL sets a new nullable
`run_micros` column on the claim row (added in place to existing tables), and
Redis rewrites the claim key's value. The scheduler records the run after it
starts one and after it converges on an existing one, and a replica that
loses the claim reads the record before it loads the flow. A recorded instant
is `NotClaimed`; an unreadable record is `ClaimFailed` and retried; a failed
record write is logged and does not fail the started run.

**Contract boundary.**

- IF-078 holds: a claim without the record is an orphan and is started
  within grace.
- Deleting a scheduled run removes the record and does not release the
  instant, identically on JSON, SQLite, PostgreSQL and Redis.
- The record is written after the run is created. A process that dies in
  between leaves the run record as the only fence until a peer converges on
  it and writes the record. That window is closed when run records outlive
  grace, hence the TTL check.
- `ironflow serve` warns, once per schedule, when the Redis state store's
  `REDIS_TTL` is not greater than `grace_seconds` plus 60. A warning, not a
  startup failure: the record already prevents the duplicate run, so
  refusing to start would stop deployments that run correctly.
- Claim lifetime is unchanged and independent of `REDIS_TTL`: the larger of
  seven days and grace plus one day, which exceeds the largest accepted
  grace (seven days) by a day. Redis restarts it when the record is written.
- A custom store keeps the trait defaults, records nothing, and is fenced by
  the run record alone. Occurrences that ran before the upgrade have no
  record.
- Not changed: an instant skipped as overlapped, at capacity or failed to
  load creates no run and no record, so a replica that restarts inside grace
  can still start it.

**Evidence.**

- Before: on the unchanged code the Redis expiry case returned `Fired` twice.
  With only the new decision check disabled, 9 of the 12 new scheduler-level
  regressions fail (expiry, delete and claim repair on JSON, SQLite and
  Redis, and two decision tests); the 3 orphan-recovery cases pass.
- After, default features: library 761 passed (1 ignored), `scheduler` 128,
  `storage` 96, `api` 67, `cli` 100, `serial` 191 with one test thread,
  `scheduler_admission` 1.
- After, `postgres,redis` features, live against disposable Redis and
  PostgreSQL containers: `scheduler` 144, including 10 Redis and 6
  PostgreSQL cases (fence, record contract, column upgrade path);
  `storage_redis` 95; the startup-warning CLI test 2.
- Stability: the 10 Redis scheduler tests passed 25 of 25 consecutive runs
  and `storage_redis` 5 of 5 with every core busy. The new tests poll key
  state instead of sleeping, and the older fixed-sleep Redis claim-expiry
  test was changed to poll as well.
- `cargo fmt --all -- --check`, the module-size check, and Clippy with
  warnings denied on default and `postgres,redis` targets pass.
- Not run: the full integration gate, a multi-process or deployed replica
  test, and `DELETE /runs/{id}` over HTTP (the regressions call the store's
  `delete_run`, which the handler uses).
