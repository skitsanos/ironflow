# IF-201 — A Redis TTL shorter than a schedule's grace window re-runs a completed occurrence

## Evidence and boundary

Review of `develop` at 1.21.1-dev.1 on 2026-11-12, by reading. Not executed:
no Redis instance was used.

- Since IF-078 the scheduler's execution fence is the deterministic run ID,
  not the claim. In `decide` (`src/scheduler/evaluation.rs:133-147`), a claim
  result of `Ok(false)` ("claimed by a peer") is only logged
  (`:152-179`) and evaluation proceeds to `start`, which converges on the
  existing run through `init_run_owned`.
- On Redis, a finished run's hash expires after `REDIS_TTL`. The
  initialization script treats a missing hash as a new run
  (`src/storage/redis_store/scripts/init.lua:16-28, 109-118`). The claim key
  lives for at least seven days (`redis_store/claims.rs:26-46`), so it still
  reports `false`, but nothing consults it as a fence.
- A scheduler that starts later seeds its watermark at `now - grace` and
  enumerates the already-completed instant again.

Trigger: `grace_seconds: 86400` with `REDIS_TTL=3600`. The 02:00 run
finishes and its record expires about an hour later. Any replica that starts
or restarts before 02:00 the next day runs the flow a second time for the
same instant.

Boundary: nothing validates the TTL against configured grace windows
(`src/cli`, `src/scheduler`). `docs/ARCHITECTURE.md` and
`docs/REPLICA_DEPLOYMENT.md` promise one run record per instant and no
replay, and the trait documentation for `claim_schedule`
(`src/storage/mod.rs:178-185`) still describes the claim as the fence. An
explicit `DELETE /runs/{id}` inside the grace window has the same effect on
any backend; only Redis does it implicitly. SQL stores keep records until
deleted and are not affected.

## Required outcome and acceptance

- Fail startup, or warn loudly, when `REDIS_TTL` is not greater than the
  largest configured `grace_seconds` plus a margin.
- Make a lost claim with a missing run distinguishable from an orphaned
  claim, for example by recording "run created" in the claim, so the instant
  is not started again.
- Regression with the `redis` feature against a disposable instance: finish
  a scheduled run, expire its record, restart the scheduler inside the grace
  window, and assert no second run.
- Correct the two documents and the `claim_schedule` trait documentation.
