# IF-223 — Data transform follow-ups: YAML non-finite and large numbers, CSV formula cells, neq on a missing field

## Evidence and boundary

Recorded on 2026-11-14 from the sibling audit done while fixing IF-196.

- (a) Reproduced by that session: `yaml_parse` turns `.nan` and `.inf` into
  `null`, and integers above the signed 64-bit range into rounded floats.
  This is the loss IF-196 removed from `csv_parse`.
- (b) Reproduced: `csv_stringify` writes a cell that starts with `=` (also
  `+`, `-` or `@`, by reading) unchanged. A spreadsheet opens it as a
  formula, so exported untrusted text can execute as one.
- (c) Observed and now documented: in `data_filter`, an item without the
  field matches neither `eq` nor `neq`. IF-187 made `!=` the exact negation
  of `==` for guards; whether `neq` should include items that lack the field
  is undecided.

## Outcome and validation

Each item was reproduced through the node on the unfixed tree by its new
regression before the fix, and has its own commit.

**(a) Numbers.** Reproduced: `yaml_parse` gave `null` for `.nan`, `.inf`,
`-.Inf`, `+.inf` and `1e999`, and a rounded float for
`9223372036854775808`, `-9223372036854775809` and longer integers.
`json_parse`, `json_extract_path` with `parse_json` and the Lua
`json_parse()` rounded an integer literal outside `i64::MIN..=u64::MAX`, and
an integer above `i64::MAX` reached Lua as the nearest float, from
`json_parse()` and from the context. All of these are now strings of the
source text, the option `csv_parse` uses. YAML source text is recovered by a
second, schema-free read made only when a document holds such a number, so
it survives aliases and merges; `!!float .inf` has no plain text and fails
the step. Unchanged: integers in range, floats written as floats (`1e30`,
`1.0e19`), `!!float` on an integer literal, fractional precision (a double,
as in every parser), and JSON `1e999` and `NaN`, which already failed.
`yaml_stringify` already refused an integer above `i64::MAX`; its error now
names the value. `xml_parse` returns text only (pinned), and Lua-to-JSON
already rejected non-finite numbers (by reading). Not changed: nodes that
parse provider or HTTP JSON with their own `serde_json` call.

**(b) Formula cells.** Reproduced: `=1+1`, `+cmd`, `-2+3`, `@SUM(A1)` and
header names were written unchanged. Following the OWASP CSV injection
guidance, a text cell that begins with `=`, `+`, `-`, `@`, tab, carriage
return, line feed or a full-width form of the first four is written with a
leading apostrophe, headers included. Number values, and text that is
wholly one decimal number (`-5`, `+1.5e3`), are unchanged; text with a
leading space is unchanged, as the guidance does not cover it. The default
is on; `escape_formulas = false` writes raw cells and a non-boolean value
fails the step. `csv_parse` returns the apostrophe as part of the text.

**(c) `neq`.** Reproduced: an item without the field matched neither `eq`
nor `neq`. Decision: a missing field (or an item that is not an object)
compares as `null`, and `neq` is the exact negation of `eq`, as for guards
(IF-187). `eq` with a `null` value therefore selects what `not_exists`
does. A comparison operator without `value` returned an empty result and
now fails the step; under the negation rule it would otherwise match every
item. `gt`, `lt`, `gte`, `lte` and `contains` still exclude an item whose
field is missing or of another type, and are documented as not being
negations of each other. `deduplicate`, which shares the equality helper,
keeps one item without the key and treats `null` as a separate key; this is
unchanged, documented and pinned.

Decisions a maintainer may overrule: strings rather than a failed step for
(a), including at the Lua boundary; neutralization on by default and the
numeric-text exemption for (b); missing-as-`null` and the failure on an
omitted `value` for (c).
