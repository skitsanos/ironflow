# IF-147 — Native grouped PDF slices for page-limited document providers

## Required outcome and acceptance

- Specify an explicit opt-in mode or dedicated node that writes multipage PDF
  slices without intermediate one-page files. Keep existing `pdf_split` defaults,
  selectors, and output keys backward compatible.
- A 243-page fixture grouped by 30 produces nine files: eight with 30 pages and
  one with three, preserving page order and identity. An explicit 31-60 selection
  can produce one 30-page file under the new contract.
- Define filenames, per-file page metadata, repeated/discontiguous selection
  behavior, collision handling, and partial-output semantics before implementation.
- Preserve shared PDF load limits, inherited page attributes, dependency isolation,
  bounded materialization, tracked blocking ownership, and cancellation checkpoints.
- Add deterministic PDF-content regressions, CLI coverage, and documentation.

## Evidence and boundary

Registered on 2026-09-15 from the HARMOny ingestion hand-off. Its OCR provider
accepts at most 30 pages per request. This is the reported provider constraint,
not a universal OCR limit. At registration, `pdf_split` wrote one file per
selected page; a range changed selection, not output grouping. IF-145 fixed
interpolation only.

The original workaround: split once in the parent, distribute selected file lists,
and `pdf_merge` each worker's list when the provider requires one multipage input.
This worked but materialized intermediate files.

The user explicitly chose to register grouped output separately from IF-145 and
IF-146, then authorized its implementation on 2026-09-15 while explicitly holding
the release until they test the candidate on another machine.

## Outcome and validation

`pdf_split.pages_per_file` is an optional integer, default `1`, bounded by
`IRONFLOW_MAX_PDF_SPLIT_PAGES`. A value greater than `1` selects pages first,
preserves their order, and writes multipage groups directly from one loaded
source. No intermediate single-page files are written or reloaded.

- Default and explicit `1` retain legacy naming, overwrite/duplicate behavior,
  and output keys. Grouped mode rejects duplicate selected page identities before
  creating the output directory.
- Group names are `<stem>_part_001.pdf` onward; numbering is in selection order.
  Path inputs use their filename stem; artifact inputs use their SHA-256 digest.
- Existing `_files`, `_page_count` (selected pages), and `_success` keys remain.
  Grouped mode adds `_parts`, containing `path`, ordered 1-based `pages`, and
  `page_count` for each file, with the configured output prefix.
- Group files use the shared rooted staged writer and bounded PDF serializer,
  flushed/synced and atomically published with no overwrite. Existing files,
  symlinks, and special-file destinations are refused. Checks happen per group;
  completed groups remain on later failure/cancellation, and unfinished staging
  is removed during unwinding. No batch rollback or retry/resume is promised.
- The source passes existing byte/stream/object limits. Each cloned group graph
  is additionally bounded by `IRONFLOW_MAX_PDF_OBJECTS`, including its new tree
  and catalog. Each serialized group is capped by `IRONFLOW_MAX_PDF_BYTES`.
  Neither limit is a hard RSS ceiling or cumulative output-directory byte cap.
- Shared resources are retained once per group. Inherited page attributes and
  in-group annotation links are preserved; references to excluded pages and the
  old page tree/catalog are disconnected. This is extraction, not redaction or
  document-level bookmark/signature preservation.
- Tracked blocking ownership and cancellation checkpoints cover graph building
  and staged writes. Opaque parsing calls remain cooperatively interruptible only
  at their surrounding checkpoints.

Updated the node/reference/loading/CLI docs, example catalog, and runnable
`examples/08-extraction/pdf_split_grouped.lua`. The example accepts `input_path`
and `pages_spec` context overrides and isolates each run's retained output.

## Regression and validation evidence

Pre-implementation at `266c87d`, the new grouped tests failed: a 243-page fixture
produced 243 files instead of nine, `31-60` produced 30 files instead of one,
and invalid `pages_per_file` was ignored. The legacy compatibility test passed.

Post-implementation focused validation on macOS arm64, Rust 1.98.1:

- `cargo test --lib nodes::image::pdf_merge_split`: 11 passing tests, including
  retained graph limits, output-byte rejection, cancellation during staged
  writes, no-overwrite publication races, and existing merge regressions.
- `cargo test --test test_pdf_split_groups --test test_pdf_split_group_safety
  --test test_pdf_split_group_runtime --test test_pdf_merge_split_nodes
  --test test_pdf_page_graph --test test_pdf_merge_safety
  --test test_pdf_load_safety --test test_file_alias_roots`: 36 passing tests.
  Coverage includes all 243 page identities across nine groups, runtime range
  interpolation, reordered/discontiguous selections, shared resources,
  annotation isolation, invalid sizes, duplicates, collisions, malformed later
  groups, inherited attributes, directory aliases, and shared loading limits.
- The runtime tests execute the actual CLI and a disposable loopback `serve`
  process using verified artifact inputs. `POST /flows/run` produces a 30-page
  slice for `31-60`; `GET /runs/{id}` returns the persisted source-page metadata.
  Both split examples validate strictly and execute in isolated directories.
- `cargo test --test test_pdf_page_rendering -- --ignored --nocapture`: both
  Poppler rendering tests explicitly executed and passed. Reordered grouped
  pages and legacy split/merge pages are pixel-identical to their source pages;
  the two grouped page renders were also visually inspected.
- The example catalog classification test passed. Formatting, module-size policy,
  `cargo clippy --all-targets -- -D warnings`, `cargo audit --deny warnings`,
  issue-registry validation, and `git diff --check` passed.

This is focused default-feature and local CLI/HTTP evidence, not a full integration
gate, hosted CI run, cross-platform qualification, or live OCR-provider test.
Release remains on hold pending the user's validation on another machine.
