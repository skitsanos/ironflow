# IF-147 — Native grouped PDF slices for page-limited document providers

## Required outcome and acceptance

- Specify an explicit opt-in mode or dedicated node that writes multipage PDF
  slices without intermediate one-page files. Keep existing `pdf_split` defaults,
  selectors, and output keys backward compatible.
- A 243-page fixture grouped by 30 produces nine files: eight with 30 pages and
  one with three, preserving page order and identity. An explicit 31-60 selection
  can produce one 30-page file under the new contract.
- Define filenames, per-file page metadata, repeated/discontiguous selection
  behavior, collision handling, and partial-output semantics before implementation.
- Preserve shared PDF load limits, inherited page attributes, dependency isolation,
  bounded materialization, tracked blocking ownership, and cancellation checkpoints.
- Add deterministic PDF-content regressions, CLI coverage, and documentation.

## Evidence and boundary

Registered on 2026-09-15 from the HARMOny ingestion hand-off. Its OCR provider
accepts at most 30 pages per request. This is the reported provider constraint,
not a universal OCR limit. Existing `pdf_split` writes one file per selected page;
a range changes selection, not output grouping. IF-145 fixes interpolation only.

Current workaround: split once in the parent, distribute selected file lists,
and `pdf_merge` each worker's list when the provider requires one multipage input.
This is functional but materializes intermediate files.

The user explicitly chose to register grouped output separately from IF-145 and
IF-146. No grouped-output implementation or runtime validation is claimed here.
