# IF-129 — Notification response bodies bypass HTTP body admission limits

## Required outcome and acceptance

- Read Slack and Resend response bodies through bounded streaming admission, including chunked responses and oversized Content-Length.
- Apply the documented HTTP byte ceiling without returning a successful partial body or masking cancellation.
- Compare notification nodes with the generic HTTP control under a small cap and cover within-limit success and provider failures.

## Evidence and cause

Fresh review on 2026-09-12, finding R24. See
[AUDIT_2026-09-12.md](./AUDIT_2026-09-12.md) for the reviewed candidate,
evidence boundaries, and complete finding-to-issue mapping.

[Source: notify/slack.rs:100](../../src/nodes/notify/slack.rs), [Resend: resend.rs:52](../../src/nodes/notify/email/resend.rs).

These nodes collect `response.text()` without a byte bound. Under a 1024-byte configured HTTP body ceiling, the generic HTTP control correctly failed but both notification nodes retained a 4096-byte response. A timeout alone does not bound a fast response's memory consumption. Apply bounded streaming reads and test declared and chunked bodies. Evidence: API probe log.

## Outcome and validation

Resolved on 2026-09-13. Slack and Resend now share
`util::provider_http::notification_response_text`, which applies
`IRONFLOW_MAX_HTTP_BODY_BYTES` (default `52428800`) to success and error bodies.
Declared oversize is rejected before body collection. Every chunk is checked
against the remaining byte budget before allocation/copy; unknown-length and
chunked bodies cannot bypass admission. Allocation failure returns an error.

The reader remains directly awaited, with no detached worker. It yields between
admitted chunks so immediately ready streams do not prevent executor cancellation.
Overflow and read failure return no partial body. Only an admitted, complete
in-memory body is passed through Reqwest's text decoder, preserving charset,
BOM stripping, and replacement-character behavior. Existing JSON-or-text output,
custom output prefixes, provider-status failures, and endpoint/body redaction
remain intact. Original URI-bearing transport errors are not retained as sources.

### Contract boundary

- The cap bounds retained response body bytes, not HTTP client buffers, decoded
  text/JSON size, total process memory, or outgoing notification payloads.
- Within-limit provider failures still report their status and redacted detail;
  an oversized provider error instead reports the byte-limit failure. No partial
  notification result fields are published on failure or cancellation.
- HTTP delivery is not transactional. A failed response read does not prove that
  the message/email was not delivered, and retrying can duplicate delivery.
- No change to SMTP, generic HTTP response handling, other provider-specific
  ceilings, retry policy, dependencies, toolchain pins, skills, hooks, or config
  defaults. New documentation clarifies this existing HTTP environment setting.
- The existing Slack example can use a loopback `SLACK_WEBHOOK`. The Resend
  example accepts an optional `RESEND_API_URL` for its `api_url` parameter; this
  is an example convention, not a new node-level environment fallback.

### Regression evidence

Before the fix, the new declared/chunked regression passed its generic HTTP
control and then failed because Slack returned the complete 4096-byte body with
`result_success = true` under a 1024-byte limit. The same test now passes for both
notification nodes. The HTTP control sets `fail_on_status = false` when comparing
error-body admission, since the default HTTP behavior skips non-2xx bodies.

Post-fix validation on Rust 1.98.1:

- `cargo test --test test_notification_response_limits`: 7 tests, with isolated
  child environments and local synthetic HTTP fixtures. Matrices cover oversized
  declared/chunked success and error bodies, oversized headers with no body bytes,
  empty/1023/1024/1025-byte bodies, cumulative chunks, JSON/text output, charset,
  BOM, invalid UTF-8 replacement, 400/429/500 errors with redaction, interrupted
  declared/chunked bodies, and request timeout after a valid JSON prefix.
- The same target covers actual workflow cancellation and step timeout while
  awaiting EOF, terminal task/run statuses, and absence of partial context output.
  Both updated Lua examples validate and run against loopback endpoints with
  valid and oversized responses, correct exit statuses, preserved successful
  data, and redacted errors without partial output. No real provider was called.
- `cargo test --test test_slack_notification_node`: 10 tests passed.
- `cargo test --test test_send_email_node`: 12 tests passed.
- `cargo test --test test_provider_redirect_security`: 4 tests passed.
- `cargo clippy --all-targets -- -D warnings`, `cargo fmt --all -- --check`,
  module-size policy, `cargo audit --deny warnings`, issue-registry validation,
  and `git diff --check` passed.

This is 33 distinct focused tests, not the full integration gate, live
Slack/Resend/SMTP verification, or deployment validation. No real credentials
