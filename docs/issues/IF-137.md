# IF-137 — Postgres and Redis stores cannot connect over TLS: sqlx has no TLS feature

## Required outcome and acceptance

- The release binaries connect to a Postgres that requires encryption with
  `?sslmode=require` (and `verify-ca`/`verify-full` when a CA is supplied).
- `sqlx` gains the `tls-rustls` feature (rustls + ring, no OpenSSL dependency,
  links into the static musl build); the Redis backend is checked for the same
  gap.
- Test against a Postgres started with `ssl=on` and `hostssl … scram-sha-256`
  only: `IRONFLOW_STORE=postgres` with `sslmode=require` starts, migrates and
  runs a workflow; the plaintext URL is rejected by the server as before.

## Evidence and cause

Found on 2026-07-28 and re-verified on 2026-09-14 against release tags up to
v1.18.0 while enabling the shared run store of the HARMOny `ironflow-hooks`
service.

[Source: Cargo.toml:66](../../Cargo.toml).

```
sqlx = { version = "0.9", features = ["runtime-tokio", "any", "sqlite"] }
```

The target cluster (Patroni, `pg_hba.conf` with `hostssl` only) rejects
plaintext with `no encryption`; adding `sslmode=require` fails inside the
binary with `TLS upgrade required by connect options but SQLx was built without
TLS support enabled`. Verified earlier that with `tls-rustls` in the feature
list the same URL connects, creates the `ironflow_*` tables and records runs
against a local Postgres started with `ssl=on`. That change is not on any
branch or tag of this repository, so every environment that mandates TLS to
its database is limited to the per-pod JSON store.

## Outcome and validation

- The `postgres` feature enables `sqlx/tls-rustls` (Rustls/ring). The `redis`
  feature enables `redis/tokio-rustls-comp`, including native certificate roots.
  The optional direct Rustls dependency enables explicit ring selection; no
  OpenSSL or insecure certificate-bypass feature was added.
- SQL state/event stores and TLS Redis state/event clients install the ring
  provider before certificate verification when an embedding application has
  not already installed a provider. This avoids the dual ring/AWS-LC feature
  ambiguity in the dependency graph, while respecting an existing provider.
- PostgreSQL `require`, `verify-ca`, and `verify-full` retain their SQLx
  semantics. Redis `rediss://` verifies the certificate and hostname, with
  native roots or `SSL_CERT_FILE`/`SSL_CERT_DIR`. `#insecure` is not enabled.
  Plaintext URLs remain explicit choices; no insecure fallback was introduced.
- CLI and replica documentation explain configuration and the fact that
  published v1.18.1 and earlier binaries do not contain this fix. Existing
  `-full` and Docker feature selections pick it up on their next build.
- `scripts/test_store_tls.ts` creates disposable TLS-only stores and is required
  in both Linux feature CI and the local integration gate. The check skill and
  repository-policy tests cover the gate. It must run with Bun's
  `--no-env-file` option, not inherited database configuration.

## Validation

Baseline: the published v1.18.1 Apple Silicon `-full` binary failed the new
fixture at PostgreSQL `sslmode=require` with the reported missing-TLS error.
An initial feature-only patch exposed a Rustls provider panic under `verify-ca`;
explicit provider initialization fixed it. Negative acceptance checks now
reject panics and timeouts as invalid test outcomes.

Post-fix checks on 2026-09-14 with Rust 1.98.1 and Bun 1.4.2:

- `scripts/test_store_tls.ts` passed against PostgreSQL 18.6 and Redis 8.10.1
  in fresh loopback-only Docker instances with generated certificates and random
  credentials. PostgreSQL CLI workflows/migrations passed for all three modes.
- PostgreSQL `verify-full` and Redis verified TLS passed `serve` workflow
  execution, shutdown/restart, durable context retrieval, SSE event replay and
  CLI inspection of the retained run.
- Both backends rejected plaintext, an unrelated CA and a wrong hostname;
  Redis also rejected `#insecure`. Owned containers and temporary files were
  removed. No production or shared storage was used.
- Default and full-feature Clippy and library/focused tests passed. The provider
  initialization regression verifies idempotence. Dependency audit passed with
  no new advisory exceptions or package-version upgrades.
- Independent `cargo check --no-default-features --features postgres --lib` and
  `cargo check --no-default-features --features redis --lib` checks passed; each
  optional backend can enable its TLS support without the other feature.
- A clean `rust:1.98.1-alpine` Linux/ARM64 build ran
  `cargo build --locked --features postgres,redis --bin ironflow` successfully.
  `--version` executed, `readelf` found no interpreter, and `file` identified a
  statically linked aarch64 ELF. This checks the current source/lockfile with
  musl, not an optimized x86_64 release artifact.

This resolves the local source defect, not publication. The full release
matrix, including x86_64 musl and Windows, must still run at the next authorized
release boundary; no existing tag, binary or deployment was modified.

Integration recheck on 2026-09-14: the complete TLS acceptance script passed
again with the `1.18.1-dev.6` candidate after integrating PR #180 and its Rustls
0.23.45 security update. PostgreSQL 18.6 and Redis 8.10.1 verified CLI/serve
persistence and rejected all negative cases; owned test resources were removed.
