# IF-137 — Postgres and Redis stores cannot connect over TLS: sqlx has no TLS feature

## Required outcome and acceptance

- The release binaries connect to a Postgres that requires encryption with
  `?sslmode=require` (and `verify-ca`/`verify-full` when a CA is supplied).
- `sqlx` gains the `tls-rustls` feature (rustls + ring, no OpenSSL dependency,
  links into the static musl build); the Redis backend is checked for the same
  gap.
- Test against a Postgres started with `ssl=on` and `hostssl … scram-sha-256`
  only: `IRONFLOW_STORE=postgres` with `sslmode=require` starts, migrates and
  runs a workflow; the plaintext URL is rejected by the server as before.

## Evidence and cause

Found on 2026-07-28 and re-verified on 2026-09-14 against release tags up to
v1.18.0 while enabling the shared run store of the HARMOny `ironflow-hooks`
service.

[Source: Cargo.toml:66](../../Cargo.toml).

```
sqlx = { version = "0.9", features = ["runtime-tokio", "any", "sqlite"] }
```

The target cluster (Patroni, `pg_hba.conf` with `hostssl` only) rejects
plaintext with `no encryption`; adding `sslmode=require` fails inside the
binary with `TLS upgrade required by connect options but SQLx was built without
TLS support enabled`. Verified earlier that with `tls-rustls` in the feature
list the same URL connects, creates the `ironflow_*` tables and records runs
against a local Postgres started with `ssl=on`. That change is not on any
branch or tag of this repository, so every environment that mandates TLS to
its database is limited to the per-pod JSON store.

## Outcome and validation

- The `postgres` feature enables `sqlx/tls-rustls` (Rustls/ring). The `redis`
  feature enables `redis/tokio-rustls-comp`, including native certificate roots.
  The optional direct Rustls dependency enables explicit ring selection; no
  OpenSSL or insecure certificate-bypass feature was added.
- The original fix had SQL state/event stores and TLS Redis state/event
  clients install the ring provider before certificate verification when an
  embedding application had not already installed one. This avoids the dual
  ring/AWS-LC feature ambiguity in the dependency graph, while respecting an
  existing provider. Since 2026-09-15 the provider is installed once at process
  start instead; see the follow-up below and [IF-141](IF-141.md).
- PostgreSQL `require`, `verify-ca`, and `verify-full` retain their SQLx
  semantics. Redis `rediss://` verifies the certificate and hostname, with
  native roots or `SSL_CERT_FILE`/`SSL_CERT_DIR`. `#insecure` is not enabled.
  Plaintext URLs remain explicit choices; no insecure fallback was introduced.
- CLI and replica documentation explain configuration and the fact that
  published v1.18.1 and earlier binaries do not contain this fix. Existing
  `-full` and Docker feature selections pick it up on their next build.
- `scripts/test_store_tls.ts` creates disposable TLS-only stores and is required
  in both Linux feature CI and the local integration gate. The check skill and
  repository-policy tests cover the gate. It must run with Bun's
  `--no-env-file` option, not inherited database configuration.

## Validation

Baseline: the published v1.18.1 Apple Silicon `-full` binary failed the new
fixture at PostgreSQL `sslmode=require` with the reported missing-TLS error.
An initial feature-only patch exposed a Rustls provider panic under `verify-ca`;
explicit provider initialization fixed it. Negative acceptance checks now
reject panics and timeouts as invalid test outcomes.

Post-fix checks on 2026-09-14 with Rust 1.98.1 and Bun 1.4.2:

- `scripts/test_store_tls.ts` passed against PostgreSQL 18.6 and Redis 8.10.1
  in fresh loopback-only Docker instances with generated certificates and random
  credentials. PostgreSQL CLI workflows/migrations passed for all three modes.
- PostgreSQL `verify-full` and Redis verified TLS passed `serve` workflow
  execution, shutdown/restart, durable context retrieval, SSE event replay and
  CLI inspection of the retained run.
- Both backends rejected plaintext, an unrelated CA and a wrong hostname;
  Redis also rejected `#insecure`. Owned containers and temporary files were
  removed. No production or shared storage was used.
- Default and full-feature Clippy and library/focused tests passed. The provider
  initialization regression verifies idempotence. Dependency audit passed with
  no new advisory exceptions or package-version upgrades.
- Independent `cargo check --no-default-features --features postgres --lib` and
  `cargo check --no-default-features --features redis --lib` checks passed; each
  optional backend can enable its TLS support without the other feature.
- A clean `rust:1.98.1-alpine` Linux/ARM64 build ran
  `cargo build --locked --features postgres,redis --bin ironflow` successfully.
  `--version` executed, `readelf` found no interpreter, and `file` identified a
  statically linked aarch64 ELF. This checks the current source/lockfile with
  musl, not an optimized x86_64 release artifact.

This resolves the local source defect, not publication. The full release
matrix, including x86_64 musl and Windows, must still run at the next authorized

Integration recheck on 2026-09-14: the complete TLS acceptance script passed

### CI fixture follow-up, 2026-09-15

[CI run 34883610002](https://github.com/skitsanos/ironflow/actions/runs/34883610002)
passed the feature-enabled Rust tests, but the first TLS acceptance command
failed with `Connection reset by peer`. The fixture used socket-only
`pg_isready`, which can accept the official PostgreSQL image's temporary
initialization server before its final TCP listener is available. Three fresh
disposable starts reproduced socket readiness while TCP returned no response.

The fixture now waits for an authenticated `SELECT 1` over explicit TCP with
`sslmode=verify-full` and the fixture CA. Polling has a 30-second deadline;
timed-out commands, nonzero exits and unexpected output cannot satisfy it.
Failure diagnostics do not expose command arguments or credentials. Tests cover
the probe's connection settings, premature readiness, query failures, exact
output matching and deadline handling. This follow-up fixes the test fixture,
not the production TLS implementation; the prior local results do not establish
that the hosted run passed.

Post-fix local validation on 2026-09-15: all 47 Bun policy/regression tests,
the issue registry, formatting, module-size policy and
`cargo clippy --all-targets -- -D warnings` passed. A live socket-only
PostgreSQL instance satisfied the old probe but was rejected by the new one.
The locked full-feature binary passed the complete PostgreSQL 18.6/Redis 8.10.1
TLS acceptance script, including CLI/serve persistence and every negative
case. All owned containers, volumes and fixture files were removed. These
results cover the local fixture change; hosted Linux CI verification awaits
publication and a new run.

### Provider installation follow-up, 2026-09-15

A code review of commit `874b28f` on 2026-09-15 found that the per-store
provider installation above did not cover every TLS client. `db_query` and
`db_exec` (`src/nodes/database/sql.rs`) open their own `AnyPool` and never
called `storage::tls::initialize_provider`, so a `postgres` feature build
running with the default JSON state store panicked on a step whose connection
URL used `sslmode=verify-ca`. The defect and its mechanism are recorded as
[IF-141](IF-141.md).

The fix moved installation to process start. `ironflow::initialize_tls_provider`
is the single public, idempotent, feature-independent entry point; `main`
calls it immediately after environment bootstrap and before the Tokio runtime
is built. The three per-store call sites in `SqlStateStore::new_with_prefix`,
`SqlEventStore::new_with_prefix` and `redis_config::client` were removed.
Embedders of the library must now call the entry point themselves before
building a runtime. The idempotency regression in `src/storage/tls.rs` is
unchanged.

Validation on 2026-09-15 (local source, focused targets):

- `cargo check --features postgres,redis` passed.
- `cargo check` (default features) passed.
- `cargo test --lib --features postgres,redis storage::tls` passed
  (`provider_initialization_is_idempotent`).
- `cargo fmt --all -- --check` and `python3 -B scripts/check_module_size.py`
  passed.

The live `scripts/test_store_tls.ts` acceptance script and the full Clippy gate
were not rerun for this follow-up; they belong to the integration boundary.

### Fixture and gate follow-up, 2026-09-15

The same review found three defects in the acceptance tooling added for this
issue. `waitForReady` in `scripts/storage_tls/fixture.ts` re-checked the clock
after a probe returned, so a genuine success that landed at the deadline was
discarded, and its hard 30 s budget was narrower than the attempt-based loop it
replaced; the trailing check is gone and the default budget is 90 s with the
per-probe clamp retained. `scripts/test_store_tls.ts` had no SIGINT/SIGTERM
handling, and Bun does not run `finally` blocks on a signal, so an interrupted
gate leaked the `ironflow-tls-*` containers and the temporary CA/server keys;
the gate now tracks its children, removes the containers and key directory
once, and exits 130/143. The gate also gained a default-store `db_query` probe
over `require`, `verify-ca` and `verify-full`, which is the regression test for
[IF-141](IF-141.md). Bun policy tests cover the late-success and budget cases
and an end-to-end interrupt with fake `docker`/`ironflow` binaries.

The full gate passed locally on 2026-09-15 with the reworked fixture (PostgreSQL
18 and Redis 8 containers, every acceptance and rejection case, the three
`db_query` probes); no `ironflow-tls-*` containers or temporary directories
remained afterwards.
