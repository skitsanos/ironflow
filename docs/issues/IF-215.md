# IF-215 — Parsing, planning and fan-out paths that still do unbounded work

## Evidence and boundary

Recorded on 2026-11-13. Collected from the fixes for IF-173 to IF-175,
IF-188 and IF-189. Each item says how it was established; none was
re-verified for this page.

- (a) Measured: HTML parsing is quadratic in nesting depth, about 16 s for
  100,000 nested `<div>` in an optimized build. The Markdown paths stop early
  (IF-174); `extract_html` with `format = "text"` is uncapped, though it
  observes cancellation.
- (b) Measured: `html_to_markdown` output is not charged against an output
  limit. At the 128-level cap, 323 KB of input produced 20 MB.
- (c) Measured: `topological_phases` in `src/engine/recovery.rs` is
  quadratic; a 10,000-step dependency chain took 10 s to validate,
  unoptimized (IF-175).
- (d) By reading: `mcp_client` relies on `rmcp`'s fixed 16 MiB response cap;
  a reply of that size enters workflow context.
- (e) By reading: the `json_parse` node, unlike the Lua global fixed in
  IF-189, parses into a `serde_json::Value` with no node budget.
- (f) By reading: one S3 list page is read whole by the SDK, so an endpoint
  can still send one very large page.
- (g) By reading: each failed attempt stores one event of up to 64 KiB, and
  the retry count has no ceiling.
- (h) By reading: the nesting limit from IF-188 does not bound the total
  number of live child runs; wide `parallel_subworkflows` at each of sixteen
  levels multiply.
- (i) By reading: `ai_chunk_semantic` accepts unbounded `sg_window` and
  `poly_order`; a suspected CPU cost on long inputs (IF-195 audit).

## Outcome and validation

Resolved on 2026-11-15. Every item fails with an error that names its
limit; environment limits are registered in `limits::ALL`, so a malformed
value stops startup.

| Item | Limit | Default | Before, on the unfixed tree | After |
|------|-------|---------|-----------------------------|-------|
| (a) `extract_html` text nesting | `IRONFLOW_MAX_HTML_TEXT_DEPTH` | 1024 | 100,000 nested `<div>` accepted after 197 s | refused in under 1 s; parsing stops at twice the limit |
| (b) Markdown output | `IRONFLOW_MAX_EXTRACT_OUTPUT_BYTES`, charged while converting | 50 MiB | 600 KB of nested quotes or lists gave 73 MB; a 1 MiB header cell over 200 rows gave 212 MB | refused; output within the limit unchanged |
| (c) phase planning | none: one pass over steps and edges | n/a | 10,000-step chain: 9.8 s | 100,000 steps: 0.3 s |
| (d) `mcp_client` result | `IRONFLOW_MAX_MCP_RESULT_BYTES` | 4 MiB | 16 MiB `initialize` and 4.5 MiB `tools/list` results entered context | refused before any output key exists |
| (e) `json_parse` node, `json_extract_path` `parse_json` | `IRONFLOW_MAX_JSON_PARSE_NODES` | 1,000,000 | a 40 MB, 20-million-element array was built | refused after a counting pass |
| (f) S3 list page | `IRONFLOW_MAX_S3_LIST_PAGE_BYTES` | 16 MiB | a 16 MiB page of one key was accepted; `artifacts prune` buffered a 17 MiB page | refused unread (declared length) or cut off (streamed) |
| (g) retries | fixed | 100 per step | already refused at validation | regression and documentation added |
| (h) live child runs | `IRONFLOW_MAX_LIVE_CHILD_RUNS` | 4096 | 3 + 9 children alive under a limit of 6 | the child is refused and its step fails |
| (i) `ai_chunk_semantic` | fixed: `sim_window`, `sg_window`, `poly_order` | 101, 1001, 16 | accepted; see measurement | refused before any embedding request |

Notes and decisions:

- (b) wraps the converter's block quote, list and table handlers. Table
  padding was found while fixing: it is unbounded at any nesting depth. The
  projection is rows × the sum of column widths, so a table can be refused
  slightly below the limit.
- (e) uses its own budget, not `IRONFLOW_MAX_CONVERSION_NODES`. A native
  value may be larger than a Lua handler can convert ([IF-136](IF-136.md)),
  and the shipped `context_projection.lua` parses 200,000 numbers with this
  node. The Lua budget would have broken it.
- (f) also covers `s3_list_buckets` and the S3 listing of `artifacts prune`.
  `max_keys` is unchanged.
- (g) The finding was wrong by reading: `MAX_RETRY_COUNT` already existed.
  One step stores at most 101 attempt records of 64 KiB.
- (h) refuses instead of waiting. A waiting parent keeps its own slot, so a
  tree of waiting parents could never free one. The error is the typed
  `LiveChildRunLimit`; each level reports it alone.
- (i) Measured with the repository's filter built optimized: window equal
  to 50,000 sentences, 5.2 s; order 1,600, 18.8 s; order 3,200, 330 s, on
  the async worker. `sim_window` had the same shape and is capped too.

Contract boundary:

- (d) bounds what enters context. `rmcp` still holds a reply of up to
  16 MiB while it deserializes it.
- (e) counts values, not bytes; strings are bounded by the context text.
- (h) counts child runs of this process only, not other replicas.
- Not done: no new Lua example. The limits are process settings; all
  shipped examples validate unchanged.

Validation on 2026-11-15, unoptimized builds, local mock endpoints only:

- Failing first for every item except (g), with the results in the table.
- After: `cargo test --lib` and the area binaries `documents`, `nodes`,
  `nodes_network`, `engine`, `storage` and `serial`; `cargo fmt`, the
  module-size gate (the `recovery.rs` exception is retired), Clippy with
  default features and with `postgres,redis`, the license and notices
  gates, and `ironflow validate` on every `examples/**/*.lua`.
