# IF-208 — Renovate lockfile pull requests cannot pass CI because the notices file lists crate versions

## Evidence and boundary

Found on 2026-11-12 on `develop` at 1.21.1-dev.2, the first push that carried
IF-204.

- Renovate pull requests 255, 256 and 257 (lockfile updates of `tree-sitter`,
  `uuid` and `noyalib`) were opened on top of that push. Every build and test
  job passed, and "Repository policy" and "Security audit" failed on all
  three.
- The failed log for pull request 255 shows
  `scripts/tests/third_party_notices.test.ts`, "committed notices > every
  listed crate is a locked package and the stated count matches the rows",
  failing on the row `tree-sitter | 0.27.1`. The audit job's
  `third_party_notices.ts check` step fails for the same reason.
- Cause: `THIRD_PARTY_LICENSES.md` is committed, lists every crate with its
  version, and is checked against `Cargo.lock` in CI, the integration gate
  and the pre-commit hook (IF-204). Renovate changes the lockfile and cannot
  run `bun --no-env-file scripts/third_party_notices.ts write`.
- Consequence: every dependency pull request is red by construction. The
  three above were integrated by hand in one commit with regenerated notices
  and then closed. A red check no longer distinguishes a stale notices file
  from a real failure: pull request 258 (`html5ever` 0.40), which does not
  compile, looked the same at a glance.

Boundary: the freshness check works as designed, and release archives and
the image must keep shipping notices that match the binary. Not checked:
whether a Renovate setting available to this repository can regenerate a
file after an update.

## Required outcome and acceptance

- Choose one mechanism and record why:
  1. regenerate the notices on Renovate branches in a workflow that commits
     the result, with the token scope that needs reviewed;
  2. generate the notices at build and release time instead of committing
     them, keeping a CI check that generation succeeds and every license is
     allowed;
  3. keep the committed file but leave versions out of its rows, so only an
     added or removed crate or a license change makes it stale.
- Acceptance: a lockfile-only Renovate pull request for a patch update passes
  CI without manual work; archives and the image still ship notices that
  match the shipped dependency graph; the policy tests, `docs/SECURITY.md`
  and the release skill describe the chosen mechanism.
- Until this is resolved, dependency updates are integrated locally with
  regenerated notices and their pull requests closed with a note.
