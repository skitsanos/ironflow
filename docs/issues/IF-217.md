# IF-217 — Scheduler follow-ups: outcome labels, catch-up losses and cron messages

## Evidence and boundary

Recorded on 2026-11-13 from the fixes for IF-180, IF-182 and IF-206.

- (a) By reading: the run-permit acquire inside `FlowExecutor::run` is
  fail-fast. If the run cap fills between the capacity probe and the acquire,
  the instant is reported as `Failed` instead of `AtCapacity`.
- (b) By reading: the run permit is held while a start waits up to 5 seconds
  for a load permit, so waiting schedules occupy run capacity.
- (c) Measured twice: at startup an every-minute schedule lost 15 to 19 of
  its catch-up instants to the overlap rule, because they are evaluated back
  to back while the first run is active. Documented overlap behaviour, but
  not what operators expect from catch-up.
- (d) By reading: a 5-second permit wait followed by a parse near the
  10-second Lua limit can reach the 15-second evaluation budget, which
  consumes the due instants as `TimedOut`.
- (e) Measured: named weekday ranges across the week boundary (`Sat-Sun`,
  `Fri-Mon`) are rejected at startup while `6-7` is accepted (documented).
- (f) Measured: a cron value outside its field, a backwards range and a bad
  step are rejected without naming the field.
- (g) By reading: a scheduled instant that was skipped as overlapped, at
  capacity or failed to load creates no run and no claim record, so a replica
  that restarts inside the grace window can still start it, although the
  code comments say such skips consume the instant (IF-201).

## Outcome and validation

Resolved on 2026-11-16. Each item was reproduced with a failing regression
before its fix. (c) and (g) follow the maintainer decision of 2026-11-16:
catch-up runs only the most recent missed instant, and every skipped instant
gets a durable record.

- (a) Reproduced with the run cap at one (`Failed`). The executor now
  returns `ScheduleRun::AtCapacity`.
- (b) Reproduced: a start waiting for a load permit held the run permit. The
  load permit is now taken first and the run permit before the parse. The
  run permit is never waited for, so the order cannot deadlock.
- (c) Reproduced: 30 missed instants asked for 30 starts.
  `src/scheduler/window.rs` splits the due instants: the most recent is
  decided, the earlier ones are claimed and recorded as `Superseded` (metric
  label `superseded`, one `WARN` line per schedule and tick). At most 64 are
  recorded per tick and the watermark stops before the rest, so a longer
  backlog is no longer dropped unrecorded.
- (d) Reproduced on the paused test clock (`TimedOut`, instant gone).
  Decisions made before an expiry are kept and an undecided instant is
  `Deferred`. Bound: the third consecutive expired evaluation of a schedule
  (`MAX_BUDGET_DEFERRALS`) burns it as `TimedOut`, and grace limits every
  retry. A retry that finds its own run still active reports `NotClaimed`
  (reproduced: it was `Overlapped` with itself).
- (e) Reproduced. `Sat-Sun` equals `6-7`; `Fri-Mon` is Friday to Monday. A
  backwards numeric range (`6-1`) stays refused, the conservative choice.
- (f) Reproduced for 30 expressions. `src/scheduler/field_value.rs` applies
  the crate's bounds first, so the message names the field and quotes the
  item; the set of accepted expressions is unchanged.
- (g) Reproduced on JSON and SQLite: a replica started inside grace `Fired`
  the instant its peer had skipped. A skip (late, overlapped, at capacity,
  failed, superseded) now writes the IF-201 occurrence record, which the
  SQL, Redis and JSON stores already have; no schema changed. A failed
  write is reported as `ClaimFailed` and the instant is decided again.
  Found while fixing: a draining replica reported `AtCapacity`, which would
  now be final for every replica; it defers and records nothing instead.

Boundaries. The pre-fix failures of (c) and (g) were reproduced on JSON and
SQLite; Redis and PostgreSQL were run after the fix only, against disposable
containers. (d) is tested with an executor that never answers, not with a
real 5-second wait and 10-second parse. By reading only: the budget can
cancel a start inside the engine's run initialisation, as it could before;
the retry converges on whatever run exists. An instant burned as `TimedOut`
gets no record, because its state is indeterminate.

Validation: `cargo test --test scheduler`, `--test scheduler_admission` and
`--lib scheduler::`; the `scheduler` binary with `--features postgres,redis`
against live Redis and PostgreSQL; `cargo fmt --all -- --check`, the
module-size check, and `cargo clippy --all-targets -- -D warnings` with and
without `--features postgres,redis`. Documented in `docs/CLI_REFERENCE.md`
(Catch-up, Field syntax, Weekday field), `docs/ARCHITECTURE.md`,
`docs/REPLICA_DEPLOYMENT.md`, `docs/METRICS.md` and `docs/releases/next.md`.
