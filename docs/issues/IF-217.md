# IF-217 — Scheduler follow-ups: outcome labels, catch-up losses and cron messages

## Evidence and boundary

Recorded on 2026-11-13 from the fixes for IF-180, IF-182 and IF-206.

- (a) By reading: the run-permit acquire inside `FlowExecutor::run` is
  fail-fast. If the run cap fills between the capacity probe and the acquire,
  the instant is reported as `Failed` instead of `AtCapacity`.
- (b) By reading: the run permit is held while a start waits up to 5 seconds
  for a load permit, so waiting schedules occupy run capacity.
- (c) Measured twice: at startup an every-minute schedule lost 15 to 19 of
  its catch-up instants to the overlap rule, because they are evaluated back
  to back while the first run is active. Documented overlap behaviour, but
  not what operators expect from catch-up.
- (d) By reading: a 5-second permit wait followed by a parse near the
  10-second Lua limit can reach the 15-second evaluation budget, which
  consumes the due instants as `TimedOut`.
- (e) Measured: named weekday ranges across the week boundary (`Sat-Sun`,
  `Fri-Mon`) are rejected at startup while `6-7` is accepted (documented).
- (f) Measured: a cron value outside its field, a backwards range and a bad
  step are rejected without naming the field.

## Required outcome and acceptance

- (a) Report `AtCapacity`. (b) Acquire the load permit first, or document
  the hold. (d) Treat a budget expiry before the run starts like a deferral.
- (c) Decide whether catch-up should run one instant per schedule, queue
  them, or stay as it is with a clearer document.
- (e), (f) Accept wrapping named ranges and name the field in the error.
- Each fix gets a scheduler regression.
