# IF-168 — Malformed IRONFLOW_MAX_* limit values silently fall back to defaults

## Evidence and boundary

Audit of `develop` at 1.20.1-dev.6 on 2026-10-28.

- `src/util/limits.rs::env_u64` parses with `.ok()`, `parse::<u64>().ok()`,
  `filter(> 0)` and `unwrap_or(default)`. It has 43 call sites across 21
  variables: `IRONFLOW_LUA_HOOK_INTERVAL`, `IRONFLOW_MAX_AUDIO_BYTES`,
  `IRONFLOW_MAX_DIRECTORY_DEPTH`, `IRONFLOW_MAX_EMBEDDING_VALUES`,
  `IRONFLOW_MAX_EXTRACT_ITEMS`, `IRONFLOW_MAX_FILE_BYTES`,
  `IRONFLOW_MAX_HTTP_BODY_BYTES`, `IRONFLOW_MAX_IMAGE_PIXELS`,
  `IRONFLOW_MAX_PDF_BYTES`, `IRONFLOW_MAX_PDF_DPI`,
  `IRONFLOW_MAX_PDF_MERGE_BYTES`, `IRONFLOW_MAX_PDF_MERGE_FILES`,
  `IRONFLOW_MAX_PDF_MERGE_PAGES`, `IRONFLOW_MAX_PDF_OBJECTS`,
  `IRONFLOW_MAX_PDF_SPLIT_PAGES`, `IRONFLOW_MAX_TASK_OUTPUT_BYTES`,
  `IRONFLOW_MAX_XLSX_CELLS`, `IRONFLOW_MAX_XLSX_ROWS`,
  `IRONFLOW_MAX_ZIP_ENTRIES`, `IRONFLOW_MAX_ZIP_METADATA_BYTES`,
  `IRONFLOW_MCP_SESSION_TTL_SECS`.
- Consequence: `IRONFLOW_MAX_HTTP_BODY_BYTES=10MB`, `=1e6`, `=-1` or `=0` all
  yield the compiled default (50 MiB) with no log line. An operator tightening
  a limit cannot tell it was ignored, and a typo in a tightening value
  silently restores the default.
- Contrast: `src/util/runtime_config.rs` fails closed for
  `IRONFLOW_MAX_CONCURRENT_TASKS`, `IRONFLOW_MAX_CONCURRENT_RUNS`,
  `IRONFLOW_MAX_CONCURRENT_FLOW_LOADS`, `IRONFLOW_MAX_RUN_SECONDS` and
  `IRONFLOW_SHUTDOWN_GRACE_SECONDS`; `tests/test_runtime_limit_config.rs`
  states the rule as "fail-closed parsing for limits whose invalid fallback
  would be unlimited". `AGENTS.md` treats environment configuration as
  untrusted input.

Boundary: no limit becomes unlimited through this path. The defect is silent
loss of operator intent and an inconsistent contract across variables.

## Required outcome and acceptance

- One parsing contract for every numeric `IRONFLOW_*` variable: invalid or
  negative values are fatal at startup for `run`, `serve`, `validate` and the
  scheduler, naming the variable and the accepted format. Define `0`
  explicitly (reject it, or allow "default" only where a node document says
  so).
- Validate all known limit variables once at startup (extending
  `runtime_config`) instead of lazily at first use, so misconfiguration
  surfaces before any run executes.
- Regressions: invalid value fatal for a representative sample of the 21
  variables across `run` and `serve`, valid override honored, unset uses the
  default.
- Update the environment table in `docs/CLI_REFERENCE.md` and every node
  document that lists one of these limits.

## Outcome and validation

Resolved on 2026-10-28 on branch `fix/if-168-limit-parsing` at 1.20.1-dev.8.

Outcome:

- `src/util/limits/env.rs` defines the one contract: a [`Limit`] is a plain
  base-10 integer without sign, unit, decimal, or exponent, surrounded by
  optional whitespace. A ceiling (`Limit::positive`) rejects `0`; a limit whose
  documentation says `0` disables it (`Limit::optional`) accepts it. A
  [`Toggle`] accepts only `true` or `false`. Errors name the variable and the
  accepted format: `IRONFLOW_MAX_HTTP_BODY_BYTES must be a positive integer`,
  `IRONFLOW_DB_MAX_ROWS must be a non-negative integer (0 disables the
  limit)`, `IRONFLOW_LUA_GC_AFTER_EXECUTION must be either 'true' or 'false'`.
- Every limit is declared once as a `Limit` const in `limits.rs` or its
  `image`, `pdf`, `xlsx` and new `process` submodules and listed in
  `limits::ALL` (53 numeric limits) and `limits::TOGGLES` (1 switch). The
  `process` submodule now owns the five capacities that
  `src/nodes/mcp/session.rs`, `subworkflow.rs`, `oauth.rs` and `cache.rs`
  used to parse privately with the same silent fallback; their `OnceLock` and
  `LazyLock` users read through it. A unit test reads the module sources with
  `include_str!` and fails when an `IRONFLOW_*` name appears there without
  being registered.
- `limits::validate_environment()` resolves every registered variable once
  and runs before any store opens or flow file is read: `run`, `validate` and
  `serve` call it through `cli::resolution::validate_limit_environment`
  (which also keeps the `IRONFLOW_MAX_RUN_SECONDS` check), the embedded API
  server calls it in `api::server::prepare`, and `WorkflowEngine` calls it
  before resolving task concurrency for a run, so embedders get the same
  behaviour. `runtime_config.rs` keeps its existing fail-closed parsers for
  the five concurrency and deadline variables; the contract wording is shared.
- Node-time accessors keep their names and types (`max_file_bytes()`,
  `max_lua_memory_bytes() -> Option<u64>`, …) and read lazily through
  `Limit::read`. After startup validation an invalid value can only appear if
  the environment changed later; that case logs a `warn` naming the variable
  and keeps the default instead of silently accepting it.
- `docs/CLI_REFERENCE.md` states the contract once above the environment
  tables and marks the GC switch as `true`/`false` only. Node documents list
  the variables and defaults without describing parse behaviour, so they
  needed no change; the variable rows they link to carry the contract.

Contract boundary: a value that used to be ignored now stops the process at
startup, which is the intended behaviour change. `0` keeps its documented
meaning for the Lua, `db_query` and LLM response limits and is rejected for
every ceiling, where it previously meant "use the default". The scheduler has
no separate entry point: it runs inside `serve`, which validates first.
`IRONFLOW_MAX_LIST_RECORDS`, `IRONFLOW_EVENT_MEMORY_CAPACITY`,
`IRONFLOW_MAX_REPEAT_ITERATIONS` and `MAX_BODY` already failed closed and are
unchanged.

Validation on 2026-10-28:

- Failing first: `malformed_ceilings_are_fatal_for_run_serve_and_validate` and
  `disableable_limits_reject_negative_values_and_toggles_reject_words` in
  `tests/test_runtime_limit_config.rs` failed before the change because `run`
  went on to open the store and `validate` to read the flow file; both pass
  after. They cover eight ceilings (`10MB`, `-1`, `0`, `1e6`, blank, `soon`,
  `many`, `0`) across `run`, `serve` and `validate`, three disableable limits
  with `-5`, `unlimited` and `25MB`, and the GC switch with `yes`.
  `documented_zero_disables_and_valid_overrides_are_honored` shows
  `IRONFLOW_LUA_MAX_MEMORY_BYTES=0` accepted and `IRONFLOW_MAX_FLOW_SOURCE_BYTES=16`
  reaching the flow-source check.
- Unit tests in `limits/env.rs`: ceilings accept ` 42 ` and reject `0`, `-1`,
  `10MB`, `1e6`, blank, `4.0` and `+4` (the last one surfaced that
  `u64::from_str` accepts a leading sign, so the parser now requires digits
  only); disableable limits accept `0`; toggles accept only `true`/`false`;
  every `IRONFLOW_*` name in the limits module tree is registered exactly once.
- `tests/zip_metadata/cli.rs` previously asserted that `0` and `invalid`
  values of `IRONFLOW_MAX_ZIP_METADATA_BYTES` silently restored the default;
  it now asserts the startup rejection. No other test depended on the old
  behaviour.
- Full default suite through `scripts/test_rust_targets.ts`: 20 targets,
  1,831 tests passed, 0 failed (1,824 before this change plus the seven new
  tests). `cargo fmt --all -- --check`, module-size policy (`limits.rs`
  stays under the 300-line target), `cargo clippy --all-targets -- -D warnings`
  with default features and with `postgres,redis`, `cargo test --doc`, and
  `bun test scripts/tests/*.test.ts` pass.
- Not run here: live Redis/PostgreSQL suites (storage code is untouched) and the
  release-build example loop.
