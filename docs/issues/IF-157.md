# IF-157 — DOCX importers lose RTL alignment and infer incompatible body/table defaults

## Trigger and confirmed mechanism

On 2026-10-26 the user reported that the generated multilingual DOCX was entirely
left-aligned in Codex Preview while the PDF looked correct. The DOCX emitted
`w:jc=start` on every paragraph. A browser reproduction using the installed
Codex app's unmodified `docx-preview-8513c2dacad2.js` asset (app version
26.1021.31345) confirmed that all 14 RTL paragraphs, including headings, list
items and table cells, computed to `text-align: left` despite `direction: rtl`.
The renderer maps unrecognized justification values, including start, to left.

Exporting a temporary PDF copy of the document the user opened in Apple Pages
showed that Pages already respected RTL alignment. It exposed two other importer
defects: absent default Normal styling caused body paragraphs to inherit heading
formatting, and missing table-grid/cell widths collapsed table columns to about
one character. LibreOffice had inferred acceptable defaults, so testing only
that renderer did not reveal the defects. PDF generation was unaffected.

## Implemented outcome

- Supply an explicit default Normal paragraph style and direction-specific body
  and heading styles with physical left/right alignment.
- For RTL paragraph alignment, emit OOXML AlternateContent: Office 2010-aware
  readers use logical start; simpler readers have physical right alignment in
  the fallback. Readers that skip AlternateContent can use the paragraph style.
  This preserves Word/LibreOffice's RTL behavior without making their mirrored
  interpretation of legacy right alignment move text to the left.
- Give code paragraphs explicit LTR direction and left alignment, including
  when the workflow forces RTL for ordinary paragraphs.
- Emit equal-width table grids, fixed table layout, and matching cell widths
  based on the configured page width and margins, rather than relying on imports
  to infer missing geometry.
- Update the Markdown generation guide, DOCX node page, and unreleased notes.

## Outcome and validation

- `test_markdown_docx_alignment` has three regressions: structured XML checks of
  logical/physical/style fallbacks across headings, body, lists and cells;
  forced LTR/RTL with LTR code; and grid/cell widths under A4/Letter/margins.
- All 15 tests across the alignment, multilingual, document and CLI/serve
  runtime integration targets passed after the final changes.
- `cargo clippy --all-targets -- -D warnings`, formatting, module-size policy,
  strict validation of the multilingual example, and diff whitespace passed.
- A real CLI run generated the final sample successfully. The installed Codex
  renderer, loaded unchanged into an isolated Playwright browser, reproduced the
  old failure and verified all 14 RTL paragraphs right-aligned after the fix.
  The app package itself was not modified. This tests its renderer, not its
  entire surrounding UI or an updated app version.
- Exported PDFs from Apple Pages and bundled LibreOffice were rendered and
  visually checked. Pages no longer inherited heading formatting into body
  text or collapsed the table. The user's original open document was preserved.
- DOCX still depends on viewer fonts and pagination. The tested Codex renderer
  does not mirror table column order for `w:bidiVisual`, although cell alignment
  is correct; Pages/LibreOffice do mirror it. The generator retains the standard
  table ordering property rather than reversing the stored cells for one viewer.
  No Microsoft Word or Google Docs runtime was available for live qualification.
- The subsequent full native integration gate also passed; IF-156 records its
  coverage. Stable publication and hosted acceptance are separate boundaries.
  The RTL PDF extraction follow-up is tracked in IF-156.
