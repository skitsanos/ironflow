# IF-231 — chrono and chrono-tz are reported as unmaintained

## Evidence and boundary

Found on 2026-11-17, when `cargo audit --deny warnings` in the integration
gate failed on two advisories that had not been in the advisory database
earlier the same day:

- RUSTSEC-2026-0543: `chrono` is unmaintained, all versions (locked: 0.4.45).
- RUSTSEC-2026-0555: `chrono-tz` is unmaintained (locked: 0.10.4).

Both are informational notices with no patched version. Neither names a
vulnerability. The advisories recommend `jiff` or `time`. Only the advisory
text was read; the upstream discussion it links was not.

`chrono` is a direct dependency used across scheduling, date formatting,
storage records and logging (83 source and test files), and `chrono-tz`
supplied named time zones for schedules only (`date_format` takes numeric
offsets and never used it). `chrono` also arrives
through `calamine`, `cron`, `lopdf` (its `chrono` feature) and `rmcp`, so it
stays in the dependency graph, and in the audit, even if IronFlow's own code
stops using it.

Exposure: none known today. The risk is that a future defect in date
parsing, time zone data or arithmetic is not fixed upstream. `chrono-tz`
embeds the IANA time zone database at build time, so zone rules stop
following new IANA releases once it stops publishing.

## Exceptions

Two reviewed exceptions were added to `.cargo/audit.toml` on 2026-11-17, with
the maintainer's approval, because no update can clear the warnings. Stage 1
retired the `chrono-tz` one. The policy test in
`scripts/tests/repository_policy.test.ts` allows exactly the `chrono` one
beside the SQLite one and fails when the crate leaves `Cargo.lock` while its
entry remains. `docs/SECURITY.md` (Dependency advisories) records
them.

## Stage 1: named time zones (done, 2026-11-17)

The maintainer chose `jiff`, migrated in stages, with `cron` kept as the
expression evaluator. Stage 1 removed `chrono-tz`.

- `src/scheduler/zone.rs` (`ScheduleZone`) resolves zones with `jiff` 1.0 and
  converts to `chrono` types at its edge. `timing.rs` still feeds `cron` naive
  local times and resolves them itself, with the same gap probe and
  earlier-instant rule. A timezone-aware evaluator was not adopted: it would
  emit both instances of a repeated hour.
- Zone data: the IANA database compiled into the binary (`jiff-tzdb`, release
  2026f), with `jiff`'s default features off so the host's zoneinfo, `TZ` and
  `TZDIR` are never read. Reasons: replicas compare claim keys and must agree
  on rules; Windows has no system database; the result is the same on every
  platform and in any image. Cost: about 207 KB of zone data in the binary
  (the `chrono-tz` tables it replaces are gone), and rule changes arrive only
  with an IronFlow release. The policy test pins the feature set.
- Names must match the database spelling exactly, as before. `jiff` looks
  names up without regard to case, so `ScheduleZone` rejects a name that is
  not returned unchanged, and rejects `Etc/Unknown`.
- RUSTSEC-2026-0555 is retired from `.cargo/audit.toml`; the policy test
  fails if `chrono-tz` returns to `Cargo.lock`.

### Parity evidence

`tests/test_schedule_zone_parity.rs` compares fired instants and claim keys
with `tests/scheduler/fixtures/zone_parity.txt`, recorded from the `chrono-tz`
implementation before the change (the first commit of this stage). It covers
gap coalescing, fold deduplication, IF-180 weekday numbering, day-field
union, 30- and 45-minute offsets, skipped days (Apia 2011, Kiritimati 1994,
Kwajalein 1993), direct resolution before 1970 and up to year 9999, the
instant-to-wall-clock conversion, and a sweep of 31 zones and six expressions
over 2012 to 2035. All 597 zone names `chrono-tz` accepted still load.

Differences found:

- `America/Havana`, 2026 and 2027 only. Data, not behaviour: 2026f has no
  transition between March 2026 and November 2027 where 2025b had two. The
  fixture was recorded again for those lines. This was read from the bundled
  data; the IANA announcement was not.
- After 2100 `chrono-tz` applied no daylight saving; `jiff` continues the
  rules. No schedule reaches those years, because `cron` enumerates 1970 to
  2099, and the recording stops at 2099 for zones with rules. A test states
  the new behaviour.

`test_schedule_zones.rs` pins the bundled release to 2026f, so a `jiff-tzdb`
update fails there first and the fixture is recorded again under review.

Breaking changes, library API only: `ScheduleConfig::timezone()` returns
`&ScheduleZone`; `resolve_local` and `claim_key` take `&ScheduleZone`;
`DueInstant::instant` is `DateTime<FixedOffset>`. Configuration, CLI and
stored claim keys are unchanged.

Validation (default features unless stated): `cargo fmt --check`, the
module-size gate, Clippy on all targets with default and
`postgres,redis` features, the `scheduler`, `scheduler_admission`, `serial`,
`cli`, `storage` and `examples` binaries, library tests, the policy tests,
`cargo audit --deny warnings` and the license and notices gates. No live
store, Windows or container run was made.

## Stage 2: the scheduler's own time types (done, 2026-11-18)

`chrono` is used in `src/scheduler/` only by `cron_boundary.rs`, which labels
a wall-clock time as UTC for `cron` and reads the match back. A policy test
fails if another scheduler module imports it. Elsewhere a wall-clock time is
`jiff::civil::DateTime` and an instant is `jiff::Timestamp` or
`jiff::ZonedDateTime`, so the two cannot be mixed. All arithmetic is
`jiff::SignedDuration`, an exact number of seconds: elapsed time on an
instant, a clock reading moved by that much on a wall-clock time. No calendar
unit is used, so nothing changes length across a daylight-saving change.
Claim keys are written out field by field instead of by a formatter.

### Evidence

- The stage 1 recording passes unchanged except two rows (below).
- `tests/test_schedule_time_edges.rs` was recorded from the `chrono`
  implementation in its own commit, then run against `jiff` with only its
  three time-building helpers changed: both window ends to the nanosecond,
  lateness as whole seconds (grace 300 still fires at 300.999 s, is late at
  301), the startup watermark's fraction, zero elapsed time, and the first
  and last years `cron` enumerates.
- `cron` 0.17 enumerates 1970 to 2100, measured; stage 1 said 2099. The
  stage 1 difference does include the year 2100: measured on 2026-11-18 with
  `chrono-tz` 0.10.4 and `jiff` 1.0 side by side (New York, Berlin, Sydney,
  January and July), the two agree through 2099, and from the summer of 2100
  `chrono-tz` applies standard time where `jiff` applies daylight time. A
  schedule that fires in a daylight-saving period of 2100 therefore runs one
  hour earlier in UTC than the old code computed. `jiff` follows the zone's
  rules; no action is taken. Accepted by the maintainer, with the year-9999
  limit below.
- Leap seconds: the scheduler parses no timestamps. `jiff` cannot represent
  one and `Timestamp::now()` never returns one, so the `chrono` leap-second
  form can no longer enter; the adapter reads such a value from `cron` as no
  match.

Differences found:

- `jiff::Timestamp` ends at 9999-12-30T22:00:00Z and starts at
  -9999-01-02T01:59:59Z (26 hours inside the civil range). `resolve_local`
  returns `None` beyond them, where `chrono` returned an instant. Two
  recorded year-9999 rows are listed as accepted in the parity test; the
  fixture is not re-recorded. No schedule reaches these years.
- Defect fixed in its own commit: a time with no instant because it is out
  of range was probed like a daylight-saving gap and resolved to the first
  representable instant, up to six hours away. Stage 1 had the same fault
  beyond the year 9999. Only a skipped time is probed now.

### Conversion edges (for stage 3)

No time value crosses out of the scheduler; these are the edges:

- Clock: `Timestamp::now()` in `runtime.rs`, twice. `Scheduler::new` and
  `evaluate` take the instant as an argument.
- Stores: `claim_schedule`, `schedule_run_recorded` and `record_schedule_run`
  receive the claim key as `&str` and a TTL as `u64` seconds. Stores stamp
  their own records.
- Engine: the executor receives the claim key; it becomes the
  `_schedule_instant` context value and the deterministic run id.
- Decisions and metrics: `Decision::key` (string), `Outcome::Late
  { lateness_seconds: i64 }`; metric labels carry the outcome only.
- Logs: keys, `lateness_seconds`, and `catch_up_from` and
  `previous_occurrence` as `YYYY-MM-DDTHH:MM` text.

Breaking changes, library API only: `Scheduler::new` and `evaluate` take
`jiff::Timestamp`; `CronSchedule::after` takes and yields
`jiff::civil::DateTime` by value; `due_instants`, `resolve_local`, `claim_key`
and `DueInstant::local` use `jiff::civil::DateTime`; `DueInstant::instant` and
the results of `resolve_local` and `ScheduleZone::earliest_instant` are
`jiff::ZonedDateTime`; `ScheduleZone::local_time` takes `jiff::Timestamp`.
Configuration, CLI, stored claim keys and records are unchanged.

Validation (default features unless stated): `cargo fmt --check`, the
module-size gate, Clippy on all targets with default and `postgres,redis`
features, the `scheduler`, `scheduler_admission`, `serial`, `cli`, `storage`,
`engine` and `examples` binaries, library tests, the policy tests,
`cargo audit --deny warnings`. No live store, Windows or container run.

## Stage 3: stored and published timestamps (done, 2026-11-18)

Outside the scheduler an instant is a `jiff::Timestamp`. `chrono` is imported
only by `scheduler/cron_boundary.rs` and the two `date_format` files; a
policy test scans `src/` for any other use. No stored or published form
changed. `jiff`'s defaults do differ (it writes `.12Z` where `chrono` wrote
`.120Z`, and `as_microsecond` rounds toward zero), so `src/util/timestamp.rs`
writes every form itself and `jiff`'s `serde` feature stays off: a timestamp
field without an explicit form does not compile.

### Inventory (forms before and after)

| Form | Where |
| --- | --- |
| `Z`, fraction of 0, 3, 6 or 9 digits (shortest exact) | serde: JSON store run and summary files (and the summary digest over them), Redis `info`, summary and event values, the Redis legacy-incarnation digest, API and SSE bodies, `list --format json`, `inspect`, run-list cursors |
| `+00:00`, same fraction rule | SQL event `timestamp` column, Lua `now_rfc3339()` |
| `Z`, always 9 digits | SQL run and task `started`, `finished` |
| integer microseconds, rounded down | SQL `started_micros`, `claimed_micros`, `run_micros`, retention cutoff; JSON catalog, delta and lease records; Redis ordered-catalog members (16 hex digits, sign bit flipped) |
| integer milliseconds, rounded down | Lua `now_unix_ms()`; task `duration_ms` is truncated elapsed time |
| `YYYY-MM-DD HH:MM:SS` UTC | `ironflow list` table |
| input only | `artifacts prune --before` (RFC 3339), embeddings `Retry-After` (HTTP date) |

No client time: SQL and Redis lease deadlines (database clock, Redis `TIME`),
metrics (monotonic durations), logs (`tracing`'s own clock), the embeddings
OAuth expiry (`Instant`). Only the one-time backfill of pre-sequence SQL
event rows orders by timestamp text; its bytes are unchanged.

### Evidence

`tests/storage/fixtures/timestamps/instants.tsv` holds 25 instants recorded
from `chrono` 0.4.45 with each form: every fraction width, trailing zeros,
both sides of 1970, sub-microsecond values before 1970, years 0000, 9999 and
below zero, and both ends of the `jiff` range. The golden tests were
committed and run against the `chrono` code first (SQLite, PostgreSQL and
Redis), then against `jiff` with only the instant constructor changed:

- exact JSON for `RunInfo`, `RunSummary`, `TaskState` and `RunEvent`, absent
  and `null` values, and every recorded text form read back;
- a JSON store directory written by the old code: records with their
  digests loaded, listed, and rewritten with the same bytes, and its catalog
  file decoded record by record;
- SQL (SQLite and PostgreSQL): written columns compared as text, rows
  inserted in each form and read, listing order, `started_micros` backfill,
  and the retention cutoff inside one microsecond before 1970;
- SQL events: column and payload bytes, replay, a column that spells the
  instant differently, and one that names another instant (corruption);
- Redis: records in the old form listed in order, read, and rewritten with
  the same bytes; ordered-member strings; events;
- cursor bytes, the `list` table, the Lua helpers, `Retry-After` dates.

The recording caught one library fault before it shipped:
`Timestamp::from_microsecond` refuses the fraction of the last representable
second, so microseconds are converted by hand.

### Differences (all need a record edited by hand)

- Range: `jiff` holds -9999-01-02T01:59:59Z to
  9999-12-30T22:00:00.999999999Z; `chrono` held years -262143 to 262142. A
  text or catalog value outside it is now corruption. Not fixable in `jiff`.
- Spellings only `chrono`'s lenient reader took are refused: surrounding
  spaces, a space before the offset, a one-digit hour, a tenth fraction digit.
  A leap second `:60` reads as `:59`, where `chrono` kept the extra second.
- Fixed: SQL timestamps before year 0000 were written as `-0001-...` and
  refused by the same version's reader. They load now.
- `jiff` also reads some ISO 8601 spellings `chrono` refused (no seconds,
  basic format, a bracketed zone). Nothing writes them.

Rolling upgrade: a new writer produces only bytes the old writer produced, so
an old replica reads and orders them as before, and the reverse holds for
every value a clock can produce. No migration.

Breaking changes, library API only: `started` and `finished` on `RunInfo`,
`RunSummary` and `TaskState`, `RunEvent::timestamp`, `RunCursor::started`,
`RunLease::at` and `expires_at`, `StateStore::prune_before` and
`reconcile_expired_run_leases` use `jiff::Timestamp`. `chrono` loses its
`serde` feature; `Cargo.lock` is unchanged.

Validation: `cargo fmt --check`; the module-size gate; Clippy on all targets
with default features, with `postgres,redis,cjk-fonts` and with no default
features; every test target through `scripts/test_rust_targets.ts` with
default features (20 targets) and with `postgres,redis,cjk-fonts` against
disposable PostgreSQL and Redis containers (23 targets, single-threaded, as
the integration gate runs them); doc tests; the policy tests;
`cargo audit --deny warnings`; the license and notices gates. No Windows,
container-image or deployed run.

## Remaining stage

- Stage 4: `date_format`, the `lopdf` `chrono` feature, and `chrono` through
  `calamine`, `cron` and `rmcp`.

## Required outcome and acceptance

- Decide the replacement for IronFlow's own time handling (`jiff` or `time`)
  and migrate the direct uses, with regressions for schedule evaluation
  across daylight-saving changes, stored timestamp formats (existing records
  must still load), and `date_format` parsing and output.
- Done in stage 1: remove `chrono-tz` and drop its exception.
- Drop the `chrono` exception when `calamine`, `cron`, `lopdf` and `rmcp` no
  longer resolve it, or when a maintained release line exists and the advisory
  is withdrawn.
- Review the `chrono` exception again by 2026-12-17 if it is still present.
