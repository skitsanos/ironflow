# IF-231 — chrono and chrono-tz are reported as unmaintained

## Evidence and boundary

Found on 2026-11-17, when `cargo audit --deny warnings` in the integration
gate failed on two advisories that had not been in the advisory database
earlier the same day:

- RUSTSEC-2026-0543: `chrono` is unmaintained, all versions (locked: 0.4.45).
- RUSTSEC-2026-0555: `chrono-tz` is unmaintained (locked: 0.10.4).

Both are informational notices with no patched version. Neither names a
vulnerability. The advisories recommend `jiff` or `time`. Only the advisory
text was read; the upstream discussion it links was not.

`chrono` is a direct dependency used across scheduling, date formatting,
storage records and logging (83 source and test files), and `chrono-tz`
supplied named time zones for schedules only (`date_format` takes numeric
offsets and never used it). `chrono` also arrives
through `calamine`, `cron`, `lopdf` (its `chrono` feature) and `rmcp`, so it
stays in the dependency graph, and in the audit, even if IronFlow's own code
stops using it.

Exposure: none known today. The risk is that a future defect in date
parsing, time zone data or arithmetic is not fixed upstream. `chrono-tz`
embeds the IANA time zone database at build time, so zone rules stop
following new IANA releases once it stops publishing.

## Exceptions

Two reviewed exceptions were added to `.cargo/audit.toml` on 2026-11-17, with
the maintainer's approval, because no update can clear the warnings. Stage 1
retired the `chrono-tz` one. The policy test in
`scripts/tests/repository_policy.test.ts` allows exactly the `chrono` one
beside the SQLite one and fails when the crate leaves `Cargo.lock` while its
entry remains. `docs/SECURITY.md` (Dependency advisories) records
them.

## Stage 1: named time zones (done, 2026-11-17)

The maintainer chose `jiff`, migrated in stages, with `cron` kept as the
expression evaluator. Stage 1 removed `chrono-tz`.

- `src/scheduler/zone.rs` (`ScheduleZone`) resolves zones with `jiff` 1.0 and
  converts to `chrono` types at its edge. `timing.rs` still feeds `cron` naive
  local times and resolves them itself, with the same gap probe and
  earlier-instant rule. A timezone-aware evaluator was not adopted: it would
  emit both instances of a repeated hour.
- Zone data: the IANA database compiled into the binary (`jiff-tzdb`, release
  2026f), with `jiff`'s default features off so the host's zoneinfo, `TZ` and
  `TZDIR` are never read. Reasons: replicas compare claim keys and must agree
  on rules; Windows has no system database; the result is the same on every
  platform and in any image. Cost: about 207 KB of zone data in the binary
  (the `chrono-tz` tables it replaces are gone), and rule changes arrive only
  with an IronFlow release. The policy test pins the feature set.
- Names must match the database spelling exactly, as before. `jiff` looks
  names up without regard to case, so `ScheduleZone` rejects a name that is
  not returned unchanged, and rejects `Etc/Unknown`.
- RUSTSEC-2026-0555 is retired from `.cargo/audit.toml`; the policy test
  fails if `chrono-tz` returns to `Cargo.lock`.

### Parity evidence

`tests/test_schedule_zone_parity.rs` compares fired instants and claim keys
with `tests/scheduler/fixtures/zone_parity.txt`, recorded from the `chrono-tz`
implementation before the change (the first commit of this stage). It covers
gap coalescing, fold deduplication, IF-180 weekday numbering, day-field
union, 30- and 45-minute offsets, skipped days (Apia 2011, Kiritimati 1994,
Kwajalein 1993), direct resolution before 1970 and up to year 9999, the
instant-to-wall-clock conversion, and a sweep of 31 zones and six expressions
over 2012 to 2035. All 597 zone names `chrono-tz` accepted still load.

Differences found:

- `America/Havana`, 2026 and 2027 only. Data, not behaviour: 2026f has no
  transition between March 2026 and November 2027 where 2025b had two. The
  fixture was recorded again for those lines. This was read from the bundled
  data; the IANA announcement was not.
- After 2100 `chrono-tz` applied no daylight saving; `jiff` continues the
  rules. No schedule reaches those years, because `cron` enumerates 1970 to
  2099, and the recording stops at 2099 for zones with rules. A test states
  the new behaviour.

`test_schedule_zones.rs` pins the bundled release to 2026f, so a `jiff-tzdb`
update fails there first and the fixture is recorded again under review.

Breaking changes, library API only: `ScheduleConfig::timezone()` returns
`&ScheduleZone`; `resolve_local` and `claim_key` take `&ScheduleZone`;
`DueInstant::instant` is `DateTime<FixedOffset>`. Configuration, CLI and
stored claim keys are unchanged.

Validation (default features unless stated): `cargo fmt --check`, the
module-size gate, Clippy on all targets with default and
`postgres,redis` features, the `scheduler`, `scheduler_admission`, `serial`,
`cli`, `storage` and `examples` binaries, library tests, the policy tests,
`cargo audit --deny warnings` and the license and notices gates. No live
store, Windows or container run was made.

## Remaining stages

- Direct `chrono` use in the scheduler seam, storage timestamps (existing
  records must still load), logging and `date_format`.
- The `lopdf` `chrono` feature, and `chrono` through `calamine`, `cron` and
  `rmcp`.

## Required outcome and acceptance

- Decide the replacement for IronFlow's own time handling (`jiff` or `time`)
  and migrate the direct uses, with regressions for schedule evaluation
  across daylight-saving changes, stored timestamp formats (existing records
  must still load), and `date_format` parsing and output.
- Done in stage 1: remove `chrono-tz` and drop its exception.
- Drop the `chrono` exception when `calamine`, `cron`, `lopdf` and `rmcp` no
  longer resolve it, or when a maintained release line exists and the advisory
  is withdrawn.
- Review the `chrono` exception again by 2026-12-17 if it is still present.
