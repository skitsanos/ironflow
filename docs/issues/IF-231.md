# IF-231 — chrono and chrono-tz are reported as unmaintained

## Evidence and boundary

Found on 2026-11-17, when `cargo audit --deny warnings` failed on two
advisories new that day: RUSTSEC-2026-0543 (`chrono`, all versions) and
RUSTSEC-2026-0555 (`chrono-tz`). Both are informational, name no
vulnerability and have no patched version; only the advisory text was read.
`chrono` was used in 83 source and test files and also arrived through
`calamine`, `cron`, `lopdf` and `rmcp`.

The maintainer chose `jiff` 1.0, in stages, keeping `cron` as the expression
evaluator. Each stage first committed tests recorded from the `chrono`
implementation, then migrated.

## Outcome and validation

1. **Named zones.** `chrono-tz` is removed and its exception retired.
   Schedule zones come from the IANA database compiled into the binary
   (release 2026f), never from the host. Fire instants and claim keys were
   compared over 31 zones for 2012 to 2035 and every edge case on record.
2. **Scheduler.** Wall-clock times, instants and durations are `jiff` types.
   One adapter, `scheduler/cron_boundary.rs`, exchanges wall-clock values
   with `cron`.
3. **Stored and published timestamps.** `util/timestamp.rs` writes every
   form byte for byte as before, on all four stores, so replicas on both
   implementations share a store with no migration.
4. **`date_format` and the remaining edges.** The node reads its own strftime
   dialect (`nodes/utility/strftime/`), because `jiff`'s differs in
   specifiers, padding, accepted spellings and error text. A recording of
   2638 cases is compared on every run; 9.3 million generated cases, run
   once through both implementations and not kept, differed only for years
   outside the new range. `extract_xlsx` converts date cells itself, so
   `calamine` and `lopdf` no longer enable `chrono`.

Accepted differences:

- `America/Havana`, 1 November 2026 to 14 March 2027: zone data 2026f keeps
  daylight time, so schedules fire one hour earlier in UTC.
- A schedule firing in a daylight-saving period of the year 2100 runs one
  hour earlier in UTC; `chrono-tz` stopped applying the rules after 2099.
- Dates are held for the years -9999 to 9999, where `chrono` held -262143 to
  262142. A stored timestamp outside them is corruption, and `date_format`
  fails the step. The golden test lists the 81 recorded cases affected.
- Timestamp spellings only the lenient `chrono` reader took are refused in
  stored records and `artifacts prune --before`: surrounding spaces, a
  one-digit hour, a tenth fraction digit.

Defects found and fixed on the way: an out-of-range wall-clock time resolved
as a daylight-saving gap; SQL rows before the year 0000 that could not be
read back; [IF-232](IF-232.md); [IF-233](IF-233.md); [IF-234](IF-234.md).

Breaking changes, library API only: the scheduler's public time types and
every timestamp on `RunInfo`, `RunSummary`, `TaskState`, `RunEvent`,
`RunCursor`, `RunLease` and `StateStore` are `jiff` types;
`docs/releases/next.md` lists each. Configuration, CLI, flows, stored records
and claim keys are unchanged.

### Boundary: the remaining exception

`rmcp` 3.12 moved to `jiff`. `chrono` stays in `Cargo.lock` through
`cron` and IronFlow's adapter for it, which enables none of its features. The
acceptance items for IronFlow's own code are met; the item "drop the
exception" is not, and cannot be while those crates resolve it. One reviewed
exception for RUSTSEC-2026-0543 therefore remains in `.cargo/audit.toml`,
reviewed on 2026-11-18 and due again by 2026-12-17, with its exposure and
exit in `docs/SECURITY.md`. The policy test fails if the entry outlives the
crate, if any other crate resolves `chrono`, if IronFlow enables a `chrono`
feature, or if a module other than the adapter imports it. Replacing `cron`
with an evaluator that does not use `chrono` was not attempted.

### Validation

Stages 1 to 3 were validated when they landed, the third with every test
target also on `postgres,redis,cjk-fonts` against disposable PostgreSQL and
Redis containers. Stage 4, on default features
unless stated: `cargo fmt --check`; the module-size gate; Clippy on all
targets, also with `postgres,redis`; all 20 test targets through
`scripts/test_rust_targets.ts`; the Bun and Python policy tests; the license
and notices gates; validation and a run of `examples/20-date/date_format.lua`;
the registry check. Feature-gated tests, live stores, Windows and the
container image were not run for stage 4.

`cargo audit --deny warnings` passes with the one `chrono` exception, after
the `lettre` update recorded in [IF-235](IF-235.md).
