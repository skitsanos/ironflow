# IF-194 — pdf_to_image and pdf_thumbnail can bind Pdfium only once per process

## Evidence and boundary

Review of `develop` at 1.21.1-dev.1 on 2026-11-12, by reading IronFlow and
`pdfium-render` 0.9.4. Not executed: no Pdfium build compatible with 0.9.4
was available, so the failure below is derived from the two code paths.

- Each execution calls `load_pdfium()` and then `Pdfium::new(bindings)`
  (`src/nodes/image/pdf_render/worker.rs:33-34, 79-80`).
- `load_pdfium` (`src/nodes/image/common.rs:74-89`) calls
  `Pdfium::bind_to_library` or `bind_to_system_library` every time.
- In `pdfium-render` 0.9.4, `Pdfium::new` stores the bindings in a
  process-global `OnceCell` (`pdfium.rs:70, 213`), and every `bind_to_*`
  function returns `Err(PdfiumLibraryBindingsAlreadyInitialized)` once that
  cell is set (`pdfium.rs:107-189`).
- Expected result: the first render in a process succeeds. Every later
  render, in the same flow or in any later request to `ironflow serve`,
  fails with `Failed to load pdfium ... PdfiumLibraryBindingsAlreadyInitialized`.
- The suite cannot catch this: `tests/test_pdf_image_nodes.rs:46-49` treats
  any error containing "pdfium" or "failed to load" as a missing-capability
  skip, and CI has no Pdfium library.

Boundary: affects only builds with the default `pdf-render` feature and a
Pdfium library installed. The dependency moved from the 0.8 line to 0.9
without a change to `load_pdfium`.

## Outcome and validation

Resolved on 2026-11-15, after the maintainer decided that day to move to a
pure-Rust renderer if a spike passed.

**Spike** (`hayro` 0.9.0, MIT or Apache-2.0, no unsafe code; executed with an
optimized build on one machine unless marked as read).

- Fidelity: `markdown_to_pdf` output (Latin, a 61-row table, an image,
  Ukrainian, CJK, Hebrew, Arabic) and the sample fixture rendered at 72, 150
  and 300 DPI with the expected dimensions; checked by eye. Read only: JPEG
  2000, JBIG2 and CCITT are decoded; knockout and non-isolated groups and
  color-key masks are not.
- Gates: audit and license policy pass (589 packages, no exception).
- Size: stripped release binary 52,662,176 to 55,851,712 bytes (+6.1%).
- Cost: a 24.6-megapixel A4 page took at most 29 ms and 122 MB; seven A4
  pages at 300 DPI through the node took 0.97 s and 71 MB.
- Malformed input: 20,000 seeded mutations of the fixture, no panic. But
  unguarded the rasterizer never finished a 5 KiB file of 30 nested forms,
  used 1.1 GB on a 1 MiB stream bomb, and drew truncated files as blank
  pages. It has no cancellation hook.

**Outcome.**

- Both nodes use the built-in renderer in every default build; parameters,
  outputs and the DPI, page and pixel limits are unchanged.
- The gaps are closed outside the rasterizer: the shared loading policy
  runs first; streams a page can reach are decoded under
  `IRONFLOW_MAX_PDF_DECOMPRESSED_STREAM_BYTES`; a metering pass counts
  drawing operations against the new `IRONFLOW_MAX_PDF_RENDER_OPERATIONS`
  (1,000,000), refuses images above `IRONFLOW_MAX_IMAGE_PIXELS`, and checks
  cancellation every 256 operations. The nested-forms file now fails in
  0.63 s at 20 MB. Drawing an admitted page is not interruptible.
- Pdfium is removed, by the maintainer's choice on 2026-11-15: no library
  compatible with `pdfium-render` 0.9 was available, CI provisions none, and
  the limits above would not apply to it. The binding, `PDFIUM_LIB_PATH` and
  the per-render bind that caused this finding no longer exist.

**Validation.**

- Executed: `cargo test --test documents test_pdf_render_nodes::` (three
  renders in one process, ranges, thumbnail sizes, every limit, hostile
  pages, step timeout and run deadline, malformed and encrypted input);
  `test_pdf_load_safety::` extended to both nodes; the `serial` node tests
  with their skip removed; `cargo test --test examples`, where both examples
  joined the clean-checkout matrix; Clippy for default features.
- Not executed: the original two-render failure, on any tree. It remains
  derived from the two code paths and is closed by removing them.
