# IF-110 — Image resize omits a potentially dominant intermediate allocation

## Required outcome and acceptance

- Account for actual resampling peak memory before entering the decoder/resizer, including source_width * target_height float intermediates and checked arithmetic.
- Reject a bounded crossed-dimension fixture under a deliberately low working-memory ceiling while admitting an ordinary image within budget.
- Keep aspect-ratio, output dimensions, cancellation, and artifact behavior intact; document what the allocation limit covers.

## Evidence and cause

Fresh review on 2026-09-12, finding R05. See
[AUDIT_2026-09-12.md](./AUDIT_2026-09-12.md) for the reviewed candidate,
evidence boundaries, and complete finding-to-issue mapping.

[Source: image_basic/resize.rs:65](../../src/nodes/image/image_basic/resize.rs).

The budget checks retained source plus final output, but image 0.25.10's Lanczos resize first allocates an Rgba32F intermediate with dimensions `source_width * target_height`. A bounded 100x1 to 1x100 probe succeeded under a 1024-byte working-allocation limit even though that intermediate alone is 160,000 bytes. Scaling crossed dimensions can greatly exceed the configured memory ceiling while source and destination stay small. No large-allocation or crash probe was run.

Fix and coverage: budget the actual resampling peak, including the float intermediate, or use a resampling strategy with a bounded intermediate. Evidence: extraction probe `resize`, plus the locked image crate's `imageops/sample.rs` implementation.

## Outcome and validation

Resolved locally on 2026-09-13, after PDF-fix commit `a813d26`. The shared image
loader now accepts an admission callback after header inspection, before
`DynamicImage::from_decoder` materializes pixels. Resize uses that callback
and rechecks the decoded dimensions, color type, and byte length before calling
Lanczos3. File and artifact inputs retain the same opened/verified handle;
Base64 inputs use the same admission path.

The resize budget models the locked image 0.25.10 sampler: retained source plus
the `source_width * target_height * 16` byte float intermediate, then the larger
of vertical filter scratch or final output plus horizontal filter scratch.
Scratch allows a full source axis of f32 weights, rounded vector capacity and
overlapping storage during growth. Same-size copies admit source plus output
without resampling buffers. All component sizes and sums use checked arithmetic;
individual buffers must also fit the platform's addressable allocation size.
Re-audit this estimate when the dependency's sampling implementation changes.

The new CLI regression failed before the fix: a 100x1 RGB PPM resized to 1x100
reported success under a 1 KiB ceiling. After the fix it rejects path, Base64,
and verified-artifact inputs and leaves an existing output untouched. A valid
PPM header with missing pixels produces the resize admission error under the
small budget but the decoder error under a sufficient budget, proving the
check precedes pixel decoding. A sufficient budget still admits the complete
crossed-dimension fixture. Ordinary width-only, height-only, exact-size, and
same-size requests preserve expected dimensions and pixel values; an expired
deadline produces no output.

  crossed dimensions, vertical scratch, same-size copies, all ten dynamic-image
  color types, overflow/addressability, aspect ratio, and output pixel limits.
- `cargo test --lib util::execution`: one tracked-worker lifecycle test passed.
- `cargo test --test test_image_util_nodes --test test_artifact_nodes --test

  including five new resize regressions with isolated CLI processes and stores.
- `cargo test --test test_pdf_image_nodes image_ -- --skip pdf_to_image`: six
  image transform/conversion tests passed. No native PDFium claim is made.
- `cargo clippy --all-targets -- -D warnings`, `cargo fmt --all -- --check`,
  module-size policy, `cargo audit --deny warnings`, issue-registry validation,
  and `git diff --check`: passed.
- The updated `examples/08-extraction/image_resize.lua` validated and executed
  in an isolated temporary working directory/store with a cleared environment,
  producing a 140x105 PNG.

The 50 focused tests are local evidence, not a new full integration gate,
feature-backend test, or deployment result. This estimate covers known image
buffers, not total process memory: codec/header internals, encoding scratch,
encoded/Base64 inputs, workflow context, allocator overhead, and concurrent
tasks remain outside it. Opaque decoding/resampling/encoding still observes
cancellation only between operations. Node documentation, CLI limit reference,
and the Lua example describe these boundaries.
