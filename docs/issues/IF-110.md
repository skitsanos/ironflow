# IF-110 — Image resize omits a potentially dominant intermediate allocation

## Required outcome and acceptance

- Account for actual resampling peak memory before entering the decoder/resizer, including source_width * target_height float intermediates and checked arithmetic.
- Reject a bounded crossed-dimension fixture under a deliberately low working-memory ceiling while admitting an ordinary image within budget.
- Keep aspect-ratio, output dimensions, cancellation, and artifact behavior intact; document what the allocation limit covers.

## Evidence and cause

Fresh review on 2026-09-12, finding R05. See
[AUDIT_2026-09-12.md](./AUDIT_2026-09-12.md) for the reviewed candidate,
evidence boundaries, and complete finding-to-issue mapping.

[Source: image_basic/resize.rs:65](../../src/nodes/image/image_basic/resize.rs).

The budget checks retained source plus final output, but image 0.25.10's Lanczos resize first allocates an Rgba32F intermediate with dimensions `source_width * target_height`. A bounded 100x1 to 1x100 probe succeeded under a 1024-byte working-allocation limit even though that intermediate alone is 160,000 bytes. Scaling crossed dimensions can greatly exceed the configured memory ceiling while source and destination stay small. No large-allocation or crash probe was run.

Fix and coverage: budget the actual resampling peak, including the float intermediate, or use a resampling strategy with a bounded intermediate. Evidence: extraction probe `resize`, plus the locked image crate's `imageops/sample.rs` implementation.

## Progress
