# IF-195 — date_format ignores input offsets; date_format and html_sanitize panics stall the run

## Evidence and boundary

Review of `develop` at 1.21.1-dev.1 on 2026-11-12, reproduced with a local
optimized build.

1. Wrong instant. `date_format({ input = "2024-06-15 10:30:00 +0200",
   input_format = "%Y-%m-%d %H:%M:%S %z" })` returns `10:30:00Z` and unix
   `1718447400`. The same instant given as RFC 3339
   (`2024-06-15T10:30:00+02:00`) returns `08:30:00Z` and `1718440200`. With
   an explicit `input_format`, the node parses through
   `NaiveDateTime::parse_from_str`, which accepts `%z` and discards it
   (`src/nodes/utility/date.rs:109-124`).
2. Panic on `output_format`. `output_format = "%Y-%m-%d %H:%i"` panics in
   chrono's formatter (`date.rs:136-143`). The run ends `stalled: execution
   failed: workflow execution panicked`, and the step's `on_error` handler
   does not run. Unknown specifiers and a trailing `%` behave the same.
3. Panic in `html_sanitize`. `allowed_tags = { "p", "style" }` panics inside
   ammonia (`` `style` appears in `clean_content_tags` and in `tags` ``),
   with the same stalled run (`src/nodes/utility/html_sanitize.rs:40-58`).
   `script` behaves the same by reading.

By reading: `allowed_tags = {}` converts to a JSON object, fails
`as_array()`, and falls back to ammonia's default allow-list instead of
stripping all tags. `docs/nodes/date_format.md` says `timezone` defaults to
UTC, but without it an RFC 3339 input keeps its own offset.

Boundary: items 2 and 3 are contained by the coordinator's panic handling,
so the process survives, but a bad node parameter becomes a run-level
infrastructure failure that bypasses retries and `on_error`. Format strings
and tag lists can come from interpolated context.

## Required outcome and acceptance

- When the input format carries an offset or zone specifier, parse with an
  offset-aware parser and convert; reject formats whose offset would be
  ignored.
- Validate `output_format` items before formatting and return a node error.
- Remove or reject `script` and `style` in `allowed_tags`; treat a present
  non-array value as an error and an empty list as "no tags".
- Regressions for each case, asserting a step failure that `on_error` can
  handle.
- Correct the `timezone` default wording.

## Outcome and validation

Resolved on 2026-11-13.

- **Offsets.** `input_format` is parsed once into chrono's `Parsed`
  (`src/nodes/utility/date_input.rs`). A parsed offset (`%z`, `%:z`, `%#z`,
  `%+`) is applied and kept, as for an RFC 3339 input. Without one the value
  is UTC as before. chrono skips a `%Z` name unread, so `UTC`, `GMT`, `UT`,
  `Z` or no name stay UTC and any other name fails the step, unless a numeric
  offset is also parsed.
- **`output_format`.** Items are validated with `StrftimeItems::parse` and
  written with `write!`, never `to_string()`. That covers unknown
  specifiers, a trailing `%`, bad modifiers and widths (`%#m`, `%03d`), and
  `%#z`, which is a valid item that only parses. Locale specifiers (`%c`,
  `%x`, `%X`, `%r`) are fixed strings because `unstable-locales` is off.
- **`html_sanitize`.** The node sets only tags, comments and `link_rel`, so
  of the assertions in ammonia 4.2.5's `clean_dom` only "tag in
  `clean_content_tags`" is reachable. Such tags are rejected against the
  builder's own set (`script`, `style`). An empty list or empty Lua table
  allows no tags; any other non-list value, or a non-string entry, is an
  error.
- **Same class, fixed here.** A `timezone` such as `+999999999:00`
  overflowed `h * 3600` (panic in debug builds, wrap in release); it is now
  checked. An OAuth token response with a huge `expires_in` overflowed
  `Instant + Duration` in `src/nodes/ai/embeddings/oauth.rs` (by reading);
  such a token now expires at once.
- **Contract boundary.** Changed results: offset inputs give a different,
  correct instant and keep their offset; non-UTC `%Z` names, `allowed_tags`
  that is not a list of strings, and `script`/`style` now fail the step;
  `allowed_tags = {}` strips every tag instead of using the default list.
  Unchanged: auto-detected inputs, naive formats, `%s`, valid output
  specifiers, and lists of ordinary tags. Coordinator panic handling is
  untouched. `link_rel` is still neither interpolated nor type-checked.

Evidence, debug build:

- Before, with `ironflow run`: item 1 gave `10:30:00Z` / `1718447400`
  against `08:30:00Z` / `1718440200` for RFC 3339; `%H:%i`, a trailing `%`,
  and `allowed_tags` with `style` or `script` each ended `stalled:
  execution failed: workflow execution panicked` with the handler not run.
  `allowed_tags = {}` and `allowed_tags = "p"` returned the default-list
  output, and RFC 3339 input without `timezone` kept `+02:00`.
- Before, tests: 13 of the 15 added tests failed on the unfixed source; the
  two that passed pin unchanged behavior.
- After: the same flows give `08:30:00Z` / `1718440200`, and each panic case
  ends `success` with the step failed and its `on_error` handler run.
  Passing: library 734 (1 ignored), `nodes` 280, `engine` 304, `examples`
  11, `nodes_network` 144, `serial` 191 single-threaded; both examples
  validate and run; formatting, module size and
  `cargo clippy --all-targets -- -D warnings` pass.
- Not run: release builds, and a live OAuth endpoint (unit test only).

Audit of other nodes for user values reaching a panicking call, by reading
only: durations, chunk sizes, concurrency, slicing, image and PDF
parameters, header, CSV and mail builders are guarded. Open, not fixed:
`ai_chunk_semantic` accepts unbounded `sg_window` and `poly_order`, a
suspected CPU cost and not a panic; comrak and htmd internals and step-level
engine options were not read.
