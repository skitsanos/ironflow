# IF-162 — One integration test binary per test file drives disk and CI compensation

## Evidence and boundary

Audit of `develop` at 1.20.1-dev.6 on 2026-10-28.

- `cargo metadata` reports 177 `test` targets plus the lib, bin and example
  (180 selections). `tests/` holds 1,371 test functions, fewer than eight per
  binary on average; many binaries hold one to three tests.
- Every test binary links the whole `ironflow` library and its 571 reachable
  crates (AWS SDK, pdfium-render, parley/krilla, image, mlua, sqlx,
  tree-sitter, rmcp).
- Compensation that exists only because of this layout:
  `scripts/test_rust_targets.ts` runs batches of eight targets (23 `cargo test`
  invocations per suite) and deletes each batch's executables;
  `scripts/integration_gate.sh` exports `CARGO_INCREMENTAL=0` and runs
  `cargo clean --package ironflow` before, between and after phases;
  `.github/workflows/ci.yml` sets `CARGO_BUILD_JOBS=2`, `line-tables-only`
  debug info and `cache-targets: false` on every `Swatinem/rust-cache` step so
  no target artifacts are cached; `AGENTS.md` documents reclaiming linked test
  executables to avoid "tens of gigabytes"; `scripts/tests/rust_targets.test.ts`,
  `integration_cleanup.test.ts`, `ci_resources.test.ts` and parts of
  `repository_policy.test.ts` test that machinery.
- Measured cost (CI run 40705138098 on `develop`, 2026-10-28): Clippy and
  tests 11.5 min, feature job 12.8 min with `--test-threads=1` over every
  target, macOS 17.1 min; 51.7 runner-minutes and about 17 min wall. A
  default debug build's `target/` directory is about 12 GB.

Boundary: on macOS the Apple linker leaves DWARF in object files, so a linked
test binary (`test_types`) is about 3.3 MB there; the executable bloat is a
Linux property (CI runners and containers). Test coverage itself is good; the
finding is layout and its downstream cost.

Additional evidence, 2026-10-28, during IF-161 validation: a plain
`cargo test --all-targets` with default incremental settings grew the
`target/` directory from about 12 GB to 38 GB (29 GB under `deps`, 5 GB under
`incremental`) and failed while linking six test binaries once the disk
filled. `cargo clean --package ironflow` afterwards reclaimed about 27 GB.
The per-binary object and incremental artifacts, not only the Linux
executables, scale with the 177 targets.

## Required outcome and acceptance

- Consolidate `tests/` into a bounded set of binaries (target: at most ten),
  for example `tests/engine/main.rs`, `tests/storage/main.rs`,
  `tests/nodes_*/main.rs`, `tests/api/main.rs`, `tests/cli/main.rs` and
  `tests/examples/main.rs`, each including the existing files as modules.
  Keep `tests/support` shared. Keep storage and TLS tests in their own
  binaries so the feature job can run only those.
- The test function count must not decrease, test names stay greppable, and
  `cargo test --test <area>` selects one area.
- Afterwards: delete or reduce `scripts/test_rust_targets.ts` to a thin
  wrapper, drop the repeated `cargo clean` phases and the `CARGO_BUILD_JOBS=2`
  throttle, re-enable target caching in CI, and update `AGENTS.md`, the
  validation docs and the script tests.
- Resolution evidence: before/after `cargo metadata` target counts, CI job
  timings over at least three `develop` pushes, and peak `target/` size on a
  Linux runner.

## Outcome and validation

Resolved on 2026-10-28 on branch `fix/if-162-test-binaries` at 1.20.1-dev.8.

Outcome:

- `Cargo.toml` sets `autotests = false` and declares 20 test targets. Twelve
  area binaries (`api`, `cli`, `examples`, `engine`, `scheduler`, `storage`,
  `storage_postgres`, `storage_redis`, `nodes`, `nodes_network`, `documents`,
  `serial`) have a `tests/<area>/main.rs` root that includes the unchanged
  `tests/test_*.rs` files as `#[path]` modules; nested `#[path]` includes such
  as `support/*.rs` and the fixture directories resolve relative to the test
  file and needed no change. Eight single-file binaries keep their own
  process: `scheduler_admission`, `limits_defaults`, `conversion_limits_env`
  and `flow_load_admission` configure a process-wide `OnceLock` from the
  environment before anything else reads it; `library_tls_boundaries`
  asserts that no earlier test installed the Rustls provider; and
  `extract_execution` and `schema_execution` install a process-wide tracing
  subscriber whose gate layer holds every worker of its kind in the process
  (sharing a binary made `extract_execution` time out while other
  extractors were held); and `http_proxy_modes` sets proxy variables that
  the process-wide `LazyLock` HTTP clients in `transport.rs` capture only
  on first use, so it failed once an earlier HTTP test had built them. No
  test file moved and no test function changed.
  Three one-line source edits: `test_scheduler_decisions.rs` reaches its
  shadowed helper through `self::` instead of `crate::`,
  `redis_lease_atomicity/support.rs` imports `super::redis_support`, and
  the serve-backed case in `test_markdown_document_runtime.rs` bounds each
  HTTP request at 15 s instead of 2 s because it now shares a process with
  the PDF and PPTX cases that load the host.
- `serial` holds the 33 files that set or clear process environment variables
  (`IRONFLOW_*`, provider keys). Concurrent `setenv`/`getenv` is undefined
  behaviour, so the binary runs with `--test-threads=1`; its
  `single_threaded_harness` test fails fast when the flag is missing, and
  `scripts/test_rust_targets.ts` always supplies it. Roots whose files
  include the same shared support or fixture module more than once allow
  `clippy::duplicate_mod`; each copy stays private to its module, as it
  was when every file was a crate.
- `storage_postgres`, `storage_redis` and `library_tls_boundaries` declare
  `required-features`, so the default build skips them at target level and the
  runner reports them as feature-gated.
- `scripts/test_rust_targets.ts` keeps metadata-driven selection, the feature
  closure and executable reclamation, and replaces the batches of eight with
  two Cargo invocations: every parallel-safe target in one
  `cargo test --no-fail-fast`, then `serial` with `--test-threads=1`
  (`invocations()`, `SINGLE_THREADED`).
- `.github/workflows/ci.yml` drops `CARGO_BUILD_JOBS=2` from both Rust jobs and
  `scripts/integration_gate.sh` drops the two mid-gate
  `cargo clean --package ironflow` phases; the pre-run prune and the exit-trap
  clean remain. `cache-targets: false` stays: the four Rust jobs would each
  save a multi-gigabyte dependency artifact set against the repository's
  10 GB Actions cache budget, and the cost this finding targeted was the
  per-file executables, which are gone.
- Guards: `scripts/tests/test_layout.test.ts` asserts that autodiscovery is
  off, that every `tests/test_*.rs` belongs to exactly one binary, that
  feature-gated files live in binaries requiring the feature, that
  environment-mutating files are in `serial` or alone, and that the runner
  hands `serial` the single-thread flag. `ci_resources.test.ts` asserts the
  throttle is gone and `repository_policy.test.ts` the gate's clean
  structure. `AGENTS.md` records the rule for placing new test files and
  `README.md` mentions the area binaries.

Contract boundary: test names stay greppable as `<module>::<test>`;
`cargo test --test <area>` selects an area and `cargo test --test <area>
test_x::` one file. The feature job still runs the whole suite with
`--test-threads=1`, which [IF-166](IF-166.md) narrows. Running
`cargo test --test serial` without the flag fails on the guard instead of
racing. The release workflow, the TLS gate and the Python module-size policy
are untouched. The original acceptance asked for at most ten binaries; the
eight process-isolated files are each justified by a process-wide assumption
named in the manifest, so the result is 20 test targets instead of 177.

Validation on 2026-10-28:

- `cargo metadata` target counts: before, 177 `test` targets plus lib, bin and
  example (180 selections); after, 20 `test` targets plus lib, bin and example
  (23 selections, 20 built without optional features).
- Default suite through the rewritten runner: the parallel invocation ran 19
  targets and passed 1,639 tests (lib 568, api 52, cli 84, documents 113,
  engine 271, examples 10, nodes 247, nodes_network 123, scheduler 73,
  storage 85, the example 3, and the single-file binaries), then `serial`
  passed 184 tests with `--test-threads=1` and `http_proxy_modes` passed
  alone. 1,824 tests in total against 1,823 before the change; the one
  addition is the `single_threaded_harness` guard. `cargo test --test serial
  single_threaded_harness` without the flag fails with the documented message.
- Process-isolation evidence: with `extract_execution` inside `documents`,
  its cancellation case timed out while the gate layer held other tests'
  extractors, and the serve-backed document case hit its 2 s request
  deadline under the shared load; with `http_proxy_modes` inside `serial`,
  the system-proxy assertion saw `via: target` because an earlier test had
  built the `LazyLock` client. All three pass in the final layout.
- Feature-enabled, against disposable Redis and PostgreSQL containers with
  `--features postgres,redis -- --test-threads=1`: `cli` 89, `scheduler` 78,
  `storage` 101, `storage_postgres` 6, `storage_redis` 85 and
  `library_tls_boundaries` 2 passed (361 tests, 0 failed); the containers
  were removed afterwards.
- Gates: `cargo fmt --all -- --check`; `cargo clippy --all-targets
  -- -D warnings` with default features and with `postgres,redis`
  (`clippy::duplicate_mod` surfaced the shared support copies before the
  scoped allow); `cargo check --all-targets` with `postgres` alone and with
  `redis` alone; `bun test scripts/tests/*.test.ts` (87 pass, including the
  five new layout and runner tests); Python hook and script tests (16 and
  16); `actionlint`; shell syntax of the gate and hooks; issue registry
  check.
- Not run here: the whole suite under `--features postgres,redis`, the TLS
  gate script and the release-build Lua loop, none of whose inputs changed.
  The CI timings over several `develop` pushes and the Linux runner's peak
  `target/` size remain to be read from the workflow runs that follow this
  change; the pull request's run gives the first data point.
