# IF-222 — Document extraction fidelity follow-ups for DOCX, PPTX and PDF metadata

## Evidence and boundary

Recorded on 2026-11-13 from the IF-193 fix, by reading. On 2026-11-15 items
(b) to (e) were each reproduced by a failing regression before the fix (14
new node tests failed on the unfixed sources). (f) was run with the two
authoring tools available without a GUI session: pandoc 3.14 (PPTX and DOCX
from Markdown) and macOS `textutil` (DOCX from HTML). No office suite was
available, so (f) stays open in part.

- (a) Fixed under IF-193 on 2026-11-14.
- (b) Fixed. A comment range around or inside a text box anchored the box
  text twice (`ANCHOREDANCHORED`), and a range that only an `mc:Fallback`
  declared failed the step. The anchor collector skips fallback content as
  the block builder does.
- (c) Fixed. A run that is bold through its style was reported as plain.
  `word/styles.xml` is parsed under the existing budgets: each `w:basedOn`
  chain is rolled up (a cycle ends it), paragraph and character style
  results are combined by exclusive or, a toggle that the document defaults
  turn on stays on, and direct formatting sets the state. The rule was
  checked against the published `w:b` definition, not memory. Decisions: a
  Markdown heading does not repeat the emphasis of its own style (`# Title`,
  not `# **Title**`) while JSON reports the resolved flags; table styles,
  and `underline`, `color` and `highlight` (not toggles), are not resolved.
- (d) Fixed in both nodes. A UTF-16LE mark gave `ÿþ` and mis-decoded text, a
  language tag in a PDFDocEncoding string gave `˙de˙Größe`, and a tag stored
  as raw code bytes in a UTF-16 string gave `敮Packed`.
- (e) Fixed. `a:br` joined the text on both sides (`line oneline two`, also
  seen on the pandoc deck). It is a newline in slide paragraphs and notes,
  and a space in a table cell and the title. `extract_word` reads no
  DrawingML text; `w:br` in a text box already broke the line (pinned).
- Found on the way, each fixed with a failing-first regression: paragraphs
  of a PPTX table cell were joined without a separator (`firstsecond`), and
  a paragraph with `a:buNone` was reported as a list item, which rendered
  the plain text of the pandoc deck as bullets.
- (f) Partly verified. pandoc deck: titles, bullets and speaker notes
  extract correctly; its notes part has the slide-image, body and
  slide-number placeholders and the `a:fld` slide number that IF-193
  assumed, and that XML is now a verbatim regression. pandoc document:
  headings, direct and style-based formatting, a table, a comment with its
  anchored text, and a tracked insertion and deletion extract correctly.
  `textutil` document: direct formatting and `w:br` extract correctly.
  Neither tool writes text boxes, PPTX comments, tracked formatting changes
  (`w:rPrChange`), or header, date and footer notes placeholders; those
  still rest on hand-built fixtures. On the maintainer's decision the pandoc
  deck and document are committed with their Markdown sources in the CC0
  set under `examples/fixtures/` (its size cap raised from 100 to 128 KiB;
  the packages embed pandoc's reference templates) and are extracted by
  `test_tool_authored_documents`.

Validation, default features: `documents` 201 passed (3 ignored), `cli` 108,
`examples` 11, `extract_execution` 2, the extraction modules of `serial`
single-threaded (with a `word/styles.xml` budget case) and of `nodes`,
library extraction and PDF Info unit tests; the three changed examples
validate; formatting, module-size check and
`cargo clippy --all-targets -- -D warnings` clean. Not run: the integration
gate and feature-enabled suites.

## Required outcome and acceptance

- (f), remainder: run `extract_word` and `extract_pptx` on files saved by an
  office suite that contain a text box, comments, a tracked formatting
  change and a notes page with header, date and footer; record the result
  and fix what differs.
