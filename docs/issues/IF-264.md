# IF-264 — A UTF-8 response header value is returned as Base64 instead of a string

## Evidence and boundary

Since [IF-258](IF-258.md), `http_request` and its wrappers turned a response
header value into a string only when `HeaderValue::to_str()` accepted it,
which requires visible ASCII. Any byte at or above `0x80` produced
`{"base64": "..."}`, so a server that sends raw UTF-8, as many do for
`Content-Disposition: attachment; filename="résumé.pdf"`, gave flows an
object to decode instead of the text.

Reproduced at `75879f4` with a loopback server in
`tests/test_http_artifacts.rs`: the new test failed in both inline and
artifact modes with `content-disposition` returned as
`{"base64":"YXR0YWNobWVudDsg..."}`. A raw-socket probe, not kept as a test,
showed the HTTP client fails the request when a header value holds a C0
control byte such as `0x01`, or DEL (`0x7f`).

## Outcome and validation

- Rule (`src/nodes/http/request/response/headers.rs`): a value is a string
  when its bytes are valid UTF-8 and contain no control character other than
  horizontal tab. Anything else keeps the IF-258 `{"base64": ...}` form:
  invalid UTF-8 such as Latin-1, and C1 controls (`U+0080`–`U+009F`), which
  are valid UTF-8 but not text. DEL and C0 controls other than tab never
  reach this code because the client fails the request. The unit test still
  covers them.
- Contract change: a flow that decoded the Base64 object for a UTF-8 header
  now receives the string. Recorded in `docs/releases/next.md` under Upgrade
  Notes, `docs/nodes/http_request.md` and the four wrapper pages, and the
  `examples/05-http/http_methods.lua` comment.
- Redaction: a protected value in such a header is now matched by the
  ordinary text scan; [IF-262](IF-262.md) decoding still covers the Base64
  form.
- Other header conversions reviewed and deliberately left:
  - `Content-Type` (MIME detection) and `Retry-After` in the HTTP and
    embeddings nodes parse ASCII grammars; a non-ASCII value is invalid
    there, and the header still appears in `_headers` under the new rule.
  - The redirect `Location` check fails loudly on non-ASCII; it decides
    whether to follow, it is not flow output.
  - Forwarded webhook headers reject a non-visible-ASCII value with an
    explicit error: they are configured credentials that feed signature
    checks and the secret floor, not silently dropped output.
  - API key, idempotency key, signature and webhook content-type checks are
    validation. `Last-Event-ID` already accepts UTF-8.

### Validation

- `cargo test --test serial test_http_artifacts:: -- --test-threads=1`:
  `utf8_response_headers_are_strings_in_both_modes` fails before the fix
  and passes after; the IF-258 regression still passes.
- `cargo test --lib response::headers` (rule unit test, including DEL, C1,
  C0 and Latin-1 bytes) and `cargo test --lib util::redaction` (new
  `a_secret_inside_a_utf8_header_string_is_replaced_as_text`).
- `cargo test --test serial test_http_nodes:: -- --test-threads=1`.
- `cargo fmt --all -- --check`, `python3 -B scripts/check_module_size.py`,
  `cargo clippy --all-targets -- -D warnings`, and `ironflow validate` of the
  changed example. The example calls a public service and was not run.
