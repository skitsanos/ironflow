# IF-131 — S3 copy source keys are not URL-encoded

## Required outcome and acceptance

- URL-encode CopySource according to the CopyObject contract while preserving bucket/key boundaries and any supported version semantics.
- Do not reinterpret literal percent-encoded-looking key bytes as separators or queries.
- Capture requests for spaces, literal %2F, percent signs, Unicode, and ordinary keys; distinguish protocol tests from live S3 verification.

## Evidence and cause

Fresh review on 2026-09-12, finding R26. See
[AUDIT_2026-09-12.md](./AUDIT_2026-09-12.md) for the reviewed candidate,
evidence boundaries, and complete finding-to-issue mapping.

[Source: cloud/s3_objects.rs:255](../../src/nodes/cloud/s3_objects.rs).

The node concatenates bucket and raw key into `x-amz-copy-source`. A synthetic literal key containing `%2F` was transmitted unchanged, instead of escaping the percent sign, changing its interpretation when S3 decodes the header. Encode according to the CopyObject contract, preserving the bucket/key boundary; test spaces, percent signs, Unicode, and version query semantics. Evidence: local captured request in `/tmp/ironflow-scope-review-z7J6GT/events.json`, plus the SDK's caller-encoded CopySource contract. No live S3 request was made.

## Outcome and validation

Resolved on 2026-09-13. The copy node now passes the resolved source bucket/key
through `encode_copy_source` before handing it to the AWS SDK. The helper uses
the existing `percent-encoding` dependency to encode UTF-8 bytes, retaining only
RFC 3986 unreserved characters and `/` path separators. It does not decode input
escapes, normalize paths, or parse key text as a query. Encoding happens before
the SDK signs the request.

The [AWS CopyObject contract](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CopyObject.html)
and the locked `aws-sdk-s3` 1.146.1 documentation both require a URL-encoded
CopySource. A source key such as `reports/literal%2Fname.txt` therefore produces
`source-bucket/reports/literal%252Fname.txt` in the wire header. The original key
is retained in context output.

### Contract boundary

- `source_key` is a literal object key, including spaces, percent signs, Unicode,
  query-like text, repeated slashes, and dot segments. Callers must not pre-encode
  it. Destination-key encoding remains owned by the AWS SDK.
- There was no explicit input version selector, and none is introduced here.
  `?versionId=...` inside a source key is literal text, not an undocumented way
  to request another version. The node copies the current source version and
  continues returning source/destination version IDs from service responses.
- Credentials, region/endpoint resolution, retries, error propagation, output
  fields, and service authorization are unchanged. A failed copy returns no
  success output. This fix adds no dependency, configuration option, toolchain,
  skill, hook, or release changes.
- The node document now specifies literal-key and version behavior. The existing
  UUID-scoped S3 example uploads `original %2F.txt`, copies it, downloads and
  verifies the text, lists both objects, and deletes both on success. A failed
  example can still leave objects under its run-owned prefix, as documented.

### Regression evidence

Before implementation, running
`cargo test --test test_s3_copy literal_percent_sequences_are_encoded_before_copy`
failed on the captured header: actual
`source-bucket/reports/literal%2Fname.txt`, expected
`source-bucket/reports/literal%252Fname.txt`. This uses the actual CLI and SDK
against a loopback HTTP fixture, not a direct helper-only assertion. The same
regression passes after the fix.

Post-fix validation on the current stable Rust 1.98.1:

- `cargo test --test test_s3_copy --test test_s3_nodes`: 15 tests passed, none
  skipped. Four new tests cover ten successful explicit-key cases, a missing
  source, and validation/execution of the updated example. Cases include spaces,
  `%2F`/`%2f`/nested percent sequences, percent signs, UTF-8 text, reserved
  punctuation, CR/LF bytes, version-like query text, leading/repeated/trailing
  slashes, and dot segments.
- Wire assertions check the exact encoded CopySource, unchanged destination,
  and inclusion of `x-amz-copy-source` in the SDK's signed headers. The fixture
  resolves the decoded source key to distinguish a correct copy from a silently
  different source. Context assertions cover raw keys, success, ETag/timestamp,
  and source/destination version metadata.
- Missing-source handling exits unsuccessfully, publishes no copy success
  fields, and preserves the fixture's existing destination. The example proves
  environment-based bucket/endpoint configuration, content equality, a listing
  count of two, six expected HTTP operations, and an empty fixture after cleanup.
- `cargo fmt --all -- --check`, `cargo clippy --all-targets -- -D warnings`,
  module-size policy, `cargo audit --deny warnings`, issue-registry validation,
  and `git diff --check` passed. `rustup check` confirmed stable Rust 1.98.1 is
  current; unrelated older installed toolchains were not changed.

This is focused local protocol/CLI evidence, not a full integration gate, live
AWS/S3-compatible deployment, IAM/signature validation by AWS, or versioned
bucket integration. Fixtures use bounded bodies, temporary directories, cleared
child environments, synthetic credentials, isolated AWS config paths, and an
ephemeral loopback listener. No real credentials or remote objects were used.
