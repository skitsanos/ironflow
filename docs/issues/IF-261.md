# IF-261 — mcp_client sends an empty cursor when there is no next page

## Evidence and boundary

Found on 2026-11-20 while validating the IF-251 fix, by reading; the request
itself was not captured before the change. `list_tools` took any string as
`cursor`. The documented pattern,
`cursor = "${ctx.<key>_result.nextCursor}"`, also used in
`examples/17-mcp/mcp_stdio.lua`, interpolates to an empty string when the
previous page has no `nextCursor`, and that string was sent as a cursor. The
repository's own mock server answers an unknown cursor with an error, which
fails the step and ends the session; a server that ignores it returns the
first page again, so a flow that pages until it runs out never does.

## Outcome and validation

- `list_tools` refuses an empty `cursor` before the session is leased, with a
  message that says there is no further page. Nothing is sent and the session
  stays usable.
- The example guards its next-page step with
  `step_if("ctx.mcp_tools_result.nextCursor exists", ...)`; steps that depend
  on a skipped step still run, so the flow also completes on a single-page
  server. `docs/nodes/mcp_client.md` describes the rule and the guard.
- Regression in `tests/test_mcp_nodes.rs`
  (`stdio_lists_two_pages_using_the_returned_cursor`): after the last page an
  empty cursor fails, a following first-page request succeeds on the same
  session, and the server trace holds three `tools/list` requests, not four.
- Validation: that test, the end-to-end example test
  (`cli_stdio_example_reassembles_responses_and_closes_its_session`), the
  `examples` binary and validation of the example. Only the stdio transport
  is exercised; the check runs before any transport code.
