# IF-200 — artifacts prune cannot get past a first page of still-referenced digests

## Evidence and boundary

Review of `develop` at 1.21.1-dev.1 on 2026-11-12, by reading. Not executed.

- `local_candidates` (`src/artifacts/retention.rs:46-79`) walks the digest
  directory and returns the first `limit` files older than the cutoff, in
  directory order, then stops. The remote variant
  (`src/artifacts/remote_retention.rs:11-67`) does the same in key order.
- The CLI (`src/cli/commands/artifacts.rs:27-46`) computes which candidates
  retained runs still reference, skips those, deletes the rest, prints
  `inspected N, retained N, deleted N`, and exits. `--limit` is capped at
  100.
- There is no cursor and no "skip retained and keep scanning". Retained
  candidates do not leave the listing, so they are returned first on the
  next invocation as well.

Trigger: a store where at least `limit` old artifacts are still referenced
by retained runs, with unreferenced old artifacts later in listing order.
Every invocation then reports `inspected 100, retained 100, deleted 0`, and
the orphans behind them are never reached. Old artifacts referenced by
long-retained runs are the normal case for an active deployment, so storage
grows without bound while pruning appears to run.

Secondary, by reading: `collect_references`
(`src/cli/commands/artifacts.rs:105-106`) aborts the whole prune if any
retained run holds a string that starts with `artifact://` but is not a
canonical URI.

Boundary: the existing resume test
(`tests/test_artifact_retention.rs`) covers orphans only, which leave the
listing when deleted. Directory order was assumed stable for an unchanged
directory; S3 key order is deterministic. Pruning is offline-only by
contract (IF-101), so no race is claimed here.

## Required outcome and acceptance

- Keep scanning until `limit` unreferenced candidates are found or the
  listing ends, or accept and print a continuation marker so repeated
  invocations make progress.
- Skip and report non-canonical `artifact://` strings instead of aborting.
- Regressions for local and remote backends: more than `limit` retained old
  digests followed by orphans, asserting the orphans are deleted within a
  bounded number of invocations.
- Document the progress guarantee in the `artifacts prune` section of
  `docs/CLI_REFERENCE.md`.

## Outcome and validation

Resolved 2026-11-14. Both leads were reproduced with the real CLI before the
change; the remote backend used a loopback S3 mock, no cloud service.

Before (unfixed tree, 6 of 9 regressions then written failed):

- Local: 30 old digests referenced by one retained run plus 5 orphans,
  `--limit 2`. Three invocations each printed
  `inspected 2, retained 2, deleted 0`; all 5 orphans remained.
- Remote: 7 referenced digests sorting before 5 orphans, `--limit 2`: the
  same line three times, no orphan deleted.
- Secondary: a context string `artifact://customer-token-…` ended the prune
  with `artifact URI must start with 'artifact://sha256/'`.

Outcome:

- An invocation examines one window of at most `--scan` stored digests
  (new, 1–10000, default 10000) in ascending digest order after `--after`
  (new), audits retained runs once against the old candidates in it, skips
  referenced ones without counting them and deletes at most `--limit`
  unreferenced ones. `--limit` now bounds deletions, not inspection.
- A second output line says `complete`, or `incomplete: … continue with
  --after <sha256>`. Everything up to the printed digest is resolved, so
  looping on it covers N digests with D deletable in at most
  ⌈N/scan⌉ + ⌈D/limit⌉ invocations. Both mechanisms were needed: scanning
  past retained candidates fixes the reported stall, and the marker keeps
  one invocation bounded when the store outgrows a window.
- Bounds per invocation: S3 lists at most `scan` keys in ⌈scan/1000⌉
  requests; local mode reads the directory names once (the local order is
  now digest order, not directory order), holds at most `scan` names and
  stats at most `scan` files; one pass over run summaries in 100-record
  pages, one run in memory, ended early when every candidate is referenced;
  at most `limit` deletions. There is no wall-clock limit.
- Non-canonical `artifact://` strings are skipped and reported on standard
  error as a count and up to five run IDs, never by value. A malformed
  spelling of a stored digest (upper case, suffix) still retains it.
- In S3 mode a full window holding no digest key fails closed rather than
  reporting progress.

Contract boundary: pruning stays offline-only behind `--confirm-offline`;
list, audit, delete order is unchanged, so a reference written during the
command is still outside the contract. A bare digest outside an
`artifact://` string is not a reference, as before. The reference pass costs
one read of every retained run per invocation.

After: the same stores are emptied of orphans in three invocations
(`inspected 32, retained 30, deleted 2` twice, then `deleted 1` and
`complete`), and no referenced digest is removed on either backend. With
`--scan 4`, 12 referenced digests before 2 orphans finish in 4 invocations by
following the marker, with at most 4 keys listed per invocation on S3. The 7
CLI regressions (4 local, 3 remote) and the existing resume test pass, with 3
new unit tests. Library tests 759 passed, 1 ignored; `cli` 98, `storage`
103, `nodes` 296, `nodes_network` 163, `api` 68, `serial` 191 with one
thread. `cargo fmt --all -- --check`, the module-size check and
`cargo clippy --all-targets -- -D warnings` pass. The documented resume loop
was run against the built binary.

Not run: real S3 or MinIO, `scripts/replica_acceptance.ts`, PostgreSQL and
Redis state stores (the audit uses only the shared `StateStore` paging
calls), and stores larger than a few dozen artifacts; the 10,000 window was
not load-tested. The integration gate was not run.
