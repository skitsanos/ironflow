# IF-265 — IF-254 SQLite regression forced WAL instead of the store's own journal mode

## Evidence and boundary

Found on 2026-11-20 while reviewing IF-254. Its SQLite regression ran
`PRAGMA journal_mode=WAL` before replacing a run between the two inspection
reads, and the context-merge race tests (`tests/test_sql_context_concurrency.rs`)
did the same. The PostgreSQL half of IF-254 had no recorded live run.

Read: `SqlStateStore::new_with_prefix` connects with `AnyPoolOptions` and the
plain URL, and sets no journal mode. sqlx 0.9 deliberately leaves
`journal_mode` unset and applies a 5 s busy timeout, so a new state database
keeps SQLite's default rollback journal (`delete`). WAL applies only when an
operator converts the file, after which it persists for every connection.

Reproduced: every pooled connection of a new store reports `delete`. In that
mode a writer cannot commit past an open inspection; with a reader that never
finishes, `delete_run` fails with a backend error after the busy timeout and
the run is unchanged. The original sequential IF-254 test therefore only
passed because of the forced WAL. Also observed: right after a WAL switch an
idle pooled connection still reports `delete` until it next reads the file,
so a mode check must read first.

No defect in the product was found: no mixed record, no hang, and no
unbounded wait in either mode.

## Outcome and validation

- `src/storage/sql_store/inspection/tests.rs` runs the replacement in the
  store's default journal, asserting every pooled connection reports
  `delete`, and again on a file converted to WAL. The replacement now runs
  concurrently with the open inspection under a 15 s bound: in WAL and
  PostgreSQL it commits beside the snapshot, in rollback mode it waits for
  the reader. Either way the open inspection returns only the original and
  the next one only the replacement.
- A new rollback-mode test keeps an inspection open while a writer tries to
  delete the run: the writer fails within the busy timeout, the snapshot and
  stored run stay original, and replacement succeeds once the reader ends.
- The context-merge race tests run in both `delete` and `wal`, asserting the
  file's mode instead of assuming it; merge-semantics and cancellation tests
  use the default mode.

Validation on 2026-11-20:

- `cargo test --lib sql_store` and `cargo test --test storage` pass (default
  features, SQLite only).
- Live: with `--features postgres`, `IRONFLOW_POSTGRES_TEST_REQUIRED=1` and a
  disposable `postgres:latest` container (PostgreSQL 19.0) removed afterwards,
  `postgres_replacement_between_inspection_reads` and the PostgreSQL context
  concurrency tests pass.
- `cargo fmt --all -- --check`, `python3 -B scripts/check_module_size.py` and
  `cargo clippy --all-targets -- -D warnings` pass.

Only test code changed; no production storage behavior changed.

Since IF-267 the stores open SQLite files in WAL by default, with
`IRONFLOW_SQLITE_WAL=false` selecting the rollback journal; these tests now
set either mode through the store instead of a forced pragma.
