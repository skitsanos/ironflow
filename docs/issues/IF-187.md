# IF-187 — step_if and if_node comparisons against true, false and nil are always false

## Evidence and boundary

Review of `develop` at 1.21.1-dev.1 on 2026-11-12, reproduced with a local
optimized build. With context `ready = true`, `off = false`, `n = 1`, `s =
"yes"`:

| Guard | Expected | Result |
|---|---|---|
| `ctx.ready == true` | run | skipped |
| `ctx.ready != false` | run | skipped |
| `ctx.off == false` | run | skipped |
| `ctx.missing == nil` | run | skipped |
| `ctx.ready` | run | ran |
| `ctx.n == 1` | run | ran |
| `ctx.s == 'yes'` | run | ran |

- `compare_values`
  (`src/nodes/composition/conditional/expression.rs:49-80`) tries a numeric
  comparison, then falls back to strings. When the left value is not a
  number or string (boolean, null, object, array), `left.as_str()` is `None`
  and every operator returns `false`, so `==` and `!=` are both false for
  the same operands.
- The guard reports route "false" and the run finishes `success` with the
  step skipped, so nothing signals the problem.
- The repository's own parse test uses this idiom
  (`tests/test_lua_runtime.rs:505`) without asserting the runtime result.

Boundary: `docs/nodes/if_node.md` lists numeric and string operands only, so
part of this is an undocumented limit. Comparing with a boolean literal is
the natural way to write a guard, and a silent skip is the worst failure
mode for it. Related: IF-008.

## Required outcome and acceptance

- Support `true`, `false` and `nil` literals for `==` and `!=`, with `!=`
  defined as the negation of `==` for every operand type.
- For operand types that remain unsupported (objects, arrays, ordering on
  booleans), fail validation or the guard step with a clear error instead
  of routing "false".
- Regressions: the table above at runtime through `step_if` and `if_node`,
  plus an unsupported comparison that now errors.
- Document the full operand and literal grammar in `docs/nodes/if_node.md`
  and `docs/LUA_FLOW_GUIDE.md`, and add an example flow.

## Outcome and validation

Cause: the comparison fell back from numbers to strings and returned false
for every other left value, for `==` and `!=` alike.

Implementation: `conditional/comparison.rs` parses `<path> <operator>
<literal>` and classifies the right operand as number, quoted string,
`true`, `false`, `nil` or unquoted word. `!=` is computed as the negation of
`==`. A comparison with no defined result returns a typed error that
`if_node` reports with the condition; the message names the operand and the
JSON type of the context value, not the value. The flow loader rejects
conditions that are invalid for any context.

| Context value | `==` is true for | Ordering |
|---|---|---|
| absent or `null` | `nil` | error |
| boolean | the same boolean literal | error |
| number | an equal number literal | numeric |
| string | an operand with the same text, quoted or not | error |
| object or array | nothing; any operand except `nil` is an error | error |

An ordering operator whose right operand is not a number fails flow loading.

Results that change, besides the table in this page:

- `ctx.missing != nil` was true and is false.
- `!=` across types was false and is true: a number against a non-numeric
  operand, `null` against anything except `nil`, a boolean against anything
  except the same boolean, an object or array against `nil`.
- `ctx.n > nil`, `ctx.n < 'abc'` and `ctx.a > ctx.b` were false and fail
  loading. Ordering any value that is not a number (absent, `null`, string,
  boolean, object, array), and an object or array compared with a non-nil
  operand, were false and fail the guard step. `ctx.retries > 3` with
  `retries` unset therefore fails instead of skipping.

Kept exactly: numeric and string comparisons, `exists`, truthiness, a string
compared by text with an unquoted operand (the string `"5"` equals `5`, the
string `"true"` equals `true`) and a number never equal to a quoted string.

Contract boundary: the right operand is a literal and is never read from the
context. There is no `and`, `or`, `not` or grouping: a path with spaces,
quotes, parentheses or operator characters, an unquoted operand of several
words, a quoted operand that contains its own quote, a missing operand and
a literal in place of the path (`true`, `1 == 1`)
all fail flow loading, where they used to route false (or, for
`ctx.s == hello world` and `'it's'`, compare as one string). The condition
is split at its
leftmost operator; the search used to prefer `==` wherever it stood, so
`ctx.s != 'a==b'` split inside the quoted operand and routed false. A flow definition built without the Lua loader gets the runtime
error only.

The diagnostic scrubber read `==` after a key with a credential-like name
as an assignment and replaced the second `=`, so a guard error showed
`ctx.credentials =[REDACTED] 'x'`. An unquoted value that is exactly `=` is
now read as a comparison operator and left alone
(`util/sensitive_url/values.rs`); a value that starts with `=`
(`password==pw`) is still replaced. The compared operand was never hidden
by this shape, before or after.

Evidence, unoptimized build:

- Before, `ironflow run` with the context above: through `step_if` and
  through `if_node` the first four guards of the table skipped their step
  and the run finished `success`. The new tests failed on the unchanged
  code (4 of 5 in `test_guard_comparisons`, and `load_flow_with_step_if`);
  the test of unchanged results passed before and after.
- After: all seven guards run their step through both forms.
  `ironflow validate` exits 1 for `ctx.n > nil` naming step and condition;
  `ctx.ready > 0` on a boolean finishes `failed` with
  `if_node cannot evaluate condition 'ctx.ready > 0': operator '>' cannot
  order ctx.ready, which holds a boolean`.
- `tests/test_guard_comparisons.rs` runs 24 literal cases, 34 unchanged
  cases and 11 runtime errors through both forms, plus 28 load-time
  rejections; 14 unit tests cover negation over 14 values and 15 operands
  and the path and operand grammar. The 23 grammar rejections loaded and
  routed false before the change.
- Library 687 passed (1 ignored), `engine` 297, `nodes` 258, `examples` 11,
  `cli` 95, `serial` 187 single-threaded, and for the scrubber change `api`
  60, `nodes_network` 134, `scheduler` 113, `storage` 96. All 160 example
  flows pass `ironflow validate`; `examples/03-control-flow/guard_literals.lua`
  runs to `success`. `step_if.lua` and `conditional_routing.lua` succeed with
  their documented context and now fail without it. Formatting, module-size
  gate and Clippy with warnings denied pass.
- Not run: the integration gate, feature-enabled builds, live stores and an
  optimized build.
