# IF-187 — step_if and if_node comparisons against true, false and nil are always false

## Evidence and boundary

Review of `develop` at 1.21.1-dev.1 on 2026-11-12, reproduced with a local
optimized build. With context `ready = true`, `off = false`, `n = 1`, `s =
"yes"`:

| Guard | Expected | Result |
|---|---|---|
| `ctx.ready == true` | run | skipped |
| `ctx.ready != false` | run | skipped |
| `ctx.off == false` | run | skipped |
| `ctx.missing == nil` | run | skipped |
| `ctx.ready` | run | ran |
| `ctx.n == 1` | run | ran |
| `ctx.s == 'yes'` | run | ran |

- `compare_values`
  (`src/nodes/composition/conditional/expression.rs:49-80`) tries a numeric
  comparison, then falls back to strings. When the left value is not a
  number or string (boolean, null, object, array), `left.as_str()` is `None`
  and every operator returns `false`, so `==` and `!=` are both false for
  the same operands.
- The guard reports route "false" and the run finishes `success` with the
  step skipped, so nothing signals the problem.
- The repository's own parse test uses this idiom
  (`tests/test_lua_runtime.rs:505`) without asserting the runtime result.

Boundary: `docs/nodes/if_node.md` lists numeric and string operands only, so
part of this is an undocumented limit. Comparing with a boolean literal is
the natural way to write a guard, and a silent skip is the worst failure
mode for it. Related: IF-008.

## Required outcome and acceptance

- Support `true`, `false` and `nil` literals for `==` and `!=`, with `!=`
  defined as the negation of `==` for every operand type.
- For operand types that remain unsupported (objects, arrays, ordering on
  booleans), fail validation or the guard step with a clear error instead
  of routing "false".
- Regressions: the table above at runtime through `step_if` and `if_node`,
  plus an unsupported comparison that now errors.
- Document the full operand and literal grammar in `docs/nodes/if_node.md`
  and `docs/LUA_FLOW_GUIDE.md`, and add an example flow.
