# IF-135 — A failed sub-workflow reports only its status, not the failing task's error

## Required outcome and acceptance

- `subworkflow` with `on_error = "ignore"` sets `{output_key}_error` (and the
  un-namespaced equivalent) to the failing task's error message, or to a
  summary that includes it, instead of `Subworkflow '<name>' finished with
  status: failed`.
- `parallel_subworkflows` result entries carry the same text in `error`, and
  the `fail_fast` message lists each failed child's reason.
- The text is subject to the same redaction as other stored context.
- Test with a child whose handler calls `error("boom")` and with a child whose
  node fails (an HTTP 400): the parent context exposes both messages.

## Evidence and cause

Found on 2026-09-14 while building the document-ingestion flows of the HARMOny
`ironflow-hooks` service (IronFlow 1.18.1-dev.4).

[Source: composition/subworkflow.rs:192](../../src/nodes/composition/subworkflow.rs)
and [parallel_subworkflows.rs:151](../../src/nodes/composition/parallel_subworkflows.rs).

The parent receives `Subworkflow 'ingest_document' finished with status:
failed` whatever went wrong inside the child. An ingestion job that fans out
over uploaded files therefore cannot tell the caller *why* a file failed —
"OCR provider rejected a 32-page document" versus "unsupported file type" versus
"database unreachable" all look the same in the job record.

Every orchestrating flow in that service now records its reason in a context
key from a step that succeeds (`ingest_failure = "extraction failed: …"`), then
fails the run in a separate guard step, so the parent can read the text from
the child's partial context. Three flows carry that scaffolding purely to work
around the missing message; a handler that errors publishes nothing, so there
is no lighter alternative today.

## Outcome and validation

- The executor's live scheduling state keeps unresolved failures in task-name
  order. Completed child execution carries a bounded summary through
  `ExecutionOutcome`, finalization, and `ChildRunResult`, alongside the full
  redacted child context. Ordinary public runs do not retain this summary.
- Summaries select at most eight unresolved failures. Names are capped at
  128 UTF-8 bytes and messages at 768 bytes, including truncation markers;
  omitted failures are counted and the task summary stays below 8 KiB.
  Credential and execution-overlay redaction happen before truncation.
- Successful recovery removes the original error from the summary, even if
  durable inspection still records that task as failed. Dependency skips do
  not create extra failures. A failed recovery handler leaves both unresolved
  reasons eligible for selection.
- Waiting single-child calls expose the same description under
  `subworkflow_error` and, when configured, `{output_key}_error`, or return it
  for `fail_fast`. Parallel entries and their input-ordered aggregate errors
  include child reasons. Repeat and tool-dispatch consumers use the same live
  contract; tool result/content selection is unchanged.
- Cancellation and unavailable details keep a status-only fallback. Existing
  infrastructure/finalization errors still follow their error path and do not
  become successful partial child results. No context/history reload was added
  to reconstruct task errors; existing finalizer task-state checks are unchanged.
- Node docs, the Lua guide and architecture describe all four consumers. The
  offline example pair is registered in the example catalog.

## Added Regression Targets

- `tests/test_child_failure_details.rs`: a Lua handler calling `error("boom")`,
  the real HTTP node against a local synthetic HTTP 400 response, single
  ignore/fail-fast with and without namespacing, parallel entry/aggregate
  reasons, multiple unresolved/recovered failures, and repeat/tool consumers.
  Its `offline_child_failure_example_validates_and_runs` CLI case validates both
  IF-135 example files strictly and runs them from an isolated temporary directory
  with the test build's binary and a cleared environment.
- `engine::executor::error_handler::summary::tests`: deterministic selection,
  UTF-8 byte/count bounds, omission markers, recovery exclusion, and credential
  redaction before truncating both task names and messages.
- `engine::executor::engine::tests::child_failures`: retained failed task history
  after recovery, parent execution-overlay redaction across every consumer,
  and a cancelled live child with no task-failure summary.
- Existing `child_results` coverage now checks summaries with JSON, SQLite,
  and null stores; handle tests cover status-only fallback. Existing coordinator
  finalization-timeout and nested cancellation targets remain relevant.

## Validation

The standalone offline example is
[`if135_child_error_details.lua`](../../examples/11-subworkflow/if135_child_error_details.lua),
with the [`if135_error_child.lua`](../../examples/11-subworkflow/if135_error_child.lua)
helper beside it. It asserts tolerated namespaced, unnamespaced, and parallel
child details, preserved partial context, and successful-child metadata. The
parent succeeds with `child_error_details_verified = true`; the helper
also succeeds when run alone without its opt-in failure input. Runtime
validation used the freshly compiled CLI and isolated storage.
