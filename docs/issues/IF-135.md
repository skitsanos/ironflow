# IF-135 — A failed sub-workflow reports only its status, not the failing task's error

## Required outcome and acceptance

- `subworkflow` with `on_error = "ignore"` sets `{output_key}_error` (and the
  un-namespaced equivalent) to the failing task's error message, or to a
  summary that includes it, instead of `Subworkflow '<name>' finished with
  status: failed`.
- `parallel_subworkflows` result entries carry the same text in `error`, and
  the `fail_fast` message lists each failed child's reason.
- The text is subject to the same redaction as other stored context.
- Test with a child whose handler calls `error("boom")` and with a child whose
  node fails (an HTTP 400): the parent context exposes both messages.

## Evidence and cause

Found on 2026-09-14 while building the document-ingestion flows of the HARMOny
`ironflow-hooks` service (IronFlow 1.18.1-dev.4).

[Source: composition/subworkflow.rs:192](../../src/nodes/composition/subworkflow.rs)
and [parallel_subworkflows.rs:151](../../src/nodes/composition/parallel_subworkflows.rs).

The parent receives `Subworkflow 'ingest_document' finished with status:
failed` whatever went wrong inside the child. An ingestion job that fans out
over uploaded files therefore cannot tell the caller *why* a file failed —
"OCR provider rejected a 32-page document" versus "unsupported file type" versus
"database unreachable" all look the same in the job record.

Every orchestrating flow in that service now records its reason in a context
key from a step that succeeds (`ingest_failure = "extraction failed: …"`), then
fails the run in a separate guard step, so the parent can read the text from
the child's partial context. Three flows carry that scaffolding purely to work
around the missing message; a handler that errors publishes nothing, so there
is no lighter alternative today.
