# IF-219 — Diagnostic scrubber over-redacts and misses some key forms

## Evidence and boundary

Recorded on 2026-11-13 from the fixes for IF-176 and IF-177.

- (a) Measured: scrubbing a diagnostic twice over-redacts. A `key: value`
  ends at a line break, the scrubber turns the break into a space, and the
  second pass (node, then engine) takes the following lines as the value. On
  one line, a `Header: value` credential also removes ordinary words up to
  the next comma. Over-redaction only.
- (b) By reading: the scrubber does not match a Lua bracket key
  (`["password"] = "x"`) or `key => value`.
- (c) Decision needed: a sender who controls a forwarded header can still
  blank a string of eight or more bytes that a later step outputs (IF-176,
  IF-011). Closing it means choosing record-only scrubbing or failing the
  step.

Boundary: (a) and (c) lose information but leak nothing; (b) can leave a
secret in a diagnostic when a tool prints it in one of those forms.

## Outcome and validation

Resolved on 2026-11-16. Each item was reproduced with a failing test before
its fix. The contract is in `docs/SECURITY.md`.

- (a) Fixed. Reproduced: a second pass turned `password: [REDACTED] retrying
  connection to db attempt 2, giving up` into `password: [REDACTED], giving
  up` (six unit tests failed). A value after `:` is now one word, as after
  `=`; a `Bearer` or `Basic` value and any `Authorization` value is the
  scheme and its credential; a value that already starts with the marker is
  complete; a cut diagnostic is marked once. Behaviour change: an unquoted
  value with spaces after `:` loses only its first word.
- (b) Fixed. Reproduced: both forms kept the value, and `=>` produced
  `password =[REDACTED]> "x"`. Four more forms that tools print had the same
  result and are fixed: `:=`, a flag and its argument (`--password x`), a
  wrapped value (`password: Some("x")`) and an XML element. A JSON key with
  spaces around its colon already matched and is pinned. A mebibyte of each
  form is scanned in linear time.
- (c) Decided by the maintainer on 2026-11-16: record-only scrubbing.
  Reproduced through the webhook route: with a header equal to text a step
  returned, the next step read `[REDACTED]` and a `step_if` comparing it was
  skipped. Uses of the overlay redactor:

  | Use | Class | Now |
  | --- | --- | --- |
  | Step output, failure output (`_error_output`), child result to its parent | data | not redacted |
  | Task history, stored initial and final context | record | redacted |
  | Task error, events, logs, `_error_message`, child failure summary, panic message | record | redacted once |

  The stored context is written at run start and end only, in the record
  form, and `GET /runs/{id}` returns it, so no guarantee for stored runs is
  weaker. Every step reads `ctx._headers` directly and a transformed copy was
  never recognized, so the removed pass kept nothing out of a record. A
  recovery handler still receives the redacted error text.
- Found on the way, each in its own commit: URLs joined without whitespace
  (`postgres://h/a,postgres://user:pw@h2/b`) were read as one URL and the
  later ones kept their credentials; the first fix for that was quadratic
  and was made linear.

Not covered by a test: log output, by reading (it uses the redacted text). A
child run keeps no record of its own.
