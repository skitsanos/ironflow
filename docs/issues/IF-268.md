# IF-268 — Agents cannot learn which context keys a node writes or when they become readable

## Evidence and boundary

Read, not reproduced with an agent. A coding agent writing a flow has to
guess node output contracts. With `nodes.http_get` and
`output_key = "invoice"`, a natural guess is `${ctx.invoice.data}`; the node
publishes `invoice_data` in inline mode and `invoice_artifact` in artifact
mode ([http_get](../nodes/http_get.md)), and a consumer sees either value
only after the producing phase ends. All three readings are valid Lua.

Current state, read from the code:

- The `Node` trait exposes only `node_type()` and `description()`;
  parameters, defaults and outputs exist only as prose in `docs/nodes/`
  (105 pages).
- `ironflow nodes` takes no arguments and lists names and descriptions.
- `ironflow validate --strict` reports unknown nodes, missing dependencies,
  cycles, condition syntax and Lua-handler warnings. It has no JSON output
  and does not check `${ctx.…}` reads against upstream producers, so the
  mistakes above pass validation and fail only at runtime.
- The repository skills cover engine maintenance; none targets users who
  only author `.lua` flows against an installed binary.

## Required outcome and acceptance

Phased; each phase lands and is measured before the next is committed.

1. **Context reads in validation.** `validate --strict` flags a literal
   `${ctx.key}` read that no step in an earlier phase declares it writes,
   and a read placed in the same phase as its producer.
   `validate --format json` emits diagnostics with stable codes, severity,
   step and source location where known. Reads from Lua callbacks, or keys
   computed from input, are reported as unknown, never as errors.
2. **Output contracts in the binary.** Nodes declare versioned output
   metadata (keys, the configuration that selects them, inline versus
   artifact) and one working example. Start with HTTP, file I/O,
   transforms and subworkflows; add parameters and defaults after outputs.
   `ironflow nodes describe <node> --format json` returns the installed
   version's contract. A test runs each declared example and fails when
   the keys written differ from the keys declared, so the metadata cannot
   drift from the code.
3. **Authoring skill.** A portable skill for downstream projects: check
   `ironflow --version`, find the nearest example in
   `examples/catalog.json`, read contracts through `nodes describe` (not
   copied into the skill), write the flow, run `validate --strict`, and
   exercise it with an offline fixture. It ships with the release.
4. **Editor annotations.** LuaLS annotations for `Flow`, `flow:step`, the
   chainable methods and `nodes.*`, generated from the same catalog.

Out of scope until phase measurements justify them: a dedicated
`ironflow lsp` and an `ironflow mcp` authoring server. Either would wrap
phases 1–2 and must not add a second source of node metadata.

Measurement: give Codex, Claude Code and OpenCode the same task (repair a
flow with a wrong HTTP output key and a missing dependency). Record whether
each reaches the expected fixture output, how many repair attempts it
takes, and which mistakes survive `--strict`. Repeat after phases 1 and 2.

Docs: [CLI reference](../CLI_REFERENCE.md) for the new flags and
subcommand, node pages kept consistent with the declared metadata, and the
examples catalog for any example added.
