# IF-145 — `pdf_split` does not interpolate its `pages` parameter

## Required outcome and acceptance

- `pages` accepts `${ctx.key}` interpolation like the node's `path` and `output_dir`
  parameters, so a page range computed at runtime can drive the split.
- Non-interpolated literals keep their current parsing and error messages.
- Test with `pages = "${ctx.range}"` where the context holds `"31-60"`: the node
  materialises pages 31–60; a missing or malformed context value produces the existing
  `Invalid page number` error mentioning the resolved text.

## Evidence and cause

Found on 2026-09-15 while adding the long-PDF path to the HARMOny `ironflow-hooks`
service (IronFlow 1.18.1-dev.8).

[Source: image/pdf_merge_split/split.rs:49](../../src/nodes/image/pdf_merge_split/split.rs).

`path` and `output_dir` go through `interpolate_ctx`; `pages` is read straight from the
config, so a worker that receives its range from the parent fails with:

```
Invalid page number: '${ctx.pages_spec}': invalid digit found in string
```

The OCR provider accepts at most 30 pages per request, so a 243-page document has to be
cut into ranges and each range OCR'd by a fan-out worker. The intended shape — every
worker splits its own range from the original file — was not possible; the flows now
split the whole document once in the parent (`pages = "all"`, one file per page) and pass
each worker the file list for its range, which works but writes up to N single-page files
where 30-page slices would do. The node documentation lists interpolation for `path` and
`output_dir` only, so this is a consistency gap rather than a documentation error.
