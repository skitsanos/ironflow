# IF-145 — `pdf_split` does not interpolate its `pages` parameter

## Required outcome and acceptance

- `pages` accepts `${ctx.key}` interpolation like the node's `path` and `output_dir`
  parameters, so a page range computed at runtime can drive the split.
- Non-interpolated literals keep their current parsing and error messages.
- Test with `pages = "${ctx.range}"` where the context holds `"31-60"`: the node
  materialises 30 one-page files containing pages 31-60. Missing or malformed
  resolved selectors produce the existing parser errors. This does not introduce
  multipage grouping; that separate feature is tracked in IF-147.

## Evidence and cause

Found on 2026-09-15 while adding the long-PDF path to the HARMOny `ironflow-hooks`
service (IronFlow 1.18.1-dev.8).

[Source: image/pdf_merge_split/split.rs](../../src/nodes/image/pdf_merge_split/split.rs).

`path` and `output_dir` go through `interpolate_ctx`; `pages` is read straight from the
config, so a worker that receives its range from the parent fails with:

```
Invalid page number: '${ctx.pages_spec}': invalid digit found in string
```

The OCR provider accepts at most 30 pages per request, so a 243-page document has to be
cut into ranges and each range OCR'd by a fan-out worker. The intended shape — every
worker splits its own range from the original file — was not possible; the flows now
split the whole document once in the parent (`pages = "all"`, one file per page) and pass
each worker the file list for its range, which works but writes up to N single-page files
where 30-page slices would do. The node documentation lists interpolation for `path` and
`output_dir` only, so this is a consistency gap rather than a documentation error.

## Outcome and validation

Implemented on 2026-09-15: `pages` now passes through the existing context
interpolator before the tracked worker parses it. Literal parsing, page limits,
load safety, and one-file-per-page semantics are unchanged. Updated the node
reference and runnable `pdf_split.lua` example to show runtime selection; the
example still defaults to pages 1-3 and accepts a caller-supplied `pages_spec`.

Pre-fix evidence at `4014c8d`: both new regression tests failed because the parser
received the literal `${ctx.range}`. Post-fix coverage:

- `pdf_split_interpolates_runtime_range_and_preserves_page_identity` builds a
  deterministic 60-page PDF, resolves `31-60`, and verifies all 30 output files
  each contain exactly one page with the correct original page text.
- `pdf_split_reports_resolved_invalid_selector_without_writing_pages` verifies
  missing and invalid context values report resolved parser errors and do not
  create the output directory.
- `cargo test --locked --test test_pdf_merge_split_nodes --test test_pdf_page_graph
  --test test_pdf_load_safety` passed: 19 tests covering literal selectors, merge,
  dependency isolation, inherited attributes, shared loading limits, and the
  changed example's CLI validation/execution.
- `ironflow validate --strict examples/08-extraction/pdf_split.lua` passed using
  the freshly built binary from an isolated working directory.
- Formatting, module-size policy, `cargo clippy --all-targets -- -D warnings`,
  `cargo audit --deny warnings`, and issue-registry validation passed.

This is focused default-feature validation, not a full integration/release gate.
Grouped PDF output remains open as IF-147, as explicitly requested.
