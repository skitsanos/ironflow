# IF-098 — Webhook authentication cannot verify signatures over the original body

## Finding

Webhook routes deserialize JSON before a workflow sees the request. The exact
request bytes are discarded, while the authentication example compares a
forwarded header directly with a shared secret inside Lua. That contract cannot
validate provider HMAC signatures correctly: even harmless JSON
re-serialization changes the signed bytes, and invalid requests can consume
flow-parse and run capacity before a workflow rejects them.

Required outcome:

- add an opt-in, fail-closed HMAC-SHA256 policy to named webhook routes;
- resolve its secret from an environment variable without forwarding,
  persisting, logging, or returning the value;
- validate one configured signature header against the original bounded body
  bytes with a constant-time comparison before loading a flow or starting a
  run;
- preserve legacy webhook routes and their empty-body/JSON context contract;
- reject missing, repeated, malformed, or mismatched signatures without
  creating a run;
- document that body-only HMAC does not provide timestamp/replay protection or
  implement provider-specific signature grammars; and
- replace the shared-secret-equality Lua example with a runnable signed-webhook
  example and focused ingress regressions.

This issue intentionally does not add a general-purpose cryptography node.
Authentication belongs at ingress so an invalid request cannot execute any
workflow step or create durable state.

## Outcome and validation

**Historical status:** Resolved on 2026-08-05.

Structured webhook configuration now accepts an optional `signature` policy
with `type: hmac_sha256`, a normalized header name, an environment-variable
secret source, and a configurable digest prefix that defaults to `sha256=`.
The server validates the environment-backed secret at startup. At ingress it
computes the HMAC over the exact body bytes admitted by the existing HTTP body
limit, decodes the supplied hex digest, and compares raw tags in constant time
before JSON parsing, flow loading, run admission, or persistence.

The signature header cannot overlap `forward_headers` or use a reserved
platform credential name. Missing, repeated, non-text, malformed, or mismatched
values return a generic `403` and create no run. Legacy scalar and structured
routes retain their empty-body and JSON-object behavior; non-empty webhook
bodies still require an `application/json` or `application/*+json` content
type. Shared HMAC and constant-time primitives now also serve API-key and Lua
bytecode authentication rather than retaining three independent comparisons.

The Lua example, CLI reference, Lua guide, architecture, implementation plan,
and example index description now describe ingress authentication. The docs
state the deliberate boundary: the generic policy covers body-only
HMAC-SHA256, but does not parse compound provider headers or provide timestamp
and replay protection for schemes such as Stripe or Slack.

Focused validation passed 16 webhook API/security integration tests, 16
webhook configuration/shared-authentication/Lua-bytecode unit tests, and the
updated `examples/15-webhooks/auth_check.lua` validation. Rust formatting, the
456-module size policy, exact all-target Clippy with warnings denied, Rust doc
tests, issue/repository-policy tests, the generated issue-registry check, and
`git diff --check` passed. No full integration gate, live storage service, or
deployed provider webhook test was run because this routine issue completion
does not touch storage and is not an integration, `develop` push, or release
boundary.
