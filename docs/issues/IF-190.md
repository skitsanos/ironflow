# IF-190 — ZIP preflight and the archive reader can select different end records

## Evidence and boundary

Review of `develop` at 1.21.1-dev.1 on 2026-11-12, reproduced with a local
optimized build and `IRONFLOW_MAX_ZIP_ENTRIES=1`.

- Archive layout: `[file data][directory B][directory A][end record A,
  comment length 23][end record B, comment length 0][1 byte]`. Directory A
  declares one entry, `benign.txt`. Directory B declares two raw entries,
  both named `same.txt`.
- `zip_list` succeeds and returns `same.txt` with a count of 1. The listed
  directory is B, which the preflight never examined.
- Control: the same two duplicate entries declared honestly with one end
  record are rejected (`declares 2 zip entries; raw count exceeds ...`).
- Cause: the preflight scans backwards and accepts only an end record whose
  comment ends exactly at end of file, so it validates A
  (`src/util/zip_preflight.rs:76-83`,
  `zip_preflight/central_directory.rs:209-215`). `zip` 9.1.3 takes the last
  signature whose comment merely fits, so it materializes B. The only later
  check is that the opened archive's entry count equals the validated count,
  after materialization and on de-duplicated names
  (`src/nodes/file/archive/read.rs:63-72`).

Consequence: the raw entry, duplicate-name and metadata budgets introduced by
IF-130 and IF-066 can be bypassed for `zip_list` and `zip_extract`, and by
reading the same preflight guards OOXML and XLSX extraction
(`src/nodes/extract/ooxml.rs:34-50`, `xlsx/guard.rs:25-52`). The comment in
`guard.rs` that constructing the archive cannot reserve an attacker-sized
metadata table no longer holds.

Boundary: per-entry and total uncompressed byte caps still apply while
copying, and path safety is unaffected. Only `zip_list` was executed; memory
amplification from an oversized directory B was not measured.

## Required outcome and acceptance

- Fail closed when any end-record signature lies after the accepted record
  or when the directory does not abut its end record.
- After opening, assert that the reader's central-directory offset and raw
  entry count equal the validated ones before using any entry.
- Regressions: the archive above is rejected by `zip_list`, `zip_extract`
  and one OOXML extractor; ordinary archives with a trailing comment still
  open.
- Update the comment in `xlsx/guard.rs` and the ZIP admission notes in the
  node documents.

## Outcome and validation

Resolved on 2026-11-12. The pinned reader is `zip` 9.5.1, not 9.1.3 as
written above; its selection code was read for this fix.

Reader selection (`format/find_central_directory.rs`,
`read/zip_archive.rs`): scanning backwards, it takes the first end signature
whose fixed fields parse and whose comment fits in the file. It reads the
directory at `record - size` when a header signature is there, else at the
first header signature after the declared offset, and treats the difference
as prepended data. ZIP64 is used only when a sentinel is set and a locator
parses; the record is tried at the locator's offset, then at any ZIP64
signature before the locator. If the directory fails to parse, the reader
falls back to an earlier signature unless the directory abuts its record.

Fix:

- `zip_preflight/end_record.rs` selects the same candidate and rejects the
  archive unless that record ends at EOF, with no fallback.
- The directory must end exactly at its end record or ZIP64 end record, so
  the reader derives archive offset zero and cannot fall back.
- `check` returns `Admitted`; `Admitted::confirm` requires archive offset
  zero, the validated directory offset and raw count, and no collapsed
  duplicates. `zip_list`, `zip_extract`, the OOXML archive and the XLSX
  guard, shared-string and style preflights call it straight after
  construction.
- The `xlsx/guard.rs` comment, node pages, `ARCHITECTURE.md` and release
  notes are updated.

Contract boundary. Newly refused: a comment holding a complete end record
(signature plus at least 18 bytes whose comment length fits), bytes after
the end record, and a gap between the directory and its record. Still
accepted: ordinary comments, signature bytes that cannot form a record, and
valid ZIP64 archives.

Disagreement cases:

- Second record in a comment, trailing bytes: closed by selection.
- Decoy directory at the declared offset with the real one abutting the
  record: reproduced (reader offset non-zero, duplicates hidden); closed by
  abutment.
- ZIP64 record found by scan, ZIP64 fields overriding classic fields, a
  locator without sentinels: closed by reading only. Only a ZIP64 gap was exercised.
- Residual: calamine's own open cannot be confirmed; it reads the same
  handle with the same crate version as the three confirmed XLSX opens. A
  `zip` upgrade must re-read the selection code.

Evidence, debug build:

- Before: `zip_list` with `max_entries = 1` on the layout above returned
  `same.txt`, count 1; a ZIP64 archive with a gap was listed; `extract_word`
  failed only later with a missing-part error. Six of seven new node tests
  failed.
- After: `zip_list`, `zip_extract`, `extract_word`, `extract_pptx` and
  `extract_xlsx` reject the layout with `has data after its ZIP end record`;
  the `zip_extract` destination is untouched.
- Passing: library 711 (1 ignored), `nodes` 265, `documents` 154 (3
  ignored), `examples` 11, `serial` 190 single-threaded, `extract_execution`
  2, `conversion_limits_env` 2; formatting, module-size check and
  `cargo clippy --all-targets -- -D warnings` clean.
- Not run: memory amplification from an oversized hidden directory, a
  multi-gigabyte ZIP64 archive, the integration gate, and the new OOXML and
  preflight unit tests against the unfixed tree.
