# IF-218 — File output and archive follow-ups

## Evidence and boundary

Recorded on 2026-11-13 from the fixes for IF-179, IF-185 and IF-190.

- (a) By reading: single-page `pdf_split` saves each page with a plain
  create; it follows a symlinked leaf and truncates in place
  (`src/nodes/image/pdf_merge_split/split.rs`, documented as the legacy mode).
- (b) By reading: the `cache` file backend writes entries with
  `std::fs::write`, so a concurrent reader can see a partial entry.
- (c) Measured: `zip_create` stores every archive entry with mode `0600`,
  whatever the source file's mode.
- (d) Measured: parent directories that file nodes create get `0755` masked
  by the umask, not `0777` masked by it.
- (e) Not compiled locally: the portable (non-Unix) rooted writer, including
  `RootedDir::existing`.
- (f) By reading: `calamine`'s own archive open is not confirmed against the
  admitted ZIP directory; it reads the same handle with the same `zip`
  version as the confirmed opens.
- (g) By reading: the `zip` reader allocates the ZIP64 extensible data sector
  in one buffer sized from the record. The preflight's metadata budget bounds
  it today.

Update, 2026-11-15: `zip` moved from 9.5.1 to 9.6.0 in 1.21.1-dev.12
(lockfile only). The re-read that (f) and (g) ask for on every `zip` upgrade
was not done for that change and is owed.

## Outcome and validation

Resolved on 2026-11-15. Every code fix has a regression that failed first.

- (a) Reproduced (a symlinked page destination was followed, an existing
  page truncated in place). Single pages now use the staged writer with
  overwrite kept, capped by `IRONFLOW_MAX_PDF_BYTES`.
- (b) Reproduced (a concurrent `cache_get` failed with `Corrupt cache
  file`). `cache_set` stages and renames; a symlinked entry is refused.
- (c) Reproduced (`0755`, `0644`, `0444` and `6755` sources all stored
  `0600`). Entries carry the nine permission bits of the opened source and
  no special bits; `zip_extract` still ignores stored modes.
- (d) Decided: created directories stay `0755` masked by the umask, as
  IF-185 measured and asserts. Now a named constant, documented per node.
  `0777` masked would create group-writable directories under umask `002`.
- (e) The fallback's unit tests run in Unix test builds, and
  `--cfg ironflow_portable_writer` selects it for the whole library; CI and
  the gate lint that build. It found one unannotated `expect`. Nothing
  compiles for Windows before the release workflow: a cross-check needs the
  MSVC toolchain for bundled C code.
- (f), (g) `zip` 9.6.0 read against 9.5.1:
  `format/find_central_directory.rs`, `format/blocks.rs`,
  `read/magic_finder.rs` and `read/config.rs` are byte-identical and
  `read/zip_archive.rs` differs by one visibility, so selection
  (`find_central_directory_end`, `ZipArchive::get_metadata`) and the ZIP64
  allocation (`Zip64CentralDirectoryEnd::parse`, record size minus 44 bytes,
  charged to the metadata budget) are unchanged. `read/mod.rs` now keeps a
  raw copy of a non-UTF-8 entry comment: one more copy of bytes the budget
  counts. `calamine` 0.38.0 `Xlsx::new` calls `ZipArchive::new` on the same
  bytes with the single locked `zip`.

Two defects found by that reading, fixed here:

- The preflight took a `0xffff` disk field as a ZIP64 marker; the reader
  (`may_be_zip64`) does not, rejects the record as multi-disk and falls back
  to an earlier one. Reproduced: one entry admitted, a hidden 40-entry
  directory opened and refused only by `Admitted::confirm`. The preflight
  now uses the reader's test. Present in 9.5.1 too.
- `Xlsx::new` probes for a compound file before opening the ZIP, and
  `Sectors::get_chain` (`cfb.rs`) has no cycle check. Reproduced outside the
  repository under an allocator capped at 256 MiB (a 3 KB looping input hit
  the cap), and inside it (a workbook behind a harmless compound header was
  extracted). `extract_xlsx` now refuses that signature first.

`scripts/reviewed_archive_readers.json` pins the reviewed versions: a policy
test fails on any other locked version (checked by editing the pin),
Renovate notes it on update pull requests, and `docs/SECURITY.md` has the
checklist.

Validation, default features, unoptimized: formatting, module size, default
Clippy and the portable-writer lint; the `nodes` and `documents` binaries,
the cache tests in `serial`, `storage` and `cli`, the library tests and the
Bun policy tests. Not run: the integration gate, feature builds, Linux,
Windows.

Left for a maintainer: reporting the `calamine` loop upstream (a report was
drafted under [IF-220](IF-220.md), item j); a Windows CI build.

Update, 2026-11-17: `zip` 9.6.1 read against 9.6.0 (lockfile only).
`read/magic_finder.rs`, `read/config.rs`, `read/mod.rs` and
`read/zip_archive.rs` are identical. `format/blocks.rs` and
`format/find_central_directory.rs` changed: a ZIP64 end record must now end
exactly at its locator (`record_size + 12` equal to the distance, where 9.6.0
accepted a shorter record), and its extensible data sector is read only after
the record is accepted. The preflight already refuses a record that does not
end at the locator (`parse_zip64_directory`), so the reader skips no record
the preflight admits, and the allocation is still the record size minus the
fixed part, charged to the metadata budget. The other changes are the
extended-timestamp flags and a refactor of `extract`, which IronFlow does not
call. No preflight change was needed; `scripts/reviewed_archive_readers.json`
names 9.6.1. Read only, with the existing preflight tests; no new probe.

Update, 2026-11-18: `zip` 9.7.0 read against 9.6.1 (lockfile only).
`format/find_central_directory.rs`, `read/magic_finder.rs`, `read/config.rs`
and `read/mod.rs` are identical. `format/blocks.rs` gains two public wrappers
(`ZipCentralEntryBlock::parse`, `ZipLocalEntryBlock::parse`) around the
existing fixed-header parser, and three files drop an unused import. Selection
and allocation are unchanged; `scripts/reviewed_archive_readers.json` names
9.7.0. Read only.

Update, 2026-11-19: `zip` 9.7.2 read against 9.7.0 (lockfile only; 9.7.1 was
never locked). `format/find_central_directory.rs`, `format/blocks.rs`,
`read/magic_finder.rs` and `read/config.rs` are identical, so selection is
unchanged. `read/zip_archive.rs` gains one field (`last_file_end`) and
`read/mod.rs` changes one line, both in the path that turns a writer back into
a reader; `read_central_header` and the per-entry name, extra-field and comment
buffers are untouched. The rest is in the crate's own `extract` and stream
extraction (`read/extract.rs`, `read/stream.rs`, `path.rs`) and in writer extra
fields; IronFlow reads entries with `by_index` and `by_name` and writes files
itself, so it calls none of that. `scripts/reviewed_archive_readers.json`
names 9.7.2. Read only.
