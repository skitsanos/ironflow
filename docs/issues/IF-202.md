# IF-202 — PostgreSQL event store takes an exclusive table lock on every startup

## Evidence and boundary

Review of `develop` at 1.21.1-dev.1 on 2026-11-12, by reading. Not executed:
no PostgreSQL instance was used, so the blocking behaviour follows from
PostgreSQL's documented lock queue rather than from a measurement.

1. Startup lock. `ensure_postgres_run_scoped_identity`
   (`src/storage/event_store/sql/migration/postgres.rs:9-19`) opens a
   transaction and runs `LOCK TABLE {events} IN ACCESS EXCLUSIVE MODE` before
   it inspects the primary key. It is called from schema setup on every
   `SqlEventStore` construction, and the already-migrated path simply
   commits. There is no `lock_timeout`.
   - If any session holds a lock on the events table (a dump, a long
     analytics query, an idle transaction), a starting replica waits
     indefinitely.
   - While it waits, new statements on that table from live replicas queue
     behind the pending exclusive lock. The engine drops events after 500 ms
     (`src/engine/executor/engine.rs:17, 208`), and SSE polls stall.
2. Counter repair. `repair_sequence_counters`
   (`src/storage/event_store/sql/schema.rs:138-157`) runs at every startup
   and upserts one row per run with `ON CONFLICT ... DO UPDATE` and no
   `WHERE`, so every counter row is rewritten and locked for the statement
   even when unchanged. Events are retained until explicitly deleted, so the
   cost grows with history.
3. Delete race, lower confidence. In `delete_run`
   (`src/storage/sql_store/retention.rs:8-31, 211-231`) the lease is read
   before the run row is locked. Under READ COMMITTED, a run with the same
   deterministic ID created between the two statements can be deleted while
   its owner holds a live lease. SQLite is not affected because the writer
   lock is already held.

Boundary: SQLite takes none of these paths in a harmful way except item 2's
writer lock for the statement. Related: IF-020 (identity migration), IF-055
(startup concurrency), IF-062 (delete must refuse a live owner).

## Required outcome and acceptance

- Inspect the primary-key shape without a table lock; take the exclusive
  lock only when the legacy key is found, with a `lock_timeout` and a clear
  startup error.
- Restrict the counter upsert to rows that are missing or behind.
- Re-read the lease after the run row is locked before deleting.
- Live `postgres` feature tests against a disposable instance: startup
  completes while another session holds a share lock on the events table;
  publishing continues during a second replica's startup; delete racing a
  re-create with the same ID never removes a leased run.

## Outcome and validation

Resolved on 2026-11-14. All three items were reproduced against a disposable
PostgreSQL 18 before the fix, with the regressions below failing first.

1. Startup lock. Reproduced: with an idle transaction holding `ACCESS SHARE`
   on the events table, a second `SqlEventStore` never finished and a live
   replica's `publish` and `list_since` stalled behind it. Now the key shape
   is read from the catalog without a table lock. Only a legacy `(id)` key
   opens a transaction with `lock_timeout = 5s`, locks, reads the shape
   again (another replica may have migrated first, IF-055) and replaces the
   key. A timeout is a `Conflict` that names the table and the migration;
   nothing changes and the next start retries.
2. Counter repair. Measured on 50,000 runs and 1,000,000 events with current
   counters: the old statement rewrote 50,000 rows (15 MB of WAL, 425 ms); a
   `WHERE` on the `DO UPDATE` alone still locked every row (2.9 MB of WAL);
   the new statement filters current rows out before the upsert and wrote
   0 rows and 0 bytes (84 ms). It still scans the events table through its
   `(run_id, sequence)` index, read-only. The guarded update never lowers a
   counter that a publisher or another starting replica advanced.
3. Delete race. Reproduced deterministically: the delete was paused after
   its lease statement, the run was created with `init_run_owned`, and the
   resumed delete removed the leased run. Now the lease is read again once
   the run row is locked. A lease that appeared rolls the attempt back and
   restarts it in lease-then-run order (three attempts), so a live owner
   gets `Conflict`. The locked run row keeps a later lease out through the
   lease table's foreign key.

Found while fixing, same area, fixed in its own commit: `CREATE INDEX IF NOT
EXISTS` requests `SHARE` before noticing the index exists, so every start of
both SQL stores waited for each open writer transaction and queued new
writers. An existing index is now detected in the catalog; a missing index
or column is created under the same 5 s bound.

Contract boundary: the bound is fixed, not a setting. A schema-changing
start can still stall statements on that table for up to 5 s per attempt.
SQLite is unchanged apart from the shared repair statement: it has one
writer lock, bounded by the driver's busy timeout, and no lock queue. The
overlap of the state and event deletes in IF-214 (a) is not changed here.

Validation:

- Live PostgreSQL, `postgres` feature (`storage_postgres`, 13 tests): the
  eight `test_sql_startup_locks` regressions cover a reader and an open
  writer during startup, publishing during a second start, the bounded and
  retryable identity migration and column addition, the repair (row
  versions unchanged), and the delete race. Before: 6 of the first 6 failed
  on the unfixed tree and the two index and column tests failed without the
  second commit. After: 13 passed, repeated five times. The `storage`
  binary with the `postgres` feature also passed live (112 tests).
- Default features: a SQLite regression for the repair statement, plus the
  library (757), `storage` (97), `api` (67), `engine` (304), `scheduler`
  (113) and `serial` (191) binaries; formatting, the module-size gate and
  Clippy with default and with `postgres,redis` features.
- Not run: a second replica starting while another builds a missing index
  on a large table (expected to time out and succeed on a later start),
  and a deployed multi-replica rollout.
