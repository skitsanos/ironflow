# IF-202 — PostgreSQL event store takes an exclusive table lock on every startup

## Evidence and boundary

Review of `develop` at 1.21.1-dev.1 on 2026-11-12, by reading. Not executed:
no PostgreSQL instance was used, so the blocking behaviour follows from
PostgreSQL's documented lock queue rather than from a measurement.

1. Startup lock. `ensure_postgres_run_scoped_identity`
   (`src/storage/event_store/sql/migration/postgres.rs:9-19`) opens a
   transaction and runs `LOCK TABLE {events} IN ACCESS EXCLUSIVE MODE` before
   it inspects the primary key. It is called from schema setup on every
   `SqlEventStore` construction, and the already-migrated path simply
   commits. There is no `lock_timeout`.
   - If any session holds a lock on the events table (a dump, a long
     analytics query, an idle transaction), a starting replica waits
     indefinitely.
   - While it waits, new statements on that table from live replicas queue
     behind the pending exclusive lock. The engine drops events after 500 ms
     (`src/engine/executor/engine.rs:17, 208`), and SSE polls stall.
2. Counter repair. `repair_sequence_counters`
   (`src/storage/event_store/sql/schema.rs:138-157`) runs at every startup
   and upserts one row per run with `ON CONFLICT ... DO UPDATE` and no
   `WHERE`, so every counter row is rewritten and locked for the statement
   even when unchanged. Events are retained until explicitly deleted, so the
   cost grows with history.
3. Delete race, lower confidence. In `delete_run`
   (`src/storage/sql_store/retention.rs:8-31, 211-231`) the lease is read
   before the run row is locked. Under READ COMMITTED, a run with the same
   deterministic ID created between the two statements can be deleted while
   its owner holds a live lease. SQLite is not affected because the writer
   lock is already held.

Boundary: SQLite takes none of these paths in a harmful way except item 2's
writer lock for the statement. Related: IF-020 (identity migration), IF-055
(startup concurrency), IF-062 (delete must refuse a live owner).

## Required outcome and acceptance

- Inspect the primary-key shape without a table lock; take the exclusive
  lock only when the legacy key is found, with a `lock_timeout` and a clear
  startup error.
- Restrict the counter upsert to rows that are missing or behind.
- Re-read the lease after the run row is locked before deleting.
- Live `postgres` feature tests against a disposable instance: startup
  completes while another session holds a share lock on the events table;
  publishing continues during a second replica's startup; delete racing a
  re-create with the same ID never removes a leased run.
