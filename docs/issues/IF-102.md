# IF-102 — Workflow composition cannot repeat a child flow with bounded carried state

## Required outcome and acceptance

IronFlow can execute one child workflow, fan out a runtime array across child
workflows, and dispatch one round of LLM tool calls. It cannot iterate a child
workflow until an explicit outcome. Flows therefore hard-code model/tool
rounds, API pages, and short polling attempts into a static DAG or hide a loop
inside unrestricted Lua code without child-run lifecycle visibility.

Required outcome:

- add a `repeat_subworkflow` composition node that executes one child flow
  sequentially until the child returns an explicit boolean completion value;
- carry only an explicit state value between iterations, inject a one-based
  iteration number, and keep static mapped input separate from child output;
- require a finite positive iteration limit, enforce a process hard cap, and
  fail when the child does not complete within that limit;
- support bounded deterministic delay/backoff between iterations while the
  enclosing step deadline and cancellation retain authority over child work;
- fail closed on missing or invalid completion/state values and failed child
  runs, without publishing a partial successful parent result;
- make every composition node available inside every nested child registry so
  repeated flows can safely compose other subworkflows;
- expose the final public child context, final state, iteration count, and
  completion status without retaining unbounded iteration history; and
- add focused success, state-carry, bounds, validation, nesting, deadline, and
  cancellation regressions plus runnable Lua documentation and example
  coverage.

The first delivery is an in-process bounded composition primitive. It does not
add durable suspension, external signals, transparent replay after process
loss, or exactly-once semantics for child side effects. The parent run keeps
its normal admission and lease ownership for the complete repeated step.

## Outcome and validation

**Resolved on 2026-08-17.** `repeat_subworkflow` now runs one child flow until
the child returns an explicit boolean completion value or the required finite
iteration limit is exhausted. Static mapped input is rebuilt for every child
run, only the configured state value crosses iterations, and the child receives
a one-based iteration number. The successful output includes the final public
child context, final state, iteration count, completion flag, and flow name;
iteration history is not retained.

The node fails closed for child failure, missing or non-boolean completion,
missing next state after an incomplete turn, and iteration exhaustion. Optional
delay and multiplicative backoff are deterministic and bounded. The process
limit defaults to 128 iterations, cannot exceed the compiled ceiling of 1024,
and can be lowered with `IRONFLOW_MAX_REPEAT_ITERATIONS`.

Composition child registries now come from one shared registration helper, so
`subworkflow`, `parallel_subworkflows`, `repeat_subworkflow`, and
`tool_dispatch` remain available recursively. Child handles cancel on drop and
inherit the execution overlay; regressions prove both explicit cancellation
and a real parent step deadline terminate an active nested shell process.

Seven focused repeat-node tests and all five nested-workflow cancellation tests
passed. The documented offline parent/helper example completed in three
iterations with the expected final state. The 137-flow catalog validation,
clean-checkout fixture runtime matrix, full `cargo test --all-targets`, module
size policy, Rust formatting, and exact all-target Clippy with warnings denied
also passed.
