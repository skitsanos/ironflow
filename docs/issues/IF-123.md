# IF-123 — Replica mode trusts backend labels instead of actual SQL dialects

## Required outcome and acceptance

- Validate resolved state/event URL dialects against selected backend labels before connecting or admitting replica mode.
- Reject local SQLite URLs disguised as shared PostgreSQL and report a secret-safe configuration error.
- Test both mismatched stores, genuine PostgreSQL replica startup, and supported standalone SQLite using the full-feature binary.

## Evidence and cause

Fresh review on 2026-09-12, finding R18. See
[AUDIT_2026-09-12.md](./AUDIT_2026-09-12.md) for the reviewed candidate,
evidence boundaries, and complete finding-to-issue mapping.

[Source: cli/replica_config.rs:18](../../src/cli/replica_config.rs), [factory: store_factory.rs:94](../../src/cli/store_factory.rs).

Setting both backend labels to `postgres` but supplying two local SQLite URLs starts the full-feature server in replica mode. It logs PostgreSQL and returns HTTP 200 readiness while opening local SQLite files. Validate the resolved URL dialect against each selected backend before connecting and before replica admission. Evidence: `/tmp/ironflow-replica-review.ts` and `/tmp/ironflow-replica-review-D1xFe7`.

## Outcome and validation

Resolved on 2026-09-14. SQL URL resolution now lives in `cli/sql_config.rs`.
It resolves environment-over-YAML precedence and compares the selected backend
with the existing `SqlDialect::from_url` detection before either SQL factory
connects. PostgreSQL requires an explicit `postgres://` or `postgresql://` URL;
SQLite accepts `sqlite:` URLs and retains its omitted-URL default local files.
Empty, unsupported, and mismatched schemes fail with a diagnostic naming the
store and setting, never the URL or a raw URL-parser error. Invalid environment
values do not fall back to YAML.

`serve` preflights both selected SQL URLs before opening either store, including
in standalone mode. Replica admission still rejects JSON/SQLite/memory backend
labels. Non-SQL backends ignore unrelated SQL URL settings. State-store CLI
commands also validate through their shared factory, and PostgreSQL feature
guards remain in place. The check establishes dialect identity, not database
topology, credentials, reachability, or whether all replicas use the same
database and namespace. Low-level dialect-selecting SQL storage constructors
and Redis behavior are unchanged.

The extraction brought `store_factory.rs` from 330 to 281 lines. Its obsolete
size exception was removed, reducing the exception budget from 11 to 10.
No dependencies, database schema, version, or release settings changed.

Validation used current stable Rust 1.98.1, isolated child processes with cleared
environments and temporary working directories, and PostgreSQL 18.6 in the
disposable `ironflow-if123-postgres` container (`postgres:latest`, loopback-only
port and temporary data filesystem). Live test executables ran outside the
repository with explicit disposable `DATABASE_URL` and
`IRONFLOW_POSTGRES_TEST_REQUIRED=1`; no live PostgreSQL test was skipped.

- Before the production fix, six of eight selected full-feature CLI tests
  failed. A `postgres`-labeled SQLite URL was accepted by `list`; invalid server
  configurations or URLs failed to exit within the bounded rejection window.
  Standalone SQLite and default JSON/memory controls passed. The live
  PostgreSQL positive test was intentionally excluded from this baseline.
- After the fix, all nine tests in `test_sql_backend_cli` passed with the
  `--all-features` binary, twice. These include each disguised SQL store under
  environment and YAML configuration, replica and standalone modes, both
  labels disguised together, URL and backend precedence, empty/unsupported
  values, secret-safe errors, and all four state-store command paths. Local
  TCP traps and absence of SQLite files verify rejection before connection
  or database creation. The default-feature build passed its five applicable
  tests as well.
- Two real PostgreSQL-backed `serve` processes, using both PostgreSQL URL
  spellings, passed HTTP readiness, executed workflows, and read each other's
  completed context. Direct database queries verified persisted events for
  both runs. Standalone SQLite passed with omitted and explicit URLs, HTTP
  execution, durable run/event rows, and subsequent CLI inspection. Unused SQL
  settings did not affect JSON/memory serving.
- The focused `cli::` unit selection passed 16 tests by default and 15 with
  all features, including three new scheme/required-URL/redaction tests and
  the respective PostgreSQL feature gates. Existing `test_cli_precedence`
  passed 17 tests and `test_config` passed 14. Across feature variants this is
  57 distinct focused Rust tests, not a full repository suite.
- `cargo fmt --all -- --check`, `python3 -B scripts/check_module_size.py`,
  `cargo clippy --all-targets -- -D warnings`,
  `cargo clippy --all-targets --all-features -- -D warnings`, and
  `cargo audit --deny warnings` passed. The 16 module-size checker tests passed;
  `cargo test --doc` passed with zero runnable doctests.
- Bun parsed the updated replica YAML fixture, and the binary validated its
  four Lua flows (`artifact_consume`, `artifact_produce`, `hold`, and `quick`).
  README, CLI/storage, architecture, replica deployment, and config field docs
  now state the URL/dialect contract. No Lua API changed.
- Both test servers were reaped, the disposable PostgreSQL container was
  removed, and the pre-existing containers were left untouched.

This is local compiled CLI/serve and live-storage evidence, not a repeat of the
full Docker replica fault gate, a hosted deployment, or release validation.
No commit of this issue or push was performed.
