# IF-214 — Event streams can be lost when a delete overlaps a new run or incarnation admission fails

## Evidence and boundary

Recorded on 2026-11-13 from the IF-184 fix. Both items are by reading; the
fix session reasoned about them and did not reproduce them.

- (a) State and events are deleted in two steps. A `DELETE /runs/{id}` that
  overlaps a new submission of the same deterministic ID (an idempotency key
  or a scheduled instant) can remove the new run's first events and fence
  them. The documents tell callers to wait for the `DELETE` response.
- (b) A failed or timed-out `begin_incarnation` (2-second bound) is only
  logged. The run then executes normally with no events and a silent SSE
  stream. There is no retry and no metric of its own.
- (c) Measured while fixing IF-216: a Redis legacy event stream whose expiry
  elapses during a migration call is reported once as `Corruption`
  ("Blocked Redis legacy event migration") although nothing is corrupt; the
  next call returns an empty stream. No data is lost and no test covers it.

Boundary: run state is unaffected in both cases; only events and SSE are
lost. A scheduled run cannot be told to wait for a `DELETE`, so (a) is not
fully a caller obligation.

## Required outcome and acceptance

- (a) Make the state delete report which incarnation it removed and have the
  event delete fence only that one, or reproduce the race and show it cannot
  affect a newer incarnation.
- (b) Retry admission within a small bound and count failures in a metric;
  if it still fails, surface it on the run (a warning event or a field)
  instead of only in the log.
- (c) Report an expired stream as expired, not as corruption.
- Regressions on memory, SQL and Redis for (a) and (b), and on Redis for (c).
