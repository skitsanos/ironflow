# IF-214 — Event streams can be lost when a delete overlaps a new run or incarnation admission fails

## Evidence and boundary

Recorded on 2026-11-13 from the IF-184 fix. Both items are by reading; the
fix session reasoned about them and did not reproduce them.

- (a) State and events are deleted in two steps. A `DELETE /runs/{id}` that
  overlaps a new submission of the same deterministic ID (an idempotency key
  or a scheduled instant) can remove the new run's first events and fence
  them. The documents tell callers to wait for the `DELETE` response.
- (b) A failed or timed-out `begin_incarnation` (2-second bound) is only
  logged. The run then executes normally with no events and a silent SSE
  stream. There is no retry and no metric of its own.
- (c) Measured while fixing IF-216: a Redis legacy event stream whose expiry
  elapses during a migration call is reported once as `Corruption`
  ("Blocked Redis legacy event migration") although nothing is corrupt; the
  next call returns an empty stream. No data is lost and no test covers it.

Boundary: run state is unaffected in both cases; only events and SSE are
lost. A scheduled run cannot be told to wait for a `DELETE`, so (a) is not
fully a caller obligation.

## Outcome and validation

Resolved on 2026-11-15. All three items were reproduced before the fix.

- (a) Every event backend records the incarnation that owns a stream when
  the run starts and removes events an earlier one left behind. The SQL and
  Redis state stores report the incarnation a delete removed, and the event
  delete is a no-op once the stream has admitted another one. The admission
  read before the state delete stands in for a store that reports nothing
  (JSON, custom stores, older runs) and guards the orphan sweep of a
  retried delete, which had the same race.
- (b) Admission is attempted three times, one second each.
  `ironflow_event_admissions_total` counts `admitted`,
  `admitted_after_retry` and `failed`; a run that was not admitted carries
  the context key `_event_stream_warning`.
- (c) A quarantined stream with a deadline that is gone reads as empty once
  the deadline has passed and is a retryable `Conflict` before.

Decisions a maintainer may overrule:

- An admitted run rejects a publisher that names no incarnation, even if
  the ID was never deleted.
- The failure in (b) is a context key, not an event, because a closed fence
  rejects events. A hanging event store can delay the first task by 3.25 s
  (was 2 s).
- A retried `DELETE` that finds state absent and the stream owned by a
  newer run returns `404`.

Boundary: with a state store that reports no incarnation, two overlapping
deletes plus a resubmission can leave the newer run's events without state
until the next `DELETE` or run under that ID. An older replica deletes in
the old way during a rolling upgrade. Storage grows by a nullable
`incarnation` column on the SQL runs table and one event-deletion row,
Redis key or memory entry per run.

Evidence:

- Before: with the event step of `DELETE` paused while the same key was
  submitted again, the new run's stream was empty on memory, SQLite,
  PostgreSQL 18.7 and Redis 8.10 (8 of 8 tests failed). An injected
  admission failure was tried once on all four (4 of 4 failed). Both (c)
  tests returned `Corruption`.
- After, focused: the same tests pass, plus the reported incarnation, the
  runs-table upgrade, the retry bound, the timeout path and the counter.
  The Redis legacy tests passed 10 of 10 repeats; neither (c) test sleeps
  past an expiry.
- After, feature-enabled against disposable PostgreSQL and Redis with the
  required-test flags: library 783, `storage` 133, `storage_postgres` 13,
  `storage_redis` 102. Default features: `api` 68, `engine` 304,
  `scheduler` 128, `cli` 108, `serial` 191 with one test thread.
- Clippy with and without `--features postgres,redis`, formatting and the
  module-size gate pass; two size exceptions were retired.
- Fixed while validating: the delete-and-resubmit tests failed in 7 of 12
  runs with `503` from the process-wide flow-load limit; the helper retries.
- Not run: the integration gate, CI, a multi-replica deployment and a live
  rolling upgrade.
