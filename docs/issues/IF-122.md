# IF-122 — SQL's unowned context merge loses concurrent successful updates

## Required outcome and acceptance

- Make unowned context read/merge/write atomic through transaction locking or incarnation/revision CAS.
- Concurrent disjoint successful updates must both survive, and delete/recreate must reject stale-incarnation writes.
- Add actual concurrent StateStore tests for SQLite and disposable PostgreSQL while preserving the separate owned/fenced update path.

## Evidence and cause

Fresh review on 2026-09-12, finding R17. See
[AUDIT_2026-09-12.md](./AUDIT_2026-09-12.md) for the reviewed candidate,
evidence boundaries, and complete finding-to-issue mapping.

[Source: sql_store/mutations.rs:155](../../src/storage/sql_store/mutations.rs).

Context is read outside a transaction, merged locally, and replaced unconditionally by run ID. Concurrent disjoint merges can both succeed while one erases the other; deletion/recreation can also admit a stale write to a new incarnation. Use transactional locking or revision CAS. Evidence: static Rust call tracing plus an actual in-memory SQLite query-level interleaving, not a compiled concurrent StateStore test. The separate engine-owned update path is fenced and is not implicated.

## Outcome and validation

Resolved on 2026-09-14. Unowned context updates now begin a transaction, take
the existing run mutation lock before reading context, merge and write through
that same connection, and commit only after a successful write. SQLite obtains
its writer lock before the first read; PostgreSQL locks the run with
`FOR UPDATE`. Errors and cancellation before commit begins drop the transaction
for rollback instead of leaving an independently queued autocommit write.
Cancellation or connection loss after COMMIT submission can still leave an
uncertain commit outcome; this is not an exactly-once acknowledgement guarantee.

The separate owned path retains its live-lease check and also takes the run
lock before reading context, preserving lease-then-run lock order. The original
review correctly separated owned-only fencing, but the new controlled
PostgreSQL regression demonstrated that the lease lock alone does not serialize
an owned writer with an unowned writer. Both paths now use the same context
reader with an explicit executor, keeping transactional reads off the pool.

Merging remains shallow: absent keys survive, duplicate keys take the last
serialized writer's value, and JSON null is a value rather than a deletion.
A stored context snapshot cannot span deletion/recreation. A missing run
returns `NotFound`; an unowned call whose first locked read occurs after
recreation can legitimately update the replacement. The API carries no owner
or incarnation token for unowned calls, and this change cannot reject deltas
prepared externally against an old incarnation. All concurrent SQL writers
must be upgraded before relying on the new guarantee. No schema, dependency,
configuration, or public workflow API changed.

Validation used file-backed SQLite in WAL mode and disposable PostgreSQL 18.6
(`postgres:latest`, container `ironflow-if122-postgres`) bound only to loopback
with a temporary data filesystem. Feature-enabled test executables ran from
`/tmp`, outside the repository's dotenv lookup path, with explicit disposable
`DATABASE_URL` and `IRONFLOW_POSTGRES_TEST_REQUIRED=1`. No live tests were skipped.

- Before the production fix, four of five compiled SQLite regressions failed:
  disjoint unowned merges, mixed owned/unowned merges, delete/recreate snapshot
  safety, and rollback of trigger side effects on a failed merge. Four of five
  PostgreSQL regressions failed: concurrent merges, two deterministically
  blocked unowned writers, a controlled mixed owned/unowned race, and a
  cancelled blocked write that later committed.
- After the fix, `cargo test --test test_sql_context_concurrency -- --nocapture`
  passed all five default-feature SQLite tests. Building the same target with
  `--features postgres` and running its executable passed all ten regressions;
  three additional complete runs passed. These cover independent store pools,
  20 simultaneous writers over six rounds per merge mode/backend, 40
  delete/recreate races per backend per run, shallow merge/null semantics,
  missing runs, corrupt JSON, rejected SQL writes, cancelled lock waits, and
  recovery after rollback. PostgreSQL lock races observe `pg_stat_activity`
  before releasing their controlling row/advisory locks.
- The feature-enabled `test_sql_state_concurrency` executable passed both
  existing task-upsert/deletion/pruning tests. `test_state_stores` passed ten
  tests with its `sql` filter plus the separately selected
  `postgres_run_leases_protect_live_peers_and_reconcile_expired_owners` test.
  Together with the new regressions, 23 distinct focused tests passed.
- `cargo fmt --all -- --check`, `python3 -B scripts/check_module_size.py`,
  `cargo clippy --all-targets -- -D warnings`,
  `cargo clippy --all-targets --features postgres -- -D warnings`, and
  `cargo audit --deny warnings` passed on current stable Rust 1.98.1. No module
  size exceptions changed.
- The disposable PostgreSQL container was removed and removal verified; the
  pre-existing unrelated PostgreSQL container was left untouched.

Architecture and CLI/storage documentation describe the locking, merge, and
rolling-upgrade boundaries. There is no new Lua API requiring an example.
Validation was focused and local, not a full integration/release gate or a
deployed CLI/serve smoke test. No commit of this issue or push was performed.
