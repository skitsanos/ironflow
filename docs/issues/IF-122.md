# IF-122 — SQL's unowned context merge loses concurrent successful updates

## Required outcome and acceptance

- Make unowned context read/merge/write atomic through transaction locking or incarnation/revision CAS.
- Concurrent disjoint successful updates must both survive, and delete/recreate must reject stale-incarnation writes.
- Add actual concurrent StateStore tests for SQLite and disposable PostgreSQL while preserving the separate owned/fenced update path.

## Evidence and cause

Fresh review on 2026-09-12, finding R17. See
[AUDIT_2026-09-12.md](./AUDIT_2026-09-12.md) for the reviewed candidate,
evidence boundaries, and complete finding-to-issue mapping.

[Source: sql_store/mutations.rs:155](../../src/storage/sql_store/mutations.rs).

Context is read outside a transaction, merged locally, and replaced unconditionally by run ID. Concurrent disjoint merges can both succeed while one erases the other; deletion/recreation can also admit a stale write to a new incarnation. Use transactional locking or revision CAS. Evidence: static Rust call tracing plus an actual in-memory SQLite query-level interleaving, not a compiled concurrent StateStore test. The separate engine-owned update path is fenced and is not implicated.

## Progress

Open. Implementation and regression validation are pending.
