# IF-132 — A continuously progressing artifact download delays cancellation until EOF

## Required outcome and acceptance

- Observe cancellation while chunks keep arriving by checking per chunk or retaining a stable polling deadline.
- Stop and clean staging promptly after timeout without waiting for remote EOF; retain admission ownership until physical work stops.
- Use a bounded loopback stream whose chunks arrive faster than the polling interval, plus a successful integrity-checked transfer and temporary-file cleanup checks.

## Evidence and cause

Fresh review on 2026-09-12, finding R27. See
[AUDIT_2026-09-12.md](./AUDIT_2026-09-12.md) for the reviewed candidate,
evidence boundaries, and complete finding-to-issue mapping.

[Source: artifacts/remote.rs:200](../../src/artifacts/remote.rs).

The 100 ms cancellation timer is recreated for each body chunk. Chunks arriving every 20 ms keep winning, and no checkpoint runs in the body path. A 0.5-second timed-out restore still received and staged all 128 KiB over about 3.5 seconds; the tracked worker held workflow drain until completion. Check cancellation per chunk or retain a stable polling deadline. Evidence: `artifact-cancel/result.json` and `events.json` in the artifact evidence directory. This is a bounded loopback transfer, not a load test.

## Outcome and validation

Resolved on 2026-09-13. The shared remote restore path now checks its
`ExecutionControl` after response headers, before every body wait, and after
each chunk/EOF result. Fast arrivals can no longer repeatedly win the select
without observing cancellation. The existing 100 ms poll remains in place for
idle body waits, and publication retains its existing final checkpoint.

The fix applies to descriptor-based `ArtifactStore::open` and canonical-URI
`open_uri` restores. It preserves declared/actual byte admission, SHA-256
verification, immutable publication, and existing temporary-file cleanup. No
new worker is spawned: built-in consumers still use tracked blocking workers,
and physical worker lifetime remains attached to task/run admission.

### Contract boundary

- Cancellation during a restore drops the response and removes private staging
  before worker exit, without publishing a partial cache object. `write_file`
  leaves an existing output unchanged when its input restore is cancelled.
- Checkpoints are cooperative, not hard real-time preemption. An in-progress
  synchronous write, hash, or filesystem sync must return before the next check.
  The 100 ms idle poll is not a total cancellation latency guarantee.
- No change to upload/retry semantics, object authorization, other storage
  backends, dependencies, toolchain pins, configuration defaults, skills, or hooks.
  Architecture and `write_file` docs now describe the shared restore boundary;
  existing artifact handoff/replica-consumer examples explain cancellation.

### Regression evidence

The new progressing-download test was run before the fix. With a bounded
128 KiB object delivered in 1 KiB chunks every 20 ms, the first cancelled
descriptor restore still had not returned after the one-second observation
window; the fixture had already emitted 43 chunks. It failed with
`cancelled restore kept downloading`. The same regression passes after the fix.

Post-fix validation on Rust 1.98.1:

- `cargo test --lib artifacts::`: 19 tests passed. Four new restore tests cover
  progressing and idle bodies, waiter-drop cancellation and execution deadlines,
  both descriptor/URI entry points, staging removal before EOF, successful exact
  byte restoration, cache reuse without another GET, immutable cache files, and
  digest-failure cleanup. Existing artifact integrity, publication, remote retry,
  repair, and retention-related checks remain green.
- The new worker-lifetime test deliberately holds the blocking closure after
  restore cleanup. Both run and attempt worker sets must remain non-idle until
  that physical worker is released, then drain. This proves tracked-worker
  lifetime, not a separately deployed API admission scenario.
- `cargo test --test test_artifact_restore_cli --test test_artifact_nodes`:
  6 tests passed. The replica-consumer example validates and executes descriptor
  and URI restores through the actual CLI against a loopback S3-compatible
  fixture. A one-second run deadline cancels an already progressing body before
  the whole object arrives, exits unsuccessfully with `Status: cancelled`,
  publishes no write result fields, removes staging, and preserves an existing
  destination. The handoff example validates; existing extractor/image artifact
  consumers also pass.
- `cargo fmt --all -- --check`, `cargo clippy --all-targets -- -D warnings`,
  module-size policy, `cargo audit --deny warnings`, issue-registry validation,
  and `git diff --check` passed.

This is 25 distinct focused tests, not a full integration gate or hosted S3,
multi-replica, or deployed API validation. Fixtures use bounded synthetic data,
temporary directories, explicit test credentials, and loopback endpoints. CLI
children use cleared environments and isolated AWS config paths; no real
credentials or shared service state were used.
