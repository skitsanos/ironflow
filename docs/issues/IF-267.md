# IF-267 — SQLite stores used the rollback journal, so open readers blocked and failed writers

## Evidence and boundary

Follow-up to IF-265. Read: the SQL stores set no journal mode and sqlx 0.9
leaves it unset, so every SQLite database used the rollback journal.
`ironflow serve` runs API, scheduler and executors against one database.

Reproduced on 2026-11-22 with a temporary probe against the store API (three
rounds each; absolute numbers depend on the disk): four writers
made 150 task upserts each with 32 KiB outputs while eight readers looped
over run inspections and listing pages.

| Mode | Write p50 | p99 | max | Wall time | Write failures |
|---|---|---|---|---|---|
| rollback, FULL | 4.1–4.3 ms | 28–61 ms | 96–123 ms | 0.93–1.00 s | 0 |
| WAL, FULL | 1.9 ms | 6.1–6.8 ms | 24–27 ms | 0.35–0.37 s | 0 |
| WAL, NORMAL | 1.9 ms | 5.5–5.9 ms | 12–25 ms | 0.35 s | 0 |

With an inspection held open, a rollback-mode upsert failed after 5.2 s (the
busy timeout); in WAL it committed in 1.7 ms. Serial writes without readers:
1.07 ms rollback, 0.82 ms WAL FULL, 0.78 ms WAL NORMAL.

Also checked:

- Side files get the database file's mode. SQLite created the default
  database `0644` under the umask, inside the `0700` store directory, so the
  directory was the only owner-only boundary.
- CLI (before the close below): after `ironflow run` exited,
  `ironflow.sqlite-wal` remained. A copy of
  the database file alone held every run in the trials, but that depends on
  the close at exit, so backups must use `.backup`, `VACUUM INTO` (both
  checked) or the whole directory. An api test that scanned the raw file
  after killing `serve` failed in WAL for that reason; it now reads the
  schema through SQLite.
- Before the follow-up, the opt-out only warned when it could not switch a
  WAL file in a read-only directory, and `ironflow list` continued in WAL.
- `ironflow serve`: default store opens in WAL; run and list work.
- There is no JSON-to-SQLite import, so no migration path changes.
- Read, not reproduced: WAL needs shared memory, so all processes must share
  one host, which rules out network filesystems. The container store check
  was not run.

## Outcome and validation

WAL is the default for every SQLite file the state and event stores open,
new or existing; `:memory:` stays rejected. The mode is set once per open,
since it persists in the file. Each connection pins `synchronous = FULL` and a
64 MiB `journal_size_limit`. NORMAL saved about 5 %, while FULL keeps a
reported schedule claim, lease or task result durable across power loss.

`IRONFLOW_SQLITE_WAL=false` selects the rollback journal and switches a WAL
file back. It is a startup-validated toggle (`true`/`false` only), and the
CLI rejects other values before creating the default directory or database.
If SQLite cannot confirm `DELETE`, the store refuses to open. Only WAL
selection can fall back to the existing mode with a warning. Embedders get
the same policy through `new_with_journal_mode`.

CLI regressions cover invalid configuration on a fresh path and a held WAL
file followed by a successful rollback-mode retry. The WAL and PostgreSQL
snapshot tests require the replacement to commit before the inspection reads
its tasks; the rollback test holds the reader until the writer times out.

On Unix the CLI now creates a missing default `ironflow.sqlite` or
`ironflow-events.sqlite` as `0600` before SQLite opens it, so the side files
are owner-only as well. An existing file keeps its mode and contents, and a
file named by a configured `sqlite:` URL is still created under the umask.

`StateStore::close` and `EventStore::close` (default no-op; the SQL stores
close their pool) let the CLI close its stores after every command and after
`serve` stops gracefully, bounded at 5 s with a warning. SQLite then folds the
WAL into the database file and removes the side files.

Validation on 2026-11-22:

- Failing first: with the switch disabled, the seven WAL tests failed and
  the rollback tests passed. Before the owner-only creation, the
  default-file unit test and the CLI default-backend test failed (`0644`).
  Before the close, the CLI side-file test failed (`run left
  ironflow.sqlite-wal behind`), and the store close test failed with the
  SQL `close` stubbed out.
- `cargo test --lib sql_store`, `--lib sql_config`, `--lib sqlite_journal`, `--lib limits::`,
  `--lib store_factory`, the `storage`, `api`, `cli`, `engine`, `scheduler`
  and `examples` binaries, and `--test serial test_sqlite_journal_env:: --
  --test-threads=1` pass (default features, SQLite only).
- `cargo check --features postgres,redis --all-targets`, `cargo fmt --all
  -- --check`, `python3 -B scripts/check_module_size.py` and `cargo clippy
  --all-targets -- -D warnings` pass.
