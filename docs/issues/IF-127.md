# IF-127 — Arango cursor IDs are discarded

## Required outcome and acceptance

- Expose cursor identity with continuation/close operations or consume all pages through explicitly bounded pagination.
- Preserve documented has_more/truncation semantics and clean up cursors on failure or cancellation where supported.
- Test multiple pages, empty/final pages, provider errors, and explicit close against the Cursor API contract; label mock versus live coverage.

## Evidence and cause

Fresh review on 2026-09-12, finding R22. See
[AUDIT_2026-09-12.md](./AUDIT_2026-09-12.md) for the reviewed candidate,
evidence boundaries, and complete finding-to-issue mapping.

[Source: database/arangodb.rs:162](../../src/nodes/database/arangodb.rs).

A valid paginated response exposes `has_more=true` but discards its cursor ID, so the caller cannot continue or explicitly close it. A loopback Cursor API fixture confirmed only the initial POST occurred. Preserve/expose the cursor with continuation/close operations or consume bounded pages internally. This is a mock-protocol test, not a live ArangoDB test; truncation is signalled rather than entirely silent.

## Outcome and validation

Resolved on 2026-09-14. `arangodb_aql` retains its one-batch `query` default
and now returns `{output_key}_cursor_id` alongside the existing result, count,
and has-more fields. `action = "next"` posts to the cursor-specific endpoint
without repeating the query or bind variables. `action = "close"` deletes that
cursor and accepts HTTP 202 or the specific HTTP 404/error 1600 cursor-not-found
response. Unrelated 404, authentication, provider, and malformed-response errors
remain failures. No automatic draining or query/next replay was added.

The node validates action and cursor identity before network access. Database
names are appended through URL path-segment encoding; cursor IDs are bounded to
one safe ASCII identifier. A has-more page without a valid ID, a changed ID, or
invalid result/has-more fields fails rather than reporting unusable pagination
as success. Empty pages can still have more results. Absent cursor IDs and
statistics explicitly become null, preventing stale metadata under a reused
output prefix. A final response that retains an ID exposes it for explicit close.

Connection/authentication resolution, same-origin redirect policy, and the
context-in-AQL injection prohibition are preserved. Query options accept a
validated positive `batchSize` and optional positive `ttl`, including numeric
context templates. Response admission now uses `IRONFLOW_MAX_HTTP_BODY_BYTES`
(50 MiB by default), checking declared and streamed bytes before JSON decoding.
Oversized responses fail; the node never silently truncates a batch. Decoding
can use additional memory, and this byte budget is not a total query-row cap.

An owned cleanup guard attempts one authenticated, three-second DELETE when a
validated continuation/close request fails or is cancelled. A query response
with a known ID arms the same guard before the remaining page validation.
Successful operations release this guard and transfer the cursor to the
workflow. Cleanup failures do not replace the original operation error, and a
failed continuation must not be treated as replayable. This cleanup is not
durable: unknown IDs, runtime/process shutdown, network failures, abandoned
successful pages, and later workflow-step failures still require server TTL
or explicit recovery-path close. Already completed AQL writes cannot be undone.

The node, configuration parser, and HTTP/lifecycle implementation are separate
focused modules, all below 300 lines. No module exception, dependency, database
schema, feature flag, or project version changed. Node, CLI-limit, architecture,
README, and example documentation now describe this contract. The new
`aql_pagination.lua` example reads five generated values in three batches and
closes the original cursor; the catalog now includes 138 flows.

Validation used current stable Rust 1.98.1 and deterministic loopback fixtures
following the documented
[ArangoDB Cursor API](https://docs.arango.ai/arangodb/stable/develop/http-api/queries/aql-queries/):

- Before the implementation, all five initial cursor regressions failed: IDs
  were absent, close required a query, has-more without an ID and malformed rows
  were accepted, and unknown actions reached the network. These failures are
  separate from the original review's mock-protocol observation above.
- `cargo test --test test_arangodb_cursor --test test_arangodb_node
  --test test_provider_redirect_security -- --nocapture` passed 21 tests.
  They cover three-page continuation without query replay, empty intermediate
  and final pages, explicit and expired close, TTL/batch interpolation, Basic
  and Bearer authentication, encoded database segments, invalid local inputs,
  changed IDs, HTTP and JSON errors, timeout/cancellation cleanup, unknown-ID
  cancellation, and existing query-injection and redirect protections.
- The CLI regression strictly validated all three ArangoDB Lua examples and
  ran the new five-step pagination example against the fixture. It verified
  `[1, 2]`, `[3, 4]`, `[5]`, the cleared final cursor, and explicit close, with
  exactly three POSTs and one DELETE. Its child process used a cleared
  environment, synthetic connection settings, and a temporary working directory;
  project dotenv and external credentials were not loaded.
- `cargo test --lib nodes::database::arangodb:: -- --nocapture` passed three
  response-admission tests. A real loopback HTTP connection withholds the body
  after oversized Content-Length headers, proving preflight rejection; streaming
  fixtures test cumulative/exact limits, invalid JSON, and secret-safe read errors.
  An initial synthetic-response Content-Length test used the wrong Reqwest body
  model and was replaced; it is not evidence of a production preflight defect.
- The focused example-catalog classification test passed. This totals 25 distinct
  focused Rust tests; only the three affected Lua examples were validated, not
  every example or the full repository test suite.
- `cargo fmt --all -- --check`, `python3 -B scripts/check_module_size.py`,
  `cargo clippy --all-targets -- -D warnings`, and
  `cargo audit --deny warnings` passed. A Clippy finding in the new loopback
  fixture was fixed by reading complete request headers within a fixed budget.

This is local node/CLI and mock Cursor API evidence, not live ArangoDB, cluster,
server TTL-expiry, hosted deployment, or release validation. The full integration
gate remains deferred to the next authorized push or release.
