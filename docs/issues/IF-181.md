# IF-181 — A context nested 126 levels deep makes a run record unreadable and blocks serve startup

## Evidence and boundary

Review of `develop` at 1.21.1-dev.1 on 2026-11-12.

- Reproduced on the JSON store with a local optimized build:
  `ironflow run flow.lua -c '{"a":[[ ... ]]}'` with the value nested 126
  deep fails with `could not be terminalized ... Failed to parse run ...
  recursion limit exceeded`. The run stays `pending`, its lease file remains,
  and `ironflow inspect` returns the same parse error. After the lease
  expired, `ironflow serve` on that store exited with status 1 and the same
  error; a fresh JSON store started normally.
- Depth 125 works, and 127 is rejected at input. The same depth-126 context
  on the default SQLite store completes and reads back.
- Cause: inputs are parsed with serde_json's default limit of 128, so a
  value 126 deep is admitted. The JSON and Redis stores wrap the context in a
  run record, one level deeper, serialize it without a limit, and then fail
  every read. All owned mutations read first, so the coordinator can never
  write a terminal status.
- Redis, by reading only: `reconcile_owned_runs`
  (`src/storage/redis_store/leases.rs:118-151`) takes expired leases in order
  and returns the first error that is not NotFound, so one such record stays
  at the head and no later expired lease is reaped. Startup reconciliation
  propagates the error (`src/api/server.rs:32-35`).
- Other sources of deep values: webhook and API JSON bodies, `json_parse`,
  and `xml_parse` (IF-037 caps depth at 128).

Boundary: not executed against Redis. The JSON store is maintenance-only
(IF-163) but still supported. An API key is needed to submit a body unless
the server is unauthenticated on loopback.

## Required outcome and acceptance

- Reject context and task output deeper than the stores can read back,
  before persistence, with a step or request error. Keep one shared limit
  for input parsing and storage.
- Make lease reconciliation skip and report a record it cannot decode
  instead of aborting the pass or startup, and let `delete_run` remove such
  a record.
- Regressions: depth-126 context through the CLI, a webhook body and
  `json_parse` on JSON and Redis; an undecodable record with an expired
  lease does not stop reconciliation of the next run or `serve` startup.
- Evidence: focused storage tests, the `redis` feature test against a
  disposable instance, and the JSON lease suite.

## Outcome and validation

Resolved on 2026-11-12.

- One limit, `util::json_depth::MAX_JSON_VALUE_DEPTH` = 123: a context or
  step-output value may nest that many arrays and objects. `serde_json` reads
  127, and a stored run record wraps a task-output value in four objects, so
  the task record, not the context, sets the number (a unit test pins both
  sides against a serialized `RunInfo`).
- Input: `ironflow run --context`, `POST /flows/run` and webhook bodies refuse
  a deeper value before a run exists (exit 1, `400`). `WorkflowEngine`
  refuses it for every other caller. The `json_parse` node and Lua global
  refuse deeper text.
- Step output: a deeper output fails its step with `step output refused`,
  without retry. Deeper structured failure output is dropped from the task
  record and the recovery handler.
- Storage: the JSON, SQL and Redis stores return `InvalidInput` from
  `init_run`, `update_ctx`, `upsert_task` and their owned forms, before
  writing.
- Reconciliation: JSON and Redis skip a record they cannot decode, warn with
  the run ID and continue. The record and its lease stay until `delete_run`.
  Redis pages past skipped records. JSON `delete_run` treats an undecodable
  record as non-terminal, so only a live lease protects it.
- Documented in `docs/CLI_REFERENCE.md` ("JSON nesting limit"),
  `docs/LUA_FLOW_GUIDE.md`, `docs/ARCHITECTURE.md`, the `json_parse` and
  `xml_parse` pages and `docs/releases/next.md`.

Found while fixing, same cause: step output is stored one object deeper than
context, so an output value of 124 was already unreadable on the JSON store
(reproduced; Redis stores the same record). On SQLite a `json_parse` output
of 127 left a `stalled` run that `inspect` could not read (reproduced with a
pre-fix build); SQL reconciliation never decodes, so it was not blocked.

Contract boundary: values of 124 to 126 that the SQL stores read back before
are now refused on every store. Existing undecodable records are not
repaired, only skipped and deletable: `ironflow list` still shows one and
`inspect` still reports the parse error (checked on a JSON store), and by
reading the unbounded `StateStore::list_runs` method still fails on one
(tracked in [IF-207](IF-207.md)).
Faults in a lease file or in the Redis index keys still fail a pass.
Custom stores are not checked unless they call `util::json_depth`.
PostgreSQL shares the SQL store code path and was not run live.

Regressions: `tests/test_json_depth_stores.rs`, `test_output_depth_limit.rs`,
`test_cli_context_depth.rs`, `test_request_context_depth.rs`,
`test_redis_json_depth.rs`, a `serve` startup test in
`src/api/server/tests.rs`, and unit tests beside the changed modules.

Validation on the final tree:

- Before the fix (default features): 11 of the 13 new integration
  tests and the `serve` startup test failed. The JSON store stored the
  depth-126 context; reconciliation and startup stopped at `Failed to parse
  run ... recursion limit exceeded`; `delete_run` returned `Corruption`; the
  CLI and `json_parse` runs ended `could not be terminalized`; the webhook
  returned 500. The two that passed pin depth 123 reading back.
- Before the fix (live Redis 7, `redis` feature): 6 of 7 failed
  the same way, which confirms what the finding had only read: the pass
  returned `Failed to parse Redis run 'a-poisoned'` and left the next expired
  lease unreaped. The seventh passed: Redis `delete_run` already removed such
  a record, because its script decodes with Lua `cjson`.
- After, default features: `cargo test --lib` 653 passed, 1 ignored;
  `--test storage` 89; `--test engine` 291; `--test api` 59; `--test cli` 94;
  `--test nodes` 247; `--test serial -- --test-threads=1` 186. Also run
  because they drive the changed engine and Lua paths: `scheduler` 109,
  `examples` 11, `nodes_network` 133, `documents` 136 (3 ignored),
  `conversion_limits_env` 2, `scheduler_admission` 1, `flow_load_admission` 1.
- After, live service: `redis` feature against a disposable Redis 7 container
  with `IRONFLOW_REDIS_TEST_REQUIRED=1`: `cargo test --features redis --test
  storage_redis` 92 passed, including the 7 new tests and the existing
  script-fault suite.
- `cargo fmt --all -- --check`, `python3 -B scripts/check_module_size.py`,
  `cargo clippy --all-targets -- -D warnings` and
  `cargo clippy --all-targets --features postgres,redis -- -D warnings`
  passed.
- Not run: the full integration gate, live PostgreSQL, a deployed instance,
  and the 90-second lease expiry through a real `serve` process (the startup
  path is covered by the unit test with an already expired lease).
