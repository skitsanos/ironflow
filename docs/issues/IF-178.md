# IF-178 — extract_pdf font decoding is unbounded for wide ToUnicode ranges and long glyph strings

## Evidence and boundary

Review of `develop` at 1.21.1-dev.1 on 2026-11-12.

1. ToUnicode ranges (reproduced). Hand-built one-page PDFs of about 1.2 KB
   whose font carries a ToUnicode CMap with a single `bfrange`:

   | Range | Result (local debug build) |
   |---|---|
   | `<0001> <00FF>` | 37 MB peak RSS, under 1 s |
   | `<000001> <FFFFFE>` | 286 MB peak RSS, 16.7 s |
   | `<00000001> <FFFFFFFE>` | still running and growing when stopped at 20 s, with `:timeout(5)` on the step |

   On the optimized build the 4-byte case was still running at 25 s with
   `:timeout(2)`. `extract_page` (`src/nodes/extract/pdf/text.rs:15-19`)
   calls `get_font_encoding_with_limit` for each font on each page; the limit
   bounds the CMap stream's decompressed bytes only. lopdf 0.46.0 then builds
   a reverse map by iterating every code in every range
   (`encodings/cmap.rs:93-142`), inside one uninterruptible call on a tracked
   worker. The run cannot finish until it returns, and the map is rebuilt per
   page.
2. Glyph strings (by reading, not executed). `collect`
   (`text.rs:85-91`) charges one item per 4 KiB of operand and then decodes
   the whole operand with `bytes_to_string`. A `bfchar` target may hold 256
   UTF-16 units, so a multi-megabyte `Tj` string expands by orders of
   magnitude before `IRONFLOW_MAX_EXTRACT_OUTPUT_BYTES` is compared.

Boundary: `docs/nodes/extract_pdf.md` describes CMap decoding as bounded.
IF-091 and IF-111 bounded load and stream decompression, not range spans or
decoded length. Memory figures for the 4-byte case are extrapolated.

## Required outcome and acceptance

- Before calling lopdf, scan each ToUnicode stream and charge total range
  span and longest target against an explicit budget; reject over-budget
  fonts as a node error. Cache decoded encodings per font object.
- Decode operands in bounded chunks, admitting each against the remaining
  output budget, or reject when input length times the longest target exceeds
  it.
- Regressions: the three PDFs above (the two wide ones fail fast with bounded
  memory), a long-string fixture, and unchanged output for the existing CID
  fixtures (IF-093, IF-156).
- Report the range-expansion behaviour upstream and record the link here.

## Outcome and validation

Resolved on 2026-11-12 at 1.21.1-dev.3.

Re-check against lopdf 0.47.0, the pinned release, before designing the fix:

- Defect 1 is unchanged. `ToUnicodeCMap::from_sections` still inserts one
  reverse-map entry per code of every range, and the three PDFs reproduce
  (table below).
- Defect 2 was confirmed with a generated fixture: a 1.6 KB PDF whose one-byte
  code maps to 256 units, shown 262,144 times, reached 577 MB before the
  output limit was compared.
- Upstream: lopdf `main` caps the reverse map at 65,536 entries since
  [J-F-Liu/lopdf#665](https://github.com/J-F-Liu/lopdf/pull/665) (2026-11-10),
  not yet released. Read only, not executed: that loop does not count codes
  past the end of an array destination, so `<00000000> <FFFFFFFF> [<0041>]`
  still walks the whole span. Nothing was reported upstream from this work;
  whether to report that remainder is the owner's decision.

Outcome:

- `pdf/cmap_scan.rs` (new) measures a decoded ToUnicode stream in one linear
  pass without building a table. It charges `bfchar` destinations by UTF-16
  units and `bfrange` lines by code span times longest destination. Range mode
  starts at any literal `beginbfrange` and ends only at an `endbfrange`
  outside a comment, so a section cannot be hidden by a comment or a string.
- `pdf/fonts.rs` (new) admits each font dictionary once per call against
  `IRONFLOW_MAX_PDF_EXTRACT_CMAP_ENTRIES` (default 1,048,576, cumulative,
  validated at startup), then lets lopdf decode it once and reuses the
  encoding on every page. An over-budget font is an ordinary node error.
- A glyph string is admitted by its worst case before lopdf decodes it. A
  worst case of at most 1 MiB, or one that fits the remaining output budget,
  is decoded in one call and its text admitted exactly. Above that,
  single-byte fonts are decoded in pieces of at most 1 MiB worst case;
  code-mapped and UTF-16 strings are rejected.
- Docs: `nodes/extract_pdf.md`, `PDF_LOADING.md`, `ARCHITECTURE.md` and the
  limits table in `CLI_REFERENCE.md` state the bound and its units.

Contract boundary:

- Behavior change: fonts whose ToUnicode CMaps total more than the limit fail
  the node; sixteen full two-byte ranges are over the default. A ToUnicode
  stream is charged even when lopdf 0.47 ignores it because of `/Encoding`.
  Two font dictionaries that share one stream are charged twice.
- Behavior change: a code-mapped or UTF-16 glyph string whose worst case
  exceeds both 1 MiB and the remaining output budget is rejected even if its
  actual text would have fitted. The worst case is six UTF-8 bytes per UTF-16
  unit, because lopdf re-reads decoded units that begin with a UTF-8
  byte-order mark.
- The scan over-charges rather than follow ambiguity: range lines inside a
  comment of a `bfrange` section count, and a range destination that contains
  a comment fails the font.
- Not a memory ceiling. lopdf keeps about 130 bytes per admitted entry until
  the call ends: 15 full two-byte fonts (983,040 entries) peaked at 162 MB
  against a 37 MB baseline. Its parse of an admitted CMap is still one
  uninterruptible call, bounded by the limit (2.0 s for that PDF).
- A font-mapping stream is now bounded by the remaining output budget only
  when its font is first used, not on every page.
- No other node resolves font encodings. No flow syntax or node parameter
  changed; the `extract_pdf.lua` example comment now names the limit.
- All measurements are from unoptimized builds on one host.

Validation on 2026-11-12, `ironflow run` with `:timeout(5)` on the step, peak
memory of the CLI process:

| PDF | Before | After |
|---|---|---|
| `<0001> <00FF>`, 1,089 bytes | 37 MB, extracts `ABC` | 37 MB, extracts `ABC` |
| `<000001> <FFFFFE>`, 1,083 bytes | 255 MB, timeout reported after 6.0 s | node error in 0.1 s, 37 MB |
| `<00000001> <FFFFFFFE>`, 1,086 bytes | 1,641 MB and growing, killed at 25 s | node error in 0.1 s, 37 MB |
| long glyph string, 1,646 bytes | 577 MB, then output-limit error | output-limit error in 0.3 s, 38 MB |

- Failing first: of the eight new node tests, five failed on the unfixed
  tree: both wide-range tests, both long-string tests and the cumulative
  budget. The narrow range, the shared-font document and the in-budget long
  destination passed before and after.
- After: `nodes::extract::pdf` 11 unit tests. They include thirteen disguised
  forms of one range that lopdf itself accepts and the scan still charges in
  full, 3,000 generated CMaps of which the more than 1,500 that lopdf accepts
  are compared with its own parse (none under-charged, comment-free ones
  exact), five adversarial fillers of several megabytes scanned in under 5 s
  each, cancellation mid-scan, and the byte-order-mark worst case.
  `test_extract_pdf_font_bounds` 8, two of them through the CLI with the
  child's peak memory held within 48 MiB of the narrow run.
  `test_extract_pdf_font_limits` 1, the limit at its exact boundary.
- Unchanged fixtures: the IF-093 CID fixture test and the IF-156 ActualText
  tests pass without edits. With `--features cjk-fonts`,
  the generated multilingual PDF still round-trips through `extract_pdf`
  (`test_pdf_actual_text` 9).
- Targets: library 650 (1 ignored), `documents` 144 (3 ignored), `nodes` 247,
  `examples` 11, `serial` 187 single-threaded, `extract_execution` 2,
  `limits_defaults` 2, `cli` 92, `engine` 287, `api` 56.
- `cargo fmt --all -- --check`, the module-size gate and
  `cargo clippy --all-targets -- -D warnings` pass.
