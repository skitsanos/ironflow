# IF-185 — Staged writers publish mode 0600 and write_file append loses concurrent writes

## Evidence and boundary

Review of `develop` at 1.21.1-dev.1 on 2026-11-12, reproduced with a local
optimized build under umask 022.

1. File mode.
   - `write_file` creating a new file produced `-rw-------`.
   - Overwriting an existing `0644` file left it `0600`.
   - `append = true` on a `0755` script left it `0600`.
   - The staged file is created with mode `0o600`
     (`src/nodes/file/archive/rooted/unix/syscalls.rs:63-73`) and renamed
     over the destination; only `copy_file` reapplies a mode
     (`src/nodes/file/io/write.rs:149-170, 197-202`).
   - By reading, the same staging call serves `zip_create`, `zip_extract`,
     `pdf_merge`, grouped `pdf_split` and the Markdown document nodes.
2. Concurrent append.
   - A flow with eight parallel `write_file` steps appending one line each
     to the same file, run twice, reported all 16 steps successful and left
     10 lines.
   - Append reads the existing file, writes it plus the new input to a
     staged file and renames (`write.rs:133-137, 177-205`). Two writers read
     the same base and the last rename wins.

Boundary: IF-140 found the same published-`0600` defect and fixed it for
`copy_file` only. `docs/nodes/write_file.md` does not mention a private mode
or append concurrency. Before the staged writer, `write_file` honoured the
umask, kept an existing mode, and used `O_APPEND`. Portable (non-Unix)
behaviour was not checked.

Added on 2026-11-12 with IF-179: `image_resize`, `image_crop`, `image_rotate`,
`image_flip`, `image_grayscale`, `image_watermark`, `image_convert`,
`image_to_pdf` and the `transcribe` `output_file` now publish through the same
staging call (`src/nodes/file/staged_output.rs`). Measured before IF-179 under
umask 022, they created `0644` files and a replaced `0640` file stayed `0640`;
they now publish `0600`, and their node documents say so. A fix here has to
cover them.

## Required outcome and acceptance

- On replace and append, carry the existing destination's permission bits to
  the staged file. For new files apply `0666 & ~umask`, or keep `0600` and
  document it per node as a deliberate contract.
- Serialize appends per destination within the process, and document that
  cross-process appends are last-writer-wins unless a stronger mechanism is
  added.
- Regressions: new, overwrite and append modes for `write_file`; one
  representative archive, PDF and Markdown output; N parallel appends keep N
  lines.
- Update the affected node documents.

## Outcome and validation

Cause: the staged file is created `0600` so nothing reads it early, and that
mode was published as it was. Append was read, stage, rename with nothing
holding the destination in between.

Implementation:

- `StagedFile::commit` (`rooted/unix/staged.rs`) sets the published mode on
  the open staged file immediately before the rename. A replaced regular
  file passes on its nine permission bits. A new file gets the mode the
  platform gives a plain create in that directory, measured once per node
  execution with an empty probe file (`default_file_mode`), because the umask
  cannot be read without changing it for every thread. The staged file is
  still created `0600`.
- `copy_file` keeps publishing the source mode (IF-140) through
  `publish_with_permissions`, which wins over both rules.
- `zip_extract` ignores permission metadata in the archive, as it did before
  the staged writer: new entries get the default mode, replaced ones keep
  theirs.
- `write/serial.rs` holds one destination per `write_file`-family request
  (`write_file`, `copy_file`, `base64_decode`) from before the existing file
  is read until the commit. The key is the pinned directory's device and
  inode plus the case-folded leaf, so path aliases share it. A waiter checks
  cancellation and the step deadline every 20 ms.

Measured through the CLI on an unoptimized build under umask 022, before on
the unchanged code and after the fix; `transcribe` was measured in-process
against a local provider fixture:

| Node | New file | Replaced `0640` file |
|---|---|---|
| `write_file` | `0600` → `0644` | `0600` → `0640` |
| `zip_create` | `0600` → `0644` | `0600` → `0640` |
| `zip_extract` (entries stored `0644` and `0755`) | `0600` → `0644` | `0600` → `0640` |
| `pdf_merge` | `0600` → `0644` | `0600` → `0640` |
| `markdown_to_pdf` | `0600` → `0644` | `0600` → `0640` |
| `image_resize` | `0600` → `0644` | `0600` → `0640` |
| `transcribe` `output_file` | `0600` → `0644` | `0600` → `0640` |

| `write_file` case | Before | After |
|---|---|---|
| Overwrite of a `0644` file | `0600` | `0644` |
| `append = true` on a `0755` script | `0600` | `0755` |
| Created parent directories | `0755` | `0755` |
| 8 parallel appends, flow run twice | 13 of 16 lines | 16 of 16 |
| 32 parallel appends in one process | 1 of 32 lines | 32 of 32 |

Under umask 027 the fixed build created `0640` files and `0750` directories
and left the replaced modes alone.

Contract boundary:

- Only the nine permission bits are carried. Setuid, setgid and sticky bits
  are dropped, and the replacement is a new inode owned by the IronFlow
  process, so group bits apply to that process's group.
- The mode is applied by `fchmod` just before the rename; a failure fails
  the step and removes the staged file.
- Extracted scripts are not executable until a later step makes them so.
- Serialization is in-process and covers the `write_file` family only.
  Another process, or another node replacing the same file, is
  last-writer-wins, and the documents say so. Waiters are not served in
  arrival order. Two Unicode normalizations of one name on a
  normalization-insensitive volume are not recognized as one destination.
- A slow input, such as a remote artifact restore, holds its destination for
  the whole write.
- Non-Unix platforms keep their native permissions. The portable writer was
  compiled and its lock tests run by selecting it on a Unix host; it was not
  built or run on Windows.
- Created parent directories are unchanged: `0755` masked by the umask.

Validation on 2026-11-12, default features, unoptimized build:

- Failing first, on the unchanged code: 9 of 10 tests in
  `tests/test_staged_output_modes.rs` (the tenth guards the `copy_file`
  mode), all 3 in `tests/test_document_output_modes.rs`, the image test in
  `tests/test_image_output_safety.rs` (18 mismatches over nine node and
  format cases) and the `transcribe` test. Every mode failure reported `600`;
  the append test kept 1 of 32 lines.
- `a_new_file_is_0666_masked_by_the_process_umask` was added after the fix.
  It runs the CLI in a child with umask 022, 027, 002 and 077, and fails with
  `600` when the commit-time mode change is disabled.
- After: those tests pass, with unit tests for the staged file (owner-only
  until commit, explicit permissions win) and the destination lock (waits
  for release, stops on cancellation, directory alias and case).
- `cargo fmt --all -- --check`, `python3 -B scripts/check_module_size.py`
  and `cargo clippy --all-targets -- -D warnings` pass.
- `cargo test --lib`: 645 passed. Area binaries: `nodes` 258, `documents`
  140, `nodes_network` 134, `examples` 11, `cli` 92, `engine` 287, and
  `serial` 186 with `--test-threads=1`; none failed.
- Not run: the full integration gate, feature-enabled builds, Linux and
  Windows hosts.
