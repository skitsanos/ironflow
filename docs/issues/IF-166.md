# IF-166 — CI re-runs the full suite in the feature job and rebuilds release to validate examples

## Evidence and boundary

Audit of `develop` at 1.20.1-dev.6 on 2026-10-28, using CI run 40705138098
(push to `develop`).

| Job | Minutes |
|---|---:|
| Test (macos-latest) | 17.1 |
| Full feature checks and storage tests | 12.8 |
| Clippy and tests (ubuntu-latest) | 11.5 |
| Build (ubuntu-latest) | 6.0 |
| Security audit | 3.5 |
| Repository policy | 0.4 |
| Format | 0.3 |
| Validate example flows | 0.2 |
| Total runner-minutes | 51.7 |

- `rust-features` runs `scripts/test_rust_targets.ts --features postgres,redis -- --test-threads=1`
  over every target although only storage and TLS tests need Redis or
  PostgreSQL; the default job already ran the same suite in parallel.
- `build-linux` (`cargo build --release`) exists to feed `validate-examples`,
  which runs `ironflow validate` over `examples/**/*.lua`.
  `tests/test_example_catalog.rs::evaluated_examples_validate_and_cover_the_builtin_registry`
  already loads every example through `LuaRuntime::load_flow`, checks registry
  coverage and `validate_dag`; `cmd_validate` adds only the printing of Lua
  `undefined_global` warnings.
- `test-macos` runs the full suite on every push and pull request.
- `release.yml` builds eight variants (four targets times default and full).
- `scripts/tests/repository_policy.test.ts` asserts these shapes ("example
  validation reuses only the Linux release build", "CI shares compilation
  within bounded Rust jobs"), so changes need matching test edits.
- The `cache-targets: false` setting and job throttles are driven by the test
  layout recorded in [IF-162](IF-162.md).

Boundary: CI is green and about 17 minutes wall clock; the finding is
redundant work, not a failing or unsafe pipeline.

## Required outcome and acceptance

- The feature job runs only storage and TLS targets (after IF-162, or via an
  explicit target list), keeping `--test-threads=1` only for those.
- Drop `build-linux` and `validate-examples` from pull-request CI, or restrict
  the release build to pushes on `main` and tags. If validation warnings
  matter, assert them inside the example catalog test.
- Decide macOS scope: platform-specific subsets (file, archive, process and
  path tests) on every run and the full suite on `main`.
- Update `repository_policy.test.ts`, the validation section of `AGENTS.md`
  and any CLI or architecture references.
- Resolution evidence: before/after runner-minutes and wall time over at least
  three `develop` pushes.

## Outcome and validation

Resolved on 2026-10-28 on branch `fix/if-166-ci-scope` at 1.20.1-dev.8, after
[IF-162](IF-162.md) made the test binaries selectable by area.

Outcome:

- `scripts/test_rust_targets.ts` accepts `--test <name>` (repeatable). The
  selection still comes from Cargo metadata, so feature gating, the `serial`
  single-thread rule and executable reclamation apply unchanged; a name that is
  not a test target of the package is an error, so a typo cannot run nothing.
  `rust_targets.test.ts` covers parsing, filtering and the unknown-name error.
- The CI feature job (`rust-features`) keeps the full-feature Clippy pass but
  runs only the binaries that hold feature-gated tests: `storage`,
  `storage_postgres`, `storage_redis`, `library_tls_boundaries`, `cli`,
  `scheduler` and `documents` (the CJK renders behind `cjk-fonts`), with
  `--test-threads=1` confined to that job. The default job already runs every
  other target in parallel.
- `test-macos` runs the platform-sensitive areas on pull requests (`nodes`,
  `cli`, `engine`, `serial`: files, paths, archives, processes and the CLI) and
  the whole suite on pushes to `main` and `develop` and on manual dispatch.
- `build-linux` and `validate-examples` run on pushes and dispatch only. Pull
  requests still load every Lua example through the `examples` binary
  (`test_example_catalog`), which evaluates each flow against the registry.
- `repository_policy.test.ts` asserts the feature-job target list, the two
  macOS steps and their conditions, and the push-only guard on the release
  build and example validation; `AGENTS.md` documents `--test` and the CI
  scope.

Contract boundary: pull-request CI loses the release-profile build and the
release-binary example loop, both of which still run on every push to
`develop` and `main` and in the release workflow. macOS pull-request coverage
narrows to the four platform-sensitive binaries; the full macOS suite still
runs on every push. Local validation is unchanged: the gate still runs
everything, and `scripts/test_rust_targets.ts` without `--test` is still
full-target coverage.

Validation on 2026-10-28:

- `bun test scripts/tests/*.test.ts`: 90 pass, including the new
  `rust_targets.test.ts` cases for `--test` parsing, metadata filtering and the
  unknown-name error, and the `repository_policy.test.ts` assertions on the
  feature-job command, the two macOS steps and the push-only release build.
- `actionlint .github/workflows/*.yml` passes.
- Runner smoke: `scripts/test_rust_targets.ts --test examples --test
  limits_defaults` selected exactly those two targets (10 and 2 tests passed)
  and reclaimed their executables.
- Not measured here: runner-minutes and wall time over at least three `develop`
  pushes, which the next pushes provide. The pre-change baseline is the run
  recorded in the evidence above (51.7 runner-minutes, about 17 minutes wall).
