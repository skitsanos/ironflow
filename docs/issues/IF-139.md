# IF-139 — Base64 file output follows destination symlinks and truncates their targets

## Required outcome and acceptance

- `base64_decode` with `output_file` refuses a final symlink or special file.
- Existing regular destinations are replaced atomically; decode, admission,
  cancellation or write failures preserve the prior file and remove staging.
- Keep URL-safe decoding, byte limits and output-context keys compatible.
- Prove that a synthetic symlink target is unchanged, including a dangling
  destination link, and test successful replacement and failure cleanup.

## Evidence and cause

The IF-133 through IF-138 review on 2026-09-14 found that
`src/nodes/utility/encoding.rs` writes decoded bytes with `tokio::fs::write`.
Unlike `write_file`, this follows a destination-file symlink and truncates its
writable target. An attacker must control the destination namespace; no
unauthenticated remote exploit or production data loss was established.
The same implementation is present in v1.18.0 and v1.18.1.

Reproduced with the published v1.18.1 Apple Silicon binary and a disposable
directory: decoding into a symlink succeeded and changed its target from a
sentinel to the decoded payload. No existing user files were involved.

This is independent of IF-134: accepting a configured directory alias must not
permit following an untrusted destination-file symlink.

## Outcome and validation

`base64_decode` now hands decoded bytes to the existing tracked atomic writer
used by `write_file`. A sibling staging file is flushed and synced before
publication; failed decoding, size admission, cancellation or commit leaves
the old destination intact. Destination-file symlinks, dangling links and
special files are refused. URL-safe decoding, byte limits and output keys are
unchanged. Missing parent directories are created using the shared root policy.

Unix operations use pinned directory handles and no-follow final components.
Portable platforms keep observed-link checks and atomic replacement but still
require protection against hostile parent-directory mutation. Base64 decoding
itself remains in memory; the new cancellation guarantees cover the tracked
file-writing stage, not preemptive interruption of the decoder.

## Validation

Post-fix checks on 2026-09-14 with Rust 1.98.1:

- All 6 `test_base64_write_safety` tests passed: URL-safe binary replacement,
  malformed-input preservation, existing/dangling destination links, expired
  write deadline, FIFO refusal without a reader, and strict validation/execution
  of the binary-file example with no leftover scratch outputs.
- `test_base64_decode_limit` passed. Shared writer/archive tests passed for
  symlink/special-file refusal, atomic failure cleanup and tracked cancellation.
- The symlink regression verifies the target's sentinel bytes remain unchanged,
  or absent for a dangling link, while the original link itself is preserved.
- Default and full-feature Clippy, formatting, module-size policy, dependency
  audit and example-catalog checks passed for the batch. This is local source
  validation; the vulnerable published v1.18.1 binary was not replaced.
