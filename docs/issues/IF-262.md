# IF-262 — A protected value inside a non-text response header is recorded unredacted

## Evidence and boundary

Found on 2026-11-20 while validating the IF-258 fix, by reading; no run
record was produced to show it. Since IF-258 the HTTP nodes report a response
header value that the client cannot read as text, which includes any
non-ASCII byte, as `{"base64": "<bytes>"}`. The scrubber that withholds
forwarded webhook header values from stored task output, events and
responses (IF-219) matches text. An upstream that echoed a protected value in
a header that also held one non-ASCII byte therefore had the whole value
stored in Base64, where it was an empty string before IF-258.

Data inside a running workflow is not scrubbed, by design (IF-219), and a
flow that encodes a value itself is outside this finding.

## Outcome and validation

- `SecretRedactor` recognizes an object that is exactly `{"base64": text}`,
  decodes it, and when the bytes contain a protected value replaces the
  object with the same shape holding the Base64 of `[REDACTED]`
  (`src/util/redaction/encoded.rs`). Both scrub paths use it. Bytes that are
  not UTF-8 are read lossily, which leaves a secret's own bytes intact.
- Contract boundary: only that exact one-key shape is decoded, and only when
  a redactor has protected values. An object with other keys, or text that is
  not standard padded Base64, is treated as before. Decoding is linear in the
  value, as the text scan already is.
- Unit tests in that module: a secret after a non-UTF-8 byte is replaced in
  the borrowed and the owned scrubber, including inside an array of repeated
  header values; a harmless encoded value, a two-key object, invalid Base64
  and a redactor without protected values are left alone.
- Validation: the 20 redaction unit tests, default Clippy and `cargo fmt`.
  No end-to-end test sends such a header through a webhook-started run.
  `docs/nodes/http_request.md` states the behaviour.
