# IF-105 — Serve cannot host an optional same-origin static frontend

## Required outcome and acceptance

`ironflow serve` exposes the workflow API but always returns `404` at `/`.
Operators who need a small dashboard, workflow form, or status page must deploy
and configure a second HTTP server even when a single same-origin application
would be sufficient.

Required outcome:

- add an optional `static` configuration section; absence must preserve the
  current API-only route surface, while presence enables a static root whose
  directory defaults to `./public` relative to the process working directory;
- fail startup when the configured root is missing, unreadable, a symlink, or
  not a directory instead of silently running without the expected frontend;
- stream `GET` and `HEAD` responses with extension-derived content types,
  conditional caching, byte ranges, and optional precompressed sidecars;
- serve the configured index for `/` and directory requests without directory
  listings, while rejecting traversal, backslash, malformed path, and symlink
  escapes from the configured root;
- keep static resources public and preserve the existing API authentication
  boundary; API and operator routes must always win and reserved prefixes may
  never be shadowed by files;
- support an opt-in single-page-application fallback only for extensionless
  `GET`/`HEAD` navigation requests accepting HTML; missing assets, unsupported
  methods, and reserved API paths must retain their normal `404`/`405` behavior;
- expose optional cache-control configuration without replacing the file
  service's validators, and apply `X-Content-Type-Options: nosniff` to static
  responses; and
- document configuration, path resolution, deployment mounting, authentication,
  route precedence, and SPA boundaries, with focused compatibility and security
  regressions.

This initiative does not add server-side rendering, templates, live reload,
directory listings, asset compilation, upload endpoints, cookie sessions, or a
private browser UI. Large-scale CDN behavior and dynamic compression remain
deployment-ingress concerns.

## Outcome and validation

**Historical status:** Resolved on 2026-08-28.

`ironflow serve` now accepts an opt-in `static:` configuration section and
streams a validated public root through the existing Axum server. The explicit
API router retains precedence and authentication; the outer static fallback
reserves every API prefix, confines decoded targets and compressed sidecars to
the canonical root, supports custom directory indexes, ranges, validators,
Brotli/Gzip sidecars, cache control, and `nosniff`, and applies the SPA shell
only to explicit extensionless HTML navigation requests. Without `static:`,
the route surface and root `404` remain unchanged.

Focused validation passed 6 static-service tests, 7 server-router tests, 25 API
integration tests, 17 CLI-precedence tests, and 14 configuration tests. The
required format check, module-size policy, exact Clippy warnings-as-errors, and
Rust doc tests passed. `cargo audit --deny warnings` initially detected newly
yanked transitive `chacha20 0.10.1`; the compatible lockfile-only refresh to
`0.10.2` cleared the warning, and the repeated 532-dependency scan passed.

The complete `scripts/integration_gate.sh` subsequently passed for the combined
release candidate, including default and Redis/PostgreSQL feature-enabled test
matrices, dependency audit, release compilation, and all 137 Lua examples. A
live `ironflow 1.18.0-dev.1 serve` process confirmed public static `GET`/`HEAD`,
`206` ranges, `304` validators, MIME and `nosniff`, configured cache control,
Gzip sidecar negotiation, directory redirects and indexes, guarded SPA fallback,
authenticated API/metrics precedence, public liveness/readiness, authenticated
flow validation and execution, and the compatibility root `404` when `static:`
is absent.

A headless Chromium smoke also loaded an index that referenced
`/assets/styles.css` and `/assets/app.js`. All three resources returned `200`
with the expected HTML, CSS, and JavaScript MIME types; the script executed and
updated the DOM, computed styles matched the stylesheet, the rendered page was
visually inspected, and no console, page, or failed-request errors occurred.
The same asset-loading path is preserved as the runnable
`examples/23-static-website` example.
