# IF-160 — Integration cleanup leaves anonymous PostgreSQL volumes

## Evidence and boundary

During the document candidate's two local gates, PostgreSQL's image-created
anonymous volume remained after `docker rm -f` removed its owned container.
Both captured volumes were explicitly removed after the gates. Shared named
volumes and unrelated containers were not touched. The separate TLS fixture
already removes anonymous volumes with `docker rm -f -v`.

## Required outcome and acceptance

- Remove anonymous volumes together with exactly the gate-owned containers.
- Never prune shared resources or pass empty container names to Docker.
- Preserve the gate's exit code and package cleanup when Docker cleanup fails.
- Cover zero, one and two owned containers in regressions and verify live
  anonymous-volume removal during integration qualification.

## Outcome and validation

Cleanup builds a local array of nonempty owned container names and removes them
with `docker rm -f -v`. Docker's volume option removes associated anonymous
volumes, not shared named volumes. No global pruning or unrelated-name lookup
was added. A failed Docker cleanup still permits package artifact cleanup and
does not replace the gate's original exit status.

Four ownership combinations and a simulated Docker-cleanup failure exercise
the production cleanup function and EXIT trap. The missing-volume-flag cases
failed before the fix; all five pass afterward. A focused live probe created a
real disposable PostgreSQL container/anonymous volume, invoked the same cleanup
with exit 42, and verified that both Docker objects were absent while exit 42
was preserved. The probe's Cargo command was isolated, so it did not delete
workspace build artifacts. Full release qualification separately runs the
entire integration gate with disposable live services.
