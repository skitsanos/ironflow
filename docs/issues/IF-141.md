# IF-141 — `db_query`/`db_exec` panic on PostgreSQL `sslmode=verify-ca` in feature builds

## Required outcome and acceptance

- A `postgres` feature build must not panic when a `db_query` or `db_exec`
  step connects with `sslmode=verify-ca`, regardless of which state or event
  store is configured.
- The Rustls crypto provider is installed exactly once, at process start,
  before any TLS client (SQL node pools, SQL stores, Redis clients) is built.
  Installation is idempotent and preserves a provider an embedder installed.
- One public entry point covers every feature combination and compiles to a
  no-op when neither storage TLS feature is enabled.
- Node and issue documentation state the supported PostgreSQL TLS modes and
  the process-wide provider contract.

## Evidence and cause

Found during code review of commit `874b28f` (the IF-133 through IF-139
resolution) on 2026-09-15.

The `postgres` feature enables `sqlx/tls-rustls` and `dep:rustls`; the `redis`
feature enables `redis/tokio-rustls-comp` and `dep:rustls`. The resulting
dependency graph compiles both the `ring` and `aws-lc-rs` Rustls backends.
When both are present, Rustls'
`CryptoProvider::get_default_or_install_from_crate_features()` cannot choose
one and panics unless a process default has already been installed.

IF-137 installed the ring provider inside `SqlStateStore::new_with_prefix`,
`SqlEventStore::new_with_prefix` and `redis_config::client`. The SQL node in
`src/nodes/database/sql.rs` (`connect`, which calls `AnyPool::connect`
directly) never called it. With `--features postgres` and the default JSON
state store no store constructor runs, so a step whose `connection` is
`postgres://...?sslmode=verify-ca` reached sqlx-core 0.9.0
`src/net/tls/tls_rustls.rs:155` with no provider installed. That line is the
`accept_invalid_hostnames` branch (`verify-ca`): it calls
`WebPkiServerVerifier::builder(...)` without an explicit provider and resolves
the process default. `require` uses sqlx's dummy verifier with its explicit
ring provider, and `verify-full` uses `with_root_certificates` on a
`ClientConfig` already built with that provider, so only `verify-ca` was
affected. The IF-137 acceptance script configures PostgreSQL state and event
stores whose constructors installed the provider first, so it could not observe
the node-only path.

## Outcome and validation

- `ironflow::initialize_tls_provider()` in `src/lib.rs` is the single public,
  idempotent, feature-independent entry point. Its body is gated to
  `storage::tls::initialize_provider` and is empty without `postgres` or
  `redis`.
- `src/main.rs` calls it immediately after `bootstrap_environment`, before the
  tracing subscriber and the Tokio runtime, so every TLS client built later in
  the process finds the provider installed.
- The library also installs the provider, idempotently, at each public
  storage boundary (`SqlStateStore::new_with_prefix`,
  `SqlEventStore::new_with_prefix`, `redis_config::client`, which both Redis
  stores use) and in the SQL nodes' `connect`. Review of the first fix, which
  had removed the per-store installs, showed that an embedder constructing
  `RedisStateStore` or `RedisEventStore` over `rediss://` without the new
  startup call hit the provider panic again; the library must not depend on
  the executable's startup sequence. The idempotency regression in
  `src/storage/tls.rs` is retained.
- Contract boundary: the provider is process-wide state. The CLI installs it
  at startup; the library installs it before it builds any TLS client of its
  own, so embedders get a connection error rather than a panic even if they
  never call `ironflow::initialize_tls_provider()`. Calling it early remains
  the recommendation when an embedding application builds other Rustls
  clients first, and an embedder that installed a different provider keeps
  it. SQLite and plaintext connections are unaffected. No sqlx, Redis or
  Rustls version or feature changed, and no certificate-verification behavior
  was relaxed.
- `docs/nodes/db_query.md` and `docs/nodes/db_exec.md` document the supported
  PostgreSQL TLS modes and the process-wide provider; IF-137 records the
  follow-up.

## Validation

Post-fix checks on 2026-09-15 (local source, focused targets):

- `cargo check --features postgres,redis` passed.
- `cargo check` (default features) passed.
- `cargo test --lib --features postgres,redis storage::tls` passed
  (`provider_initialization_is_idempotent`).
- `cargo fmt --all -- --check` and `python3 -B scripts/check_module_size.py`
  passed.

`tests/test_library_tls_boundaries.rs` (`--features redis`, its own test
binary so nothing else installs the provider first) constructs both Redis
stores over `rediss://` against a loopback listener that closes every
connection and asserts a connection error. Before the boundary installs were
restored both tests panicked at `rustls-0.23.45/src/crypto/mod.rs:249`; after,
both pass. The PostgreSQL `verify-ca` verifier is only built after the server
accepts TLS, so that boundary is covered by the live gate below rather than by
an in-process test.

Live validation on 2026-09-15 (local macOS host, Docker 29.8.0, locked
`--features postgres,redis` debug binary): `bun --no-env-file
scripts/test_store_tls.ts target/debug/ironflow` passed end to end, including
the new default-store `db_query` probes over `require`, `verify-ca` and
`verify-full` against a disposable TLS-only PostgreSQL 18 container. Each probe
exited 0, printed no panic, and returned `rows = [{"answer": 1}]`. The
pre-fix `verify-ca` panic was established from the review and the sqlx-core
0.9.0 source rather than rerun; the gate is the regression guard going
forward. Hosted Linux CI runs the same gate in the `rust-features` job.
`scripts/test_store_tls.ts`, `cargo clippy --all-targets -- -D warnings` and
`cargo test --doc` were not run here and belong to the integration boundary.
No published binary, tag or deployment was modified.
