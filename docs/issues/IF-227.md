# IF-227 — Verify extract_xlsx date cells against a workbook saved by Excel

## Evidence and boundary

Split from IF-222 (f) on 2026-11-16. Verification that could not be done;
no defect is known.

The three workbooks in the sample run of 2026-11-16 (up to 16,007 rows;
formulas, rich strings, currency formats, one merged range) matched the
sheet XML in every cell, but none has a date cell. How `extract_xlsx`
returns dates, times and date-times that Excel stores as serial numbers
with a date number format (documented as ISO-8601 strings) is covered only
by the repository's own test fixtures, not by a file Excel saved.

## Sample run of 2026-11-17

A workbook saved by Excel for the web, with made-up values, was compared with
the sheet XML and the cell styles' number formats. The file stays outside the
repository. Excel for the web offers no 1904 date system, so that case is
still untested.

| Cell | Number format | Stored value | `extract_xlsx` returns |
| --- | --- | --- | --- |
| Date | 14 (built-in) | `46096` | `2026-03-15T00:00:00` |
| Time | 20 (`h:mm`) | `0.604166…` | `1899-12-31T14:30:00` |
| Date and time | 22 | `46096.604166…` | `2026-03-15T14:30:00` |
| Custom date | 164 `dd mmm yyyy` | `46096` | `2026-03-15T00:00:00` |
| Before 1900-03-01 | 14 | `46` | `1900-02-15T00:00:00` |
| Duration | 46 (`[h]:mm:ss`) | `1.5625` | `1900-01-01T13:30:00` |
| Long date | 165 (locale long date) | `46096` | `2026-03-15T00:00:00` |

Reproduced defect: **a duration is returned as a date.** 37:30:00 comes back
as `1900-01-01T13:30:00`, which loses the day and misstates the value.
`src/nodes/extract/xlsx/cells.rs` converts every `Data::DateTime` with
`as_datetime()` and ignores the duration type that `calamine` reports for
elapsed-time formats.

By reading, not a defect: a time-only cell is returned on Excel's day zero,
`1899-12-31`, and the node page does not say so.

## Required outcome and acceptance

Needs a workbook saved by Excel (and, if obtainable, one by LibreOffice)
with made-up values:

- a date, a time and a date-time in built-in formats,
- a date in a custom number format,
- a date before 1900-03-01 and, if the application offers it, a workbook
  using the 1904 date system,
- a duration format such as `[h]:mm`.

Acceptance: compare each cell with the sheet XML and the style's number
format, record the structure here, and confirm the node page describes what
a caller receives for each kind. Fix any defect with a hand-built fixture
and a failing-first regression.

## Outcome and validation

- **Fixed:** `src/nodes/extract/xlsx/cells.rs` now checks
  `ExcelDateTime::is_duration()` (calamine 0.38.0) and returns an elapsed-time
  cell as an ISO-8601 duration with hours as the largest unit: `1.5625` under
  `[h]:mm:ss` is `PT37H30M`; zero is `PT0S`; a negative span is `-PT1H30M`;
  fractional seconds keep up to three digits (`PT0.5S`, calamine rounds to
  milliseconds). This matches how `DurationIso` cells already pass through.
- **Decision, time of day only:** unchanged. It stays on Excel's day zero,
  `1899-12-31T14:30:00` (`1904-01-01T14:30:00` in a 1904-system workbook),
  and `docs/nodes/extract_xlsx.md` now says so. Changing it would break
  flows that read the part after `T` or compare whole strings; a time-only
  type is a separate decision for the maintainer.
- **Regressions:** `tests/test_extract_xlsx_datetimes.rs` (hand-built
  fixtures; failing first on `1900-01-01T13:30:00`) covers a duration over
  24 hours, zero, negative, fractional seconds, a 2400-hour value, the
  time-only cell, and a `date1904="1"` workbook (date shift, duration
  unaffected, time-only). Unit tests in `cells.rs` cover the formatter.
- **Real workbook:** re-read in place after the fix; the duration cell
  returns `PT37H30M` and the other six cells are unchanged from the table.
- **Boundary:** the 1904 path is verified only with a hand-built workbook; no
  Excel-saved 1904 workbook exists (Excel for the web has no such option), and
  no LibreOffice-saved workbook was compared.
