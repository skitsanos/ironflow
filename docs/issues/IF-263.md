# IF-263 — The PostgreSQL test image is not pinned consistently

## Evidence and boundary

Found on 2026-11-20 after the 1.23.0 release, by reading the four places
that start a PostgreSQL server for IronFlow:

- `deploy/replica/docker-compose.yml` runs `postgres:19-alpine`.
- `scripts/integration_gate.sh`, the `rust-features` service in
  `.github/workflows/ci.yml` and the live TLS fixture
  (`scripts/storage_tls/fixture.ts`) run `postgres:latest`.

The local `postgres:latest` image reported `PG_MAJOR=19` on the day, so the
four happened to agree on the major version; nothing kept them agreeing. A
new major release would move the gate, CI and the TLS acceptance to it the
day it is published, while the replica stack, the one documented
deployment, stays on 19. The storage suites would then validate a server the
documented deployment does not run, and the Debian-based `latest` already
differs from the Alpine image the replica stack uses. Renovate did not
manage any of the four references. No failure was reproduced; the finding is
drift and the absence of a guard.

[IF-167](IF-167.md) kept `redis:latest` and `postgres:latest` floating by
maintainer decision so that the storage suites follow current server
releases. That reasoning is respected here: the pin is a major-version tag,
not a digest, so patch releases still arrive without a repository change.
Redis is out of scope: no deployment surface names a Redis image, so there
is nothing for the test image to disagree with, and IF-167's decision stands.

## Outcome and validation

- `postgres:19-alpine`, the replica stack's existing image, is now the one
  reference: a `postgres_image` variable in the gate, `postgresImage` in the
  TLS fixture, and the `postgres` service image in CI.
- `renovate.json` adds a regex manager for the two script variables (CI and
  the compose file are read by Renovate's own managers) and a
  `PostgreSQL image` group with `pinDigests: false`.
- `scripts/tests/postgres_image.test.ts` reads the image each source starts
  (the gate variable and the commands that use it, the CI service, the
  fixture export, the compose service), requires one `postgres:<major>-alpine`
  value and no other literal PostgreSQL image in those files, and runs the
  Renovate regex against the gate and fixture. `renovate.test.ts` checks the
  group for all three managers. Pointing CI back at `postgres:latest`, or the
  gate at another tag, fails the new test.
- `docs/REPLICA_DEPLOYMENT.md`, `docs/CLI_REFERENCE.md` and the
  `check-ironflow` skill describe the shared image without repeating the tag.

Validation on 2026-11-20, local only: `bun test scripts/tests/*.test.ts`
(104 pass), `actionlint`, `bash -n` on the gate, the skill validator, and
`scripts/test_store_tls.ts` against `postgres:19-alpine` (PostgreSQL 19.0, all
PostgreSQL and Redis checks pass). Because CI and the gate move from the
Debian-based `latest` to Alpine, the PostgreSQL feature suites also ran
against a disposable `postgres:19-alpine`: the library tests (949 pass), the
`storage` binary (155) and `storage_postgres` (16), serially. CI itself and
the full integration gate were not run. Renovate's behaviour is modelled by
the tests, not observed on a Renovate run.
