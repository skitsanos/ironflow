# IF-152 — AWS SigV4a retains an affected bigint dependency

## Evidence and boundary

On 2026-10-24, cargo audit identified RUSTSEC-2026-0387 in
`crypto-bigint 0.5.5`: arithmetic intended to be constant-time may contain
secret-dependent branches. The patched version is >=0.7.6. The latest AWS
cohort (`aws-sdk-s3 1.155.0`, `aws-sigv4 1.6.3`) updates its P-256 dependencies
to the patched line but retains a direct optional `crypto-bigint ^0.5.4`
dependency for SigV4a key derivation. No compatible 0.5 patch is published.
IronFlow explicitly enables the S3 `sigv4a` feature. This is separate from
the eMudhra certificate-authority incident.

## Required outcome and acceptance

- Keep `cargo audit --deny warnings` fail-closed without a silent exception.
- Either obtain approval to disable SigV4a and document the loss of S3
  Multi-Region Access Point support, or retain the feature and hold integration
  pending an upstream fix or a separately reviewed remediation.
- Preserve standard regional S3 and S3 Vectors signing and storage workflows.
- Validate the final resolved default and feature-enabled dependency graphs.

## Outcome and validation

On 2026-10-24 the user approved disabling SigV4a and documenting the limitation.
The S3 dependency no longer enables `sigv4a`. Regional SigV4 signing remains;
S3 Multi-Region Access Points are unsupported. Node, artifact and security
documentation state this boundary. No audit exception or vendored crypto patch
was introduced. The resolved lockfile contains neither the affected bigint nor
its SigV4a curve dependencies. `cargo audit --deny warnings` passes with no
warnings and an empty ignore list. Policy tests guard both this feature
exclusion and the absence of affected bigint versions.

The CLI regression `tests/test_s3_signing_cli.rs` passes in focused default
and full-feature tests. With isolated synthetic credentials, GET/PUT/HEAD/DELETE
presigning uses `AWS4-HMAC-SHA256` and a regional S3 credential scope. A
Multi-Region Access Point fails without returning a regional signed URL; the
current SDK reports a missing endpoint configuration. No AWS service or real
credential is used. Default/full-feature Clippy and the full integration gate
pass; the new signing tests and final evidence also require PR #217's final CI.

## 2026-10-28 restoration follow-up

The user approved restoring SigV4a after the upstream fix shipped. The original
trigger, mitigation and 2026-10-24 validation above remain historical evidence;
they are not claims about the restored build.

Development explicitly enables the S3 `sigv4a` feature with SDK minimum
`1.156.0`, which requires signer `>=1.6.4`. Default SDK features remain disabled.
After refreshing a stale local registry index, default and full-storage-feature
metadata both resolve a single `crypto-bigint 0.7.10`, including the P-256 path.
There is no local crypto patch, advisory suppression or trust-store rollback.
Policy regressions guard the SDK minimum, enabled feature, signer floor and
every resolved bigint copy. A fresh `cargo audit --deny warnings` passed.

Before the restoration, the new MRAP header regression failed while its regional
control passed; two positive MRAP CLI regressions also failed, and the feature
policy test failed. After restoration, both header regressions and all five
CLI regressions passed. They cover GET/PUT/HEAD/DELETE, global MRAP endpoints,
regionless credential scope, session tokens, configurable region sets, regional
SigV4 preservation, invalid path-style refusal and the new example. A separate
`serve` regression passed MRAP and regional presigning through the HTTP API.
All use isolated synthetic credentials; the header interceptor aborts before
transmission and presigning sends no S3 request.

The README, node, artifact, security and draft release documentation now describe
restored MRAP signing and AWS's remaining restrictions. Account-level bucket
listing is not MRAP management, and MRAP copy is destination-only. No live AWS
permissions, replication, routing or failover test is claimed. This working
change is not evidence of publication or a production rollout.

The full local integration gate passed with `IRONFLOW_TEST_PUBLIC_TLS=1`:
all 180 Cargo targets passed in both default and full-storage-feature runs,
strict Clippy passed for both configurations, 76 policy tests and all 156 Lua
examples passed, and the fresh advisory audit passed without exceptions.
Public TLS controls accepted a valid chain and rejected the four compromised
eMudhra chains. Disposable PostgreSQL 18.6 and Redis 8.10.3 services passed TLS
CLI, serve, restart and replay checks, along with certificate, plaintext and
insecure-bypass rejection checks. After the gate exited successfully, an
independent Docker check confirmed no IronFlow test containers or the captured
PostgreSQL anonymous volume remained. These are local results, not hosted CI
or live AWS acceptance.
