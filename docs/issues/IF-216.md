# IF-216 — Redis legacy-expiry tests fail intermittently on a loaded machine

## Evidence and boundary

Recorded on 2026-11-13 from the IF-184 fix session.

- Measured by that session: tests in
  `tests/redis_atomicity/event_legacy_expiry.rs` and
  `event_legacy_recovery.rs` failed in three of five `storage_redis` runs
  while other builds were running, and passed 19 of 19 on re-run, on both the
  unfixed and the fixed tree.
- By reading: the tests set key expiries of one to two seconds with
  `PEXPIRE` and then perform several steps before sleeping past the deadline
  (`sleep` of 1,100, 1,700 and 2,200 ms). Under load the steps before the
  sleep can outlast the expiry.
- The integration gate runs this binary against live Redis. Two other tests
  of the same kind failed a gate or a session run on 2026-11-12 and were
  fixed by widening their windows (the IF-182 deferral test and the
  artifact-restore CLI test).

Boundary: not reproduced for this page, and no defect in the store is
suspected. A failure blocks a push, because the gate receipt is required.

## Required outcome and acceptance

- Reproduce under load against a disposable Redis, then remove the race:
  longer expiries with matching waits, or polling `PTTL` and key state
  instead of fixed sleeps.
- Evidence: 20 consecutive passes of the affected tests while a parallel
  build runs, against a disposable instance with
  `IRONFLOW_REDIS_TEST_REQUIRED=1`.

## Outcome and validation

Resolved on 2026-11-13 by test changes only; no store code changed.

Reproduced against a disposable Redis with `IRONFLOW_REDIS_TEST_REQUIRED=1`,
debug build, while sibling builds and twelve busy-loop processes ran:

- Full `storage_redis` binary with default test threads: 10 of 10 runs
  failed, each in one to four of the tests below and in no other test.
- With `--test-threads=1` (the gate's mode) the seven tests of the two files
  passed 6 of 6, so the gate-mode failure was not reproduced here.

Cause per test:

- `redis_hostile_persist_past_the_deadline_expires_instead_of_restoring`,
  `redis_expired_legacy_quarantine_releases_its_persistent_state` and
  `redis_expired_owned_current_quarantine_ignores_an_unowned_raw_collision`
  armed expiries of 1,000, 2,000 and 1,500 ms and then connected a store and
  ran a 32-step migration call that had to finish first. Under load it did
  not. Observed: the first call returned `Corruption` ("Blocked Redis legacy
  event migration") when the snapshot expired during the call, or an empty
  list when the stream expired before it. A test timing assumption.
- `redis_legacy_reverse_restore_respects_the_aggregate_byte_limit` (the
  `event_legacy_recovery.rs` failure) has no expiry: its 18 MB seed pipeline
  failed with `timed out`, the Redis client's default 500 ms response
  timeout on the fixture connection.

Change:

- The three deadline tests connect the store before arming the expiry, time
  the steps that must precede it, collect their results and assert them only
  after checking the time. A setup that used more than three quarters of the
  expiry is repeated on a fresh key prefix with the next expiry of 2, 8 and
  32 seconds and logs that it did; it fails if all three are outrun.
  Assertions are otherwise unchanged or stricter (snapshot TTL alignment is
  now asserted in all three).
- Fixed sleeps are gone: two tests poll until the snapshot family is absent
  (60-second limit), and the hostile-`PERSIST` test waits the `PTTL` it
  observed before the `PERSIST` plus 100 ms, then polls for the cleanup.
- The byte-limit test seeds and dumps through a fixture connection with a
  60-second response timeout. The store under test keeps its defaults.
- Keys stay under each fixture's unique prefix, so nothing is shared with
  other tests in the binary.

Evidence after the change, same instance and load:

- The seven tests with `--test-threads=1`: 22 of 22 consecutive passes, no
  repeat needed; 9.3 to 11.8 s per run.
- Full binary, default threads: 25 of 26 passes. The repeat path ran three
  times and passed at 8 seconds. The one failing run failed six other tests
  with `timed out` and none of the tests above.
- Full binary with `--test-threads=1`: 3 of 3 passes, 95 tests, 60 to 70 s.
- Added run time without extra load: about 0.6 s for the seven tests.
- `cargo fmt --all -- --check`, the module-size check and Clippy with and
  without `--features postgres,redis` passed.

Not run: the integration gate, PostgreSQL tests and CI.

Not fixed here, tracked in [IF-214](IF-214.md) item (c) and [IF-220](IF-220.md) items (l) and (m):

- A legacy stream whose TTL elapses during a migration call is reported once
  as `Corruption` ("blocked") although nothing is corrupt; the next call
  returns an empty stream. Observed in the reproduction, not covered by a
  test.
- Both Redis stores and the shared test fixture use the client's default
  500 ms response timeout, which is not configurable. With default test
  threads under load it failed six unrelated `storage_redis` tests in 1 of
  26 runs.
