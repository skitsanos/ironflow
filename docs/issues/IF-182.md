# IF-182 — Schedules due in the same tick lose occurrences to the flow-load limit

## Evidence and boundary

Review of `develop` at 1.21.1-dev.1 on 2026-11-12, reproduced against a local
`ironflow serve` on the default SQLite store with six schedules, all `cron:
"* * * * *"`, running a one-step flow.

- Of 28 due instants, 9 logged `scheduled run failed ... server is at maximum
  concurrent flow-loading capacity` and never started later. Eight were
  catch-up instants at startup; one was a live instant where five schedules
  ran and the sixth was dropped.
- `evaluate` drives every schedule concurrently
  (`src/scheduler/evaluation.rs:116-128`). Each claims its instant and then
  `FlowExecutor::run` takes a flow-load permit with a fail-fast
  `try_acquire_owned` (`src/scheduler/execution.rs:199-202`,
  `src/api/admission.rs:83-91`). The default
  `IRONFLOW_MAX_CONCURRENT_FLOW_LOADS` is 2. A refusal becomes
  `Outcome::Failed`, and only `ClaimFailed` holds the watermark back
  (`evaluation.rs:223-249`), so the claimed instant is consumed.
- No run record was created for the refused instants, so a retry would have
  been safe.
- Two in-flight `/flows/validate` or `/flows/run` parses at tick time have
  the same effect on a single schedule.

Boundary: `docs/CLI_REFERENCE.md` says a scheduled instant is skipped at load
capacity, but here the scheduler creates the contention itself with ordinary
hourly or daily jobs that share a minute. Not tested on PostgreSQL or Redis.

## Required outcome and acceptance

- Do not consume an instant on a pre-start capacity refusal: wait for the
  permit within the evaluation budget, or treat the refusal like
  `ClaimFailed` so the next tick retries inside the grace window.
- Regressions: eight schedules due at one instant with two load permits all
  produce exactly one run each; a held permit delays rather than drops an
  instant; the grace window still bounds retries.
- Correct the capacity wording in `docs/CLI_REFERENCE.md` and
  `docs/ARCHITECTURE.md`.
- Evidence: focused scheduler tests through the real `FlowExecutor`.

## Outcome and validation

Resolved on 2026-11-12 by waiting for the permit, with deferral as the
fallback.

- `FlowExecutor::run` now waits up to `FLOW_LOAD_WAIT` (5 seconds, well inside
  the 15-second evaluation budget) for a flow-load permit through
  `acquire_flow_load_permit_within`. Waiting was chosen over retry-only
  because the scheduler creates this contention itself: retrying on the
  30-second tick would start two schedules per tick, so eight jobs sharing a
  minute would finish 90 seconds late and a 60-second grace would still drop
  some.
- A wait that expires returns `ScheduleRun::Deferred`, which becomes
  `Outcome::Deferred` (metric outcome `deferred`). Nothing was parsed and no
  run exists, so the watermark stops before the instant exactly as it does
  for `ClaimFailed`, and later ticks retry it. The retry re-reads the existing
  claim, passes the grace check and starts the deterministic run ID, so grace
  still bounds it. Evaluation stops at a deferred instant so later instants of
  that schedule start in order and do not each spend the budget waiting.
- Contract boundary: API and webhook loads stay fail-fast (`503`).
  `IRONFLOW_MAX_CONCURRENT_RUNS` still skips a scheduled instant, and a flow
  that fails to load still consumes it. The run permit is held while the
  start waits for a load permit.
- The overlap scan moved unchanged in behavior to `src/scheduler/overlap.rs`
  to keep `execution.rs` under the module-size target.
- `docs/CLI_REFERENCE.md`, `docs/ARCHITECTURE.md`, `docs/METRICS.md` and
  `docs/releases/next.md` describe the delay instead of a skip.

Evidence, on a debug build with the default two load permits; the tests use
the JSON store:

- Before the fix, through the real `FlowExecutor`
  (`tests/test_scheduler_load_admission.rs`): eight schedules due at one
  instant and one schedule evaluated while two `/flows/validate` parses held
  both permits each failed with `Failed { error: "server is at maximum
  concurrent flow-loading capacity" }`.
- After the fix the same two tests pass, plus two written with it: an expired
  wait defers two schedules with no run created, and at 95 seconds late the
  300-second-grace schedule fires once while the 60-second-grace one is
  `Late`; a stub-executor test shows a deferred instant stops its window and
  all six instants fire in order on the retry.
- Passing after the fix: `scheduler` 113 (ten consecutive runs), `api` 59,
  `engine` 291, `serial` 187 single-threaded, `scheduler_admission` 1,
  `flow_load_admission` 1, library unit tests 670 with 1 ignored, and the
  test-layout policy test.
- Live check after the fix: `ironflow serve` on SQLite with eight
  `* * * * *` schedules for about three minutes logged no flow-load refusal
  or deferral. Both live instants started 8 of 8. Of the 40 catch-up instants
  at startup, 21 started and 19 were skipped by the overlap rule because the
  previous run of the same schedule was still active.
- `cargo fmt --all -- --check`, `python3 -B scripts/check_module_size.py` and
  `cargo clippy --all-targets -- -D warnings` pass.

Not run: PostgreSQL or Redis stores, and the integration gate.
